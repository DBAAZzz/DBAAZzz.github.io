# 计算机网络与浏览器缓存

## Q1：DNS 解析过程是什么？

### 这题在考什么

是否理解 DNS 查询中缓存与递归解析的完整链路，而不是把“根、顶级域、权威”的固定顺序当成无条件的真实流程。

### 面试时可以这样说

> 域名要先变成可连接的地址，连接才能建立，这一步就是 DNS 做的。客户端通常先查本地三层缓存：浏览器、操作系统、本地网络。这三层都没命中，就交给递归解析器。递归解析器自己也可能有缓存；没有的话，就从根服务器开始，依次问顶级域，再问权威 DNS。拿到记录以后，按 TTL 缓存下来。注意一点：真实系统里还可能经过 CNAME、CDN 调度、IPv4/IPv6 选择和 DoH，所以“固定按四层查询”只是没有缓存时的简化路径。

### 对方很可能继续问

- DNS 为什么既用 UDP 又可能用 TCP？
- CDN 如何根据 DNS 调度节点？
- DNS 预解析有什么收益和风险？

### 一句话记住

DNS 先查缓存，未命中再逐层问根、顶级域、权威——固定四层只是没有缓存时的简化路径。

## Q2：TCP 为什么需要三次握手？

### 这题在考什么

是否理解三次握手确认的是双向收发能力和初始序列号，而不是只会背“SYN、SYN+ACK、ACK”三个报文；同时看你能不能解释为什么两次不够。

### 面试时可以这样说

> TCP 建立连接之前，双方要先确认两件事：我发的对方能收到，对方发的我也能收到。三次握手就是来做这个确认的，顺便把初始序列号同步好。第一步，客户端发 SYN；第二步，服务端回 SYN+ACK，表示收到了客户端的同步请求，同时把自己的序列号发过去；第三步，客户端再回一个 ACK。所以为什么不能只做两次？因为两次握手时，服务端没办法确认客户端有没有收到自己的同步信息，而且更难排除历史上重复的连接请求。注意一点：握手建立的只是可靠传输状态，不代表应用数据已经安全，所以 HTTPS 还要再加一层 TLS。

### 对方很可能继续问

- 四次挥手为什么通常是四次？
- TIME_WAIT 的作用是什么？
- TCP 为什么会出现队头阻塞？

### 一句话记住

三次握手：确认双向收发、同步初始序列号；只做两次，服务端无法确认客户端收到了自己的同步信息。

## Q3：HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

### 这题在考什么

是否理解三个版本在连接模型上的演进，从多条连接排队到单连接多路复用、再到 QUIC 上按流独立恢复丢包，而不是只记“HTTP/2 更快”的结论。

### 面试时可以这样说

> 先看 HTTP/1.1：它支持持久连接，但同一条连接上的响应要按顺序来，并发能力受限，所以浏览器通常同时开好几条连接。HTTP/2 的解法是：在一条 TCP 连接上做二进制分帧，实现多路复用，再加上头部压缩。但是注意一点，它底层还是 TCP，一旦丢包，这条连接上的所有流都会被阻塞。HTTP/3 干脆换掉传输层，把传输放到 QUIC 上，也就是跑在 UDP 上；这样一来，不同流可以各自独立恢复丢包，连接建立和网络切换也都能改善。所以说，版本升级不等于页面一定更快，还要看网络、服务端和资源策略。

### 这里容易说错

HTTP/2 的多路复用解决了应用层的请求排队，但没有消除 TCP 层的队头阻塞。HTTP/3 也不代表“UDP 不可靠”：可靠性和拥塞控制都由 QUIC 实现。

### 一句话记住

1.1 靠多连接，2 靠单连接多路复用，3 换 QUIC 让流独立恢复丢包。

## Q4：HTTPS 如何保证安全？

### 这题在考什么

是否理解 HTTPS 的安全来自“证书链验证身份、密钥协商、对称加密”的组合，而不是把它简化成“就是加了密”；同时看你能不能说出它解决不了哪些问题。

### 面试时可以这样说

> HTTPS 说白了就是 HTTP 跑在 TLS 之上。TLS 做四件事：第一，通过证书链验证服务端身份；第二，通过密钥协商得到一个会话密钥；第三，用会话密钥做对称加密，保护传输内容；第四，用认证机制保证内容没有被篡改。所以 HTTPS 主要解决三个问题：窃听、篡改和冒充。注意一点：业务自身的问题它管不了，比如 XSS、错误授权，或者用户的终端已经被控制，这些 HTTPS 都防不住。

### 对方很可能继续问

- 为什么不直接一直使用非对称加密？
- 浏览器如何验证证书？
- HTTPS 能不能防中间人攻击？

### 一句话记住

证书链验身份、密钥协商出会话密钥、对称加密保内容，解决窃听、篡改、冒充三类问题。

## Q5：强缓存和协商缓存有什么区别？

### 这题在考什么

是否理解强缓存和协商缓存的本质区别是“要不要向服务端确认”，而不是只背 `Cache-Control` 和 304 这些名词；同时看你能不能给出静态资源与 HTML 的落地策略。

### 面试时可以这样说

> 强缓存就是：响应里带着 `Cache-Control` 这样的信息，下次命中时直接复用本地副本，不向服务端确认。协商缓存不一样：请求会带上 `If-None-Match` 或者 `If-Modified-Since`，服务端判断资源没变化，就返回 304，浏览器继续用本地那份。所以落地时，静态资源通常用内容哈希文件名，配合长期的 `max-age, immutable`；HTML 不能这么干，要用较短的缓存，或者每次都验证，这样才能及时引用新版本资源。

### 如果对方让你继续讲

`ETag` 用资源标识比较内容，精度通常比基于时间的 `Last-Modified` 高，但它的生成和跨节点一致性有成本。用共享缓存时，还要关注 `public/private`、`s-maxage` 和 `Vary`。`no-cache` 表示使用前要先验证，不等于完全不缓存；`no-store` 才是完全不缓存。

### 对方很可能继续问

- 为什么 HTML 不能和 hash 静态资源使用相同缓存策略？
- 发布后用户为什么可能出现“新 HTML + 旧资源不存在”？
- Service Worker 缓存与 HTTP 缓存是什么关系？

### 一句话记住

强缓存直接复用、不问服务端，协商缓存 304 确认后复用；静态资源走长缓存，HTML 走验证。

## Q6：跨域是什么，CORS 如何工作？

### 这题在考什么

是否理解 CORS 是“服务端授权、浏览器执行”的机制，而不是把跨域理解成服务端之间的网络限制；同时看你能不能说清同源的三要素和预检 OPTIONS 的作用。

### 面试时可以这样说

> 先说什么叫同源：协议、主机、端口都一样，才算同源。同源策略限制的是页面读取不同源的敏感响应。那跨源读取怎么办？CORS 就是服务端通过响应头来授权浏览器跨源读取的机制。注意一点：某些非简单请求会先发一个预检 OPTIONS，确认方法和请求头允不允许。再提醒一个边界：CORS 是浏览器的安全策略，不是服务端之间的网络限制，而且不能用来替代身份认证和权限校验。

### 对方很可能继续问

- 什么请求会触发预检？
- 带 Cookie 的跨域请求需要什么配置？
- 为什么 Postman 能成功而浏览器报跨域？

### 一句话记住

CORS 靠服务端响应头授权浏览器跨源读取，非简单请求先预检 OPTIONS；它是浏览器策略，不替代认证。

## Q7：Cookie、Session、Token 怎么选？

### 这题在考什么

是否理解 Cookie、Session、Token 分属“数据载体、服务端状态、凭证机制”三个维度，而不是把它们当成同一维度上的三选一；同时看你能不能从风险角度给出选择依据。

### 面试时可以这样说

> 先分清一件事：Cookie、Session、Token 不是同一维度的替代品。Cookie 是浏览器保存、并按规则自动随请求携带的数据载体；Session 是服务端保存会话状态的一种方案；Token 是客户端携带的凭证格式或者机制。所以 Web 登录里，常见做法是把不透明的 Session ID 或者 Token 放在 Cookie 里，并配上 `HttpOnly`、`Secure` 和合适的 `SameSite`。具体选哪个，重点看五件事：撤销能力、跨域需求、服务端状态、XSS/CSRF 风险和运维复杂度。

### 一句话记住

Cookie 是载体、Session 是服务端状态、Token 是凭证机制，三者不同维度，选型看撤销、跨域和 XSS/CSRF 风险。

## 几个高频追问怎么接

### HTTP/2 有多路复用，为什么还会卡？

同一条 HTTP/2 连接，底层跑的还是 TCP。某个包丢失时，TCP 必须按序交付，后续已经到达的数据也要等缺失包重传，此时这条连接上的 HTTP/2 流都会受影响。HTTP/3 把不同流放进 QUIC 的独立流里，一个流丢包不会阻塞其他流的数据交付。

### `no-cache` 为什么还能看到磁盘缓存？

因为 `no-cache` 允许保存响应，只是每次使用前必须向服务端验证。验证通过返回 304，浏览器继续使用本地副本。真正不允许存储的是 `no-store`。Network 面板显示 “from disk cache” 时，要结合请求是否真的发出去了来判断，不能只看字面标签。

### 发布新版本后，为什么有人报资源 404？

常见原因是 HTML 和 hash 资源的发布顺序或保留策略有问题。用户拿到旧 HTML，旧资源却已经被删除；或者新 HTML 已经生效，新资源还没全部上传。正确做法是先上传新资源，再切入口，同时给旧资源保留一个回滚窗口。

### CORS 报错应该从哪里查？

先看有没有发预检，再看预检的状态码和响应头；然后看实际请求是否带 Cookie、自定义请求头或非简单方法。服务端要对请求的 Origin 做精确判断；允许凭证时，要返回具体的 Origin，不能同时用 `Access-Control-Allow-Origin: *`。
