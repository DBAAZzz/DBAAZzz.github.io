# Vue 与 React 框架原理

## Q1：Vue 3 响应式原理是什么？

### 这题在考什么

考你能不能讲清“**读取时收集依赖、写入时触发更新**”的机制，而不是只会背出 Proxy 这个名词。

### 面试时可以这样说

> Vue 3 响应式的核心是 Proxy，用它拦截对象的读取和修改。副作用函数执行的时候，读到哪个数据，track 就把“目标对象、key、effect”这组依赖记下来；之后写入数据，trigger 就找到相关的 effect，交给调度器去刷新。

### 如果对方让你继续讲

调度器会去重并批量刷新：同一个 effect 在一轮同步修改里被反复触发，最终只保留一次刷新，不会每触发一次就渲染一次。`ref` 用包装对象统一处理原始值：访问 `.value` 时收集依赖，写入时触发更新。

### 对方很可能继续问

**为什么需要 effect 栈？**

effect 会嵌套：内层执行完，要把“当前 effect”恢复成外层的，否则外层后续读取的依赖会记到内层头上。栈就是用来保存和恢复这个现场。

**数组、Map、Set 如何追踪？**

数组和普通对象走 Proxy 的 get/set 就能覆盖，包括索引和 `length`；Map/Set 的增删查是方法调用，Proxy 拦不到默认方法，需要对 `add`、`delete`、`has`、`forEach` 这些做专门包装。

**`reactive` 解构后为什么可能失去响应？**

解构是把“当时的值”取出来，之后和代理再无关系。要保持响应就得持续通过代理访问，或者用 `toRefs` 把每个属性包成 ref。

**`shallowReactive` 适合什么场景？**

只代理第一层、不做深层转换。适合大列表、嵌套很深但只改第一层、或数据里混着无需响应式的复杂对象，省掉深层代理的开销。

### 一句话记住

读时 track 记依赖，写时 trigger 找 effect，调度器去重批量刷。

## Q2：Vue 的 nextTick 解决什么问题？

### 这题在考什么

考你能不能说清 `nextTick` 等的是“**Vue 更新队列完成**”，而不是把它当成“浏览器下一次重绘”的保证。

### 面试时可以这样说

> Vue 修改响应式数据后，不会每改一次就同步更新一次 DOM，而是把组件更新任务去重后，放进一个异步队列。`nextTick` 返回的 Promise，会在当前批次 DOM 更新完成后执行，所以你想读更新后的 DOM，就在它里面读。

### 如果对方让你继续讲

注意一点：`nextTick` 只保证 Vue 的更新队列完成，不等于浏览器已经把像素画到屏幕上。DOM patch 完之后，浏览器还要再走布局和绘制流程，patch 完成和像素上屏之间没有必然的先后保证。所以你要对齐视觉帧时，得再结合 `requestAnimationFrame`。

### 对方很可能继续问

**更新队列怎么去重？**

每个组件的更新任务带唯一 id，入队时打上“已在队列”标记，同一轮里重复触发只保留一个；队列按 id 升序刷新，保证父组件先于子组件更新。flush 结束后清掉标记，下一轮可以再次入队。

**为什么用微任务调度？**

微任务在同步代码结束后立刻清空，早于 `setTimeout` 这类宏任务，能让 DOM 更新尽量在同一帧内完成。早期没有 Promise 环境下的降级方案（MutationObserver、setTimeout）现在已被 Promise 统一。

**nextTick 里再改数据会怎样？**

会触发新一轮依赖收集，任务排进下一个更新队列，不会死循环；但连续这样写会把更新拆成多轮，拖慢渲染节奏。

### 这里容易说错

不要回答“`nextTick` 就是 Promise”。Promise 只是它常用的调度基础，`nextTick` 的关键语义是等 Vue 当前这一批更新完成。

### 一句话记住

`nextTick` 等的是 Vue 的更新队列，不是像素上屏。

## Q3：computed 和 watch 怎么选？

### 这题在考什么

考你能不能讲清两者的分工——**computed 声明派生值、watch 执行副作用**，而不是把两者当成功能重叠的监听工具。

### 面试时可以这样说

> 一句话：computed 用来声明派生值，watch 用来执行副作用。computed 有缓存，依赖不变就不会重算，所以里面要写无副作用的逻辑；watch 是状态变化之后，去执行异步请求、打日志、做命令式同步这类事。能用 computed 表达的数据，就不要再用 watch 维护一份同步状态。

### 如果对方让你继续讲

用 watch 时，还要处理立即执行、深度、刷新时机和异步竞态这几个配置点。另外记住一条：watch 不产出值，只负责在变化发生时执行操作。那种“监听一个状态、再把结果同步进另一个状态”的写法，多数时候可以改成 computed 直接声明。

### 对方很可能继续问

**computed 的缓存怎么实现？**

computed 本身是懒执行的 effect：首次读取才计算并收集依赖；依赖变化时只把它标成“脏”，并不立刻重算，等下次被读取才重新求值。没人读就不算，这就是缓存的来源。

**watch 的 flush 三种取值有什么区别？**

默认 `pre` 在组件更新前执行；`post` 在组件更新后执行，能拿到更新后的 DOM；`sync` 不进队列，数据一变就同步执行，只留给确实需要同步联动的场景。

**computed 里能发请求吗？**

不能。computed 必须同步返回、保持无副作用，异步和重试的时机都不可控；异步逻辑交给 watch 或请求缓存库，结果再声明成派生状态。

### 一句话记住

computed 声明派生值，watch 执行副作用。

## Q4：虚拟 DOM 和 Diff 的价值是什么？

### 这题在考什么

考你能不能讲清虚拟 DOM 的价值在**可维护的编程模型和可预测的更新**，而不是“它一定比手写 DOM 快”。

### 面试时可以这样说

> 虚拟 DOM 就是用 JavaScript 对象描述 UI。有了这层描述，框架可以在更新前比较新旧结构，算出必要的宿主操作，也就能跨平台组织声明式更新。注意一点：它不是在所有场景都比手写 DOM 快，价值更多在可维护的编程模型和可预测的更新。

### 如果对方让你继续讲

虚拟 DOM 比较的结果，最终要落到必要的宿主操作上，这一层抽象就是它能跨平台的基础。现代框架还会靠编译期静态标记、跳过稳定子树这些手段，压低通用 Diff 的成本。

### 对方很可能继续问

**Vue 3 的编译期优化做了什么？**

编译器给动态节点打 PatchFlag，更新时只比对动态绑定、跳过静态内容；静态节点提升到渲染函数外，配合 Block Tree 把比对范围从整棵树缩到动态子树。

**React 和 Vue 的 Diff 有什么不同？**

React 不做双端比较，沿单向链表从左向右遍历，靠 key 命中复用，成本控制交给优先级调度；Vue 有编译期信息辅助，运行时比较更精确。共同点是都只做同层级比较，跨层移动等于重建。

**编译型框架（Svelte、Solid）为什么可以没有虚拟 DOM？**

它们在编译期分析出状态和 DOM 的对应关系，直接生成定向更新代码，省掉运行时 Diff；代价是约束更严。虚拟 DOM 是用一点运行时开销，换通用性和灵活性。

### 一句话记住

虚拟 DOM 买的是可预测的更新模型，不是绝对性能。

## Q5：列表 key 为什么重要？

### 这题在考什么

考你能不能讲清 key 是节点**跨渲染的稳定身份**，而不是随便给一个唯一值或直接用索引了事。

### 面试时可以这样说

> key 表示同级节点在两次渲染之间的稳定身份，Diff 靠它判断节点是新增、删除、移动还是复用。如果用索引当 key，插入或排序会让身份和数据错位，可能造成组件状态和输入内容错误。

### 如果对方让你继续讲

索引 key 相对安全，前提有两个：列表不会重排，条目没有独立状态。反过来，只要列表可能插入、删除或排序，或者条目带独立状态，索引当 key 就保证不了身份稳定。

### 对方很可能继续问

**用随机数当 key 会怎样？**

每次渲染 key 都不同，框架认为旧节点全部销毁、新节点全部新建：状态丢失、输入框清空、性能最差，比索引 key 更糟。

**为什么不要跨层级移动节点？**

Diff 只在同层级进行，节点挪到另一层会被当作“旧层删除、新层新建”，整棵子树重建。保持层级稳定，用 `v-if` 或条件渲染控制显隐。

**key 还有什么用法？**

key 变化会被视为全新节点，可以用来强制重置组件状态，比如切换 tab 时强制重新挂载内容，Vue 和 React 都适用。

### 一句话记住

key 是节点的稳定身份；列表会重排、条目有独立状态时，不要用索引。

## Q6：React 的渲染阶段和提交阶段有什么区别？

### 这题在考什么

考你能不能抓住两个阶段的真正区别——**能否中断**，而不是只背“渲染阶段算变更、提交阶段改 DOM”。

### 面试时可以这样说

> React 更新分两个阶段：渲染阶段计算新 UI 和变更，可以被中断或重新执行，所以 render 必须保持纯净；提交阶段把变更应用到 DOM，并执行相应的布局副作用，这一阶段不能随意中断。

### 如果对方让你继续讲

可中断性带来的直接后果是：渲染阶段里同一段 render 逻辑可能执行不止一次，里面只要带副作用，就会重复触发。提交阶段则把确定的变更一次性应用到 DOM。另外，并发能力改变的主要是渲染工作的调度，不代表 JavaScript 会多线程同时执行组件。

### 对方很可能继续问

**useEffect 在哪个阶段执行？**

提交阶段 DOM 更新完成后异步调度执行，不阻塞浏览器绘制；useLayoutEffect 则在 DOM 变更后、绘制前同步执行，适合测量布局和必须赶在绘制前完成的修改。

**渲染阶段被中断后为什么要重跑？**

中断时本次渲染的结果不会提交，恢复后从调度器重新执行工作单元，直到拿到完整结果才进入 commit。这也是 render 必须纯净的原因：重复执行不能产生不同结果。

**startTransition 改变了什么？**

它把更新标记为低优先级：输入回显这类紧急更新可以打断过渡渲染先执行，过渡内容晚点上屏，还能用 isPending 展示等待状态。改变的是调度顺序，不是最终结果。

### 一句话记住

render 算变更、可中断、要纯净；commit 上 DOM、不可中断。

## Q7：React Hooks 为什么有调用顺序限制？

### 这题在考什么

考你能不能讲清 Hooks 靠**调用顺序**和内部状态槽位对应，而不是把这条规则当成死记的语法限制。

### 面试时可以这样说

> React 需要靠每次渲染时 Hooks 稳定的调用顺序，把每个 Hook 调用和它内部的状态槽位对应起来。也就是说，如果你把 Hook 放进条件或循环，不同渲染的调用顺序就可能变化，状态就会错位。

### 如果对方让你继续讲

这种对应只依赖调用顺序，所以 Hook 只能在组件函数顶层调用，不能进条件、循环或嵌套函数。自定义 Hook 可以组合行为，但它最终还是在组件渲染期间被调用，所以同样要守这条规则。

### 对方很可能继续问

**`useEffect` 依赖数组如何判断？**

重渲染后对数组逐项做 `Object.is` 浅比较，任何一项变化就重新执行。所以依赖里放对象、函数这类引用值时，每次渲染的新引用都会触发执行。

**stale closure 为什么出现？**

回调捕获的是“那次渲染”的 state 和 props 快照；等异步回调真正执行时，组件已经重渲染了多轮，读到的还是旧值。解法：补依赖、函数式更新，或用 ref 存最新值。

**`useMemo` 是否应该默认使用？**

不默认。它自身也有存储和比较的成本，先用 Profiler 证明重算或引用变化确实是瓶颈，再针对性加。

### 一句话记住

Hook 认的是调用顺序；放进条件和循环，状态就会错位。

## Q8：React Fiber 是什么，如何做到可中断渲染？

### 这题在考什么

考你能不能讲清 Fiber 把渲染工作拆成**可中断、可恢复的工作单元**，以及为什么需要链表结构，而不是把“Fiber”当成 React 16 的版本代名词。

### 面试时可以这样说

> Fiber 是 React 16 重写的协调引擎。每个组件对应一个 Fiber 节点，节点之间用 child、sibling、return 指针连成链表。有了这个结构，渲染工作就能拆成一个个小工作单元，调度器每处理完一个单元都可以检查有没有更高优先级的事要处理——有就让出主线程，之后从断点恢复。这就是时间切片和可中断渲染的结构基础。

### 如果对方让你继续讲

补充一点：React 还有双缓存结构，current 树对应屏幕上已提交的 UI，workInProgress 树在内存里构建，完成后一次性替换成新的 current。中断恢复的前提也是 render 纯净——重复执行不能产生副作用。

### 对方很可能继续问

**调度器怎么决定什么时候让出主线程？**

调度器按优先级给任务排序，用宏任务（MessageChannel）安排回调，每个时间片处理若干工作单元后检查该帧剩余时间；有更高优先级任务插入或时间片用完，就保存进度、让出线程，浏览器得以处理输入和绘制。

**state 更新有没有优先级？**

有。React 用 lane 模型划分优先级：同步离散输入最高，transition 更新是低优先级。高优先级更新可以打断正在进行的低优先级渲染，先算先提交，低优先级的进度作废重算。

**startTransition 和 useDeferredValue 有什么区别？**

startTransition 标记“某段更新不紧急”，适合把耗时的状态切换包起来；useDeferredValue 标记“某个派生值可以晚点算”，适合输入驱动的列表过滤。前者管更新，后者管值，都能让输入保持响应。

### 一句话记住

Fiber 链表把渲染拆成可中断、可恢复的工作单元，调度器按优先级切片执行。

## Q9：setState 是同步还是异步？

### 这题在考什么

考你能不能跳出“同步/异步”的口语争论，讲清**批处理和调度**才是本质，而不是背“18 之前异步、之后全异步”的结论。

### 面试时可以这样说

> setState 从来不是异步 API，它做的事是把更新排进队列、合并之后再调度渲染。所谓“异步”，指的是调用后立刻读 state 读到的还是旧值，因为这一轮更新被批处理了。React 18 之前，批处理只发生在事件处理函数里，setTimeout 或原生事件里是同步刷新；18 之后自动批处理覆盖所有场景，包括 Promise 回调和原生事件。要立刻拿到更新后的 DOM，可以用 flushSync 强制同步刷新。

### 对方很可能继续问

**为什么连续三次 setState(count + 1)，count 只加一？**

每次传入的都是同一轮渲染的 count 快照，三个更新基于同一个旧值计算，结果相同，React 再合并执行。要累加得用函数式更新 `setCount(c => c + 1)`，更新队列会依次基于上一个结果计算。

**批处理发生在什么时机？**

事件处理函数、生命周期、Promise 回调里的多次 setState 都先入队，等当前同步逻辑走完，React 再统一进入 render 和 commit。批处理减少了渲染次数，也是“读不到新 state”的原因。

**flushSync 什么时候用？**

需要“更新后立刻读 DOM”的场景，比如测量布局、对接强同步的第三方库。它是逃逸口不是默认项，滥用会把批处理打散、增加渲染次数。

### 这里容易说错

不要说“setState 是异步函数”。调用本身是同步的，只是更新被排队延后处理；读不到新值的锅在批处理，不在异步。

### 一句话记住

setState 是排队合并再调度：读不到新值是批处理，不是异步 API。

## Q10：状态管理如何选？

### 这题在考什么

考你能不能按**状态所有权**做选择，而不是“项目一复杂就上 Pinia/Redux”。

### 面试时可以这样说

> 选状态管理，先按状态所有权来分。组件局部状态，留在组件里；服务端缓存，交给请求缓存工具；跨页面、由多个模块修改的客户端状态，再进入 Pinia、Redux 这样的全局 Store。

### 如果对方让你继续讲

全局化是有成本的：状态一进全局 Store，生命周期、同步和测试的成本都会增加。设计 Store 时，按业务领域拆分，派生值用计算得到，异步并发和持久化要有明确策略。

### 对方很可能继续问

**服务端状态为什么单独管？**

它有缓存、失效、重验证、竞态这些独立问题，交给 TanStack Query、SWR 这类请求缓存工具；全局 Store 只留真正的客户端状态。混放会让 Store 沦为服务端数据的镜像，同步成本极高。

**Redux 和 Pinia 的核心差异？**

Redux 是单一 store、显式 dispatch 加纯 reducer、强制不可变更新（RTK 已经简化了大量样板）；Pinia 按 store 拆分、允许直接修改状态、和组合式 API 贴合。选型差异更多在团队约定和生态，不在性能。

**哪些状态应该放 URL？**

筛选、分页、tab 这类可分享、可回退的视图状态放 query 参数，刷新不丢、链接直接还原场景；全局 Store 留给跨页面的运行时共享状态。

### 一句话记住

先看状态属于谁：局部留组件，服务端给缓存，跨模块才进全局 Store。

## 几个高频追问怎么接

### Vue 的依赖收集为什么不能只有一个全局数组？

因为更新某个对象的某个 key 时，只该触发真正读取过这个 key 的 effect。常见的结构是 `WeakMap<target, Map<key, Set<effect>>>`。WeakMap 让目标对象在失去其他引用后还能被回收，key 级别的 Set 负责去重和精确触发。

### `nextTick` 以后为什么元素尺寸有时仍不对？

`nextTick` 等的是 Vue 本轮 DOM patch 完成，不保证图片已经加载，也不保证浏览器已完成这一帧的布局和绘制。如果尺寸依赖图片，就等资源就绪；如果要观察真实尺寸变化，考虑 ResizeObserver；如果只想等到下一次视觉更新，可以结合 rAF。

### `useMemo` 为什么不能默认到处加？

它本身也要存依赖和缓存，每次渲染还要比较依赖。计算很轻、依赖经常变的时候，缓存成本可能比重算还高。更麻烦的是，无意义的 memo 会增加理解成本。正确顺序是先用 Profiler 证明重算或引用变化确实是瓶颈。

### 项目里如何解释状态边界？

可以拿用户列表页举例。筛选框输入属于组件状态；列表请求结果属于服务端状态，交给查询缓存；当前登录用户和跨页面权限属于全局状态。这样按所有权拆，比一句“复杂项目用 Pinia”更有说服力。
