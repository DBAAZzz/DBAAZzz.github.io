# JavaScript 异步、模块与并发

## Q1：浏览器事件循环怎么工作？

### 这题在考什么

考你能不能抓住驱动执行顺序的那个循环——**当前同步代码 → 清空微任务 → 渲染机会 → 后续任务**，而不是把每种异步 API 硬塞进一张宏任务/微任务表格。

### 面试时可以这样说

> JavaScript 任务在主线程执行。一个任务结束，调用栈清空之后，浏览器会执行微任务检查点，把当前可执行的微任务持续清空；随后浏览器可能进行渲染，然后再进入后续任务。`setTimeout` 回调属于任务，Promise reaction 和 `queueMicrotask` 属于微任务，`requestAnimationFrame` 在浏览器更新渲染的阶段执行，不应简单归为宏任务。注意一点：微任务如果不断产生新微任务，渲染就会被一直推迟；长同步任务则会直接阻塞交互。

现场回答不必一上来背规范，开口就用核心那句话；等面试官给出具体代码，再把题目里出现的 API 逐个放进对应队列。

### 如果对方让你继续讲

碰到这类题，判断顺序可以归纳成五步：

1. 先执行当前同步代码；
2. 遇到异步 API 时注册回调；
3. 当前任务结束后清空微任务；
4. 浏览器根据刷新节奏决定是否更新渲染；
5. 执行后续任务。

“宏任务”只是常用的教学称呼，规范里对应的词其实是 task。计时器只保证最短等待时间，不保证到点立即执行。渲染也不是每个任务结束后必然发生。

项目里更值得讲的是卡顿。假如一次点击处理了 200ms 同步逻辑，这期间事件和绘制都进不来；就算用 Promise 把这 200ms 拆成一串微任务，浏览器仍然可能没有机会绘制。所以，真正想把控制权还给浏览器，就要把工作拆到后续 task，或者放进 Worker。

### 对方很可能继续问

**为什么 Promise 递归会让页面无法渲染？**

因为一次微任务检查点会持续处理新加入的微任务。每个 Promise 回调又创建下一个 Promise 回调，队列就一直清不空，浏览器迟迟等不到渲染机会。

**`await` 后面的代码什么时候执行？**

执行到 `await` 时，函数会先暂停，把控制权交出去。等待值兑现后，后续代码以 Promise reaction 的方式继续，也就是进入微任务。`await` 一个普通值，也不会同步接着往下跑。

**怎么拆 Long Task？**

先确认能不能减少工作量。不能减少时，再按业务边界分批处理，并在批次之间让出主线程。视觉反馈先更新，非关键计算放到后面做。纯计算量大、数据传输可控时，再考虑 Worker。

### 一句话记住

先跑完同步代码，再清空微任务，渲染机会之后才轮到后续任务。

## Q2：Promise 的实现原理是什么？

### 这题在考什么

考你能不能**抓住两条核心**：一是 Promise 的状态机规则，二是“`then` 返回新 Promise”这条链路核心。只会背一句“解决了回调地狱”，还不够。

### 面试时可以这样说

> Promise 是一个有 `pending`、`fulfilled`、`rejected` 三种状态的异步结果容器，状态一旦落定就不能再次改变。`then` 不会修改原 Promise，而是返回一个新 Promise；新 Promise 的结果由回调的返回值决定：回调返回普通值，就兑现该值；回调抛错，新 Promise 就拒绝；回调返回 Promise 或 thenable，就采用它的最终状态。还有一点，回调即使在 Promise 已经落定后才注册，也会异步执行。

这里最容易漏的是“`then` 返回新 Promise”。正因为每一步都返回新对象，链式调用才能把普通值、异步结果和异常统一传下去。

### 如果对方让你继续讲

手写时最关键的不是三个状态，而是 Promise Resolution Procedure。它要处理普通值、Promise、thenable、回调抛错和循环引用。回调的调度应该放进微任务；只用 `setTimeout` 虽然能展示链式调用，但不符合原生执行时序。

错误是沿链往下传的：没有 rejection handler 时就保持拒绝；`catch` 本质是 `then(undefined, onRejected)`；`finally` 通常透传原值或原错误，除非它自己抛错，或者返回拒绝的 Promise。

实际项目里，Promise 链的难点往往不是语法，而是**取消和并发**。原生 Promise 只表示结果，不能自动取消已经发出的网络请求。需要取消请求时，应把 `AbortSignal` 传到底层 API；需要限制并发时，要在任务启动前排队，而不是等所有请求都发出去之后再 `Promise.all`。

### 对方很可能继续问

**`Promise.all` 失败后，其他请求会取消吗？**

不会。外层 Promise 会在第一个拒绝出现时变成 rejected，但其他任务已经启动，仍会继续执行。如果业务要求一起取消，就要主动保存 AbortController，并在失败时通知剩余任务。

**`finally` 会改变原结果吗？**

通常不会。`Promise.resolve(1).finally(() => 2)` 最终仍是 1。但如果 `finally` 自己抛错，或者返回一个拒绝的 Promise，新错误会替换原结果。

### 一句话记住

状态一旦落定就不能再改，`then` 永远返回新 Promise，结果和错误都靠新对象往下传。

## Q3：CommonJS 和 ESM 有什么区别？

### 这题在考什么

考你能不能说清两者的差异根源在**加载与绑定时机**，而不是用一句“值拷贝/引用拷贝”草率概括。

### 面试时可以这样说

> CommonJS 通过 `require` 在运行时加载模块，导出的是 `module.exports` 对象；ESM 的 `import/export` 具有静态结构，导入是只读的 live binding，因此工具可以在执行前分析依赖、做 Tree Shaking。CommonJS 可以条件加载，ESM 的静态导入必须位于顶层，需要按条件加载时使用 `import()`。循环依赖两者都可能出问题，只是暴露未完成模块的方式不同，不能简单说 ESM 自动解决循环依赖。

如果面试官只问区别，不要把表格从头背到尾。优先讲三个真正影响工程的点：分析时机、导入绑定，以及它们对 Tree Shaking 和循环依赖的影响。

### 如果对方让你继续讲

ESM 分为解析、实例化和求值阶段，导入绑定会跟着导出一起更新；但如果在声明初始化之前就去读取，可能触发暂时性死区。CommonJS 首次执行后缓存 `module.exports`，再次 `require` 通常复用缓存对象。

工程上的影响包括：

- 浏览器和打包器更容易静态分析 ESM；
- Node 需要根据扩展名和 `package.json` 的 `type/exports` 判断模块格式；
- 双包发布要警惕同一依赖被 CJS/ESM 各加载一份；
- Tree Shaking 还依赖副作用标记和压缩阶段，不是用了 ESM 就一定生效。

### 对方很可能继续问

**live binding 到底是什么？**

导入方拿到的是对导出绑定的只读访问，而不是导出时值的快照。导出模块后续修改这个变量，导入方能看到新值；但导入方不能给这个绑定重新赋值。它也不是“拿到对象引用”那么简单，因为原始值导出同样可以动态更新。

**`package.json` 的 `exports` 有什么用？**

它声明一个包允许外部访问的入口，还能针对 `import`、`require`、Node 和浏览器提供不同产物。它可以阻止使用方随意深层导入内部文件，但条件导出配置不当也可能造成同一个包被加载两份。

### 一句话记住

CJS 是运行时求值加缓存对象，ESM 是静态结构加只读 live binding。

## Q4：requestAnimationFrame 为什么适合动画？

### 这题在考什么

考你能不能说清 rAF 的价值在于**回调与渲染机会对齐**，而不是把它当成固定 16.7ms 执行一次的定时器来背。

### 面试时可以这样说

> `requestAnimationFrame` 让回调与浏览器的渲染机会对齐，浏览器会在页面不可见时降低或暂停调用，因此比固定间隔定时器更适合视觉动画。它不保证固定 16.7ms 执行一次，刷新率可能是 60Hz、120Hz，主线程阻塞也会延迟回调，所以动画位移应根据时间差计算。

**核心一句话**：“rAF 对齐的是渲染机会，不是固定间隔的定时器。”

### 如果对方让你继续讲

项目里可以拿拖拽或数字滚动举例：不要假设每帧固定移动 5px，而是用回调时间戳计算已经过去多久。这样不管是高刷新率屏幕，还是掉帧，动画速度都接近一致。

### 对方很可能继续问

**`requestAnimationFrame` 是宏任务吗？**

严格说不是。它属于浏览器更新渲染过程中的回调。面试题为了好记，把它塞进宏任务表格，会掩盖它和渲染时机的关系。

**怎么避免布局抖动？**

把 DOM 读取集中在一起：先读取所有 `getBoundingClientRect`，再集中写样式。不要在循环里一边改尺寸，一边读取布局。需要按帧更新时，可以在 rAF 内批量写入。

### 一句话记住

rAF 对齐的是渲染机会，帧间隔并不固定，动画位移要用时间差而不是固定步长。

## Q5：Web Worker 能解决什么问题？

### 这题在考什么

考你能不能说清 Worker 解决的是**把重计算移出主线程**，而不是让算法本身变快，并且能算清它的启动、通信和拆分成本。

### 面试时可以这样说

> Web Worker 用独立线程执行 JavaScript，适合把较重的纯计算移出主线程，例如大数据解析、压缩和图像处理。Worker 不能直接操作 DOM，主线程与 Worker 通过消息通信；普通对象默认结构化克隆，大型二进制数据可以转移 ArrayBuffer 所有权以减少复制。它不能让算法本身变快，还会增加启动、通信和拆分成本。

### 如果对方让你继续讲

判断值不值得用 Worker，可以先估算两件事：计算有没有明显阻塞主线程，以及传入传出的数据有多大。一个只跑 2ms 的计算搬进 Worker，可能比直接执行还慢；几十 MB 数据如果反复结构化克隆，通信成本也会吃掉收益。

### 对方很可能继续问

**Worker 和 Service Worker 有什么区别？**

Web Worker 服务于页面计算，生命周期通常和创建它的页面相关；Service Worker 位于页面和网络之间，可以拦截请求、做离线缓存和推送，生命周期由浏览器管理。两者都不能直接操作 DOM，但解决的问题完全不同。

**怎么取消长任务？**

最直接的是终止整个 Worker；如果 Worker 复用成本高，可以把任务切成小块，定期检查取消标记。其实只在主线程侧不再接收结果，并不能停掉 Worker 里的 CPU 消耗。

### 一句话记住

Worker 移走的是主线程上的计算，算法不会变快，通信还有成本。

## Q6：Proxy 和 Reflect 为什么经常一起使用？

### 这题在考什么

考你能不能说清 Reflect 的作用是在 trap 里**保持默认语义**，而不是把 Proxy 和 Reflect 当成必须捆绑的一对。

### 面试时可以这样说

> Proxy 可以拦截对象的读取、赋值、删除、函数调用等内部操作，适合响应式、校验和虚拟化对象。Reflect 提供与这些内部操作对应的方法，在 trap 中调用它可以保持默认语义，并且像 `Reflect.set` 这样的 API 会明确返回操作是否成功。二者一起用不是强制要求，而是更不容易破坏语言规则。

### 如果对方让你继续讲

项目里可以联系 Vue 3：读取时收集依赖，写入时触发更新。不过不要回答成“Vue 3 就是一个 Proxy”，真正的响应式还包括 effect、依赖表和调度器。

### 对方很可能继续问

**Proxy 为什么不能直接代理原始值？**

Proxy 的目标必须是对象。Vue 的 `ref(1)` 会用一个包装对象提供 `.value`，在 getter/setter 中完成依赖追踪，不是直接给数字套 Proxy。

**Reflect 的 receiver 为什么重要？**

当 getter 里使用 `this` 时，`Reflect.get(target, key, receiver)` 能让访问语义保持在代理对象上。直接写 `target[key]` 可能让 getter 的 `this` 落到原对象，导致嵌套访问绕过代理。

### 一句话记住

Proxy 拦截操作，Reflect 保持默认语义，一起用是为了不破坏语言规则。

## Q7：Iterator 和 Generator 有什么关系？

### 这题在考什么

考你能不能理清三层关系：**Iterator 是协议，Iterable 提供迭代器，Generator 只是创建迭代器的一种简洁写法**；而不是把 Generator 当成异步方案的替代品。

### 面试时可以这样说

> Iterator 是一种按步骤产出值的协议，对象的 `next()` 返回 `{ value, done }`；Iterable 是能通过 `Symbol.iterator` 创建迭代器的对象。Generator 是创建迭代器的一种简洁方式，调用生成器函数不会立即执行函数体，而是返回 Generator，之后用 `next` 在 `yield` 之间暂停和恢复。它适合惰性序列和流程控制，但业务异步代码通常优先使用 `async/await`。

**核心一句话**：“Iterator 是协议，Iterable 出迭代器，Generator 只是简洁写法。”

### 如果对方让你继续讲

如果被问到应用，可以讲分页数据的惰性遍历：调用方只关心“要下一页”，不需要提前把所有数据加载到内存。Generator 的价值是保存暂停位置和局部状态，而不是让代码自动并发。

### 对方很可能继续问

**Generator 可以用在异步吗？**

能用，但它的历史角色已经结束。早期 `co` 这类库靠 Generator 加 Promise 模拟异步流程，`async/await` 正是这条路线的语法化。所以现代异步代码直接用 `async/await`，Generator 留给它擅长的同步场景：惰性序列和流程控制。

### 一句话记住

Generator 适合惰性序列和流程控制，不是并发替代品。

## Q8：Promise 并发方法有什么区别？

### 这题在考什么

考你能不能说清 `all`、`allSettled`、`race`、`any` 这四个方法**各自的落定条件和失败语义**，而不是死背 API 名称。常见的坑，是把“取消”“并发限制”当成 Promise 自带的能力。

### 面试时可以这样说

> 这四个方法我按落定条件来分。`Promise.all` 等全部成功，任何一个失败就整体失败，结果按输入顺序排列；`Promise.allSettled` 等全部落定，永远成功，返回每一条的成败明细；`Promise.race` 谁先落定就用谁，无论成败；`Promise.any` 谁先成功就用谁，全部失败才以 `AggregateError` 拒绝。空数组的行为也值得留意：`all` 和 `allSettled` 兑现空数组，`race` 永远挂起，`any` 直接拒绝。

### 如果对方让你继续讲

四个方法可以用两个维度来记：**等到什么时候结束**——全部成功、全部落定、第一个落定、第一个成功；**失败怎么算**——一败即败、永不失败、成败都算、全败才败。先报这个框架，再把面试官问的方法对号入座，比挨个背定义稳。

工程上有两件事总跟这些方法一起出现，但都不是 Promise 给的能力：

- **取消**：把 `AbortSignal` 传进底层请求，失败或超时时主动 `abort`。它只能取消 fetch/XHR 这类支持信号的任务，不能取消任意 Promise；
- **并发限制**：靠活跃计数加等待队列控制“同时最多发几个”，`Promise.all` 一口气全部发出的行为天生限不了流。实现见手写题的并发限制器。

超时控制用 `race` 加一个必定拒绝的定时 Promise：

```js
function withTimeout(promise, ms) {
  let timer
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error('timeout')), ms)
  })
  timeout.catch(() => {}) // 竞速失败时不产生 unhandled rejection
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer))
}
```

超时只是让调用方不再等，底下的任务并没有停；要真正停下来，还得把 `AbortSignal` 一并传下去。

### 对方很可能继续问

**`Promise.all` 失败后，其他请求会停吗？**

不会。外层 Promise 在第一个拒绝出现时就落定，但其余任务照常执行到底，只是结果被丢弃。要一起取消，得给每个请求传 `AbortSignal`，失败时主动 `abort`。

**`Promise.any` 拒绝时为什么是 `AggregateError`？**

因为失败原因有多个：`AggregateError.errors` 数组收集了每一次拒绝的原因，调用方可以统一读取，而不是只拿到第一个错误。

**空数组传进去会怎样？**

`Promise.all([])` 和 `Promise.allSettled([])` 立即兑现空数组；`Promise.race([])` 永远 pending，因为没有谁能落定；`Promise.any([])` 立即以空的 `AggregateError` 拒绝。写通用封装时，空输入最好在入口就处理掉。

### 一句话记住

`all` 等全部、`allSettled` 全都要、`race` 谁先算谁、`any` 谁先成功算谁；取消靠 `AbortSignal`，限流靠计数加队列。
