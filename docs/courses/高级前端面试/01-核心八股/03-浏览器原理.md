# 浏览器原理

## Q1：从输入 URL 到页面可交互发生了什么？

### 这题在考什么

是否理解从网络到解析、渲染再到交互的完整链路，以及“页面能看到”和“页面可交互”之间的区别，而不是只背一串阶段名词。

### 面试时可以这样说

> 浏览器先解析 URL，再根据缓存、代理和网络状态决定要不要真正发起请求；需要联网的话，就依次完成 DNS、建立传输连接和 TLS，再发送 HTTP 请求。拿到 HTML 以后，解析器构建 DOM，CSS 构建 CSSOM，两者一起生成渲染树，随后进行布局、绘制和合成。注意一点：脚本可能阻塞解析，也可能改变 DOM/CSSOM；而且页面能看到，不等于已经可交互。所以实际优化还要关注 LCP、INP 和主线程长任务。

### 如果对方让你继续讲

回答时，看面试官往哪个方向追问，再展开讲，不要一口气把网络协议背完：

- 网络阶段：缓存 → DNS → 连接 → TLS → 请求响应；
- 解析阶段：HTML 流式解析、预加载扫描、CSS/脚本依赖；
- 渲染阶段：样式计算 → 布局 → 绘制 → 合成；
- 交互阶段：脚本执行、事件处理、框架水合或挂载。

`DOMContentLoaded` 表示 HTML 解析完成、`defer` 脚本也执行完了，但图片不一定全部加载；`load` 要等页面依赖的资源全部加载完，但也不代表后面没有异步渲染。

### 对方很可能继续问

**CSS 为什么会影响脚本执行？**

浏览器构建 CSSOM 时，后续脚本如果可能读取样式或布局，就必须等相关的 CSS 准备好，才能得到正确结果。所以更准确的说法是：CSS 通常不阻止 HTML 解析，但可能阻塞渲染，也可能间接推迟脚本执行。项目里，你应该通过 Coverage 和网络瀑布，找出首屏究竟被哪份样式拖慢，而不是笼统地说“把 CSS 放底部”。

**`async` 和 `defer` 有什么区别？**

`defer` 脚本并行下载，按文档顺序在 HTML 解析结束后执行；`async` 脚本并行下载，下载完成就执行，不保证顺序。也就是说，区别在执行时机和顺序：`defer` 保顺序、等解析完，`async` 谁先下载完谁先执行。

**首屏已经出现但点击无响应，可能是什么原因？**

可能 HTML 和 CSS 已经把内容显示出来了，但主线程还在执行大段 JavaScript，或者 SSR 页面还没完成 hydration，事件监听还没绑上。排查时，先录制一次点击，看输入延迟前有没有 Long Task，再看事件处理本身和后续渲染。

### 一句话记住

从 URL 到可交互是一条“网络 → 解析 → 渲染 → 交互”的链路；页面能看到，不等于已经可交互。

## Q2：重排、重绘和合成有什么区别？

### 这题在考什么

是否理解布局、绘制、合成分别负责什么，以及什么样的改动会触发哪一步，而不是把所有性能问题都归结为“回流重绘”。

### 面试时可以这样说

> 布局负责计算元素的几何位置和尺寸，几何变了就可能重新布局；绘制负责生成颜色、文字、阴影这些绘制记录；合成负责把不同图层的结果组合到屏幕上。所以布局通常会带出后续的绘制，单纯的颜色变化可能只需要重绘；而合成层上的 `transform`、`opacity` 动画，通常可以绕开主线程的布局和绘制。注意一点，图层也占显存，不能无脑提升。

### 如果对方让你继续讲

连续的“写样式—读布局—写样式—读布局”会迫使浏览器同步刷新布局，形成 layout thrashing。优化方式是：批量读取、批量写入，用 `requestAnimationFrame` 对齐视觉更新，动画优先使用 `transform`。

不能把所有性能问题都归为“回流重绘”。实际排查时，你应该录制 Performance，检查 Long Task、Style、Layout、Paint 的时间占比，再决定优化对象。

### 对方很可能继续问

**如何定位页面掉帧？**

先录制 Performance，检查 Long Task、Style、Layout、Paint 的时间占比，再决定优化对象。layout thrashing 这类问题，就是连续的“写样式—读布局”来回交错，迫使浏览器同步刷新布局。

下面这些方向也可以提前准备：

- 哪些 API 会读取布局信息？
- `will-change` 为什么不能到处加？

### 一句话记住

布局算几何、绘制出记录、合成贴屏幕；`transform`、`opacity` 动画走合成层，绕开主线程。

## Q3：浏览器如何加载脚本和资源？

### 这题在考什么

是否理解不同加载方式对下载、执行时机和相对顺序的影响，而不是只记得 `async`、`defer` 这两个名字。

### 面试时可以这样说

> 普通同步脚本会暂停 HTML 解析并立即执行；`defer` 脚本并行下载，按文档顺序在 HTML 解析结束后执行；`async` 脚本并行下载，下载完成就执行，不保证顺序。也就是说，三者的区别就在执行时机和顺序上。模块脚本默认具有类似 defer 的行为。资源优先级还会受到预加载扫描、`preload`、`preconnect`、懒加载和浏览器调度策略影响。

### 这里容易说错

最容易混的是执行顺序：`defer` 保证相对顺序，`async` 不保证。资源提示也别搞反：`preload` 是当前页面的高优先级资源提示，`prefetch` 更偏向未来导航。注意一点：提示过多会争抢带宽，必须结合瀑布图验证。

### 一句话记住

`defer` 保顺序、等解析完，`async` 谁先下载完谁先执行；提示按需给，用瀑布图验证。

## Q4：iframe 有什么优缺点，怎么通信？

### 这题在考什么

是否理解 iframe 的隔离边界在哪里，以及同源和跨源场景下分别怎么通信，而不是只背“iframe 能隔离”的结论。

### 面试时可以这样说

> iframe 提供独立文档和较强的运行环境隔离，适合嵌入第三方页面、低信任内容，或者需要完整隔离的子系统。代价是额外的页面上下文、资源和内存开销，路由、样式、自适应高度和无障碍也更难统一。通信上，同源页面可以直接访问对方的窗口和 DOM；跨源页面要用 `postMessage`，并且严格校验 `origin` 和消息结构。对不可信内容，还应该配置 `sandbox` 和最小权限。

### 对方很可能继续问

**`postMessage` 为什么不能把 targetOrigin 写成 `*`？**

因为 `*` 表示消息可以发给任何目标窗口，等于不做任何校验；而跨源通信恰恰要求严格校验 `origin` 和消息结构，所以 targetOrigin 必须写明确的目标源。

**iframe 和微前端 JS 沙箱如何选择？**

如果内容不可信、需要强隔离，iframe 更合适；如果都是内部可信应用，并且要求统一路由、主题和交互体验，可以接受同页面运行的代理沙箱。不要把 Proxy 沙箱说成安全沙箱，它主要解决全局变量污染和副作用回收。

下面这些方向也可以提前准备：

- `sandbox` 去掉哪些能力？

### 一句话记住

同源直接访问，跨源 `postMessage` 并校验 `origin`，不可信内容再配 `sandbox`；隔离强，但代价也高。

## Q5：Shadow DOM 和 Web Components 解决什么问题？

### 这题在考什么

是否理解 Shadow DOM 封装的是样式和 DOM 结构，而不是安全边界；别把它当成 iframe 那样的隔离方案。

### 面试时可以这样说

> Web Components 是一组浏览器原生组件能力，主要包括 Custom Elements、Shadow DOM 和模板。Shadow DOM 把内部 DOM 和样式封装在宿主元素下，能降低全局 CSS 冲突，但注意一点：它不是安全边界。它适合跨框架组件和嵌入式组件；代价是样式定制、事件边界、SSR 和测试工具链更复杂。

### 对方很可能继续问

**为什么说它不是安全隔离？**

Shadow DOM 封装的只是内部 DOM 和样式，目的是降低全局 CSS 冲突，这种封装并不是安全边界。真正需要安全隔离的场景，还是要靠 iframe 这类方案。

下面这些方向也可以提前准备：

- Shadow DOM 的事件会不会冒泡到外部？
- 如何允许使用方定制内部样式？

### 一句话记住

Web Components 由 Custom Elements、Shadow DOM 和模板组成；Shadow DOM 解决样式冲突，但不是安全边界。

## Q6：浏览器和 Node.js 运行 JavaScript 有什么关键差异？

### 这题在考什么

是否理解浏览器和 Node 的差异来自宿主环境，而不是 JavaScript 语言本身，以及为什么执行细节不能互相套用。

### 面试时可以这样说

> 二者都可以使用 JavaScript 引擎执行语言本身，但宿主环境不同。浏览器提供 DOM、渲染、用户事件和 Web 安全模型；Node 提供文件、进程、网络服务和基于 libuv 的事件循环。全局对象、模块系统、计时器细节和微任务调度都可能不同，所以不能把浏览器的执行顺序直接套到 Node，也不能假设浏览器 API 在 Node 中存在。

### 一句话记住

同一门语言，不同的宿主；执行顺序、模块和 API 都不能互相套用。
