# JavaScript 核心

## Q1：如何判断 this 指向？

### 这题在考什么

是否能从调用方式判断运行结果，而不是死记“this 指向调用者”。

### 面试时可以这样说

> 普通函数的 `this` 由调用方式决定：`obj.fn()` 调用，`this` 就是 `obj`；用 `call/apply/bind` 调用，就是显式传进去的那个对象；`new` 调用，指向新实例；独立调用，严格模式下是 `undefined`。箭头函数不一样，它自己没有 `this`，直接用定义位置外层作用域的 `this`，而且 `call/apply/bind` 也改不了它。所以我判断 `this`，先看它到底是怎么被调用的，而不是看函数定义在哪。

这段话不用背。开口先只说核心一句：“普通函数看调用方式，箭头函数看定义位置”。等面试官给出具体代码，再逐条对照调用形式往下判断。

### 如果对方让你继续讲

优先级只记一个顺序就够：`new` 调用 > 显式绑定 > 方法调用 > 默认绑定。如果 `bind` 出来的新函数又被 `new` 调用，以构造调用为准。箭头函数是例外，它不建立自己的 `this`、`arguments` 和 `super` 绑定。

最容易翻车的是“把函数当参数传出去”：

```js
const user = {
  name: 'A',
  say() {
    console.log(this.name)
  },
}

setTimeout(user.say, 0) // 相当于独立调用，不再是 user.say()
```

值得展开的点是：`say` 传给 `setTimeout` 之后，剩下的只是一个函数值，原来的 `user.` 调用关系已经丢了。项目里常见的同类问题还有：把类方法当回调传、从对象上解构出方法再直接调用、把第三方 SDK 的方法存进变量再执行。

### 对方很可能继续问

**`bind`、`call`、`apply` 有什么区别？**

`call` 和 `apply` 都是立刻调用，区别只在传参：`call(ctx, a, b)` 一个一个传，`apply(ctx, [a, b])` 用数组传。`bind` 不立即执行，它返回一个新函数，把 `this` 和部分参数预先绑好。

**箭头函数为什么不能作为构造函数？**

因为箭头函数没有构造调用所需的能力，也没有自己的 `prototype`，对它用 `new` 会直接抛 `TypeError`。只答“它没有 this”不够，那只是现象之一。

**项目里怎么说？**

可以拿事件订阅举例：对象的方法要注册到事件中心时，注册和取消必须用同一个函数引用。现场 `bind` 两次会得到两个不同函数，`off` 就移除不了监听，所以一般会把绑定后的函数存起来复用。

### 这里容易说错

“谁调用就指向谁”不够准确。回调传递、解构赋值和可选链都可能改变最终调用形式。

### 一句话记住

普通函数看调用方式，箭头函数看定义位置。

## Q2：什么是闭包？

### 这题在考什么

是否理解闭包的本质是“函数 + 定义时所在的词法作用域”，而不只是背定义；同时看你对“闭包导致内存泄漏”的说法判断得准不准。

### 面试时可以这样说

> 闭包，可以理解成函数和它定义时所在词法作用域之间的一种关联。外层函数执行完之后，只要内部函数还引用着外层变量，这些变量就不会被回收。防抖、节流、函数工厂，还有 React 里的回调，都用到了闭包。注意一点：闭包本身不会造成内存泄漏。真正会泄漏的情况是——你不再需要这个闭包了，但它还被定时器、事件监听或者全局对象引用着。

如果面试官只问“什么是闭包”，答到这里就够了。不要立刻展开十个使用场景，否则很容易越说越乱。

### 如果对方让你继续讲

函数在创建时会把外部词法环境记下来，之后查找变量从当前作用域一层层往外找，所以函数即使被返回，也还能访问定义位置的变量。注意它保存的是词法环境里的绑定关系，不是“复制了一份变量”。

React 的“旧闭包”问题也源于此：每次渲染都会产生新的变量和回调；只执行一次的 effect 里，定时器回调记住的是首次渲染的值。解法要看语义：补依赖、用函数式更新，或者用 `ref` 保存最新值。

容易被忽略的是：闭包只保留它真正用到的外部环境。现代引擎确实可能做优化，但写业务代码不能依赖它。更实际的是主动控制引用生命周期——组件卸载时清掉定时器和监听，缓存设上限，大对象用完就解除持有。

### 对方很可能继续问

**外层函数结束后，为什么变量没有被回收？**

外层函数执行完，只是这次调用离开了调用栈，不代表它创建的数据都要销毁。只要返回的内部函数还可达、还引用着外层绑定，那部分环境就仍然可达，垃圾回收器不会回收它。

**闭包一定会导致内存泄漏吗？**

不会。防抖函数里保存 timer 也是闭包，但页面不再用它、也没有其他引用时，照样能被回收。真正的问题是“业务已经不用了，引用还在”，比如组件卸载后，全局事件中心还留着回调。

**怎么排查？**

在 DevTools 里重复执行同一组操作，多拍几次 Heap Snapshot。找到没按预期释放的对象后，顺着 Retainers 引用链看，确认它到底被监听器、定时器、缓存还是闭包持有。单看“内存占用很高”不能断定就是闭包泄漏。

### 一句话记住

闭包延长的是被引用词法环境的生命周期，不是自动制造内存泄漏。

## Q3：变量提升和暂时性死区是什么？

### 这题在考什么

是否理解“创建绑定”和“完成初始化”是两件事，而不是背“var 提升、let 不提升”的结论。

### 面试时可以这样说

> 每个作用域开始执行前，JavaScript 会先把变量和函数的绑定创建好。函数声明在声明之前就能调用；`var` 声明了但还没初始化时去读，得到 `undefined`；`let`、`const` 也创建绑定，但执行到声明语句之前不能访问，这段时间叫暂时性死区。所以它们的区别，不是“有没有提升”，而是绑定什么时候完成初始化。

这题的关键不是背“var 提升、let 不提升”，而是说明创建绑定和完成初始化不是同一件事。

### 如果对方让你继续讲

`var` 属于函数作用域，创建阶段就初始化为 `undefined`；`let`、`const` 属于块级作用域，创建后一直保持未初始化。`typeof` 对未声明变量通常返回 `'undefined'`，但碰到暂时性死区里的变量照样抛错。

```js
console.log(a) // undefined
// console.log(b) // ReferenceError
var a = 1
let b = 2
```

函数声明通常整体提升，声明前就能调用；函数表达式则跟着承载它的变量走。面试时别把提升说成“引擎把代码搬到了顶部”，它只是执行模型的表现，并不是真的改写源码顺序。

### 对方很可能继续问

**为什么 `typeof x` 有时也会报错？**

`x` 从未声明时，`typeof x` 返回 `'undefined'`；但当前作用域里已有 `let x`、执行位置又在声明之前，这时访问的是暂时性死区里的绑定，所以照样报错。

**`var` 在循环异步回调里为什么容易出问题？**

因为 `var` 没有块级作用域，整个循环共用同一个 `i`，等回调真正执行时，循环早就跑完了。`let` 每轮迭代都创建独立绑定，回调读到的才是当轮的值。用立即执行函数也能创建独立作用域，但现代代码优先用 `let`。

### 一句话记住

区别不在“有没有提升”，而在绑定何时完成初始化。

## Q4：原型链和 new 的过程是什么？

### 这题在考什么

是否理解原型链的属性查找机制，能不能完整说出 `new` 的步骤，而不是背结论。

### 面试时可以这样说

> JavaScript 的每个对象，内部都有一个 `[[Prototype]]` 指向另一个对象。读取自身没有的属性时，就沿着这条链往上找，直到找到，或者碰到 `null`。构造函数上的 `prototype` 属性，是给所有实例共享的那个原型对象。`new` 大概做四件事：先创建一个新对象；把这个对象的原型指到构造函数的 `prototype`；以这个新对象作为 `this` 执行构造函数；最后，只要构造函数没有显式返回一个对象，就把这个新对象返回出去。

回答时顺手画一条链：`实例 → Constructor.prototype → Object.prototype → null`。链画对了，后面属性查找和 `instanceof` 的题就不容易答错。

### 如果对方让你继续讲

需要区分三个概念：

- `Ctor.prototype`：函数作为构造函数时提供给实例的原型；
- `obj.[[Prototype]]`：对象实际的原型链接；
- `Object.getPrototypeOf(obj)`：读取原型的标准 API。

读属性会沿原型链找，普通赋值默认写在对象自己身上。`class` 提供的是更清晰的语法和更严格的规则，继承底层依然靠原型链。

### 对方很可能继续问

**`instanceof` 如何工作？**

`instanceof` 取右侧构造函数的 `prototype`，看它是否出现在左侧对象的原型链上。它判断的是原型关系，不是可靠的业务类型标签；跨 iframe、手动改原型、自定义 `Symbol.hasInstance` 这些场景都要谨慎。

**静态方法和实例方法放在哪里？**

类里普通方法放在 `Class.prototype` 上，实例通过原型链访问；`static` 方法放在类构造函数本身。如果给每个实例都重新创建一份相同的方法，会白白增加对象分配。

**`Object.create(null)` 有什么用？**

`Object.create(null)` 创建的对象没有 `Object.prototype`，所以没有 `toString`、`hasOwnProperty` 这些继承属性，也不用担心这些名字和数据 key 撞车。适合当纯字典用，但用通用对象工具时要记得它没有普通对象的方法。

### 一句话记住

`new` 四步：建对象、挂原型、绑 `this`、返回新对象。

## Q5：栈、堆和垃圾回收应该怎么理解？

### 这题在考什么

是否理解“可达性”和引用生命周期，而不是死记“基本类型在栈、对象在堆”的简化说法；有没有真实排查内存泄漏的方法。

### 面试时可以这样说

> 我不会简单说“基本类型都在栈、对象都在堆”，因为这是过度简化。更准确的说法是：执行上下文和局部绑定由引擎管理，对象通常分配在托管堆上，变量里存的是对象的引用。垃圾回收主要看对象是否仍然可达；现代 V8 用分代回收，配合标记、清理、压缩这些策略。排查泄漏时，真正要找的是那种“业务上已经不用了，但从根对象出发仍然可达”的引用链。

如果面试官不是在问 V8 源码，回收器的名字不用全背。对前端岗位更有价值的是两件事：知道什么叫“可达”，知道怎么在真实页面里把那条多余引用找出来。

### 如果对方让你继续讲

常见泄漏来源：

- 未清理的事件监听和定时器；
- 脱离 DOM 但仍被 JavaScript 引用的节点；
- 无上限增长的缓存、Map 或队列；
- 闭包持有大对象；
- 长连接和订阅没有在生命周期结束时释放。

排查先稳定复现操作，用 Performance 看内存趋势，再对比多份 Heap Snapshot 里的对象数量和 retained size，最后沿 Retainers 找引用链。某一时刻内存高不代表泄漏，关键是多轮操作、回收之后是否还在持续增长。

### 对方很可能继续问

**`WeakMap` 为什么适合保存对象关联数据？**

因为 WeakMap 对 key 的持有不会单独阻止 key 被回收——业务对象没有其他强引用时，关联数据会跟着释放。代价是 WeakMap 不可枚举，需要遍历、统计或持久化的缓存不适合用它。

**如何证明是泄漏，而不是正常缓存？**

先定一组可重复操作，比如进页面、开弹窗、离开页面，连续跑多轮，在垃圾回收之后看基线是否还在涨。再对比快照里的对象数量和 retained size：缓存有上限、会稳定下来，多半只是正常占用；数量随操作次数线性增长，才更像泄漏。

### 一句话记住

找泄漏，就是找“业务已不用、但仍从根可达”的引用链。
