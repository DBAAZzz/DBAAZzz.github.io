# Node.js 核心

## Q1：Node.js 为什么适合 I/O 密集型服务？

### 这题在考什么

是否理解 Node 的分工：主线程、事件循环、操作系统和 libuv 线程池各自承担什么；也看能不能说清它为什么不适合 CPU 密集任务，而不是停在“Node 是单线程但并发高”这句口号上。

### 面试时可以这样说

> Node.js 在主线程执行 JavaScript，异步结果由事件循环调度。注意一点：等待 I/O 时主线程并没有闲着，网络 I/O 交给操作系统，部分文件、DNS 和加密任务交给 libuv 线程池，主线程可以继续处理其他连接。所以它适合 API 网关、BFF 和实时服务。但也要说清两点：它不是“只有一个线程”；也不意味着任何高并发场景都快。CPU 密集代码仍会阻塞事件循环，需要 Worker Threads、子进程或服务拆分。

### 对方很可能继续问

- 哪些操作会使用 libuv 线程池？
- 如何发现事件循环被阻塞？
- Worker Threads 和 cluster 分别解决什么问题？

### 一句话记住

I/O 交给操作系统和 libuv 线程池，主线程专注调度；CPU 密集代码才会真正阻塞事件循环。

## Q2：Node.js 事件循环有哪些关键阶段？

### 这题在考什么

是否理解事件循环各阶段的职责，以及 `nextTick` 和微任务的插入时机，而不是死背 `setTimeout`、`setImmediate` 的固定输出顺序。

### 面试时可以这样说

> Node 的事件循环由 libuv 驱动。面试中最重要的是三个阶段：timers、poll 和 check。计时器回调在相应计时阶段处理，I/O 主要在 poll 阶段处理，`setImmediate` 在 check 阶段处理。注意一点：每次 JavaScript 回调结束后，还会处理 `process.nextTick` 队列和 Promise 微任务；递归安排 `nextTick` 可能让 I/O 饥饿。所以具体时序还受 Node 版本和运行上下文影响，不应只背固定输出。

### 对方很可能继续问

- `setImmediate` 和 `setTimeout(0)` 谁先执行？
- `process.nextTick` 为什么有饥饿风险？
- Node 新版调整计时器阶段后，会带来什么影响？

### 一句话记住

记住 timers、poll、check 三个阶段，微任务插在每次回调之后；输出顺序别背死。

## Q3：什么是 Stream，为什么需要背压？

### 这题在考什么

是否理解 Stream 分块处理的意义，以及背压为什么产生、上下游怎么协调，而不是只背“Stream 省内存”这句结论。

### 面试时可以这样说

> Stream 让数据分块处理，不必等全部内容进入内存，适合文件、网络和压缩链路。所谓背压，就是下游消费速度低于上游生产速度时，需要通知上游减慢，否则缓冲区会持续增长。Node 中 `writable.write()` 返回 `false` 时，上游应等待 `drain`；使用 `pipe` 或 `pipeline` 通常能自动协调背压，并处理错误和清理。

### 对方很可能继续问

- `pipeline` 为什么优于手工连续 `pipe`？
- `highWaterMark` 是硬内存上限吗？
- 如何上传大文件而不撑爆内存？

### 一句话记住

`write()` 返回 `false` 是背压信号，不是写入失败；等 `drain` 再继续写。

## Q4：Koa 洋葱模型是怎么实现的？

### 这题在考什么

是否理解洋葱模型的本质是 `await next()` 串起来的递归 Promise 链，而不是只记住“洋葱”这个名字。

### 面试时可以这样说

> Koa 把多个中间件组合成 Promise 链。每个中间件先执行 `await next()` 前的逻辑，然后进入下一个中间件；下游完成后，再按相反顺序执行 `await next()` 后的逻辑，所以表现为洋葱模型。它适合统一计时、日志、错误处理和响应加工。关键是必须返回或等待 `next()`，否则链路时序会被破坏。

```js
async function compose(middlewares, ctx) {
  async function dispatch(index) {
    const middleware = middlewares[index]
    if (!middleware) return
    await middleware(ctx, () => dispatch(index + 1))
  }

  await dispatch(0)
}
```

### 对方很可能继续问

- 如何防止同一个中间件多次调用 `next()`？
- Express 与 Koa 的错误处理有什么差异？
- 中间件顺序为什么重要？

### 一句话记住

`await next()` 之前的代码进、之后的代码出；漏掉 `await` 或 `return`，时序就乱。

## Q5：Node 服务如何处理 CPU 密集任务？

### 这题在考什么

是否理解 CPU 密集任务要先评估、再按任务特征选方案，而不是把 Worker Threads 当成唯一答案。

### 面试时可以这样说

> 第一步，先确认任务是不是真的 CPU 密集，同时测量它对事件循环延迟和请求 P99 的影响。确认之后再选方案：短任务可以分片或者优化算法；可以并行的 JavaScript 计算交给 Worker Threads；需要故障隔离或者要调用其他程序，就用子进程；高负载、需要独立扩缩容的能力，就拆成单独服务。注意一点：选择时还要考虑数据传输成本、任务取消、超时和进程崩溃后的恢复。

### 一句话记住

先证明任务真的阻塞了事件循环，再按特征选 Worker Threads、子进程还是服务拆分。

## Q6：如何设计 Node 服务的错误处理？

### 这题在考什么

是否理解错误要分层处理——业务错误转错误码、未知错误统一兜底并优雅退出，而不是把所有错误都用 `try/catch` 一包了事。

### 面试时可以这样说

> 错误可以分两类。可预期的业务错误，转换成明确的状态码和错误码；不可预期的错误，要记录请求上下文、堆栈和版本，交给统一边界处理。还有一点：不能依赖 `uncaughtException` 之后继续长期运行，因为进程状态可能已经不可靠。正确的做法是停止接收新请求，在有限时间内优雅退出，再由进程管理或编排系统重启。退出时别忘了，异步资源、连接和日志都需要设置退出超时。

### 一句话记住

业务错误转错误码，未知错误记上下文、优雅退出、交给编排系统重启。

## Q7：Node 服务有哪些基础安全措施？

### 这题在考什么

是否理解安全措施要落在具体入口上（校验、授权、限流、依赖、日志），而不是把安全名词背一遍。

### 面试时可以这样说

> 我可以按入口来串：先看输入输出，输入做校验、输出做编码；再看权限，身份认证与对象级授权分开处理；再看资源，限流、请求体大小和超时限制；再看攻击面，防止路径穿越、命令注入和 SSRF；工程侧还有依赖锁定、漏洞扫描和最小权限；最后是日志，不能输出密码、Token 和个人敏感信息。

想答得更好，就结合具体入口说清防护位置，别只把安全名词背一遍。

### 一句话记住

安全不是背名词，而是每项措施都知道在哪个入口生效。

## 几个高频追问怎么接

### “Node 是单线程”到底对不对？

如果你指的是 JavaScript 在进程里的那一条主执行线程，基本正确；如果你说的是整个 Node 运行时只有一条线程，那就错了。网络 I/O 可以交给操作系统处理；文件、部分 DNS 和加密任务会用到 libuv 线程池；V8 和运行时内部也可能有其他线程。

### `setImmediate` 和 `setTimeout(0)` 谁先？

在主模块里直接调度时，先后顺序可能受运行时状态影响，没有固定保证；如果在 I/O 回调里同时调度，通常是 `setImmediate` 在 check 阶段先执行。面试时先把上下文说清楚，比直接背一个输出更稳。

### 为什么 `write()` 返回 false 不能继续无脑写？

`false` 表示内部缓冲已经达到阈值，继续写会让内存不断积压。调用方应该暂停生产，等 `drain` 之后再继续写。这个返回值不代表这次写入失败，它是背压信号。

### 服务准备退出时做什么？

先停止接收新流量，再等正在处理的请求完成；然后关闭数据库、消息队列和长连接，刷新必要日志，并设一个最长退出时间。超过时间还没退出，就强制退出，避免进程一直卡在 terminating 状态。
