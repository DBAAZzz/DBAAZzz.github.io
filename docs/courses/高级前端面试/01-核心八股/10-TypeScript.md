# TypeScript

TypeScript 的面试题很少考背关键字，考的是你能不能说清**类型系统在解决什么问题、边界在哪**：它只管编译期，管不了运行时；它会收窄，也会失效；它很强大，但滥用会伤可维护性。回答这类题的套路是：先给结论和判断标准，再讲机制，最后主动说出边界。

## Q1：type 和 interface 怎么选？

### 这题在考什么

考你能不能跳出「哪个更好」的口水战，说出**真正的技术分歧点**：声明合并、联合类型、扩展方式。顺带看你有没有「团队一致性比争论更重要」的意识。

### 面试时可以这样说

> 大多数场景两者可以互换，真正的差别在三处。第一，interface 支持声明合并，type 同名会报错；第二，type 能表达联合、元组、条件类型这些 interface 写不了的形状；第三，扩展方式上 interface 用 extends，成员冲突会直接报错，type 用交叉类型，冲突会静默变成 never，问题被推迟到使用点才暴露。所以我的默认是：对外暴露、可能被下游扩展的对象结构用 interface，其余统一用 type，团队风格统一比站队重要。

### 对方很可能继续问

**声明合并是什么，有什么用？**

同名 interface 的成员会自动合并成一个类型。典型用途是扩展写不了源码的类型：给 `Window` 加自定义属性、给第三方库的配置项补字段。type 做不到，重名就是重复定义错误。

**type 能做哪些 interface 做不了的？**

联合类型、元组、原始类型别名、映射和条件类型，比如 `type Status = 'idle' | 'loading' | 'error'`。至于性能，interface extends 的报错更清楚，但这点差异不构成选型依据，风格混用才是真正的维护成本。

### 一句话记住

公共可扩展结构用 interface，其余用 type，团队统一比争论重要。

## Q2：any、unknown、never 有什么区别？

### 这题在考什么

考你知不知道这三个类型站在类型关系的**两个极端**：any 双向关闭检查，unknown 只进不出、用前必须收窄，never 是空集。判断点是 unknown 能不能讲出「安全在哪」。

### 面试时可以这样说

> any 相当于把类型检查关掉：任何值能赋给它，它也能赋给任何类型，错误会一路传染。unknown 是它的安全版——任何值都能赋进来，但用之前必须收窄，比如 typeof、instanceof 或自定义谓词，不然连属性访问都不行。never 是空类型，代表不可能存在的值，最有用的场景是穷尽性检查：

```ts
function area(shape: Shape) {
  switch (shape.kind) {
    case 'circle': return 1
    case 'square': return 2
    default:
      const _exhaustive: never = shape // 联合加了新分支，这行立刻报错
      return _exhaustive
  }
}
```

将来加一个 `kind: 'triangle'`，`shape` 在 default 分支就不再是 never，赋值直接编译报错，把漏改的分支逼出来。返回 never 的函数是 throw 或死循环，调用点之后的代码会被控制流分析视为不可达。

### 对方很可能继续问

**unknown 收窄之后才能用，具体怎么做？**

typeof、instanceof、in、自定义 `is` 谓词都行。典型场景是 `JSON.parse` 的返回值和 catch 的异常变量：strict 下 catch 变量默认是 unknown，逼你先判断再取 message，而不是直接 `.message` 裸奔。

**为什么说 any 会传染？**

赋值是双向检查：`const x: any = getData()` 之后，`x` 参与的每个表达式都不再检查，错误会静默流向下游。unknown 相反，把问题堵在「使用点」，逼当处收窄，不影响别处。

### 一句话记住

any 关检查，unknown 逼收窄，never 标不可能。

## Q3：泛型和约束解决什么问题？

### 这题在考什么

考你是不是把泛型当炫技工具。判断点：能不能一句话说清它解决的是**复用逻辑的同时保住类型**，并且给得出真实场景。

### 面试时可以这样说

> 泛型解决的问题是：一段逻辑要在多个类型上复用，但每次调用的类型各不相同。不用泛型，要么每个类型抄一遍，要么用 any 把类型信息丢掉。约束 extends 负责回答「这个类型参数至少得长什么样」，泛型默认值负责让老调用方不用改。我不觉得泛型越多越厉害，能用具体类型说清的不上泛型。

### 如果对方让你继续讲

```ts
async function request<T>(url: string): Promise<T> {
  const res = await fetch(url)
  if (!res.ok) throw new Error(res.statusText)
  return res.json() as Promise<T>
}
```

这是最贴业务的例子：`T` 把「这次请求返回什么」的决定权交给调用方，类型跟着接口走而不是跟着封装走。再进一步，函数体内要访问泛型上的属性时必须加约束，比如 `pluck<T, K extends keyof T>(obj: T, key: K): T[K]`，`K extends keyof T` 保证 key 一定存在，返回值还能精确到 `T[K]`。

### 对方很可能继续问

**泛型默认值什么时候有用？**

给已有函数追加类型参数时保持兼容：老调用方不传新参数就走默认值，不用全量改调用点，库升级时特别常见。

**什么时候不该用泛型？**

类型固定只有一个形态时，泛型是噪音；类型参数只出现一次、从不参与推断，多数是过度设计。判断标准是「逻辑确实跨类型复用，且类型之间存在联动关系」。

### 一句话记住

泛型是「复用逻辑、保住类型」，约束是「说清类型参数至少长什么样」。

## Q4：类型收窄有哪些手段？

### 这题在考什么

考你知不知道收窄是**控制流分析**的产物：编译器顺着 if、switch 推导当前分支里值是什么。真正拉开差距的是「收窄什么时候会失效」。

### 面试时可以这样说

> 常用五类：typeof 收原始类型，instanceof 收类实例，in 收对象成员，判别联合靠公共字面量字段收分支，最后是自定义谓词 `is`，比如 `state is Loaded<T>`，把复杂判断封装成可复用的收窄函数。建模上我最推荐判别联合，每个分支带一个字面量 kind，switch 一下类型就跟着分支走。

### 对方很可能继续问

**`is` 和返回 boolean 的普通函数差在哪？**

返回 boolean 时编译器不知道 true 意味着什么；`state is Loaded<T>` 是显式契约：返回 true，参数在后续代码里就是 `Loaded<T>`。代价是谓词可能写错，它只是你单方面的声明，编译器不校验它真的成立。

**为什么收窄在回调里会失效？**

回调是延迟执行的，编译器无法保证执行时值没被重新赋值，所以 `let` 变量的收窄进不了闭包；换成 `const` 声明，因为不存在重新赋值，收窄可以带进去。实务解法是判断完先存一个 const 局部变量。另外注意 `as` 是断言不是收窄，它不做任何运行时判断；判别联合也优于 `data?: T` 这种可空字段建模，后者就算收窄了 status，data 依然是 `T | undefined`。

### 一句话记住

收窄靠控制流分析，const 才能把收窄带进回调，as 不是收窄。

## Q5：常用工具类型的原理是什么？

### 这题在考什么

考你有没有穿透到实现。判断点：能不能说出这些工具类型全是**映射类型 + keyof + 索引访问**的组合，最好现场手写一个。

### 面试时可以这样说

> 这些工具类型是同一个套路：keyof 拿到所有键组成的联合，映射类型遍历键生成新结构，索引访问 `T[P]` 取出对应值的类型。Partial 是给每个键加问号，Pick 是只遍历传入的键子集，Record 是遍历给定的键集合、每个位置放同一个值类型，Omit 是 Pick 的反演，ReturnType 靠条件类型加 infer 从函数类型里抽出返回值。

### 如果对方让你继续讲

```ts
type MyPick<T, K extends keyof T> = { [P in K]: T[P] }
type MyPartial<T> = { [P in keyof T]?: T[P] }
```

`K extends keyof T` 既是约束也是文档：传进来的键必须存在；问号就是映射修饰符，同理还有 readonly，`-?` 和 `-readonly` 就是 Required 的实现原理。ReturnType 的原理一句话：`T extends (...args: any[]) => infer R ? R : never`，infer 在条件类型里声明一个待推断的占位符。

### 对方很可能继续问

**Omit 用在联合类型上有什么坑？**

`keyof (A | B)` 只会得到两个分支共有的键，所以 `Omit<A | B, K>` 会把非共有属性整块丢掉。要逐分支保留，得写分布式的版本：`type DistributiveOmit<T, K extends keyof T> = T extends any ? Omit<T, K> : never`，利用条件类型对联合自动分布的特性。

**infer 还能推什么？**

元组元素、函数参数（Parameters 的原理）、Promise 的 resolve 值（Awaited 的思路），本质都是在 extends 的模式里「挖」出一个位置。

### 一句话记住

工具类型 = keyof 拿键 + 映射变形 + 索引访问取值，infer 负责在条件类型里挖位置。

## Q6：enum、const enum 和字面量联合类型怎么选？

### 这题在考什么

考你有没有跟上 TS 社区的选型趋势，以及知不知道 **const enum 在现代构建链下的坑**。判断点：能不能说清 enum 是有运行时对象的，字面量联合是纯类型的。

### 面试时可以这样说

> 我的默认选择是字面量联合：没有运行时代价、和后端 JSON 天然对上、switch 能做穷尽性检查，这也是现在 TS 社区的主流方向。enum 的价值在于它是一个真实存在的运行时对象，能遍历、能当映射表用。const enum 本来是为了把引用点内联成字面量、省掉运行时对象，但 Vite/esbuild、swc、Babel 这类单文件转译器工作在 isolatedModules 模式下，跨文件的内联做不到：要么被降级成普通 enum 照样生成对象，要么 ambient const enum 直接报错，「零运行时」的承诺在实际项目里常常兑现不了。

### 对方很可能继续问

**isolatedModules 是什么，为什么 Vite 项目要开？**

它是「每个文件单独转译」的编译模型，esbuild、swc、Babel 都按这个方式工作；TS 开了这个选项后也按同样的假设检查代码，保证代码能被这些工具安全处理，Vite 官方模板默认开启。const enum 的跨文件内联正是这个模型做不到的事。

**那 enum 什么时候还有价值？**

需要运行时对象的时候：把所有值列出来渲染下拉框、做值和文案的映射、和后端共享同一份取值集合，这些用字面量联合就得再配一个常量对象，两处还要保持同步，反而绕。另外数字 enum 编译产物是双向对象，`Status[0]` 能反查名字，但反向映射的键会混进 `Object.keys`，算是个隐蔽的坑。

### 一句话记住

默认字面量联合，需要运行时对象才上 enum，别指望 const enum 在 Vite 里零开销。

## Q7：tsconfig 里哪些选项最影响类型安全？

### 这题在考什么

考你有没有从「会抄配置」进阶到「知道每个开关在堵哪个漏洞」。判断点：strict 之外能不能说出 TS 默认行为里**最危险的两个信任**：索引访问和可选属性。

### 面试时可以这样说

> 第一层是 strict 全家桶，它是一组开关的集合：noImplicitAny 管隐式 any，strictNullChecks 管 null 和 undefined，strictFunctionTypes 管函数参数的逆变检查，strictPropertyInitialization 管类属性初始化，还包括 catch 变量默认 unknown。第二步我会开 noUncheckedIndexedAccess：TS 默认信任所有 `arr[i]` 都拿得到值，这是类型系统和运行时行为差距最大的地方，打开后索引访问变成 `T | undefined`，逼你处理越界。再严格是 exactOptionalPropertyTypes，把「属性缺失」和「属性是 undefined」区分开。

### 对方很可能继续问

**打开这些选项后，存量代码怎么办？**

分层收紧：按目录拆 tsconfig，新模块用最严格配置，老模块逐步迁移；顺序上先补 noImplicitAny 再上 strictNullChecks，后者改动面最大；给历史遗留设 @ts-expect-error 预算，只减不增，CI 里卡住增量。noUncheckedIndexedAccess 确实会让每处索引访问都要收窄，但这是把「静默的 undefined」提前暴露，新项目值得直接开。

**exactOptionalPropertyTypes 实际影响什么？**

默认情况下 `age?: number` 允许显式传 `age: undefined`；打开后两者被区分：属性要么不传，要么是 number。对表单、配置合并这类代码影响最大，老项目打开成本高，新项目值得。

### 一句话记住

strict 是底线，noUncheckedIndexedAccess 堵住索引越界的默认信任，存量代码分层收紧。

## Q8：协变和逆变是什么？

### 这题在考什么

这个词背的人多、讲清方向的人少。判断点：能不能说清**协变保持方向、逆变反转方向**，以及 strictFunctionTypes 到底改变了什么。

### 面试时可以这样说

> 协变是指子类型关系沿着赋值方向保持：Dog 是 Animal 的子类型，所以 Dog[] 可以赋给 Animal[]，数组是协变的。函数参数方向相反，叫逆变：一个能处理任意 Animal 的函数，当然可以当成「只处理 Dog」的函数来用——参数要求越宽松的函数，越能顶替要求严格的。TS 历史上为了兼容事件回调的写法，函数参数默认按双向协变检查，逆变和协变都放行，这是不安全的；strictFunctionTypes 打开后，函数类型的参数才严格按逆变检查，但方法简写声明的参数仍然是双向协变，这是留给 DOM 和类库的兼容。

### 如果对方让你继续讲

数组协变其实是不健全的：`Dog[]` 赋给 `Animal[]` 之后，往里 push 一个普通 Animal 就静默污染了原数组，运行时没有任何检查，TS 保留它是为了可用性。函数参数的逆变则可以用代码验证：

```ts
declare const handleAnimal: (a: Animal) => void
const handleDog: (d: Dog) => void = handleAnimal // 逆变：安全，编译通过
// const bad: (a: Animal) => void = handleDog // 反向不安全：调用方可能传一只猫进来
```

### 对方很可能继续问

**为什么方法参数不跟着 strictFunctionTypes 变？**

如果 class 的方法也强制逆变，大量现有 DOM 事件和类库代码都编译不过，所以官方只对函数类型（箭头函数、函数属性）启用严格检查，方法简写保持双向协变。这也是同一份代码里 `bark(): void` 和 `bark: () => void` 检查行为可能不同的原因。

**为什么要关心这个概念？**

读报错用得上：参数位置报 `'Animal' 不能赋给 'Dog'` 这类兼容性错误时，要知道是逆变检查在起作用，常见错误就是把方向搞反。写 React 事件回调、给高阶函数传 handler 时，理解这个方向能少走弯路。

### 一句话记住

协变保方向，逆变反方向，strictFunctionTypes 只管函数类型参数，方法简写除外。

## Q9：大型项目里 TypeScript 怎么做工程化？

### 这题在考什么

考你有没有真的在多人多包仓库里维护过类型，而不是一个人写到底。判断点：有没有把**类型当成需要构建、门禁和测试的资产**。

### 面试时可以这样说

> 我会做四件事。一是产物：库和分包开 declaration 和 declarationMap，下游既能拿到类型，又能从 .d.ts 跳回源码。二是拆分：monorepo 用 project references 把大仓库切成有边界的子项目，tsc -b 增量构建，同时逼出清晰的包依赖方向。三是门禁：CI 里跑 tsc --noEmit，类型不过不许合并，别把类型错误留给运行时。四是类型测试：关键公共 API 用 vitest 的 expectTypeOf 写断言，重构改坏签名时普通单测抓不住，类型测试会在编译期直接失败。

### 如果对方让你继续讲

类型测试运行时不执行任何逻辑，断言发生在编译期，专门守护「形状」：`expectTypeOf(getUser()).resolves.toEqualTypeOf<User>()`。它和单测不冲突——类型断言在编辑器和 tsc 里就能暴露，CI 里和 noEmit 一起跑；运行时行为仍由普通单测覆盖，两者守护的东西不同。

### 对方很可能继续问

**什么时候需要手写 d.ts？**

给没有类型的 JS 库补声明、declare module 做全局扩展、环境声明（比如 window 上的自定义属性）。第三方库优先找官方或 @types 的声明，手写是兜底。

**project references 带来的约束是什么？**

每个子项目开 composite、边界清晰，跨包引用必须走声明的依赖关系，等于把「架构分层」写进了构建配置；增量构建只重编改动的包，仓库越大收益越明显。

### 一句话记住

类型是资产：有产物、有边界、有 CI 门禁、有编译期测试。

## Q10：类型体操的边界在哪？

### 这题在考什么

考价值观和分寸感。判断点：知不知道类型系统的硬边界是**运行时**，以及该在什么位置停下来换工具。

### 面试时可以这样说

> 我认为够用的标准是：能读懂 ReturnType、Parameters 这类基于条件类型和 infer 的工具类型，能写简单的映射和条件类型，再深的体操要有明确收益才写。过度体操的代价很实际：错误信息一屏读不完、编译变慢、同事改不动。更重要的边界是，类型再多也管不住运行时——接口返回、JSON.parse、URL 参数这些跨过边界的数据，类型只是编译期的假设，该上 zod 这类运行时校验，校验通过再派生类型。

### 对方很可能继续问

**为什么类型不能代替运行时校验？**

类型擦除：编译产物里没有任何类型信息，`as` 断言只是编译期的单方面声明，数据真有问题运行时照样错。接口返回的结构变了，类型不会帮你发现。

**zod 和 TS 类型怎么配合？**

schema 作为唯一事实来源，用 z.infer 推导出静态类型，静态和运行时只维护一份，不会漂移。代价是运行时开销，所以一般只在数据边界做：API 层、表单、配置加载，内部数据不重复校验。

**那怎么判断该停下来了？**

三个信号：类型签名同事读不懂、需要口头解释；改一个类型牵出半个仓库的报错；编译时间和 IDE 卡顿明显上涨。命中任何一条，就把复杂度从类型层挪到运行时，写一个普通的校验函数，比四层条件类型好维护得多。库作者除外：给下游提供精确推导（组件库的 Props 推断、路由参数联动）是体操的合理场景。

### 一句话记住

读懂条件类型和 infer 就够用，跨过运行时边界的数据交给 zod，不交给类型体操。

1. 不看资料说出 type 和 interface 的三个真实差异。
2. 用 never 写一个穷尽性检查，并解释它为什么能逼出漏改的分支。
3. 手写 MyPick，说清 keyof、映射、索引访问各负责什么。
4. 解释为什么数组协变是不安全的，以及 strictFunctionTypes 管住了哪一半。
5. 举一个「必须用运行时校验、类型断言救不了」的场景。
