# 前端安全

## Q1：XSS 是什么，如何防护？

### 这题在考什么

考你能不能讲清 XSS 的本质是**不可信内容进入了可执行上下文**，而不是只会答“过滤用户输入”；还要看防护动作有没有落在输出侧。

### 面试时可以这样说

> XSS 的本质，是浏览器把不可信内容当成脚本或者可执行 HTML 跑起来了。所以防护的核心在输出侧：按输出上下文做编码，避免把用户输入直接传给 `innerHTML`；必须渲染富文本时，就用经过维护的白名单净化库。

### 如果对方让你继续讲

还有两点要注意。第一，只在输入阶段删除 `<script>` 不够，因为不可信内容进入可执行上下文的路径不止 HTML 标签这一种。第二，CSP、HttpOnly Cookie 和依赖治理，它们的作用是降低攻击成功后的影响，属于输出编码之外的配套手段。

### 对方很可能继续问

**存储型、反射型和 DOM 型 XSS 有什么区别？**

区别在不可信内容的注入路径：存储型进数据库，每个访问者都中招；反射型藏在 URL 参数里，靠诱导点击触发；DOM 型完全在前端发生，JS 把不可信数据写进 `innerHTML` 这类危险 API，可以不经过服务器。

**Vue/React 是否自动防住所有 XSS？**

防不住所有。默认插值会转义文本，但 `v-html`、`dangerouslySetInnerHTML`、`javascript:` 伪协议这些口子仍然开放；框架只是降低常见错误的概率，不替代输出编码。

**CSP nonce 如何工作？**

每次响应生成随机 nonce，策略里写 `script-src 'nonce-xxx'`，只有带相同 nonce 的脚本标签才允许执行，注入的脚本没有 nonce 就跑不起来。nonce 必须每响应唯一，被缓存复用就失效了。

### 一句话记住

防 XSS 的落点在输出侧：按上下文编码，而不是在输入阶段删 `<script>`。

## Q2：CSRF 是什么，如何防护？

### 这题在考什么

考你能不能讲清 CSRF 利用的是**浏览器自动携带凭证**，而不是攻击者直接拿到了凭证；还要知道 CORS 为什么帮不上忙。

### 面试时可以这样说

> CSRF 利用的是浏览器自动携带身份凭证，让用户在不知情的时候，向目标站点发起一个有副作用的请求。防护上抓几条：SameSite Cookie；不可预测、且绑定会话的 CSRF Token；服务端校验 Origin/Referer；再保证 GET 不执行写操作。

### 如果对方让你继续讲

注意一点：CORS 不能替代 CSRF 防护。因为 CSRF 攻击可能不需要读取响应——只要请求发出、副作用被执行，攻击就成功了。

### 对方很可能继续问

**CSRF Token 为什么能防攻击？和登录 Token 是一回事吗？**

不是一回事。登录凭证证明“你是谁”，CSRF Token 证明“请求来自本站页面”：服务端下发与会话绑定的随机值，表单提交时带回校验。攻击者的跨站请求读不到本站页面、拿不到合法 Token，所以请求会被拒绝。

**Token 校验和 Origin 校验是什么关系？**

两道独立防线：Token 校验请求自带合法值，Origin 校验请求头里的来源。后者实现简单，但要考虑 Referer 被策略裁剪的场景；高风险写操作两个一起做，别押单一手段。

**纯 JSON 接口为什么也不能说绝对安全？**

跨站表单发不出自定义 Content-Type，但攻击者可以用 text/plain 提交、赌服务端宽松解析；CORS 拦的是读取响应，拦不住请求发出。Cookie 鉴权的写接口仍要 SameSite 加 Origin 校验。

### 一句话记住

CSRF 防的不是凭证被偷，而是凭证被浏览器自动带上。

## Q3：Token 放 localStorage 还是 Cookie？

### 这题在考什么

考你能不能按**威胁模型**做取舍，而不是背“Cookie 一定比 localStorage 安全”这类固定结论。

### 面试时可以这样说

> 这个问题没有脱离威胁模型的固定答案。先看两边各自的坑：localStorage 里的 Token 能被同源 XSS 直接读走；HttpOnly Cookie 读不走，但请求时会自动带上，所以还要考虑 CSRF。所以判断之前，先想清楚当前场景更怕哪一个，答案自然就出来了。

### 如果对方让你继续讲

具体到我的选择：常规 Web 登录，我更倾向使用 Secure、HttpOnly、合适 SameSite 的 Cookie，再配合 CSRF 防护和短会话。跨端 API、第三方客户端这些场景，就按能力选择 Bearer Token。

### 对方很可能继续问

**Refresh Token 应该放在哪？**

放 HttpOnly Cookie 或干脆留在服务端，绝不能进 localStorage——它生命周期长，一旦被 XSS 读走，损失远大于短效 access token。access token 保持短期，靠 refresh 机制轮换。

**`__Host-` 前缀的 Cookie 有什么用？**

浏览器强制要求：带这个前缀的 Cookie 必须 Secure、Path=/、不允许 Domain 属性。这能防止子域页面写 Cookie 覆盖主站会话，是会话 Cookie 的零成本加固。

**网关或 BFF 能帮什么忙？**

BFF 把真实凭证收在自己一侧，浏览器只持有不含敏感信息的会话 Cookie；对外部服务的调用由服务端持有凭证完成。前端攻击面缩小后，XSS 和 CSRF 的风险同时下降。

### 一句话记住

Token 放哪没有标准答案：localStorage 怕 XSS，Cookie 怕 CSRF，先定威胁模型再选。

## Q4：CSP 解决什么问题？

### 这题在考什么

考你能不能讲清 CSP 的定位是**纵深防御**而不是根本防护，还要能说清策略的收紧路径和常见削弱写法。

### 面试时可以这样说

> CSP 通过响应头，限制脚本、样式、图片、连接这些资源可以从哪里加载，以及哪些脚本允许执行。它是 XSS 的重要纵深防御。落地时我推荐从 Report-Only 收集违规开始，再逐步用 nonce 或 hash 收紧脚本策略。

### 如果对方让你继续讲

两个容易踩的点：第一，允许大量 `unsafe-inline` 或通配源，会显著削弱 CSP 的效果；第二，CSP 也不能替代输出编码。

### 对方很可能继续问

**`unsafe-inline` 为什么算削弱项？**

它放行所有内联脚本和内联事件处理器，注入的脚本立刻能执行，CSP 对 XSS 的纵深防御基本失效。收紧方向是 nonce 或 hash，配合构建期把 nonce 注入到产物脚本标签上。

**CSP 除了脚本还能管什么？**

`connect-src` 限制数据外带、`frame-ancestors` 防点击劫持、`base-uri` 和 `form-action` 防注入改写提交目标、`object-src` 禁插件加载。覆盖面越宽，单点失守后的损害越小。

**Report-Only 阶段具体做什么？**

用 `Content-Security-Policy-Report-Only` 只上报不拦截，收集线上真实违规；修复第三方脚本、内联样式这类误伤后，再切强制模式，避免策略上线即事故。

### 一句话记住

CSP 是纵深防御：从 Report-Only 起步、用 nonce 或 hash 收紧，替代不了输出编码。

## Q5：iframe 和 postMessage 如何保证安全？

### 这题在考什么

考你能不能讲清 postMessage 要 **origin、source、payload 多处一起校验**，而不是只校验一个 origin；还要知道嵌入不可信 iframe 时怎么收敛权限。

### 面试时可以这样说

> 对不可信的 iframe，用 sandbox 加上最小 allow 权限。消息这块：发送时指定精确的 targetOrigin；接收时 event.origin、event.source、payload 的 schema 三样一起校验。

### 如果对方让你继续讲

注意一点：通信校验通过，不等于可以放行任意操作。消息到达后仍要做业务授权，不能因为消息来自受信任窗口，就放行所有操作。

### 对方很可能继续问

**`allow-scripts` 和 `allow-same-origin` 为什么不能同时给？**

两个都给时，嵌入页可以移除自己的 sandbox 属性后重新加载，sandbox 形同虚设。不可信内容通常只给 scripts、不给 same-origin，让它落在不透明的源里。

**targetOrigin 写 `*` 的风险是什么？**

消息会发给任意窗口，如果内容里带 token、内部地址，就是直接泄露。发送前必须确定接收方 origin；嵌入关系动态变化时，也要先过白名单再发。

**origin 之外为什么还要校验 source？**

origin 回答“哪个域发来的”，source 回答“是不是我授权的那个窗口”。同一个受信任域可能有多个窗口实例，只验 origin 会放过同源的其他不可信窗口，两者一起验才能锁定通信对象。

### 一句话记住

安全 postMessage 三查 origin、source、payload，到达后还要做业务授权。

## Q6：前端供应链安全如何处理？

### 这题在考什么

考你能不能把供应链安全当成**流程与权限的治理**问题，而不是只回答“装一个漏洞扫描工具”。

### 面试时可以这样说

> 供应链安全我会当成一套工程治理来答。第一，锁住依赖：使用 lockfile 和可信 registry，CI 里做可复现安装。第二，管住引入：审查高风险安装脚本和新增依赖，扫描已知漏洞和许可证。第三，管住发布：锁定发布权限，并启用多因素认证。最后是长期维护：尽量减少依赖、维护废弃包，密钥绝不进入前端产物和源码仓库。

### 对方很可能继续问

**postinstall 脚本的风险怎么管？**

安装脚本以当前账号权限执行，是依赖投毒的主要入口。CI 里用 `ignore-scripts` 或最小权限容器，引入新依赖时人工审查它的 scripts 字段，内部再用私有 registry 做白名单。

**lockfile 变更怎么审？**

review 时单独看 lockfile diff：新增了哪些传递依赖、版本有没有被替换、registry 指向是否变了。安装统一用 `npm ci` 严格按 lock 执行，避免本地顺手升级混进发布。

**扫出漏洞就要立刻升级吗？**

先看可达性：项目是否真的调用到漏洞代码路径、利用条件是否成立。不可达的低危随常规迭代升级，可达的高危走应急流程，把精力放在真实风险上。

### 一句话记住

供应链安全是流程治理：锁依赖、审引入、控发布、减依赖，密钥绝不进产物。

## Q7：如何防止点击劫持？

### 这题在考什么

考你知不知道防点击劫持的**主战场在响应头**而不是前端脚本，还要知道页面被嵌入时怎么收白名单。

### 面试时可以这样说

> 点击劫持的防护主战场在响应头。用 CSP `frame-ancestors` 限制哪些站点可以嵌入当前页面，兼容场景可以同时设置 X-Frame-Options。仅靠前端 frame-busting 脚本不可靠。

### 如果对方让你继续讲

如果确实需要被合作方嵌入，就用精确白名单，并重新检查页面中的敏感操作。

### 对方很可能继续问

**X-Frame-Options 和 frame-ancestors 什么关系？**

X-Frame-Options 只有 DENY 和 SAMEORIGIN 两个值，语义上已被 CSP `frame-ancestors` 取代；后者支持多域名白名单，但老浏览器不认识。兼容期两个都设，新浏览器以 frame-ancestors 为准。

**frame-busting 脚本为什么不可靠？**

脚本可以被嵌入方的 sandbox 屏蔽（不给 `allow-scripts` 或 `allow-top-navigation`），还有 onbeforeunload 这类绕法。防护应该由浏览器按响应头执行，不依赖被嵌入页面自己的 JS。

**必须嵌入合作方页面时注意什么？**

用精确域名白名单、最小 allow 授权、外层套 sandbox；同时重新梳理支付、改密这类敏感操作，确保关键确认动作不易被覆盖层劫持。

### 一句话记住

防点击劫持用 CSP `frame-ancestors`（或 X-Frame-Options），前端 frame-busting 脚本不可靠。

## 几个高频追问怎么接

### React、Vue 默认转义文本，为什么还有 XSS？

默认模板插值通常会转义文本。但只要业务使用 `dangerouslySetInnerHTML`、`v-html`、拼接 URL、动态脚本或不安全的第三方组件，风险仍然存在。框架只是降低了常见错误的概率，没有替代输入信任边界和输出上下文编码。

### SameSite=Lax 后还需要 CSRF Token 吗？

要看业务和浏览器范围。SameSite 能挡住大量跨站请求，但复杂登录跳转、旧环境和同站不同源这些场景，仍需评估。高风险写操作继续使用 CSRF Token 和 Origin 校验更稳妥，别把安全押在单一响应头上。

### 前端能不能保存真正的密钥？

不能。发送到浏览器的代码和配置，最终都可被用户读取。前端可以持有短期会话凭证，但第三方服务私钥、数据库密码、模型供应商密钥这些，必须留在服务端。构建环境变量只要被打入产物，就不再是秘密。

### 项目里怎么讲一次安全取舍？

比如富文本预览：产品要求保留有限样式，但禁止脚本和任意 iframe。你可以说明：用白名单净化、限制链接协议、给外链加安全属性，再用 CSP 做第二道防线；同时保留原始内容和净化后内容的审计记录。
