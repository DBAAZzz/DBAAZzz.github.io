# 项目防守：小程序性能与工程化

下面答案里的 `[真实措施]`、`[真实约定]`、`[真实 key]`、`[真实结构]` 都是占位符，动笔前先换成你项目里的真实数据；收益归因拿不准时，宁可明说组合收益。

## Q1：主包从 1.8MB 降到 1.3MB，具体做了什么？

### 这题在考什么

这题考的不是你做过哪些优化，而是做事有没有章法：是不是**先分类再治理**，以及敢不敢把**收益的归因边界**说清楚——哪些能单项测出来，哪些只能算组合收益。

### 面试时可以这样说

> 我们没上来就压缩，而是先用构建产物分析，把主包拆开看：业务代码、公共依赖、组件、静态资源，分完类再动手。主要动作是 `[只保留真实措施]`。做完之后，相同功能口径下，主包从 1.8MB 降到了 1.3MB。这里有个细节：每项措施是逐步开启的，每开一项就保存一次构建报告，贡献就是一项项测出来的。有些部分没法独立归因，我会直接说明这是组合收益。

### 必须补齐的事实表

| --- | --- | --- | --- | --- |

### 对方很可能继续问

**为什么只看主包，不看总包？**

主包决定小程序的启动下载量，是用户感知的第一道门槛；总包影响的是后续分包加载。所以治理顺序是先主包、后全量。但口径必须一致：报 1.8MB 到 1.3MB 时，前后得是同一种统计口径，不能前面说主包、后面换总包。

**分包后，首次进入分包会不会变慢？**

会多一次分包下载，这是分包的反向成本，要主动说。缓解靠预下载配置和进入路径分析：高频路径的分包做预下载，低频分包接受首次延迟。核心分包的首次进入耗时要单独看数据，不能只报主包收益。

**1.3MB 是源文件，还是平台上传后的产物？**

是构建后、平台上传口径的产物体积，不是源码体积。这个口径要主动说清，因为源码体积和产物体积可能差很多；前后对比也只有固定口径才有意义。

### 一句话记住

先分类再治理，收益要能逐项归因；归因不了的，就明说组合收益。

## Q2：小程序性能优化怎么系统回答？

### 这题在考什么

考你有没有一个覆盖**启动、包体积、渲染通信、网络和内存**的分层框架，而不是零散地报优化手段；同时看你的措施有没有落到**数据验证**上。

### 面试时可以这样说

> 我会分成五块来讲：启动、包体积、渲染通信、网络和内存。启动阶段，控制主包和首屏依赖；运行阶段，重点是减少逻辑层和视图层之间的大对象和高频数据传输，控制节点数量，setData 的粒度也要管住；网络侧做缓存、并发和弱网降级；长页面及时释放监听和大对象。最后，所有这些措施，都用启动耗时、首屏可用时间、包体积和低端机数据来验证。

### 对方很可能继续问

**启动耗时和首屏可用时间怎么测的？**

说清口径和数据来源：起点是发起启动，终点是关键内容可交互；数据来自平台性能面板还是自建埋点。口径说不清，后面的优化收益都站不住。

**低端机怎么验证？**

真机低端机型跑固定操作，对比优化前后的启动、首屏和操作耗时，再模拟弱网看降级表现。没有低端机数据，就承认只验证了主力机型，并说明这是要补的一项。

### 一句话记住

按启动、包体积、渲染通信、网络、内存五块分层回答，每块都要落到数据验证。

## Q3：构建插件如何实现分包异步化？

### 这题在考什么

考你对**实现链路**清不清楚：识别引用、改写加载方式、更新依赖声明，以及为什么**不能只靠正则替换**，转换失败时怎么兜底。

### 面试时可以这样说

> 插件是在编译阶段动的。它先识别符合规则的组件或模块引用，确认目标属于分包之后，把引用改写成平台支持的异步组件配置或动态加载形式，同时同步更新依赖声明。这里要强调一点：实现不能只是正则替换。得基于 AST 或框架的编译结果来识别导入，还要处理别名、重复注入、跨包限制和 Source Map。碰到没法安全转换的情况，保留原逻辑，输出诊断。

### 面试前要补齐

- 准备一段输入代码和一段输出代码，能当场讲清转换前后的差异；
- 说清插件挂在哪个构建阶段；
- 说清如何识别模块所在的分包；
- 说清转换失败时如何处理；
- 说清如何验证主包确实减少、运行时没有回归。

### 对方很可能继续问

**异步化之后，组件加载失败怎么办？**

要有运行时兜底：占位提示、重试，或者降级到同步引入的备用方案。编译期转换解决的是「能不能异步」，运行时体验要另外设计，两边都说到了才算完整。

**为什么不能靠正则替换？**

一句话：正则分不清注释、字符串和同名函数，也拿不到作用域信息，误替换会直接改坏代码；识别导入必须基于编译结果。原理展开见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)。

**转换会影响 Source Map 和调试吗？**

会，所以转换要保留位置映射。验证方式是准备一个会报错的用例，确认堆栈能还原到源文件的行列。只说「做了转换」不谈调试链路，追问一定接不住。

### 一句话记住

编译期识别引用、改写加载方式、更新依赖声明；不能安全转换就保留原逻辑并输出诊断。

## Q4：编译期组件自动注入怎么做？

### 这题在考什么

考你会不会讲**自动注入的完整链路**：扫描约定、建立映射、分析使用、注入 `usingComponents`；同时看你对**隐式行为难排查**这件事有没有预案。

### 面试时可以这样说

> 我们先扫描 `[真实约定]`，建立组件名到路径的映射；然后在构建阶段分析模板或脚本里实际用到的组件，向页面配置注入 `usingComponents`，再把目标组件加进正确的依赖图。自动注入有个副作用：隐式行为出问题不好排查。所以插件会检测重名、输出转换日志，页面也允许显式覆盖自动结果。

### 对方很可能继续问

**页面显式配置和自动注入冲突时听谁的？**

显式配置优先，插件检测到冲突时输出诊断而不是静默覆盖。规则要简单：手写的一律生效，自动的只补空缺——隐式行为最大的问题就是难排查，规则越简单越好查。

**重名组件怎么处理？**

扫描阶段检测到同名不同路径就告警，注入时跳过歧义项，让页面显式声明。宁可构建期报错，不可运行时装错组件。

**自动注入对包体积有影响吗？**

有：没用到的组件不应该进依赖图，这正是「分析实际使用再注入」的原因。拿构建前后的体积对比来证明，比口头保证有用。

### 一句话记住

扫描约定建映射，构建期分析使用并注入 `usingComponents`，重名检测、日志和显式覆盖用来兜底。

## Q5：为什么用响应式 Map 管理全局状态？

### 这题在考什么

考你是否从**数据模型和更新方式**出发说明选择理由，而不是背 O(1) 这类性能口号；对 Map 的**响应式边界和生命周期管理**也要清楚。

### 面试时可以这样说

> 这份状态的本质，是按 `[真实 key]` 动态增删的集合。Map 比普通对象更清晰地表达 key-value 集合，增删和遍历的 API 也稳定。Vue 3 能追踪响应式 Map 的 `get/set/delete/iterate`。value 我们设计成 `[真实结构]`，同时控制 Map 的生命周期和最大数量。选 Map 不是为了喊 O(1) 的口号，而是数据模型和更新方式更匹配。

### 对方很可能继续问

**Map 的 key 会不会导致对象无法释放？**

会，key 是强引用，所以生命周期要管住：任务结束或页面卸载时主动 `delete`，整体设数量上限。说清你们怎么清理，比背 Map 特性重要得多。

**更新 value 内部字段，能不能触发响应？**

要看 value 是否也在响应式系统里、组件读取时有没有建立依赖。把外部普通对象直接塞进 value，再绕过代理改原字段，更新就追踪不到；value 应该用响应式结构来建。最好拿你们的真实 value 结构举例说明。

**为什么不用 Pinia 普通对象？**

这份数据是按 key 动态增删的集合，不是固定形状的业务状态：按 key 精确增删改和遍历清理是主要操作，Map 的语义更贴合；普通对象当字典还要防原型键冲突。如果业务状态是固定字段，Pinia 仍然是更常规的选择。

### 一句话记住

选 Map 是因为数据模型和更新方式匹配，不是因为 O(1)；生命周期和数量上限要管住。

## Q6：跨端框架的基本原理是什么？

### 这题在考什么

考你是否能把“原理”讲成**完整链路**：编译层转换、运行时适配、平台能力差异怎么补，以及**性能问题的来源**，而不是只说一句“一套代码多端运行”。

### 面试时可以这样说

> 跨端框架一般分两层。编译层把统一源码转换成不同平台的模板、脚本、样式和配置；运行时负责适配生命周期、事件、组件和平台 API。但不同平台的能力并不完全一致，所以“写一次到处运行”还是有前提的：需要条件编译、适配层，还有真机验证。性能问题常出在三个地方：运行时桥接、数据序列化和平台组件差异。

### 对方很可能继续问

**逻辑层和视图层为什么要分开？**

小程序把逻辑（JS）和渲染（WebView）拆在两个环境，数据更新要跨层序列化传输——这正是 setData 容易成为瓶颈的根源。理解了这个结构，合并更新、只发最小字段这些优化手段就都是推论，不是背诵。

**什么情况你会建议直接用原生？**

给出项目判断口径：强依赖单一平台能力、对启动和性能极端敏感、团队只投一个端。跨端省的是多端适配成本，不是没有成本；说得出放弃跨端的条件，比只会夸跨端更可信。

### 一句话记住

编译层做转换，运行时做适配；能力差异靠条件编译和真机验证补齐。

## 这些追问要提前准备参考答案

### 主包少了 500KB，为什么不能说都是插件贡献？

包体积的各项措施会互相影响。比如组件按需引入之后，公共依赖和压缩结果也跟着变化。除非每项措施都在同一基线下单独开启、逐项保存构建报告，否则只能说是组合收益。面试时主动说明归因边界，反而显得数据更可靠。

### 分包越多越好吗？

不是。分包能降低主包压力，但会增加分包首次加载、依赖重复、路由管理和预下载的成本。核心路径要看用户什么时候进入分包、值不值得预下载；很小而且经常一起访问的模块，没必要强行拆开。

### setData 为什么容易成为瓶颈？

小程序的逻辑层和视图层之间，需要序列化和传输数据。一次传很大的对象，或者高频更新深层结构，都会抬高通信和渲染成本。优化时要发送真正变化的最小字段、合并同一帧的更新，还要控制节点数量；不能只做 JavaScript 计算优化。

## 数据没有准备齐时，先这样整理

把 1.8MB 到 1.3MB 之间的每次构建报告找出来，记录构建提交、平台、压缩配置和各模块占用。历史无法还原时，就明确说：总收益可以确认，但单项收益当时没有独立统计，这是复盘之后要补的工程能力。

## 自测

1. 给 500KB 收益拆出可信归因表。
2. 展示构建插件转换前后的真实代码。
3. 说明一次低端机或弱网验证结果。
4. 解释分包带来的反向成本。
