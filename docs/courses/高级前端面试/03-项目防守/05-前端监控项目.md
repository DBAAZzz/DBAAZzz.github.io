# 项目防守：前端监控

本章只讲项目口径：90 秒怎么介绍、数据怎么报、取舍怎么认。错误采集、Source Map 管理、采样设计这些机制本身，统一见 [前端监控](../02-高级工程化/04-前端监控.md)。

## Q1：用 90 秒介绍监控项目

### 这题在考什么

能否用**真实数据**在限定时间内把项目讲完整：服务对象、原本的问题、你的职责、技术方案、上线结果和最大取舍，而不是只报一堆技术名词。

### 面试时可以这样说

> 先给一句话定位：这个项目服务 `[应用数/团队数]`，原来的问题是 `[错误不可见/定位耗时/发布后无法归因]`。我主要负责 `[真实职责]`。技术上有两条线：一条是统一错误、性能和请求的事件模型，另一条是建立版本与 Source Map 的关联。端侧通过采样、批量和降级控制开销，服务端做去重、聚合和告警。上线后 `[真实结果]`。最大的取舍是 `[真实取舍]`，因为当前规模下收益不足，所以没有实现 `[能力]`。

### 对方很可能继续问

**这个项目几个人做，你负责哪部分？**

团队边界口径：说清人数、你负责的部分、协作接口——服务端谁做、SDK 谁接入。「都是我做的」在追问里最容易穿帮；说清边界反而显得可信。

**告警怎么设计才没人忽略？**

按影响用户数、版本和业务等级分级，同一指纹聚合降噪，错误风暴只发升级通知。机制展开见 [前端监控](../02-高级工程化/04-前端监控.md)；项目里对应的事实是告警发到哪个群、谁负责响应、误报率多少。

### 一句话记住

90 秒里按顺序讲五件事：服务对象、原问题、方案、结果、取舍。

## Q2：白屏检测为什么使用视口采样？

### 这题在考什么

是否理解白屏检测判断的是**视口里有没有实际内容**，而不是 DOM 变没变；能不能说清为什么 **MutationObserver 只能当辅助，不能当最终判断**。

### 面试时可以这样说

> 先理清一件事：白屏要判断的是用户视口里有没有实际内容，而不是 DOM 是否发生变化。我们的做法是，在 `[真实时机]` 对视口关键区域取多个采样点，通过 `elementFromPoint` 判断命中的是否仍是根容器，再结合 `[路由状态/关键元素/错误事件]` 降低误报。为什么不用 MutationObserver 做最终判断？因为它只能说明 DOM 发生过变化，骨架屏和无效更新也会触发，而且持续监听有额外噪音。

### 面试前要补齐

- 采样点的数量和位置；
- 触发时机与超时时间；
- 骨架屏、弹窗、空状态的排除规则；
- 误报率如何人工抽样验证。

### 对方很可能继续问

**误报率怎么统计？**

灰度期只上报不告警，抽样把判定为白屏的会话用截图或回放做人工核对，统计误报率和漏报率；上线后持续看误报率，超过阈值就收紧条件或调整超时。没有这一步，白屏告警很快变成“狼来了”。

**白屏和错误监控怎么关联？**

白屏判定要结合当时的错误事件和资源失败一起看：根节点为空、同一时刻又有脚本报错，基本能直接定位原因。元素采样只能判断“空”，错误事件才能解释“为什么空”。

### 一句话记住

白屏看的是视口里有没有真实内容，DOM 变化不足以做最终判断。

## Q3：采样率到底是什么维度？

### 这题在考什么

能否把采样率的**统计口径**说准确：当前到底是按事件随机采样，还是按用户稳定采样，两者能支撑的分析有什么差别。

### 回答前先修正口径

如果当前实现确实是每个请求执行 `Math.random() < 1 / rate`，那准确的说法就是按事件随机采样：`rate` 表示平均每 N 个取一个，而不是用户稳定采样。

### 面试时可以这样说

> 先说清口径：当前成功请求按事件采样，失败请求全量采集，目的是控制高频成功日志的成本。这种方式适合估计总体分布，但无法保证单个用户链路完整。如果要做会话漏斗或用户行为关联，我会改为基于 userId/sessionId 的稳定哈希采样，并把采样概率写入事件，服务端聚合时做权重修正。

### 对方很可能继续问

**采样概率为什么要写进事件？**

有权重才能还原总体估计：不记录采样率，按事件采样之后的分位数就是一个没有统计意义的数字。这一条是按事件采样能不能用于分析的分界。

**错误为什么全量？**

错误量小、价值高，全量采集成本可控；只有错误风暴时才动态降采样，并配合指纹聚合计数，保住“总共错了多少”这个结论。按用户和按事件采样的完整对比见 [前端监控](../02-高级工程化/04-前端监控.md)。

### 一句话记住

先分清按事件采样还是按用户采样：前者估总体分布，后者保链路完整。

## Q4：Source Map 服务如何部署？

### 这题在考什么

是否理解 Source Map 的安全是**完整闭环**：构建不公开引用、CI 上传受控、访问有鉴权，而不是把“放内网”当成安全结论。

### 面试时可以这样说

> 部署上有几条要连起来说。构建使用不公开引用 Source Map 的配置；CI 按应用和版本上传到受控目录；静态服务器不暴露该路径。错误事件携带 release 和压缩文件位置，解析服务据此找到对应 Map 还原源码。解析结果做缓存，原 Map 按版本保留周期清理。最后补一句容易漏的：仅仅“放内网 Nginx 目录”不等于安全，还要有访问控制、上传鉴权和版本完整性校验。

### 对方很可能继续问

**版本对不上、还原失败怎么办？**

找不到 Map 时不静默失败：上报原始压缩堆栈并标记“未还原”，按版本统计还原率，还原率突降本身就要告警——通常意味着发布流程断了。完整流程见 [前端监控](../02-高级工程化/04-前端监控.md)。

**旧版本 Map 什么时候清理？**

按版本保留周期清理，周期要覆盖一个回滚窗口；还没退场的版本就把 Map 删了，线上错误就永远还原不了。给出真实保留时长，比说“定期清理”可信。

### 一句话记住

Source Map 的安全是完整闭环，仅仅放进内网目录不等于安全。

## Q5：SSE 日志断线怎么处理？

### 这题在考什么

能否把 **EventSource 的自动重连**和**消息补偿**分开讲，敢不敢承认当前只做了重连、没有补发，并说清这个取舍**为什么不影响任务正确性**。

### 面试时可以这样说

> 先区分两个概念：原生 EventSource 会自动重连，但自动重连不等于消息补偿。当前项目如果只实现了重连，我会如实说明：日志消息没有持久化序号和补发，重连后只能继续看最新输出。我们接受这个取舍，是因为构建的最终状态通过独立接口查询，短暂缺日志不影响任务正确性。如果日志完整性成为要求，就给消息分配递增 ID，服务端保存有限窗口，客户端用 Last-Event-ID 补发。

### 对方很可能继续问

**为什么不用 WebSocket？**

日志是服务端到客户端的单向流，SSE 基于 HTTP，接入和自动重连都更简单；当前没有高频双向消息，没必要承担 WebSocket 的心跳和协议维护成本。后续要双向交互或二进制消息再重新评估。

**EventSource 如何携带认证？**

同域场景靠 Cookie；跨域或需要自定义头时，用 fetch 流式读取实现 SSE，或者在建立连接时带短期 token。要说清你们项目用的是哪种，别两个方案都背。

**多实例服务端怎么续接同一任务日志？**

任务状态和日志缓冲不能只在单实例内存里：日志按 task ID 写入集中存储，重连时按 ID 路由或从存储续读，续接位置靠消息序号。当前只部署单实例就如实说，并给出扩展方案。

### 一句话记住

自动重连不等于消息补偿，先如实说现状，再说清取舍为什么不伤正确性。

## Q6：如何证明 SDK 没有拖慢业务？

### 这题在考什么

有没有**真实证据链**证明 SDK 的开销可控，而不是空口说“对业务零影响”；证据没备齐时，能不能如实说明自己验证到了哪一步。

### 面试时可以这样说

> 我们给 SDK 设了包体积和运行开销预算。接入前后在同一台低端设备跑固定操作，比较主线程任务和内存；SDK 内部记录队列长度、丢弃事件和上报失败。错误风暴下会降低普通事件采样率、限制队列，远程配置也可以直接关闭非核心插件。当前如果没有完整对比数据，我会如实说只完成了哪些验证，不会直接说“对业务零影响”。

上面这段话需要这几项证据支撑，面试前先逐项核对：

- SDK 的 gzip 体积；
- 初始化和单事件处理的耗时；
- 队列长度、丢弃数和上报流量；
- 错误风暴的压测结果；
- 低端机接入前后的 Long Task 和内存对比；
- 远程关闭和降采样开关。

### 对方很可能继续问

**采样和降级会不会影响监控数据本身？**

会，所以要自监控：队列长度、丢弃数、上报失败单独记录。监控 SDK 影响了业务、或者自己的数据丢了都不知道，两种情况都不算合格。SDK 低侵入的完整设计见 [前端监控](../02-高级工程化/04-前端监控.md)。

**错误风暴怎么处理？**

端上对同一指纹做本地聚合计数，只上报“指纹 + 次数”；服务端配合动态降采样和限流。风暴处理的机制展开见 [前端监控](../02-高级工程化/04-前端监控.md)。

### 一句话记住

证明不拖慢业务靠数据证据链，证据不全就如实说验证到了哪一步。

## 这些追问要提前准备参考答案

### 为什么白屏采样不只取屏幕中心？

有些正常页面的中心区域本来就是空的，或者弹窗正好遮住中心，只取一个点很容易误判。多个点覆盖上中下和左右区域，能减少单点误判。采样点也不能无限增加，因为每次 `elementFromPoint` 都有成本，最终应通过已标注的页面样本调参数。

### 骨架屏会不会被判断成正常页面？

会，所以仅靠元素采样只能判断“视口是否为空”，不能判断业务是否真正可用。可以把骨架节点列为无效元素，或者要求关键内容元素在超时前出现。不同路由的关键元素不同，应允许业务配置。

### 多实例解析服务怎么找到 Source Map？

Map 不应只保存在某台实例的本地临时目录。可以放在受控对象存储或共享存储，以应用和 release 索引；解析结果再做分布式或本地缓存。若当前项目确实只部署单实例，就如实说现状和扩展方案。

## 自测

1. 所有项目数据都说明采集口径。
2. 如实区分 SSE 自动重连与消息补偿。
3. 解释白屏检测的误报案例。
4. 画出错误从浏览器到源码定位的链路。
