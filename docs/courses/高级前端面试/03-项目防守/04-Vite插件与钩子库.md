# 项目防守：Vite 插件与钩子库

## Q1：插件拦截返回的底层原理是什么？

### 这题在考什么

这题考的是你能不能把构建期 AST 转换说成具体步骤，而不是一句"运行时 Monkey Patch"带过；同时看返回路径的各种情况和返回值语义是否都覆盖完整。

### 面试时可以这样说

> 先说底层机制：插件不是在运行时 Monkey Patch 所有函数，而是在构建阶段，先定位 `[真实目标调用或函数]` 的 AST 节点，再向返回路径注入统一钩子。转换时要覆盖几种情况：直接 return、异步返回、异常路径和提前返回，同时保留原返回值的语义。来源怎么确认？我们通过作用域绑定确认目标来源，避免同名函数被误命中。最后是兜底：对无法安全处理的语法，输出编译错误或者跳过并报告。

### 面试时最好能展示

```text
转换前源码 → AST 匹配条件 → 转换后源码 → 运行时调用顺序
```

缺了这四步，面试官会怀疑它只是概念方案。

### 一句话记住

构建期定位 AST 节点、向返回路径注入钩子，运行时不做 Monkey Patch。

## Q2：为什么选择构建期注入，不用运行时方案？

### 这题在考什么

这题考的是你有没有把构建期和运行时两条路放在真实约束下比较，并且能把构建期方案的代价和你的缓解手段说完整。

### 面试时可以这样说

> 先讲为什么不用运行时方案。需要改造的调用点分散、数量多，而且要求业务无感接入。构建期注入有几个好处：可以统一注入，未命中的情况直接在 CI 暴露，运行时也不用额外挂全局代理。代价也要说清楚：插件和源码语法耦合，调试链变长。所以我们的对策是：限制匹配范围、保留 Source Map、提供关闭开关，再用 fixtures 做回归。反过来，如果业务调用点很少，或者变化频繁，我会优先用运行时显式封装。

### 一句话记住

调用点多、要无感接入就选构建期；调用点少或变化频繁再回运行时。

## Q3：如何保留完整 Source Map？

### 这题在考什么

这题考的是你是否理解自定义转换必须自己产出并验证 Source Map，而不是打开 `sourcemap: true` 就算完成。

### 面试时可以这样说

> 核心在转换阶段：不是只返回新代码，还返回这段代码相对上一阶段的 Source Map，Vite/Rollup 会继续合并后续转换的映射。具体做法是：用 `[真实生成工具]` 记录新增节点和原节点位置，再准备一个会在线上抛错的 fixture，验证最终堆栈能还原到转换前的文件和行列。最后补一句：仅配置 `sourcemap: true`，证明不了自定义转换的映射是正确的。

### 对方很可能继续问

- 多个插件连续转换时 map 如何合并？
- 注入代码没有原始位置怎么办？
- 生产 Map 如何上传和保密？

### 一句话记住

转换必须自带 Source Map 并用 fixture 验证，`sourcemap: true` 证明不了映射正确。

## Q4：Vite 插件钩子如何选择？

### 这题在考什么

这题考的是你选钩子有没有依据：按目标对象挑钩子，并用 `enforce`、`apply` 控制顺序和环境，而不是背钩子清单。

### 面试时可以这样说

> 第一步，按目标对象选钩子：解析模块请求用 `resolveId`，提供虚拟模块内容用 `load`，转换已有模块用 `transform`，处理产物用 `generateBundle` 或 `writeBundle`。第二步，用 `enforce` 和 `apply` 控制前后顺序和运行环境。第三步是提醒自己：插件逻辑尽量放在最窄的阶段，避免每个文件都做一次昂贵解析。

### 一句话记住

按目标对象选钩子，顺序和环境交给 `enforce`、`apply`，逻辑放在最窄阶段。

## Q5：如何测试一个构建插件？

### 这题在考什么

这题考的是你的测试策略是否分层且可执行，从 AST 单测一直覆盖到真实构建、产物比对和运行验证，而不是只说"跑通了"。

### 面试时可以这样说

> 我会按七层来测。第一，单元测试 AST 的输入输出。第二，用 fixtures 覆盖不同语法和失败场景。第三，跑一次真实 Vite build。第四，比对构建产物与 Source Map。第五，测重复执行是否幂等。第六，测量构建时间和转换文件数量。第七，在目标小程序或浏览器里做运行验证。

### 一句话记住

AST 单测、真实 build、产物与 Map 比对、运行验证，一层都别省。

## Q6：如何设计钩子库 API？

### 这题在考什么

这题考的是你设计 API 时是否先定语义再写接口：执行模型、错误传播、取消和快照都要显式约定。

### 面试时可以这样说

> 第一步，先定义钩子的执行模型：是串行、并行、瀑布还是可短路，同时明确错误传播、返回值合并和取消语义。第二步，注册接口返回取消函数，执行时用稳定快照，避免回调里增删导致顺序混乱。第三步，异步钩子统一超时和失败策略。最后，API 名称要表达时机和能力，比如 before/after 不能让使用方误以为能改变主流程结果。

### 一句话记住

先定执行模型和错误、取消语义，再谈接口名称。

## 这些追问要提前准备参考答案

### 如何证明插件没有误改同名函数？

不能只判断 `callee.name`。要先找到 import 声明，再通过作用域 binding 确认调用处引用的就是那个导入。中间被重命名的，也要沿 binding 识别；如果局部作用域重新声明了同名变量，就不能命中。fixtures 里要专门放一个同名局部函数作为反例。

### 为什么转换失败不做"尽量猜"？

构建插件一旦误改，问题可能到运行时才暴露，而且影响所有接入的项目。对不能确定语义的写法，明确跳过并输出位置，或者直接让构建失败，成本通常低于生成一份看似成功、行为却错误的产物。

### 注入逻辑怎么支持回滚？

插件配置要有总开关和按模块排除的能力，产物里最好记录插件版本。出问题时，可以关闭注入重新构建，而不是让业务逐个删代码。如果插件改变了运行协议，还要保证服务端在一段时间内兼容旧产物。

### 钩子回调中又注册新钩子怎么办？

一次触发应基于开始时的监听快照，新增监听从下一次触发生效，这样顺序才可预测。删除当前或后续监听的行为也要写进契约并测试，不能由数组迭代的偶然表现决定。

## 一个完整回答应该带代码证据

至少准备一段十几行的真实材料：转换前源码、转换后源码，还有 Source Map 验证截图或测试。资深面试官通常会追问节点类型、作用域和失败案例，只讲"使用 AST 注入"是不够的。

## 自测

1. 拿真实源码画出插件转换链。
2. 解释构建期方案的一个失败案例。
3. 展示 Source Map 验证，不只说"保留了"。
4. 定义钩子库的错误和取消语义。
