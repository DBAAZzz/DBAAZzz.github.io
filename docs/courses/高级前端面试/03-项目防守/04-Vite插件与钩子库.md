# 项目防守：Vite 插件与钩子库

本章只讲项目口径：你的插件怎么落地、怎么验证、怎么兜底。AST、Visitor、作用域绑定这些编译原理的通用机制，统一见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)；Vite/Rollup 插件体系本身见 [Webpack与Vite](../02-高级工程化/02-Webpack与Vite.md)。

## Q1：插件拦截返回的底层原理是什么？

### 这题在考什么

这题考的是你能不能把**构建期 AST 转换**说成具体步骤，而不是一句“运行时 Monkey Patch”带过；同时看**返回路径的各种情况**和**返回值语义**是否都覆盖完整。

### 面试时可以这样说

> 先说底层机制：插件不是在运行时 Monkey Patch 所有函数，而是在构建阶段，先定位 `[真实目标调用或函数]` 的 AST 节点，再向返回路径注入统一钩子。转换时要覆盖几种情况：直接 return、异步返回、异常路径和提前返回，同时保留原返回值的语义。来源怎么确认？我们通过作用域绑定确认目标来源，避免同名函数被误命中。最后是兜底：对无法安全处理的语法，输出编译错误或者跳过并报告。

AST 匹配、作用域绑定这些机制的通用写法属于编译原理，展开见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)；这里重点讲你们项目怎么组合它们。

### 面试时最好能展示

```text
转换前源码 → AST 匹配条件 → 转换后源码 → 运行时调用顺序
```

缺了这四步，面试官会怀疑它只是概念方案。

### 对方很可能继续问

**钩子注入后，运行时的调用顺序是什么样的？**

转换只改写源码，运行时行为就是普通函数调用：原逻辑前后插入钩子。所以真正要讲的是转换前后的代码差异——准备一段十几行的真实对照，当场讲清调用顺序，比任何示意图都有说服力。

**如何验证转换没有改变原有语义？**

fixtures 输入输出对比、幂等验证、再到目标环境运行验证，逐层兜住。分层测试策略见下面 Q5，这里先给结论：只比对代码文本不够，必须有运行验证。

**误改同名函数怎么防？**

不判断函数名，而是沿 import 声明和作用域绑定确认调用处的真实来源。具体做法和反例设计，见文末「如何证明插件没有误改同名函数」。

### 一句话记住

构建期定位 AST 节点、向返回路径注入钩子，运行时不做 Monkey Patch。

## Q2：为什么选择构建期注入，不用运行时方案？

### 这题在考什么

这题考的是你有没有把**构建期和运行时两条路**放在真实约束下比较，并且能把构建期方案的**代价和缓解手段**说完整。

### 面试时可以这样说

> 先讲为什么不用运行时方案。需要改造的调用点分散、数量多，而且要求业务无感接入。构建期注入有几个好处：可以统一注入，未命中的情况直接在 CI 暴露，运行时也不用额外挂全局代理。代价也要说清楚：插件和源码语法耦合，调试链变长。所以我们的对策是：限制匹配范围、保留 Source Map、提供关闭开关，再用 fixtures 做回归。反过来，如果业务调用点很少，或者变化频繁，我会优先用运行时显式封装。

### 对方很可能继续问

**构建期方案怎么灰度和回滚？**

插件提供总开关和按模块排除能力，CI 先 dry-run 统计命中量，异常时下一版直接关闭注入重新构建，业务代码一行不动。回滚设计见文末追问。

**什么信号说明该退回运行时方案？**

转换失败率上升、fixtures 维护成本超过收益，或者调用点数量降到个位数——工具跟着规模走，规模变了结论就重估。

**调试链变长怎么缓解？**

保留 Source Map 让堆栈还原到源码，转换日志带文件和位置，fixtures 让问题在本地可复现。三件套齐了，调试链长一点是可接受的代价。

### 一句话记住

调用点多、要无感接入就选构建期；调用点少或变化频繁再回运行时。

## Q3：如何保留完整 Source Map？

### 这题在考什么

这题考的是你是否理解**自定义转换必须自己产出并验证 Source Map**，而不是打开 `sourcemap: true` 就算完成。

### 面试时可以这样说

> 核心在转换阶段：不是只返回新代码，还返回这段代码相对上一阶段的 Source Map，Vite/Rollup 会继续合并后续转换的映射。具体做法是：用 `[真实生成工具]` 记录新增节点和原节点位置，再准备一个会在线上抛错的 fixture，验证最终堆栈能还原到转换前的文件和行列。最后补一句：仅配置 `sourcemap: true`，证明不了自定义转换的映射是正确的。

### 对方很可能继续问

**多个插件连续转换时 map 如何合并？**

每次转换基于输入 map 生成新 map，工具链自动串联合并；任何一环丢掉输入 map，后面的堆栈就指向中间产物而不是业务源码。合并机制展开见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)。

**注入代码没有原始位置怎么办？**

新增节点尽量带上位置信息；实在没有就映射到注入点附近。验证标准相应降低为「能定位到这段是插件注入的代码」，而不是假装它有源码位置。

**生产 Map 如何上传和保密？**

构建产物不公开引用 Map，CI 按应用和版本上传到受控存储，访问有鉴权，按保留周期清理。部署闭环展开见 [前端监控](../02-高级工程化/04-前端监控.md)。

### 一句话记住

转换必须自带 Source Map 并用 fixture 验证，`sourcemap: true` 证明不了映射正确。

## Q4：Vite 插件钩子如何选择？

### 这题在考什么

这题考的是你选钩子有没有依据：**按目标对象挑钩子**，并用 `enforce`、`apply` 控制顺序和环境，而不是背钩子清单。

### 面试时可以这样说

> 第一步，按目标对象选钩子：解析模块请求用 `resolveId`，提供虚拟模块内容用 `load`，转换已有模块用 `transform`，处理产物用 `generateBundle` 或 `writeBundle`。第二步，用 `enforce` 和 `apply` 控制前后顺序和运行环境。第三步是提醒自己：插件逻辑尽量放在最窄的阶段，避免每个文件都做一次昂贵解析。

### 对方很可能继续问

**`enforce` 在你们项目里的真实用途是什么？**

说出一个真实的顺序依赖案例：比如转换插件要在其他处理同一文件的插件之前执行，就设 `pre`。讲不出具体案例，这个配置就只是抄来的。

**Vite 独有钩子用过哪些？**

按项目实际答：`configureServer`（本地开发中间件）、`transformIndexHtml`（往 HTML 注入脚本）这类。每个钩子都要能配一个真实用途；说不出用途就别报名字。

**dev 和 build 行为不一致怎么排查？**

先查 `apply` 配置和钩子阶段的差异，再用同一个 fixture 分别跑两种环境比对产物。不一致多数来自钩子只在其中一条链路执行。

### 一句话记住

按目标对象选钩子，顺序和环境交给 `enforce`、`apply`，逻辑放在最窄阶段。

## Q5：如何测试一个构建插件？

### 这题在考什么

这题考的是你的测试策略是否**分层且可执行**，从 AST 单测一直覆盖到真实构建、产物比对和运行验证，而不是只说“跑通了”。

### 面试时可以这样说

> 我会按七层来测。第一，单元测试 AST 的输入输出。第二，用 fixtures 覆盖不同语法和失败场景。第三，跑一次真实 Vite build。第四，比对构建产物与 Source Map。第五，测重复执行是否幂等。第六，测量构建时间和转换文件数量。第七，在目标小程序或浏览器里做运行验证。

### 对方很可能继续问

**fixtures 怎么组织？**

每个用例一组输入、期望输出和参数，覆盖正常语法、边界语法、应当失败三类；幂等用例把输出再跑一遍，断言结果等于自身。组织方式的细节见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)。

**性能基线怎么定？**

记录转换文件数和构建耗时，插件开启前后对比；超过阈值就收缩匹配范围或优化实现。没有基线，插件把构建拖慢一倍都发现不了。

**运行验证覆盖到什么程度？**

至少覆盖注入钩子的主路径和一条失败路径，在真实小程序或浏览器里跑通完整流程。运行验证发现的问题，产物比对永远发现不了。

### 一句话记住

AST 单测、真实 build、产物与 Map 比对、运行验证，一层都别省。

## Q6：如何设计钩子库 API？

### 这题在考什么

这题考的是你设计 API 时是否**先定语义再写接口**：执行模型、错误传播、取消和快照都要显式约定。

### 面试时可以这样说

> 第一步，先定义钩子的执行模型：是串行、并行、瀑布还是可短路，同时明确错误传播、返回值合并和取消语义。第二步，注册接口返回取消函数，执行时用稳定快照，避免回调里增删导致顺序混乱。第三步，异步钩子统一超时和失败策略。最后，API 名称要表达时机和能力，比如 before/after 不能让使用方误以为能改变主流程结果。

### 对方很可能继续问

**钩子库和事件总线有什么区别？**

事件总线不关心返回值，钩子库的核心契约是执行模型和返回值语义——瀑布传递、可短路、结果合并。只按发布订阅设计，会漏掉返回值和错误传播这些硬问题。

**异步钩子的超时怎么定？**

按钩子职责设上限，超时按失败策略处理：跳过并告警，或者整体失败。绝不能让一个卡死的回调拖住整个流程。

**怎么让使用方不误用 API？**

命名表达时机和能力，before/after 的语义写进文档和类型签名；再设计几个反面例子自检——能改变主流程结果的回调，绝不能叫 `onXxx` 这种纯通知的名字。

### 一句话记住

先定执行模型和错误、取消语义，再谈接口名称。

## 这些追问要提前准备参考答案

### 如何证明插件没有误改同名函数？

不能只判断 `callee.name`。要找到 import 声明，再沿作用域绑定确认调用处引用的就是那个导入；中间被重命名的也要沿 binding 识别，局部作用域重新声明了同名变量的场景不能命中。绑定识别的通用做法展开见 [Babel与插件系统](../02-高级工程化/03-Babel与插件系统.md)；fixtures 里要专门放一个同名局部函数作为反例。

### 为什么转换失败不做“尽量猜”？

构建插件一旦误改，问题可能到运行时才暴露，而且影响所有接入的项目。对不能确定语义的写法，明确跳过并输出位置，或者直接让构建失败，成本通常低于生成一份看似成功、行为却错误的产物。

### 注入逻辑怎么支持回滚？

插件配置要有总开关和按模块排除的能力，产物里最好记录插件版本。出问题时，可以关闭注入重新构建，而不是让业务逐个删代码。如果插件改变了运行协议，还要保证服务端在一段时间内兼容旧产物。

### 钩子回调中又注册新钩子怎么办？

一次触发应基于开始时的监听快照，新增监听从下一次触发生效，这样顺序才可预测。删除当前或后续监听的行为也要写进契约并测试，不能由数组迭代的偶然表现决定。

## 一个完整回答应该带代码证据

至少准备一段十几行的真实材料：转换前源码、转换后源码，还有 Source Map 验证截图或测试。资深面试官通常会追问节点类型、作用域和失败案例，只讲“使用 AST 注入”是不够的。

## 自测

1. 拿真实源码画出插件转换链。
2. 解释构建期方案的一个失败案例。
3. 展示 Source Map 验证，不只说“保留了”。
4. 定义钩子库的错误和取消语义。
