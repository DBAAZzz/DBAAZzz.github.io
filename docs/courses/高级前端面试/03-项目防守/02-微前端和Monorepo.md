# 项目防守：微前端与 Monorepo

先补齐事实：子应用数量、团队数量、发布频率、主子应用技术栈、你负责的范围、上线前后的数据。下面的答案，只能使用其中真实的部分。

## Q1：为什么选择 micro-app，而不是 qiankun 或 Module Federation？

### 这题在考什么

这题考的不是框架对比知识，而是你有没有用真实约束和 PoC 数据支撑选型。是否理解选型是约束下的综合取舍，而不是比出哪个框架绝对更好。

### 面试时可以这样说

> 当时的核心问题不是单纯复用模块，而是让 `[子应用数量]` 个应用保持独立开发和发布，同时由主应用统一导航和身份。我们用一个 PoC 比较了 micro-app、qiankun 和 Module Federation。micro-app 的自定义元素接入方式与现有应用改造成本更低，并且能满足当前的 JS/样式隔离要求；Module Federation 更适合运行时模块共享，不能单独覆盖应用生命周期和治理；qiankun 生态成熟，但 `[写真实不选择原因]`。最终选择不是因为某框架绝对更好，而是当前约束下综合成本最低。

### 如果对方让你继续讲

- PoC 测了哪些场景？
- 路由、弹窗、全局样式和动态脚本是否验证？
- micro-app 出现故障如何降级？
- 如果现在重做，结论是否一样？

### 这里容易说错

“micro-app 性能比 qiankun 好”这个说法没有测试口径，不能作为选型结论。

### 一句话记住

选型比的是当前约束下的综合成本，不是框架绝对优劣。

## Q2：apps 和 packages 如何划分？

### 这题在考什么

是否理解公共包下沉的边界是稳定职责和清晰所有者，而不是看代码重复了几次；同时看你能不能把配套治理，比如跨层导入限制和版本策略，说清楚。

### 面试时可以这样说

> `apps` 放可以独立运行和部署的应用，`packages` 放拥有明确公共契约、被多个应用复用的能力。是否下沉不以代码重复两次作为唯一依据，我会检查它是否有稳定职责、独立测试价值和清晰所有者。与单一业务流程强绑定的代码继续留在应用内，避免公共包变成业务垃圾场。

### 对方很可能继续问

- 公共包由谁维护？
- 如何限制跨层导入？
- 包更新后如何判断受影响应用？
- 所有包是否统一版本？

### 一句话记住

下沉看的是稳定职责、独立测试价值和清晰所有者，不是重复次数。

## Q3：为什么共享逻辑使用源码直引？

### 这题在考什么

是否理解源码直引换来的是本地开发链路打通，而不是 CI 总成本更低；语法兼容和发布场景这些代价要能说清楚。

### 面试时可以这样说

> 原先应用依赖公共包构建产物，开发公共包时需要先 build/watch，应用 HMR 和调试链路割裂。我们让工作区内应用直接引用源码，由各应用构建工具统一转换，从而减少中间构建并保留源码调试。代价是每个应用必须能处理公共包的语法和样式，发布库时仍要生成正式产物；同时要把源码包纳入缓存输入和类型检查。

### 对方很可能继续问

- 源码包包含 Vue SFC 或特殊语法怎么办？
- CI 中如何避免不同应用转译结果不一致？
- 第三方使用这个包时怎么办？

### 一句话记住

源码直引优化本地开发链路，发布时仍要正式产物。

## Q4：如何处理依赖版本冲突？

### 这题在考什么

是否理解依赖冲突要按运行时、工具和宿主契约分类处理，而不是一把 overrides 全部压平；强制措施的副作用也要能说清楚。

### 面试时可以这样说

> 先给依赖分类：必须单实例的运行时依赖、允许多版本共存的工具依赖、需要由使用方提供的 peer dependency。用 workspace 约束内部包，用 peerDependencies 表达宿主契约，必要时用 overrides 临时收敛已知冲突，并在 CI 检查重复版本和非法依赖。overrides 是仓库级强制措施，会掩盖真实兼容问题，因此必须记录原因和移除条件。

### 对方很可能继续问

- `strict-peer-dependencies` 解决什么问题？
- Vue/React 为什么通常需要单实例？
- 构建工具应该放 dependency 还是 devDependency？

### 一句话记住

先分类依赖，再各管一段；overrides 要记录原因和移除条件。

## Q5：主子应用通信和状态同步怎么做？

### 这题在考什么

是否理解跨应用通信的核心是保住独立发布和可测试边界，而不是共享 Store 图方便；桥接协议的版本、数据真源和失败处理要能说清。

### 面试时可以这样说

> 我们没有直接共享整个 Pinia Store，而是通过 `[真实通信机制]` 暴露版本化的 bridge。主应用只提供身份、主题、导航和少量跨应用事件，业务状态由各子应用自己拥有。初始化时先完成 bridge 注册，再进行一次状态快照水合，后续通过带版本或时间戳的事件增量同步。卸载时统一退订。这样牺牲了一部分直接访问便利，换取独立发布和可测试边界。

### 对方很可能继续问

- `bridgeHelper` 的真实底层机制；
- Store ID、payload 结构和版本不一致时的行为；
- 主子应用谁是数据真源；
- 重复事件、乱序和卸载后的处理。

### 一句话记住

不共享 Store，共享带版本的桥接协议。

## Q6：子应用怎么独立部署和回滚？

### 这题在考什么

是否理解回滚的核心是切换入口映射，而不是重新构建；灰度、监控指标和回滚窗口要能串成完整链路。

### 面试时可以这样说

> 子应用每次构建产生不可变版本，部署后先健康检查，再更新环境配置中的入口映射。主应用运行时读取经过校验的版本配置。灰度按用户或组织稳定分桶，监控错误率、加载成功率和关键操作；超过阈值时只回切入口映射，不重新构建。旧版本至少保留一个回滚窗口。

### 一句话记住

回滚只切入口映射，不重新构建，旧版本保留一个回滚窗口。

## 这些追问要提前准备参考答案

### micro-app 的 JS 隔离是安全隔离吗？

不是。代理沙箱主要把子应用对全局对象的读写放到代理环境里，并在卸载时恢复副作用。主子应用仍运行在同一个页面上下文，可信边界没有真正隔开。第三方或低信任页面应该用 iframe，而不是指望 Proxy 防恶意代码。

### 主子应用 Pinia 版本不一致怎么办？

最稳的答案不是“强制全部升级”，而是不要把 Pinia 实例当跨应用协议。bridge 只传普通、可校验的数据结构，双方各自在自己的 Store 中消费。如果确实共享运行时实例，就必须明确兼容版本和单实例约束，这会降低独立发布能力。

### 源码直引会不会把公共包编译多次？

会有这个可能。不同应用各自构建时都会转换源码，所以它优化的是本地开发链路，不一定优化 CI 总成本。这需要依靠任务缓存、受影响构建和合理的包边界控制。对外发布或构建昂贵的包仍然可以使用产物依赖。

### 子应用加载失败时用户看到什么？

主应用应有超时和错误边界，展示明确的重试或降级页面，而不是空白容器。错误事件要带子应用名和版本。关键业务还可以保留旧版本入口；非关键模块可以临时关闭，不让一个子应用拖垮整个壳应用。
