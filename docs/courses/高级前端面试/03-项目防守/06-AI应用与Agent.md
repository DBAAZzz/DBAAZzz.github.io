# 项目防守：AI 应用与 Agent

## Q1：Partial JSON 增量解析解决什么问题？

### 这题在考什么

是否理解流式返回的任意数据块都可能停在字符串、数组或对象中间，所以解析不能反复直接 `JSON.parse`，而要维护增量状态、只更新已安全识别的字段；同时看你对“解析失败不能执行工具或写入正式数据”这条底线是否清楚。

### 面试时可以这样说

> 先说问题在哪：模型用流的方式返回结构化结果时，任何一个数据块都可能停在字符串、数组或者对象的中间。这时候直接 `JSON.parse`，会不断失败；要是等完整结果回来再解析，用户又看不到增量内容。我们的方案分两步：用 `[真实库或算法]` 维护增量解析状态，只把已经安全识别的字段更新到 UI；流结束之后，再用 Zod 做一次完整校验。最后是一条底线：解析失败时，不会执行工具，也不会写入正式数据。

### 对方很可能继续问

- 一个对象什么时候算完整？
- 模型修改前面字段怎么办？
- 断线后的半成品保留还是丢弃？

### 一句话记住

流式阶段只更新已安全识别的字段，流结束后再做完整校验，解析失败不执行工具、不写正式数据。

## Q2：Zod 在这里做什么？

### 这题在考什么

是否理解 TypeScript 类型只在编译期存在，不能证明模型运行时输出可信；以及 schema 校验之外，高风险字段还需要服务端权限和范围校验。

### 面试时可以这样说

> 我先点破一个误区：TypeScript 类型只在编译期存在，它不能证明模型运行时输出可信。Zod 做的是运行时验证：检查字段类型、必填项和业务约束，并且能产出明确错误。然后分两个阶段讲：流式阶段，数据可以当 partial 状态展示；完整结果出来之后，必须通过完整 schema 才能进入后续业务。最后补一句边界：高风险字段还要做服务端权限和范围校验，不能只依赖 schema。

### 一句话记住

运行时可信靠 Zod 校验；高风险字段还要服务端权限和范围校验。

## Q3：Vercel AI SDK 帮你做了什么？

### 这题在考什么

是否说得出实际使用的包、版本和 API，以及流式链路里哪部分是 SDK 提供、哪部分是自己实现，而不是只答一句“封装了流式输出”。

### 别只说概念

必须说出实际使用的包、版本和 API，不要只回答“封装了流式输出”。至少准备这四点：

- 使用的是文本流、对象流还是工具调用；
- 服务端流如何转换为前端可消费的数据；
- 中止、超时和错误如何传递；
- 哪部分是 SDK 提供，哪部分是你自己实现。

### 面试时可以这样说

> 我们使用 `[真实 API]` 管理 `[文本/对象/工具]` 的流式响应，它负责 `[真实能力]`。业务层这边，我们额外实现了 `[增量解析/状态合并/鉴权/审计]`。至于为什么没有完全依赖 SDK，原因是 `[真实边界]`。

### 一句话记住

说清用哪个 API 做了什么，再说清哪部分是自己实现的。

## Q4：模型输出为什么不稳定？

### 这题在考什么

是否理解模型按概率生成 token，输出不稳定是常态，系统要靠结构化输出、schema 校验、有限重试和确定性兜底来应对，而不是把“提示模型输出 JSON”当可靠协议。

### 面试时可以这样说

> 根因一句话：模型按概率生成 token，所以即使提示相同，输出也可能在字段顺序、缺失项、格式和内容上变化；流式、模型版本和上下文变化，还会进一步放大差异。结论就是：系统不能把“提示模型必须输出 JSON”当可靠协议。实际应对靠四件事：结构化输出能力、schema 校验、有限重试、确定性兜底，再把失败样本加入回归集。

### 一句话记住

不把“提示模型输出 JSON”当协议，靠结构化输出、校验、重试和兜底。

## Q5：思维过程与结构化结果如何处理？

### 这题在考什么

是否区分“产品需要的可验证最终结果和必要解释”与“模型的私有推理过程”，并知道最终动作只依据结构化字段、工具结果和业务校验。

### 面试时可以这样说

> 我先给一个判断：产品真正需要的是可验证的最终结果和必要解释，不依赖、也不展示模型的私有推理过程。然后是适配问题：不同模型提供的推理摘要、额外通道和结构化输出能力都不一样，所以我们通过适配层，把用户可见的解释和最终 schema 分开。最后强调一句：即使拿到推理相关内容，也不能把它当事实依据；最终动作，仍然要根据结构化字段、工具结果和业务校验执行。

### 一句话记住

解释可以给用户看，动作只认结构化字段、工具结果和业务校验。

## Q6：Agent 工具调用如何保证安全？

### 这题在考什么

是否理解模型只能提出调用建议、权限必须由服务端按当前用户重新判断，读写要分级，返回内容也要当不可信输入处理。

### 面试时可以这样说

> 我分四层说。第一层，每个工具使用严格 schema，并且在服务端根据当前用户重新鉴权；模型只能提出调用建议，不能绕过权限。第二层，读操作和写操作分级，高风险写入必须要求用户确认。第三层，请求带幂等键、超时和审计 ID。第四层，返回内容也视为不可信输入，防止外部数据通过提示注入改变系统规则。

### 一句话记住

模型只提建议，权限由服务端按当前用户重新判断，返回内容也不可信。

## Q7：这个 AI 项目如何衡量效果？

### 这题在考什么

是否用任务集和量化指标衡量效果，而不是凭“感觉不错”；以及有没有把线上失败样本脱敏后回收进评估集的机制。

### 面试时可以这样说

> 我们不看“回答感觉不错”这种评价。做法是建立 `[真实样本数]` 条任务集，关注五个指标：任务完成率、结构化输出通过率、工具参数正确率、P95 延迟，还有单任务成本。线上发现的失败样本，脱敏之后回收到评估集。要说不足也直接说：当前最大的不足是 `[真实不足]`，下一步会补 `[具体动作]`。

### 一句话记住

用任务集和指标说话，失败样本脱敏后回收到评估集。

## Q8：为什么这个项目需要 Agent，而不是固定工作流？

### 这题在考什么

是否讲得清项目里真正不确定的环节是什么、为什么用户输入不能提前穷举，同时知道权限校验、数据写入和流程边界要由代码控制。

### 面试时可以这样说

> 我先说真正不确定的部分：这个项目里，`[真实的不确定环节]`，用户输入没办法提前穷举，所以需要模型根据 `[真实上下文]` 来选择 `[工具或下一步]`。同时要说清边界：权限校验、数据写入和流程边界，仍然由代码控制。反过来我也准备了一个判断标准：如果实际流程每次都是固定的三步，我不会硬说它是 Agent，而会叫它带模型能力的工作流。

这个问题经常用来判断候选人是不是追概念。你既要准备一个“为什么需要”的理由，也要准备一个“哪些地方坚决不用模型”的边界。

### 一句话记住

说得清哪里不确定才需要 Agent，也说得清哪里坚决不用模型。

## Q9：任务执行到一半断了，怎么恢复？

### 这题在考什么

是否把任务拆成可独立完成、可保存结果的步骤，恢复链路是否覆盖幂等键、权限核对和人工兜底，而不是整条任务盲目重跑。

### 面试时可以这样说

> 我们的做法是：把任务状态拆成 `[真实状态]`，每个可以独立完成的步骤，都保存结果和执行状态。断线恢复的时候，先从服务端读取 checkpoint，核对权限和外部数据，再从未完成的节点继续。已经成功的写操作，靠幂等键避免重复执行；没法自动恢复的步骤，标记为需要人工处理，而不是把整条任务盲目重跑。

如果项目目前没有 checkpoint，不要编造。可以诚实地说当前只支持失败后整体重试，再补充它会导致什么问题，以及你准备如何改造。

### 一句话记住

拆步骤、存 checkpoint；恢复靠幂等键和人工兜底，不盲目重跑。

## Q10：项目里的记忆是怎么设计的？

### 这题在考什么

是否区分当前任务状态、短期对话和长期用户记忆，以及长期记忆的写入条件、过期和用户隔离有没有想清楚。

### 面试时可以这样说

> 我先把记忆分三类：当前任务状态、短期对话、长期用户记忆。当前任务的关键字段用结构化状态保存，不能只靠聊天记录；较早的对话，可以摘要或者按需检索。长期记忆只保存确实跨任务有价值、来源清楚的内容，并且要考虑过期、修改、删除和用户隔离。最后一条硬约束：模型不能自行把所有对话永久写入记忆。

准备时把自己的真实情况填进去：保存在哪里、写入条件是什么、检索 key 是什么、怎么处理旧信息。如果项目只保留当前会话，也可以明确说没有长期记忆。

### 一句话记住

任务状态结构化保存，长期记忆只存确实跨任务有价值、来源清楚的内容。

## Q11：RAG 如何保证答案有来源且不会越权？

### 这题在考什么

是否理解权限过滤必须发生在检索与服务端数据层，答案要带回可点击引用，而不是先检索敏感内容、再靠 Prompt 要求模型保密。

### 面试时可以这样说

> 链路是这样设计的：文档入库时，保存来源、版本和权限元数据；查询时，先按当前用户做权限过滤，再做召回和重排。传给模型的片段带文档 ID，最终答案返回可点击引用。这里有一条底线：权限必须在检索与服务端数据层生效，不能先检索出敏感内容，再通过 Prompt 要求模型保密。

追问通常会落到一个真实失败案例。准备说明你遇到过的是切块、召回、重排还是生成问题，以及如何把它单独验证出来。

### 一句话记住

权限在检索和数据层生效，答案带回来源，不靠 Prompt 保密。

## Q12：为什么要用多 Agent？单 Agent 不行吗？

### 这题在考什么

是否只在角色、工具权限或并行任务确实能拆开时才用多 Agent，以及没有拆分理由时，能不能说清单 Agent 加确定性校验更便宜、更好调试。

### 面试时可以这样说

> 我的判断标准是：只有当 `[角色、工具权限或并行任务]` 确实可以拆开时，我才会使用多 Agent。每个 Agent 有明确输入输出，由 `[真实组件]` 持有最终状态和仲裁结果，同时限制总步骤和总成本。反过来，如果只是让多个模型讨论同一个问题，我会优先用单 Agent 加确定性校验，因为更容易调试，也更便宜。

如果你的项目没有多 Agent，直接回答“当前没有使用”并解释原因，通常比强行包装更专业。

### 一句话记住

角色、权限或并行任务真能拆开才用多 Agent，否则单 Agent 加确定性校验。

## Q13：你如何定位一次 Agent 失败？

### 这题在考什么

是否有沿 trace 逐层定位失败的排查方法，而不是只看最终回答；每一步是否有 task ID、版本、耗时、token 和错误分类这些记录。

### 面试时可以这样说

> 我不会只看最终回答，而是沿着 trace 一步一步看：检索有没有拿到正确证据，模型有没有选对工具，参数有没有通过 schema，工具有没有执行成功，结果有没有正确写回状态。每一步都要记录 task ID、模型和 Prompt 版本、耗时、token、工具状态和错误分类。先定位失败层级，再决定改检索、Prompt、工具契约还是业务逻辑。

准备一个真实失败样本，按“现象—证据—排除—根因—修复—回归验证”讲。没有实际指标就不要虚构成功率和成本数字。

### 一句话记住

沿 trace 定位失败层级，再决定改检索、Prompt、工具契约还是业务逻辑。

## Q14：并发、延迟和成本怎么控制？

### 这题在考什么

是否先通过 trace 找到主要耗时和 token 消耗再决定优化，缓存 key 是否包含权限、数据版本和模型配置，任务是否有总时间、步骤和费用上限。

### 面试时可以这样说

> 第一步不是直接上手段，而是先通过 trace 找到主要耗时和 token 消耗，再决定优化哪里。`[真实项目]` 使用了 `[并行工具调用/模型分级/上下文压缩/缓存/步骤预算]`。缓存 key 要包含 `[权限、数据版本和模型配置]`，避免不同用户串数据。每个任务还要有总时间、最大步骤和费用上限，超过后就停止，并返回可理解的结果。

回答缓存时要特别小心：实时数据、个性化结果和带权限的检索，不能只按问题文本复用。

### 一句话记住

先看 trace 找大头；缓存 key 带权限和版本；任务设时间、步骤和费用上限。

## Q15：Agent 前端如何展示一个长任务？

### 这题在考什么

是否把长任务设计成多状态、带 task ID 和序号的事件流与可恢复快照，而不是一条不断变长的消息加一个 loading；取消和错误呈现是否清楚。

### 面试时可以这样说

> 前端不应该只有一条不断变长的消息和一个 loading。任务至少有这些状态：等待模型、调用工具、等待确认、重试、完成、失败和取消。流式事件带 task ID、step ID 和序号，前端按状态合并；断线之后，从服务端任务快照恢复。用户还可以取消未完成的步骤，并且能清楚看到哪些外部动作已经成功、哪些还没有执行。

这里很适合体现前端优势。准备好讲状态结构、流式协议、乱序去重、取消机制和错误呈现，而不只是说“用了 SSE”。

### 一句话记住

状态机加带 ID 的事件加快照恢复，用户能取消，也能看到哪些动作已执行。

## 这些追问要提前准备参考答案

### 流中字段已经显示，后面模型又改了怎么办？

UI 要把流式对象当暂存状态，而不是已提交数据。解析器产出新快照后，可以覆盖未确认字段；真正触发业务动作，要等完整流结束并通过 schema。对于用户已经基于旧字段操作的场景，需要冻结已交互部分，或明确显示“生成中”。

### schema 校验失败要不要自动重试？

可以有限重试，但先区分是临时格式问题，还是提示、模型能力根本不匹配。重试要带原错误反馈，并有次数和成本上限。高风险任务校验失败时，宁可返回可理解错误，也不能猜一个默认值继续执行。

### 如何证明 AI 功能比固定规则更好？

先建立基线。若固定规则已经能稳定完成任务，Agent 可能只是增加延迟和成本。用同一任务集比较完成率、人工修正次数、耗时和费用；只有模型确实处理了规则难覆盖的输入，才有引入价值。

### 外部文档里的提示注入怎么处理？

检索内容只作为数据，不获得系统指令优先级。工具权限由服务端按用户和业务规则判断，文档不能让模型自行扩大权限。高风险动作要求确认，并记录模型看到的证据和最终工具参数，便于审计。

## 面试前一定确认真实实现

把当前使用的模型、SDK 版本、具体 API、增量解析库、schema 和一个失败样本写下来。如果这些信息说不清，面试官会认为“Partial JSON、Zod、Agent”只是简历关键词。

## 自测

1. 画出一条流式数据从模型到 UI 的状态变化。
2. 明确你使用的真实 SDK API。
3. 给出三种结构化输出失败案例。
4. 解释工具 schema 通过后为什么仍需鉴权。
5. 解释为什么项目需要 Agent，而不是固定流程。
6. 画出任务状态、checkpoint 和恢复路径。
7. 准备一次检索、决策或工具调用失败的真实排查过程。
8. 说明前端如何展示、取消和恢复一个长任务。
