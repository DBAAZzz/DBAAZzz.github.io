# 项目防守：AI 应用与 Agent

本章只讲项目口径：你的项目怎么衡量效果、怎么定位一次失败、为什么需要 Agent。RAG 链路、多 Agent 机制、记忆架构这些原理题的完整展开，见 [AI应用工程](../02-高级工程化/07-AI应用工程.md) 和 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

## Q1：Partial JSON 增量解析解决什么问题？

### 这题在考什么

是否理解流式返回的任意数据块都可能停在结构中间，所以解析不能反复直接 `JSON.parse`；关键判断点是**“解析失败不能执行工具或写入正式数据”**这条底线。

### 面试时可以这样说

> 先说问题在哪：模型用流的方式返回结构化结果时，任何一个数据块都可能停在字符串、数组或者对象的中间。这时候直接 `JSON.parse`，会不断失败；要是等完整结果回来再解析，用户又看不到增量内容。我们的方案分两步：用 `[真实库或算法]` 维护增量解析状态，只把已经安全识别的字段更新到 UI；流结束之后，再用 Zod 做一次完整校验。最后是一条底线：解析失败时，不会执行工具，也不会写入正式数据。

增量解析的通用做法和伪代码展开在 [AI应用工程](../02-高级工程化/07-AI应用工程.md)，这里讲清你们用的库和兜底边界就够。

### 对方很可能继续问

**一个对象什么时候算完整？**

权威信号只有两个：流正常结束，或者模型的结束原因表明输出终止。中间用容错解析“猜”出来的完整只能用于预览渲染，业务执行永远等权威信号加完整校验。

**模型修改前面字段怎么办？**

UI 要把流式对象当暂存状态，而不是已提交数据：解析器产出新快照就覆盖未确认字段；真正触发业务动作必须等流结束并通过 schema。用户已经基于旧字段操作的部分，要冻结或明确标“生成中”。

**断线后的半成品保留还是丢弃？**

UI 层可以保留已渲染的预览并明确标注“内容不完整”；业务层不认半截结果——可重试的走重试或续传，涉及写操作的宁可整体作废。机制展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)。

### 一句话记住

流式阶段只更新已安全识别的字段，流结束后再做完整校验，解析失败不执行工具、不写正式数据。

## Q2：Zod 在这里做什么？

### 这题在考什么

是否理解 **TypeScript 类型只在编译期存在**，不能证明模型运行时输出可信；以及 schema 校验之外，**高风险字段还需要服务端权限和范围校验**。

### 面试时可以这样说

> 我先点破一个误区：TypeScript 类型只在编译期存在，它不能证明模型运行时输出可信。Zod 做的是运行时验证：检查字段类型、必填项和业务约束，并且能产出明确错误。然后分两个阶段讲：流式阶段，数据可以当 partial 状态展示；完整结果出来之后，必须通过完整 schema 才能进入后续业务。最后补一句边界：高风险字段还要做服务端权限和范围校验，不能只依赖 schema。

### 对方很可能继续问

**schema 校验通过就安全了吗？**

不。schema 只证明形状合法，不证明业务合法：不存在的用户 ID、越权操作、超范围的金额都能通过校验。所以高风险字段要再过服务端权限和业务规则，两层各管各的。

**校验失败要不要自动重试？**

可以有限重试，但要带原错误反馈，并设次数和成本上限；先区分是临时格式问题，还是提示与模型能力根本不匹配。高风险任务校验失败时，宁可返回可理解错误，也不能猜一个默认值继续执行。

**Zod 和 TypeScript 什么关系？**

一句话：同一份 schema 两处生效——编译期给 TypeScript 推导类型，运行时用 parse 校验数据形状。展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)。

### 一句话记住

运行时可信靠 Zod 校验；高风险字段还要服务端权限和范围校验。

## Q3：Vercel AI SDK 帮你做了什么？

### 这题在考什么

是否说得出**实际使用的包、版本和 API**，以及流式链路里哪部分是 SDK 提供、哪部分是自己实现，而不是只答一句“封装了流式输出”。

### 别只说概念

必须说出实际使用的包、版本和 API，不要只回答“封装了流式输出”。至少准备这四点：

- 使用的是文本流、对象流还是工具调用；
- 服务端流如何转换为前端可消费的数据；
- 中止、超时和错误如何传递；
- 哪部分是 SDK 提供，哪部分是你自己实现。

### 面试时可以这样说

> 我们使用 `[真实 API]` 管理 `[文本/对象/工具]` 的流式响应，它负责 `[真实能力]`。业务层这边，我们额外实现了 `[增量解析/状态合并/鉴权/审计]`。至于为什么没有完全依赖 SDK，原因是 `[真实边界]`。

### 对方很可能继续问

**SDK 版本升级怎么评估？**

锁定版本，升级前跑评估集回归——SDK 的流式协议和工具调用 API 都出过破坏性变更。升级要当一次依赖变更对待，不是顺手 update。

**哪部分坚持自己实现，为什么？**

按项目实际答：增量状态合并、鉴权、审计这些和业务强耦合的部分自己实现；纯管道能力交给 SDK。说清边界，比「全用 SDK」或「全手写」都更可信。

### 一句话记住

说清用哪个 API 做了什么，再说清哪部分是自己实现的。

## Q4：模型输出为什么不稳定？

### 这题在考什么

是否理解输出不稳定是模型机制决定的**常态**，系统要靠**结构化输出、schema 校验、有限重试和确定性兜底**应对，而不是把“提示模型输出 JSON”当可靠协议。

### 面试时可以这样说

> 根因一句话：模型按概率生成 token，所以即使提示相同，输出也可能在字段顺序、缺失项、格式和内容上变化，这是机制决定的常态，不是提示词写得不够好（机制展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)）。结论就是：系统不能把“提示模型必须输出 JSON”当可靠协议。我们项目的应对靠四件事：结构化输出能力、schema 校验、有限重试、确定性兜底，再把失败样本加入回归集。

### 对方很可能继续问

**提示词里写“必须输出 JSON”能解决吗？**

只能减少格式错误，不能当可靠协议：模型版本、上下文长度、流式设置都可能让约束失效。约束要落在 schema 校验和兜底代码里，不落在希望里。

**重试和兜底怎么分工？**

格式类失败走有限重试，带上错误反馈；能力类失败——反复生成不合法数据——不重试，直接走确定性兜底或转人工。重试用光就降级，不让用户等一个永远出不来的结果。

### 一句话记住

不把“提示模型输出 JSON”当协议，靠结构化输出、校验、重试和兜底。

## Q5：思维过程与结构化结果如何处理？

### 这题在考什么

是否区分**“产品需要的可验证最终结果和必要解释”**与**“模型的私有推理过程”**，并知道最终动作只依据结构化字段、工具结果和业务校验。

### 面试时可以这样说

> 我先给一个判断：产品真正需要的是可验证的最终结果和必要解释，不依赖、也不展示模型的私有推理过程。然后是适配问题：不同模型提供的推理摘要、额外通道和结构化输出能力都不一样，所以我们通过适配层，把用户可见的解释和最终 schema 分开。最后强调一句：即使拿到推理相关内容，也不能把它当事实依据；最终动作，仍然要根据结构化字段、工具结果和业务校验执行。

### 对方很可能继续问

**推理内容能存下来用于调试吗？**

能，但要和展示分开：调试 trace 里保留模型返回的推理摘要，产品界面只给可验证结果和解释；保存按日志标准脱敏。存和展示是两条线，混在一起就有泄露和误导风险。

**不同模型的推理能力不一样，怎么适配？**

适配层隔离：把「用户可见解释」和「最终结构化结果」拆成两个通道，换模型只动适配层，业务代码只认结构化字段。没有这层，换模型就是全链路改造。

### 一句话记住

解释可以给用户看，动作只认结构化字段、工具结果和业务校验。

## Q6：Agent 工具调用如何保证安全？

### 这题在考什么

是否理解**模型只能提出调用建议、权限必须由服务端按当前用户重新判断**，读写要分级，返回内容也要当不可信输入处理。

### 面试时可以这样说

> 我分四层说。第一层，每个工具使用严格 schema，并且在服务端根据当前用户重新鉴权；模型只能提出调用建议，不能绕过权限。第二层，读操作和写操作分级，高风险写入必须要求用户确认。第三层，请求带幂等键、超时和审计 ID。第四层，返回内容也视为不可信输入，防止外部数据通过提示注入改变系统规则。

完整的安全防线清单（提示注入、防重、隐私最小化）展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)。

### 对方很可能继续问

**schema 通过后为什么还要鉴权？**

schema 只校验参数形状，“这个用户能不能做这件事”是业务判断。模型可能被注入诱导，也可能生成合法但越权的调用，所以权限必须由服务端按当前用户重新判断一次。

**怎么防止同一个写操作被执行两次？**

写操作带幂等键，服务端保存“键 → 结果”的映射，重放直接返回上次结果；高风险动作再加用户确认和审计。模型重试、用户刷新都会造成重复发起，防重必须做在服务端。

**外部文档里的提示注入怎么处理？**

检索内容只作为数据，不给系统指令优先级；工具权限由服务端按用户和业务规则判断，文档不能让模型自行扩大权限；高风险动作要求确认，并记录模型看到的证据和最终工具参数，便于审计。展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)。

### 一句话记住

模型只提建议，权限由服务端按当前用户重新判断，返回内容也不可信。

## Q7：这个 AI 项目如何衡量效果？

### 这题在考什么

是否用**任务集和量化指标**衡量效果，而不是凭“感觉不错”；以及有没有把**线上失败样本脱敏后回收进评估集**的机制。

### 面试时可以这样说

> 我们不看“回答感觉不错”这种评价。做法是建立 `[真实样本数]` 条任务集，关注五个指标：任务完成率、结构化输出通过率、工具参数正确率、P95 延迟，还有单任务成本。线上发现的失败样本，脱敏之后回收到评估集。要说不足也直接说：当前最大的不足是 `[真实不足]`，下一步会补 `[具体动作]`。

### 对方很可能继续问

**评估集样本从哪来？**

真实流量脱敏采样打底，线上失败样本脱敏后优先回收，边界和对抗样本定向构造；评估集跟代码一样有版本，模型、提示、检索任何一项变更都要跑回归。建设方法展开见 [AI应用工程](../02-高级工程化/07-AI应用工程.md)。

**这些指标里你最看重哪个？**

给出你的排序和理由：先看任务完成率——任务没完成，其他指标没有意义；成本和延迟是约束条件，完成率达标之后才是优化项。有排序比报一堆指标更显判断。

**人工修正怎么统计？**

界面上提供“采纳 / 修改后采纳 / 拒绝”动作并埋点；“修改后采纳”占比上升，通常说明输出质量在退化，这个信号比点踩更早。

### 一句话记住

用任务集和指标说话，失败样本脱敏后回收到评估集。

## Q8：为什么这个项目需要 Agent，而不是固定工作流？

### 这题在考什么

是否讲得清项目里**真正不确定的环节**是什么、为什么**用户输入不能提前穷举**，同时知道**权限校验、数据写入和流程边界要由代码控制**。

### 面试时可以这样说

> 我先说真正不确定的部分：这个项目里，`[真实的不确定环节]`，用户输入没办法提前穷举，所以需要模型根据 `[真实上下文]` 来选择 `[工具或下一步]`。同时要说清边界：权限校验、数据写入和流程边界，仍然由代码控制。反过来我也准备了一个判断标准：如果实际流程每次都是固定的三步，我不会硬说它是 Agent，而会叫它带模型能力的工作流。

这个问题经常用来判断候选人是不是追概念。你既要准备一个“为什么需要”的理由，也要准备一个“哪些地方坚决不用模型”的边界。ReAct 与工作流的选型原理见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

### 对方很可能继续问

**怎么证明 Agent 比固定规则好？**

先建固定规则基线，用同一任务集比较完成率、人工修正次数、耗时和费用；只有模型确实处理了规则难覆盖的输入，才有引入价值。固定规则已经稳定完成的任务，Agent 只是增加延迟和成本。

**举一个“规则走不通、模型走通了”的真实例子。**

准备一个具体案例：某次用户输入让固定分支失效，模型选对工具后走通了流程，把时间、输入、选择和结果讲具体。举不出例子，前面说的“不确定”就站不住。

### 一句话记住

说得清哪里不确定才需要 Agent，也说得清哪里坚决不用模型。

## Q9：任务执行到一半断了，怎么恢复？

### 这题在考什么

是否把任务拆成**可独立完成、可保存结果的步骤**，恢复链路是否覆盖**幂等键、权限核对和人工兜底**，而不是整条任务盲目重跑。

### 面试时可以这样说

> 我们的做法是：把任务状态拆成 `[真实状态]`，每个可以独立完成的步骤，都保存结果和执行状态。断线恢复的时候，先从服务端读取 checkpoint，核对权限和外部数据，再从未完成的节点继续。已经成功的写操作，靠幂等键避免重复执行；没法自动恢复的步骤，标记为需要人工处理，而不是把整条任务盲目重跑。

checkpoint、幂等键和恢复校验的完整机制见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。如果项目目前没有 checkpoint，不要编造。可以诚实地说当前只支持失败后整体重试，再补充它会导致什么问题，以及你准备如何改造。

### 对方很可能继续问

**checkpoint 具体存什么？**

任务 ID、当前节点、已完成步骤的结果、待确认动作和版本信息；不要简单序列化全部内存对象。存什么，取决于恢复时需要重建什么。

**恢复时发现外部数据变了怎么办？**

恢复前核对权限、工具版本和外部数据指纹，变了就重新执行受影响节点，或者把差异交给用户重新确认，不能拿着旧上下文硬续跑。

**幂等键怎么设计？**

用业务语义的键，比如任务 ID 加步骤加操作对象，保证重试和恢复时生成同一个键。机制展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

### 一句话记住

拆步骤、存 checkpoint；恢复靠幂等键和人工兜底，不盲目重跑。

## Q10：项目里的记忆是怎么设计的？

### 这题在考什么

是否区分**当前任务状态、短期对话和长期用户记忆**，以及长期记忆的**写入条件、过期和用户隔离**有没有想清楚。

### 面试时可以这样说

> 我先把记忆分三类：当前任务状态、短期对话、长期用户记忆。当前任务的关键字段用结构化状态保存，不能只靠聊天记录；较早的对话，可以摘要或者按需检索。长期记忆只保存确实跨任务有价值、来源清楚的内容，并且要考虑过期、修改、删除和用户隔离。最后一条硬约束：模型不能自行把所有对话永久写入记忆。

记忆的写入门槛、检索和失效机制展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。准备时把自己的真实情况填进去：保存在哪里、写入条件是什么、检索 key 是什么、怎么处理旧信息。如果项目只保留当前会话，也可以明确说没有长期记忆。

### 对方很可能继续问

**长期记忆和 RAG 有什么区别？**

常常共用一套向量库，但语义不同：RAG 面向相对静态的知识库，记忆面向“这个用户、这段历史”，写入门控更严、失效更频繁、隐私更敏感。展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

**多用户的记忆怎么隔离？**

条目从写入起就带用户维度，检索层在查询时前置过滤，不靠提示词约束。隔离做在检索层还是指望模型自觉，是及格和不及格的分界。

**你们项目现在做到哪一档？**

如实回答：只有当前会话就说没有长期记忆，并说清为什么暂不做——场景不需要跨任务记忆，或隐私评估还没过。诚实分层比硬凑三类更可信。

### 一句话记住

任务状态结构化保存，长期记忆只存确实跨任务有价值、来源清楚的内容。

## Q11：RAG 如何保证答案有来源且不会越权？

### 这题在考什么

是否理解**权限过滤必须发生在检索与服务端数据层**，答案要带回**可点击引用**，而不是先检索敏感内容、再靠 Prompt 要求模型保密。

### 面试时可以这样说

> 链路是这样设计的：文档入库时，保存来源、版本和权限元数据；查询时，先按当前用户做权限过滤，再做召回和重排。传给模型的片段带文档 ID，最终答案返回可点击引用。这里有一条底线：权限必须在检索与服务端数据层生效，不能先检索出敏感内容，再通过 Prompt 要求模型保密。

RAG 完整链路——切块、召回、重排、评估——见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。追问通常会落到一个真实失败案例。准备说明你遇到过的是切块、召回、重排还是生成问题，以及如何把它单独验证出来。

### 对方很可能继续问

**回答错了，怎么判断是检索问题还是生成问题？**

把正确证据直接交给模型再问一次：能答对，就回头查切块、召回和重排；仍然答错，才是提示或模型的问题。检索和生成分开评估，比反复改 Prompt 有效。

**切块怎么切？**

按文档结构切，保留标题路径和父级信息，用真实问题集测召回效果，不固定相信某个字符数。细节见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

### 一句话记住

权限在检索和数据层生效，答案带回来源，不靠 Prompt 保密。

## Q12：为什么要用多 Agent？单 Agent 不行吗？

### 这题在考什么

是否只在**角色、工具权限或并行任务确实能拆开**时才用多 Agent，以及没有拆分理由时，能不能说清**单 Agent 加确定性校验**更便宜、更好调试。

### 面试时可以这样说

> 我的判断标准是：只有当 `[角色、工具权限或并行任务]` 确实可以拆开时，我才会使用多 Agent。每个 Agent 有明确输入输出，由 `[真实组件]` 持有最终状态和仲裁结果，同时限制总步骤和总成本。反过来，如果只是让多个模型讨论同一个问题，我会优先用单 Agent 加确定性校验，因为更容易调试，也更便宜。

多 Agent 的拓扑、状态所有权和常见故障见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。如果你的项目没有多 Agent，直接回答“当前没有使用”并解释原因，通常比强行包装更专业。

### 对方很可能继续问

**多 Agent 常见的故障是什么？**

互相转交形成死循环、重复调用同一个写工具、并行结果冲突没有仲裁、共享上下文越来越长。解法是限制步数、写操作幂等、设单一状态所有者。展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

**你们项目为什么用（或没用）多 Agent？**

按真实情况答：没用，就说当前任务单 Agent 上下文装得下、也没有权限隔离需求，强行拆是架构表演；用了，就说清角色拆分依据和最终状态归谁。两种答法都比含糊其辞强。

### 一句话记住

角色、权限或并行任务真能拆开才用多 Agent，否则单 Agent 加确定性校验。

## Q13：你如何定位一次 Agent 失败？

### 这题在考什么

是否有**沿 trace 逐层定位失败**的排查方法，而不是只看最终回答；每一步是否有 **task ID、版本、耗时、token 和错误分类**这些记录。

### 面试时可以这样说

> 我不会只看最终回答，而是沿着 trace 一步一步看：检索有没有拿到正确证据，模型有没有选对工具，参数有没有通过 schema，工具有没有执行成功，结果有没有正确写回状态。每一步都要记录 task ID、模型和 Prompt 版本、耗时、token、工具状态和错误分类。先定位失败层级，再决定改检索、Prompt、工具契约还是业务逻辑。

trace 该记什么、循环检测这些可观测性设计见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。准备一个真实失败样本，按“现象—证据—排除—根因—修复—回归验证”讲。没有实际指标就不要虚构成功率和成本数字。

### 对方很可能继续问

**怎么发现 Agent 陷入循环？**

给每次工具调用算一个“工具名 + 参数摘要”的指纹，同一指纹连续出现超过阈值就强制终止，终止原因记“循环”；单任务步骤数的 P95 突涨是更早的预警信号。

**trace 记这么细，成本会不会太高？**

参数存摘要、超大结果只存引用，敏感字段脱敏，开销可控。trace 是排障和成本归因的基础，砍掉它省下的钱，远小于一次线上事故的排查成本。

### 一句话记住

沿 trace 定位失败层级，再决定改检索、Prompt、工具契约还是业务逻辑。

## Q14：并发、延迟和成本怎么控制？

### 这题在考什么

是否**先通过 trace 找到主要耗时和 token 消耗再决定优化**，缓存 key 是否包含**权限、数据版本和模型配置**，任务是否有**总时间、步骤和费用上限**。

### 面试时可以这样说

> 第一步不是直接上手段，而是先通过 trace 找到主要耗时和 token 消耗，再决定优化哪里。`[真实项目]` 使用了 `[并行工具调用/模型分级/上下文压缩/缓存/步骤预算]`。缓存 key 要包含 `[权限、数据版本和模型配置]`，避免不同用户串数据。每个任务还要有总时间、最大步骤和费用上限，超过后就停止，并返回可理解的结果。

优化手段的优先级和 Prompt 缓存这些展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。回答缓存时要特别小心：实时数据、个性化结果和带权限的检索，不能只按问题文本复用。

### 对方很可能继续问

**流式输出算性能优化吗？**

不算。它降的是首字时间和用户的感知等待，不降总耗时。汇报数据要分开说：首字时间降了多少、总耗时降没降，混在一起说会被追问穿。

**为什么换小模型放在最后考虑？**

它影响质量，必须拿评估集验证；而砍无信息增量的调用、并行化、缓存是纯收益。上来就换小模型，钱省了、质量降了，还没有数据支撑。

### 一句话记住

先看 trace 找大头；缓存 key 带权限和版本；任务设时间、步骤和费用上限。

## Q15：Agent 前端如何展示一个长任务？

### 这题在考什么

是否把长任务设计成**多状态、带 task ID 和序号的事件流与可恢复快照**，而不是一条不断变长的消息加一个 loading；**取消和错误呈现**是否清楚。

### 面试时可以这样说

> 前端不应该只有一条不断变长的消息和一个 loading。任务至少有这些状态：等待模型、调用工具、等待确认、重试、完成、失败和取消。流式事件带 task ID、step ID 和序号，前端按状态合并；断线之后，从服务端任务快照恢复。用户还可以取消未完成的步骤，并且能清楚看到哪些外部动作已经成功、哪些还没有执行。

统一事件协议、序号和快照恢复的细节见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。这里很适合体现前端优势。准备好讲状态结构、流式协议、乱序去重、取消机制和错误呈现，而不只是说“用了 SSE”。

### 对方很可能继续问

**事件为什么要带序号？**

流式连接会重连、重复推送、乱序到达，序号用于去重和发现缺口；发现缺口就触发快照拉取——前端状态永远以服务端为准，不靠本地事件推算。

**用户中途关掉页面，回来怎么恢复？**

先拉任务快照：当前节点、已完成步骤、待确认动作，把前端状态机对齐到快照，再用序号续订增量事件。机制展开见 [Agent架构与工作流](../02-高级工程化/10-Agent架构与工作流.md)。

**工具执行的中间过程展示多少？**

展示“正在做什么”加一个参数摘要，原始入参和完整返回按需展开；中间态必须有明显的过程标记，避免被用户误读成最终结果。

### 一句话记住

状态机加带 ID 的事件加快照恢复，用户能取消，也能看到哪些动作已执行。

## 面试前一定确认真实实现

把当前使用的模型、SDK 版本、具体 API、增量解析库、schema 和一个失败样本写下来。如果这些信息说不清，面试官会认为“Partial JSON、Zod、Agent”只是简历关键词。

## 自测

1. 画出一条流式数据从模型到 UI 的状态变化。
2. 明确你使用的真实 SDK API。
3. 给出三种结构化输出失败案例。
4. 解释工具 schema 通过后为什么仍需鉴权。
5. 解释为什么项目需要 Agent，而不是固定流程。
6. 画出任务状态、checkpoint 和恢复路径。
7. 准备一次检索、决策或工具调用失败的真实排查过程。
8. 说明前端如何展示、取消和恢复一个长任务。
