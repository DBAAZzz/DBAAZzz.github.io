# 项目题回答方法

项目题不是让你复述需求。它要验证三件事：这件事是不是你做的、为什么这样做、结果是否可信。

## 先准备一张项目事实表

每个项目只写确定的事实：

| 项目事实 | 必须准备的内容 |
| --- | --- |
| 背景 | 谁遇到了什么问题，为什么必须解决 |
| 规模 | 用户量、应用数、包体积、请求量或团队规模 |
| 职责 | 你独立负责、主导还是参与了什么 |
| 方案 | 核心链路和两个关键技术决策 |
| 难点 | 最难定位或最难协调的问题 |
| 结果 | 前后对比数据，以及数据如何测得 |
| 复盘 | 哪个决定可以做得更好 |

无法确认的数据不要编。你可以直接说：“当时没有建立完整指标，这是我复盘后认为需要补上的地方”。

这句话不会减分。真正减分的是：先报一个漂亮数字，等面试官追问“怎么统计的”，再临时改口。

## 90 秒项目介绍

按下面的顺序讲：

```text
一句话背景
→ 我的职责
→ 最关键的两个动作
→ 可验证结果
→ 一个有价值的取舍
```

示例骨架：

> 这是一个服务多个业务团队的前端发布平台。我主要负责构建链路和前端监控。原来的问题是构建过程不可见、失败后定位慢。我先统一了任务状态模型，再通过 SSE 推送实时日志，并把版本、SourceMap 和错误事件关联起来。上线后，一次构建失败能直接定位到具体阶段。这里最大的取舍是：没有一开始就做完整的日志补偿，而是先保证状态最终一致。因为构建日志短暂缺失，对业务的影响低于系统复杂度的增加。

这段介绍不要完全照背。把“多个团队”“定位慢”这些词，换成你能解释的真实情况。比如：有多少应用、一次失败通常要找多久、你负责的是 SDK、服务端还是发布链路。

## 面试官如何验证真实性

### 追问 1：为什么选择这个方案？

不要只回答“因为性能好”。把候选方案、约束和决定讲出来：

> 当时比较过 A 和 B。我们的主要约束是……，A 的优势是……，但会带来……。最终选择 B，是因为它更符合当前规模。如果规模增长到……，我会重新评估。

### 追问 2：数据怎么来的？

你要说明口径、采集位置和比较周期：

> 包体积是按构建产物统计的，不是看源码大小。比较的是相同功能版本下，主包从 1.8MB 降到 1.3MB。这里还要拆开说明各项措施的贡献，不能把全部收益归到一个插件上。

### 追问 3：最难的问题是什么？

选一个存在不确定性的真实问题，把定位过程讲出来。不要把“时间紧、任务重”当技术难点。

### 追问 4：如果重做一次呢？

给出你的复盘，不要说“目前已经很好”。高级工程师应该知道当前方案欠了哪些债、下一阶段的边界在哪里。

## 一场项目追问通常怎么发展

面试官问：“这个项目最难的地方是什么？”

不要回答“技术难度大、时间也很紧”。你可以按下面的节奏回答：

> 最难的不是实现采集 API，而是保证错误版本和 Source Map 一一对应。我们一开始用发布时间做关联，遇到并行发布之后就会匹配错。后来改成由 CI 生成唯一 release，构建产物、Map 和 SDK 初始化都使用同一个值。上线前做了一个固定错误用例，确认能还原到原文件的行列。这里我负责的是 `[真实职责]`。

面试官继续问：“为什么没早点想到 release？”

可以回答：

> 第一版只服务一个应用，发布时间近似可用。应用和并发发布增加之后，原来的假设就失效了。这个问题让我意识到：版本标识应该在构建起点产生，而不是让下游根据时间去猜。

这种回答既说清了问题，也承认方案是逐步演进的。你不需要把自己包装成一开始就什么都想到了。

## 不知道答案时怎么接

如果对方追问的是你没有做过的部分，你可以说：

> 这部分当时不是我负责的，我知道它和当前链路的接口是……。如果让我接手，我会先确认……，不会直接假设现有实现。

或者：

> 当前项目没有做消息补偿，只做了自动重连。短暂缺日志当时可以接受，因为最终构建状态是从独立接口获取的。如果现在要求日志完整，我会加上消息序号，再做有限窗口的补发。

诚实说明边界，同时给出基于现状的判断。这比猜内部实现更可靠。

## 项目回答的五个危险信号

1. 所有功劳都是“我”，但说不清协作边界；
2. 数据非常漂亮，但没有测量口径；
3. 只会讲正常流程，不知道失败路径；
4. 只讲用了什么技术，不讲为什么需要它；
5. 把未上线的设计说成真实实现。

## 自测

- 能否在 90 秒内介绍项目？
- 每个结果数据能否解释采集口径？
- 能否画出核心链路？
- 能否说出两个失败场景？
- 能否说出一个没有实现的能力以及不做的原因？
