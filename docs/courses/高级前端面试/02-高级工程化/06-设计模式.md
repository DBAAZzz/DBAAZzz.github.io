# 设计模式在前端中的应用

设计模式题不要背 23 个定义。高级回答要能说清三件事：它解决了什么变化、代价是什么、什么时候不该用。

## Q1：策略模式什么时候有价值？

### 这题在考什么

是否理解策略模式解决的是"**多个可替换规则、分支持续增长**"这类变化，并且能**主动说出它不值得用的场合**，而不是只背定义。

### 面试时可以这样说

> 先看什么时候用它：一类业务里有多个可替换的规则，而且条件分支还在持续增长。这时候，把每个规则封装成统一的接口，由上下文按条件去选。比如表单校验、计费、还有不同渠道的转换，都是典型场景。好处是减少大段 if/else，规则可以独立测试。但别停在这，还要补一句：如果只有两个稳定分支，就别引入策略注册中心了，那只会增加跳转和抽象成本。

主动把"不该用的场景"说出来是这题的得分点，等对方追问出来就晚了。

### 对方很可能继续问

**什么时候保留 if/else 更好？**

分支很少、变化稳定、逻辑就地可读的时候，if/else 往往最清楚。为了两个简单分支去拆工厂、策略注册器和多个类，只会增加文件跳转。模式应该降低未来变化成本，而不是增加形式感。

**策略模式和"配置表 + 函数"有什么区别？**

很多所谓的策略模式，本质是一张 key 到函数的映射表。表驱动已经能消掉 if/else，策略模式更进一步：规则实现统一接口、可独立测试、可组合，有自己的生命周期——要增删、要组合、要按渠道开关。如果规则只是简单映射，表驱动就够了，别为了名字上模式。

**规则之间出现公共逻辑怎么办？**

抽成公共的组合函数或基类，让策略只写差异部分；复制粘贴会让规则之间逐渐漂移。横切能力比如日志、埋点，用装饰器叠加，别混进每个策略的实现里。

### 一句话记住

规则多且持续变化才上策略；分支少而稳定，留着 if/else 更划算。

## Q2：责任链和普通流水线有什么区别？

### 这题在考什么

是否理解责任链"**每个处理者可以决定不往下传**"与流水线"**每步都转换再传递**"的本质差别，并且能说出实现责任链时要**提前定好的约束**。

### 面试时可以这样说

> 责任链，是把请求依次交给一个个处理者，每个处理者自己决定：处理、拒绝，还是继续往下传。典型场景是权限校验、请求中间件、审批规则。流水线不一样，它强调的是每一步都做转换，然后把结果交给下一步。实现责任链的时候，要提前定义好三件事：短路、错误传播和顺序，同时避免处理器隐式修改共享状态。

拿请求中间件举例最自然：面试官多半天天在写，一听就懂。

### 对方很可能继续问

**Express/Koa 的中间件是责任链吗？**

是责任链思想的变体：请求依次经过每个中间件，每个中间件决定是否调用 `next` 往下传。Koa 的洋葱模型还允许下游返回后再执行收尾逻辑，等于在链上同时处理进和出。和经典责任链的差别主要在组织形式：中间件靠函数组合，经典责任链靠处理者显式持有下一个引用。

**链的顺序错了会怎样？**

顺序本身就是业务语义：便宜、能快速短路的校验放前面，昂贵的风控、库存放后面，否则每个请求都白付成本。所以顺序要当成契约固定下来——用显式数组或配置声明，再用测试锁住，而不是靠文件命名隐式约定。

**某一环抛错怎么处理？**

错误传播策略要提前定义：短路返回统一错误、跳过该环节继续走，还是包装后继续传。不定清楚，链上就会出现"谁先捕获谁负责"的模糊地带，出问题时很难定位是哪一环引入的。

### 一句话记住

责任链看每个处理者是否放行，流水线看每一步是否都转换再传递。

## Q3：观察者模式和发布订阅有什么区别？

### 这题在考什么

是否理解两者的本质区别在"**有没有事件中心解耦**"，并且能把工程上真正要紧的**依赖关系、时序、退订**这几个问题说清楚。

### 面试时可以这样说

> 这两个模式都做一对多通知，这是它们的共同点。区别在结构：经典观察者模式里，Subject 直接维护 Observer，并且直接调用它们的更新接口；发布订阅通常走一个事件中心，按主题解耦发布方和订阅方，两边不直接知道彼此的存在。工程里这两个名字经常混用，所以重点不是纠结称呼，而是把真正要紧的几件事说清楚：依赖关系、同步还是异步、事件顺序、错误隔离、还有退订机制。

名词之争一句话带过就行，赶紧转到"工程上要管什么"，那才是面试官想听的。

### 对方很可能继续问

**事件总线为什么容易失控？**

因为事件名、payload、触发顺序和所有权都没有契约。任何模块都能发、都能收，最后就没人说得清数据到底从哪来。治理的时候，要集中定义事件类型、版本和负责人，订阅必须可释放，关键业务链路不要只靠隐式广播。

**如何避免组件卸载后仍然订阅？**

订阅和退订必须成对：订阅时拿到取消函数，在卸载钩子里释放。更省心的做法是封装一层，比如 `useEventBus` 这类 hook，把订阅自动绑定到组件生命周期，卸载时自动清理；总线再提供 `once` 和按命名空间的批量清理，兜住遗漏场景。

**事件应该有版本吗？**

跨团队、跨应用通信的事件应该有：payload 结构变更时新增版本，新老订阅方并行过渡，和 API 版本化一个道理。应用内部的小型总线，用 TypeScript 类型约束事件名和 payload 就够，不必上正式的版本机制。

### 一句话记住

差别就在中间有没有事件中心：直接互相知道是观察者，按主题解耦是发布订阅。

## Q4：代理模式和装饰器模式有什么区别？

### 这题在考什么

是否理解代理和装饰器**结构相似、区别在意图**，并且**不被 JavaScript 的 Proxy 误导**成同一概念。

### 面试时可以这样说

> 代理控制的是"对原对象的访问"，典型用途有缓存、权限、懒加载和远程调用。装饰器是在保持接口不变的前提下叠加能力，比如日志、重试、指标。两者结构上可能相似，区别在意图。再澄清一点：JavaScript 的 Proxy 只是实现代理的一种语言能力，不等于所有代理模式都必须使用 Proxy。

能各举一个框架里的真实例子最有说服力，别停在 UML 图。

### 对方很可能继续问

**前端哪里能找到这两个模式的实例？**

代理：Vue 3 的响应式用 Proxy 拦截对数据的访问和修改；图片懒加载用占位控制对真实资源的访问。装饰器：axios 拦截器、给请求函数叠加重试、日志、缓存的高阶函数，都是保持原接口叠加能力。用框架里的真实实现举例，比背结构图有说服力。

**装饰器语法和装饰器模式是什么关系？**

装饰器模式是意图：不改接口、叠加职责。`@decorator` 语法只是让这种写法更顺手的语言支持，没有语法，高阶函数一样能实现装饰器模式。要点是分清"模式"和"语法"，别画等号。

### 一句话记住

结构相似、意图不同：代理管访问，装饰器加能力。

## Q5：适配器模式解决什么问题？

### 这题在考什么

是否理解适配器只是"**隔离差异的转换层**"，并且能说清它的**边界和代价**——尤其是不让它吞业务逻辑。

### 面试时可以这样说

> 适配器干的事，是把已有的接口转换成调用方需要的接口。常见场景是统一多端 API、接入第三方 SDK、还有新旧接口迁移。要注意它的边界：它应该隔离差异，而不是把所有业务逻辑都塞进这个兼容层里。另外，长期保留双向、多版本的适配会抬高维护成本，所以从一开始就要有明确的淘汰计划。

"淘汰计划"这个词容易被忽略但很加分——适配层最常见的死法就是永远迁不完。

### 对方很可能继续问

**适配器和门面模式有什么区别？**

适配器解决"接口不匹配"：已有接口和调用方期望不一致，中间做转换。门面解决"使用复杂"：给一堆子系统调用一个简化入口。两者可以叠加，但动机不同——一个为了兼容，一个为了降使用成本。把动机说清，比背结构图有用。

**统一多端的 API 层越写越大怎么办？**

这通常说明适配层在吞业务逻辑，已经越界了。处理思路：按平台拆分实现，公共部分下沉，差异用配置驱动；实在收敛不了的逻辑，宁可回到各端代码，也别让适配层长成第二套业务。

### 一句话记住

适配器只做接口转换、隔离差异，业务逻辑别塞进去，还要留淘汰计划。

## Q6：工厂和单例在前端中怎么用？

### 这题在考什么

是否理解工厂和单例**各自解决什么问题**，并且对**全局单例的代价**有清醒认识——隐藏依赖、测试污染、SSR 串状态。

### 面试时可以这样说

> 先说工厂：它把对象创建的细节从使用方那里移开，适合根据环境、配置或类型创建不同的实现。再说单例：它保证一个作用域内只有一个共享实例，比如连接管理、全局配置。但全局单例有三个代价：隐藏依赖、污染测试，还有跨请求状态问题。尤其在 SSR 里，不能把每个用户的状态放进进程级单例。

SSR 串状态是这道题最有区分度的收尾，能引到 createSSRApp 更好。

### 对方很可能继续问

**单例为什么不利于测试？**

因为它隐藏了依赖和共享状态。一个测试改过单例，另一个测试就可能继承到这个状态；并行测试和 SSR 请求隔离也会受影响。解法是依赖注入、把实例传进去，或者让单例只管理真正的进程级无状态能力。

**前端有哪些东西其实是单例？**

`window` 上的全局状态、模块级变量——ESM 模块首次 import 后会缓存导出，之后所有地方共享同一份，这就是语言层面的单例；还有 localStorage 封装、全局事件中心。理解这一点也就明白 SSR 为什么要求每个请求用 `createSSRApp` 新建实例：进程级单例装了用户态，就会在请求之间串数据。

**依赖注入在前端怎么落地？**

轻量做法就够：通过 props 或 provide/inject 把实现传下去；工厂函数创建携带依赖的实例，测试时传 mock；再往上是 DI 容器，但业务前端很少需要。目标是让依赖显式化、可替换、可测试，用什么形式不重要。

### 这里容易说错

别把单例答成"new 一次缓存起来的技巧题"——面试官等着听的是依赖隐藏、测试污染和 SSR 串状态这三个代价。

### 一句话记住

工厂屏蔽创建细节，单例保证只此一份；全局单例的三个代价要主动说出来。

## Q7：组合模式和享元模式的价值是什么？

### 这题在考什么

是否理解组合模式**统一"部分与整体"的接口**、享元模式**拆分内外状态**，并且能说出享元的**代价和适用前提**——先测量再使用。

### 面试时可以这样说

> 组合模式的价值，是让叶子对象和容器对象使用一致的接口，菜单树、权限树、组件树都是典型场景。享元模式的价值，是共享大量对象中不变的内部状态，把变化的外部状态放到使用处，适合海量相似节点或图形场景。但享元不是免费的：它会增加状态拆分和查找的复杂度，只有内存或创建成本经过测量、确实显著的时候，才值得使用。

享元那句"先测量再用"要保留，它是这道题的判断力所在。

### 对方很可能继续问

**前端哪里用到了享元思想？**

虚拟列表只渲染可见区域并复用节点，是把"节点外壳"当共享的内部状态、把数据当外部状态；Canvas 图形库里大量相同图形共享样式对象；对象池复用连接和 worker。共同点都是先识别大量对象中不变的部分，再共享它。

**组合模式和组件树是什么关系？**

前端天然在用组合模式：组件树里叶子组件和容器组件实现同一套接口（props、children），调用方不需要区分自己在渲染叶子还是子树。React 的 children、Vue 的插槽都是这个模式在框架层面的体现，所以答这题时把组件树当例子最自然。

### 一句话记住

组合统一"部分与整体"的接口，享元共享内部状态；先把成本量出来，再用享元。

## Q8：命令模式适合什么场景？

### 这题在考什么

是否理解命令模式的价值在于**把动作封装成对象以支持排队、撤销、重放**，并且能说出它的**代价和不适用场景**。

### 面试时可以这样说

> 命令模式，是把"要执行的动作"封装成一个对象。这样调用者不需要知道具体实现，而且能支持排队、记录、撤销和重放。编辑器操作、快捷键系统、任务队列，都是可能用到的场景。代价也要说：命令对象的数量会增加。如果动作简单、也不需要生命周期管理，普通函数已经足够。

判断点就一句：需不需要"动作的历史"，需要才值得把动作变成对象。

### 对方很可能继续问

**撤销功能具体怎么实现？**

两种思路：命令同时实现执行和逆操作，撤销时执行逆向，文本编辑常用；或者执行前保存状态快照，撤销时恢复，代价是快照存储。还要区分本地命令和副作用命令——发过网络请求的命令无法"真撤销"，只能做补偿操作，这个边界要提前想清楚。

**命令模式和任务队列什么关系？**

任务队列里排队的如果是普通函数，队列只能"执行"，不能撤销、重试时也没有上下文。把动作封装成带参数和状态的对象，队列才能记录、重试、取消和重放。所以判断标准不是队列本身，而是队列里的任务需不需要生命周期。

### 一句话记住

需要排队、撤销、重放时，再把动作封成命令；动作简单就用普通函数。

## Q9：原型模式和 JavaScript 原型链是一回事吗？

### 这题在考什么

是否能分清"**设计模式里的原型模式**"和"**JavaScript 语言的原型链**"，不被术语同名带偏。

### 面试时可以这样说

> 不是同一概念。原型模式是一种设计思路，通过复制已有对象来创建新对象；JavaScript 原型链，是对象属性查找和继承的机制，这是语言层面的东西。JavaScript 里确实可以用 `Object.create` 基于现有对象创建新对象，但讨论设计模式的时候，重点是复用预配置对象的创建成本，而不是背 `prototype` 那套语法。

这题就是考术语鉴别力，答完"不是一回事"再各给一句定位，干净收口。

### 对方很可能继续问

**`Object.create` 和 `new` 有什么区别？**

`Object.create(proto)` 直接以传入对象为原型创建新对象，不执行构造函数；`new` 会执行构造函数并绑定 `this`。原型模式强调的"复制预配置对象"，用 `Object.create(模板对象)` 再覆写差异字段就是典型实现。

**跨 iframe 为什么 `instanceof` 会失效？**

每个 iframe 有自己独立的一套全局构造函数，两边的 `prototype` 对不上，判断自然失败。这恰好说明原型链是对象之间的链接关系，不是全局类型表；所以跨环境判断数组要用 `Array.isArray` 这类基于内部特征的方法，而不是依赖某个Realm的构造函数。

### 一句话记住

原型模式是"复制对象、复用创建成本"的思路，原型链是语言的属性查找机制，同名但不是一回事。

## 用业务例子区分几个容易混的模式

假设要处理一笔订单，把几个容易混的模式过一遍：

- 根据会员等级选择折扣算法，这是策略模式；
- 订单依次经过参数校验、权限、库存和风控，其中某一步可以拒绝继续，这是责任链；
- 订单成功后通知积分、消息和数据分析，发布方不关心订阅者，这是发布订阅；
- 给原有下单调用增加日志和重试，但保持原接口，可以理解为装饰器；
- 把旧支付 SDK 的参数格式转成新业务接口，是适配器。

同一个项目可能同时使用多个模式。回答的时候，先说变化点，再说模式名字，不要反过来为了套模式去解释业务。

## 面试加分方法

回答任何模式的时候，都补一句"什么时候不用它"。模式的价值是管理变化，不是让代码看起来更抽象。

## 自测

1. 用同一个业务例子区分策略与责任链。
2. 说明事件总线的三个治理要求。
3. 给出一个单例造成测试污染的案例。
4. 为项目中的一个 if/else 判断是否值得使用模式重构。
