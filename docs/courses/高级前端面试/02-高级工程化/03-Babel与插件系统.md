# Babel 与编译插件

## Q1：Babel 的工作流程是什么？

### 这题在考什么

是否能把 Babel 的工作链路说成**解析、转换、生成**三个阶段，并分清**语法转换与运行时 API 支持是两件事**。

### 面试时可以这样说

> 我按三个词来讲 Babel 的流程：解析、转换、生成。第一步，Parser 把源码解析成 AST；第二步，插件通过 Visitor 在遍历的时候检查或者修改节点；第三步，Generator 再把 AST 输出成代码和 Source Map。中间还有一个 Preset，它就是把一组插件和配置打包起来的集合。最后说一个边界：Babel 主要转换的是语法，新的运行时 API 能不能用，还得靠 polyfill，或者目标环境本身就支持。

### 如果对方让你继续讲

遍历是深度优先，每个节点有 enter 和 exit 两个时机，插件常在 enter 里定位和修改节点；转换中新增的节点要带上位置信息，否则生成代码的 Source Map 和报错定位会缺失。

### 对方很可能继续问

**Parser 是如何处理 JSX 和 TypeScript 的？**

Babel 默认只解析标准 JS，JSX 和 TS 靠语法插件开启：preset-react 带 JSX 语法支持，preset-typescript 带 TS 语法支持。注意 TS 插件只负责解析、转译时直接丢弃类型，不做类型检查，类型安全要另外交给 tsc，这是 Babel 转译 TS 的经典边界。

**插件顺序与 Preset 顺序有什么影响？**

插件先于 Preset 执行；插件按声明顺序从前往后跑，Preset 按声明顺序从后往前跑，这点和直觉相反。顺序影响转换叠加的效果：两个都处理同类节点的插件，前后顺序不同结果就不同。拿不准别背规则，写个 fixture 跑一遍最可靠。

**多段转换之后，Source Map 如何保持映射？**

每一步都要基于输入的 map 生成新 map，Babel 会把输入 Source Map 和本次转换的位置映射合并，这样 Babel → TS → 压缩这条链到最后还能映射回最初源码。任何一环丢了输入 map，后面就断了，堆栈会指向中间产物而不是业务源码。

### 这里容易说错

- 说“Babel 让新语法在旧浏览器跑起来”就停——它只转语法，`Promise`、`Array.prototype.includes` 这类运行时 API 要靠 polyfill 或目标环境自带。

### 一句话记住

解析、转换、生成三阶段；语法靠转换，运行时 API 靠 polyfill。

## Q2：AST 插件怎么写？

### 这题在考什么

是否理解 AST 插件的实现路径——**用 Visitor 按节点类型定位、通过 `NodePath` 修改节点**——并意识到**作用域、幂等性和语义保持**这些边界，而不是做字符串替换。

### 面试时可以这样说

> 我写插件的顺序是这样：先明确我要匹配的语法结构长什么样，用 Parser 拿到 AST；然后在 Visitor 里，根据节点类型和上下文定位目标；再通过 `NodePath` 完成替换、插入或者删除；最后生成代码。有几个点要一路守住：作用域、重复执行、导入去重、语义保持。只做字符串替换是不行的，那样一定会出问题。

### 如果对方让你继续讲

一个最小的改名插件示例：

```js
export default function renamePlugin({ types: t }) {
  return {
    visitor: {
      CallExpression(path) {
        const { callee } = path.node
        if (t.isIdentifier(callee, { name: 'oldApi' })) {
          callee.name = 'newApi'
        }
      },
    },
  }
}
```

这个示例还到不了生产标准：还要确认 `oldApi` 是否真的来自目标包、有没有被局部变量遮蔽，并且补上 fixtures 测试。生产级的关键一步是查绑定：

```js
CallExpression(path) {
  const binding = path.scope.getBinding('oldApi')
  if (!binding || binding.kind !== 'module') return
  // 只有绑定确实来自目标 import，才允许替换
}
```

绑定能告诉我们这个标识符从哪来——目标包的 import、局部声明还是参数遮蔽，这正是字符串替换永远做不到的事。

### 对方很可能继续问

**为什么不能直接用正则改 import？**

因为同一段文本可能出现在注释、字符串、局部变量或不同语法上下文里，正则根本分不清。AST 能告诉我们节点类型和作用域绑定。比如只想改来自 `@company/api` 的 `request`，就必须确认这个标识符的 binding 来自目标 import，而不是碰到任何叫 request 的函数都替换。

**插件重复运行会发生什么？**

如果每次都无条件插入 import 或埋点，二次构建就会重复注入。做法是给注入节点加可识别标记（注释或特定属性），或者先扫描当前作用域是否已有目标导入和调用，再用 fixture 专门跑两次转换，验证第二次输出和第一次一致。

**插件如何保留 Source Map？**

转换工具要记录生成代码片段和原始节点的位置映射，并把 map 与上一阶段的输入 map 合并。不能只返回一段新字符串，然后指望打包器自动恢复原位置。验证时准备一个转换后会抛错的 fixture，看最终堆栈是否回到原文件的准确行列。

### 这里容易说错

- 替换出的节点和被替换节点同类型时会再次进入 Visitor，注意用 `path.skip()` 控制遍历，防止无限循环。
- 只比较节点名字不看作用域。局部变量遮蔽目标名时，按名字替换会伤及无辜。

### 一句话记住

按节点类型匹配、用 `NodePath` 修改，同时守住作用域、幂等性和语义。

## Q3：`@babel/preset-env` 和 polyfill 是什么关系？

### 这题在考什么

是否分清「语法转换」和「运行时能力补齐」两件事，并知道**应用项目与库项目对 polyfill 的策略不同**。

### 面试时可以这样说

> 先讲 `preset-env`：它根据目标环境，挑出需要的语法转换插件。但注意，`Promise`、`Map` 这些运行时能力不是单纯的语法转换，得靠环境本身提供，或者注入 polyfill。策略上要分项目看：应用项目可以按使用情况注入 core-js；库项目就要谨慎，别污染全局，更适合走 runtime helpers，或者把 polyfill 策略交给使用方决定。最后提醒一句，这套配置必须和 browserslist、core-js 版本以及打包目标放在一起看。

### 如果对方让你继续讲

应用项目现在常用 `useBuiltIns: 'usage'` 配合声明 `corejs` 版本：静态分析代码用到了哪些 API，就精确注入对应模块。这套配置和 browserslist 联动，目标环境变化会同时改变语法插件和 polyfill 的注入量，所以改 browserslist 要整体回归，别只看 JS 产物。

### 对方很可能继续问

**`useBuiltIns` 的几个模式有什么区别？**

`false` 不注入 polyfill，交给使用方；`entry` 在入口按目标环境全量引入，可预测但体积大；`usage` 按代码实际用到的 API 按需注入，体积最小，但识别不了动态拼出来的 API 名。应用默认选 usage，同时必须声明 `corejs` 版本，否则会告警或注入异常。

**为什么库项目不建议注入 core-js？**

polyfill 会改写全局对象，库里一旦注入，就和使用方、其他库的 polyfill 版本耦合，可能重复引入甚至相互覆盖。库的惯例是只转语法、helper 走 runtime，polyfill 留给使用方按自己的目标环境决定，并在文档里写清兼容性要求。

**browserslist 改了会发生什么？**

它同时是转译、polyfill 注入、autoprefixer 这些工具的输入。目标调新，语法插件和 polyfill 变少，产物变小；调旧则相反。因为影响面横跨 JS 和 CSS，改动要整体回归验证，并记录到变更说明里。

### 这里容易说错

- 忘记声明 `corejs` 版本，或与安装的 core-js 大版本对不上，注入会缺失或直接告警。
- 把「语法转换」当成「兼容性全解决」——`Promise`、`fetch` 这类运行时能力不靠转换产生，缺了照样报错。

### 一句话记住

`preset-env` 管语法转换，运行时能力靠 polyfill；应用可注入，库别污染全局。

## Q4：`@babel/runtime` 解决什么问题？

### 这题在考什么

是否理解 **helper 重复内联**带来的体积问题，以及 `@babel/runtime` 的**能力边界**——去重和不污染全局可以，但代替不了全部兼容性评估。

### 面试时可以这样说

> 先说它解决的问题：Babel 转换多个文件时，可能把辅助函数在每个文件里都内联一遍，代码就重复了。`@babel/plugin-transform-runtime` 的做法，是把这些 helper 改成对 `@babel/runtime` 的导入，重复代码就少了，还可以选择不污染全局的运行时能力。但别理解过头：它不等于自动解决所有浏览器兼容问题。实例方法和 Web API，还是要按目标环境一项一项评估。

### 如果对方让你继续讲

runtime 有几个变体：`@babel/runtime` 只管 helper；`@babel/runtime-corejs3` 额外用 core-js-pure 提供不污染全局的 API 等价实现，连实例方法调用都能改写。选哪个取决于目标环境：目标很旧又不能动全局，就上 corejs3 变体。

### 对方很可能继续问

**transform-runtime 和 polyfill 注入有什么区别？**

transform-runtime 把 helper 和 API 调用改写成从 `@babel/runtime` 导入，不碰全局，适合库；polyfill 直接往全局补对象和原型方法，应用用它兜底整体环境。一句话：runtime 是“引用一份实现”，polyfill 是“把实现装进全局”。库选前者，应用可以两者结合。

**helper 内联到底浪费多少？**

单个 helper 只有几十行，但每个文件都可能内联一遍，几百个文件就是几千行重复代码，还会随 chunk 复制多份。改成 runtime 导入后，打包器还能跨 chunk 去重。中型项目这一项通常是几十 KB 级别的收益，文件越多越明显。

**编译产物还需要 core-js 吗？**

分场景。helper 由 runtime 接管后，普通 `@babel/runtime` 并不处理 `arr.includes()` 这类实例方法；要覆盖就得换 `runtime-corejs3`，或者由应用统一注入 core-js。判断依据还是目标环境——目标里最老的浏览器缺什么，就补什么。

### 这里容易说错

- 以为装了 `@babel/runtime` 就兼容无忧。默认它不处理实例方法，旧环境照样会报 `includes is not a function`。

### 一句话记住

`@babel/runtime` 减少 helper 重复、避免污染全局，但不等于全量兼容。

## Q5：如何保证自定义插件可靠？

### 这题在考什么

是否理解插件的可靠性来自**测试和边界控制**——fixtures、作用域验证、幂等性、Source Map、显式报错、dry-run 和回滚——而不是写出来能跑就行。

### 面试时可以这样说

> 我从测试和兜底两边讲。测试这边：用输入/输出 fixtures，把正常语法和异常语法都覆盖到；验证作用域绑定，避免按变量名误匹配；再设计幂等性，重复执行不能重复注入。转换质量这边：Source Map 要保留或者合并；遇到无法安全转换的代码，要明确报错，不能猜。落地这边：在真实项目里用 dry-run 输出变更统计，先看变化再动手；同时准备回滚开关和版本兼容策略。

### 如果对方让你继续讲

落地时可以套这个真实结构：

> 我们有一批旧 API 调用需要统一加租户参数，手工迁移很容易漏。插件的做法是：只匹配从指定包导入的调用，先根据作用域确认绑定，再注入参数；已经有这个参数的就跳过。CI 里先用 dry-run 输出命中和跳过的数量，人工抽查之后才开启转换。遇到无法识别的写法，不猜测，直接给出文件和位置，让业务改成显式调用。

这段话把三件事说清楚了：为什么选编译期、怎么防误伤，以及失败时怎么办。

### 对方很可能继续问

**fixtures 测试具体怎么组织？**

每个用例一个目录：input.js 放原始代码，output.js 放期望产物，options 记录插件参数。要覆盖三类：正常语法、边界语法（注释和字符串里的目标名、作用域遮蔽）、幂等（把 output 再跑一遍，结果应等于自身）。转换应当失败的用例单独放，断言报错信息，而不是看它崩没崩。

**dry-run 在 CI 里怎么落地？**

插件提供只统计不输出的模式，CI 对全仓跑一遍，输出命中、跳过、失败的数量和样例文件；和上一次的基线对比，命中量突变就先卡住，人工抽查 diff 再放行。这样插件升级有没有悄悄改变行为，一目了然。

**插件报错时，怎么不影响业务构建？**

分两种：能兜底的（个别调用点识别不了）降级为跳过并告警，留下文件和位置清单；不能兜底的（注入失败会让产物不可用）就该 fail fast，让流水线立刻停，别带病上线。关键是第一天就定好报错协议：错误码、定位信息、给业务方的修复建议。

### 这里容易说错

- 只测“能转对”，不测“转错了怎么办”。失败路径的行为——跳过还是报错——才是插件可靠性的分水岭。

### 一句话记住

fixtures 测试、幂等性、显式报错、dry-run 验证、回滚开关，缺一不可。

## Q6：编译期注入与运行时封装如何选择？

### 这题在考什么

是否能按**调用点规模、源码可控性、性能要求和失败影响范围**来权衡两种方案，而不是脱离场景说谁更好。

### 面试时可以这样说

> 两边各有各的账。编译期方案的好处：能统一改造大量调用点，运行时侵入低，还能根据静态信息做优化；代价是调试、Source Map、语法兼容更麻烦，误转换风险也更高。运行时封装反过来：更直观，容易灰度、容易撤回；但它要求业务主动接入，还可能增加运行时分支。所以怎么选？看四个维度：调用点规模、能不能控制源码、性能要求，还有失败后影响范围。

### 如果对方让你继续讲

典型场景：埋点注入、旧 API 批量迁移这种“调用点成百上千、源码统一管理”的需求适合编译期；SDK 封装、需要灰度和随时回退的能力开关适合运行时。很多团队最后是混合：编译期做标准化注入，运行时留开关控制行为。

### 对方很可能继续问

**编译期方案出问题，怎么收住影响面？**

三层防线：插件侧对识别不了的语法显式报错或跳过并记录；CI 里 dry-run 统计命中量守门；发布侧按版本启用插件，出问题下一版关掉，而不是紧急改业务代码。前提是保证幂等和语义保持——关掉插件后，代码行为必须和注入前一致。

**运行时封装的“运行时分支”代价是什么？**

每个接入点都要判断开关、走兼容逻辑，调用路径变长，分支组合一多就难维护；埋点这类高频调用还会损失性能。所以运行时方案要把判断收敛在入口一次做掉，热路径保持无分支。

**什么时候两个方案组合用？**

调用点量大但又需要灰度时：编译期统一注入埋点，运行时开关控制上报与否；或者编译期做调用标准化，运行时封装做兼容兜底。组合的前提是职责清晰：编译期管“改得全”，运行时管“控得住”。

### 这里容易说错

- 脱离规模谈方案。十几个调用点手改十分钟的事，上插件是过度工程；上万个调用点还靠手改才是真风险。

### 一句话记住

按调用点规模、源码可控性、性能要求和失败影响范围选。
