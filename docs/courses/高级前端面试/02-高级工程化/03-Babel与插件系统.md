# Babel 与编译插件

## Q1：Babel 的工作流程是什么？

### 这题在考什么

是否能把 Babel 的工作链路说成解析、转换、生成三个阶段，并分清语法转换与运行时 API 支持是两件事。

### 面试时可以这样说

> 我按三个词来讲 Babel 的流程：解析、转换、生成。第一步，Parser 把源码解析成 AST；第二步，插件通过 Visitor 在遍历的时候检查或者修改节点；第三步，Generator 再把 AST 输出成代码和 Source Map。中间还有一个 Preset，它就是把一组插件和配置打包起来的集合。最后说一个边界：Babel 主要转换的是语法，新的运行时 API 能不能用，还得靠 polyfill，或者目标环境本身就支持。

### 对方很可能继续问

- Parser 是如何处理 JSX 和 TypeScript 的？
- 插件顺序与 Preset 顺序有什么影响？
- 多段转换之后，Source Map 如何保持映射？

### 一句话记住

解析、转换、生成三阶段；语法靠转换，运行时 API 靠 polyfill。

## Q2：AST 插件怎么写？

### 这题在考什么

是否理解 AST 插件的实现路径——用 Visitor 按节点类型定位、通过 `NodePath` 修改节点，并意识到作用域、幂等性和语义保持这些边界，而不是做字符串替换。

### 面试时可以这样说

> 我写插件的顺序是这样：先明确我要匹配的语法结构长什么样，用 Parser 拿到 AST；然后在 Visitor 里，根据节点类型和上下文定位目标；再通过 `NodePath` 完成替换、插入或者删除；最后生成代码。有几个点要一路守住：作用域、重复执行、导入去重、语义保持。只做字符串替换是不行的，那样一定会出问题。

### 示例：把特定函数名替换为新名称

```js
export default function renamePlugin({ types: t }) {
  return {
    visitor: {
      CallExpression(path) {
        const { callee } = path.node
        if (t.isIdentifier(callee, { name: 'oldApi' })) {
          callee.name = 'newApi'
        }
      },
    },
  }
}
```

这个示例还到不了生产标准：还要确认 `oldApi` 是否真的来自目标包、有没有被局部变量遮蔽，并且补上 fixtures 测试。

### 一句话记住

按节点类型匹配、用 `NodePath` 修改，同时守住作用域、幂等性和语义。

## Q3：`@babel/preset-env` 和 polyfill 是什么关系？

### 这题在考什么

是否分清「语法转换」和「运行时能力补齐」两件事，并知道应用项目与库项目对 polyfill 的策略不同。

### 面试时可以这样说

> 先讲 `preset-env`：它根据目标环境，挑出需要的语法转换插件。但注意，`Promise`、`Map` 这些运行时能力不是单纯的语法转换，得靠环境本身提供，或者注入 polyfill。策略上要分项目看：应用项目可以按使用情况注入 core-js；库项目就要谨慎，别污染全局，更适合走 runtime helpers，或者把 polyfill 策略交给使用方决定。最后提醒一句，这套配置必须和 browserslist、core-js 版本以及打包目标放在一起看。

### 一句话记住

`preset-env` 管语法转换，运行时能力靠 polyfill；应用可注入，库别污染全局。

## Q4：`@babel/runtime` 解决什么问题？

### 这题在考什么

是否理解 helper 重复内联带来的体积问题，以及 `@babel/runtime` 的能力边界——去重和不污染全局可以，但代替不了全部兼容性评估。

### 面试时可以这样说

> 先说它解决的问题：Babel 转换多个文件时，可能把辅助函数在每个文件里都内联一遍，代码就重复了。`@babel/plugin-transform-runtime` 的做法，是把这些 helper 改成对 `@babel/runtime` 的导入，重复代码就少了，还可以选择不污染全局的运行时能力。但别理解过头：它不等于自动解决所有浏览器兼容问题。实例方法和 Web API，还是要按目标环境一项一项评估。

### 一句话记住

`@babel/runtime` 减少 helper 重复、避免污染全局，但不等于全量兼容。

## Q5：如何保证自定义插件可靠？

### 这题在考什么

是否理解插件的可靠性来自测试和边界控制——fixtures、作用域验证、幂等性、Source Map、显式报错、dry-run 和回滚——而不是写出来能跑就行。

### 面试时可以这样说

> 我从测试和兜底两边讲。测试这边：用输入/输出 fixtures，把正常语法和异常语法都覆盖到；验证作用域绑定，避免按变量名误匹配；再设计幂等性，重复执行不能重复注入。转换质量这边：Source Map 要保留或者合并；遇到无法安全转换的代码，要明确报错，不能猜。落地这边：在真实项目里用 dry-run 输出变更统计，先看变化再动手；同时准备回滚开关和版本兼容策略。

### 一句话记住

fixtures 测试、幂等性、显式报错、dry-run 验证、回滚开关，缺一不可。

## Q6：编译期注入与运行时封装如何选择？

### 这题在考什么

是否能按调用点规模、源码可控性、性能要求和失败影响范围来权衡两种方案，而不是脱离场景说谁更好。

### 面试时可以这样说

> 两边各有各的账。编译期方案的好处：能统一改造大量调用点，运行时侵入低，还能根据静态信息做优化；代价是调试、Source Map、语法兼容更麻烦，误转换风险也更高。运行时封装反过来：更直观，容易灰度、容易撤回；但它要求业务主动接入，还可能增加运行时分支。所以怎么选？看四个维度：调用点规模、能不能控制源码、性能要求，还有失败后影响范围。

### 一句话记住

按调用点规模、源码可控性、性能要求和失败影响范围选。

## 常见追问的参考答法

### 为什么不能直接用正则改 import？

因为同一段文本可能出现在注释、字符串、局部变量或不同语法上下文里，正则根本分不清。AST 能告诉我们节点类型和作用域绑定。比如只想改来自 `@company/api` 的 `request`，就必须确认这个标识符的 binding 来自目标 import，而不是碰到任何叫 request 的函数都替换。

### 插件重复运行会发生什么？

如果每次都无条件插入 import 或埋点，二次构建就会重复注入。做法是给注入节点加可识别标记，或者先扫描当前作用域是否已有目标导入和调用，再用 fixture 专门跑两次转换，验证幂等性。

### 插件如何保留 Source Map？

转换工具要记录生成代码片段和原始节点的位置映射，并把 map 与上一阶段的输入 map 合并。不能只返回一段新字符串，然后指望打包器自动恢复原位置。验证时准备一个转换后会抛错的 fixture，看最终堆栈是否回到原文件的准确行列。

## 一个更完整的项目回答

> 我们有一批旧 API 调用需要统一加租户参数，手工迁移很容易漏。插件的做法是：只匹配从指定包导入的调用，先根据作用域确认绑定，再注入参数；已经有这个参数的就跳过。CI 里先用 dry-run 输出命中和跳过的数量，人工抽查之后才开启转换。遇到无法识别的写法，不猜测，直接给出文件和位置，让业务改成显式调用。

这段话把三件事一起说清楚了：为什么选编译期、怎么防误伤，以及失败时怎么办。
