# 前端性能优化

## Q1：你会如何系统优化一个页面？

### 这题在考什么

这题不看你背了多少优化清单，而是看你会不会先定义用户场景与指标，再按耗时拆解定位瓶颈，最后用同口径的数据验证收益并防止回退。

### 面试时可以这样说

> 我不会先列懒加载、压缩和 CDN，而是先定义用户场景与指标。先用真实用户监控看 LCP、INP、CLS、错误率和关键业务耗时，再按网络瀑布、主线程、渲染和内存定位瓶颈。确定主要矛盾后做单变量优化，通过灰度和前后对比验证收益，同时设置性能预算避免回退。不同页面目标不同，例如内容页优先 LCP，复杂后台更关注 INP 和长任务。

### 如果对方让你继续讲

完整过程：

1. 定义：设备、网络、地域、页面和用户分位数；
2. 测量：实验室工具定位，RUM 验证真实分布；
3. 归因：把指标拆到资源、主线程、渲染和后端链路；
4. 优化：优先解决影响用户最多且投入产出高的问题；
5. 验证：同口径、同分位数、足够样本，观察业务副作用；
6. 防回退：CI 预算、线上告警、版本对比。

资深回答一定要说清数据口径。如果只说"首屏从 3 秒降到 1 秒"，却说不出设备、网络和统计分位数，这个数据就不可信。

### 一句话记住

先定指标和口径，再拆瓶颈定位，单变量验证、预算防回退。

## Q2：LCP、INP、CLS 分别是什么？

### 这题在考什么

是否清楚三个指标各自衡量什么，以及每个指标优化时要拆成哪些环节，而不是只把缩写背出来。

### 面试时可以这样说

> 先说这三个指标分别衡量什么。LCP 衡量视口中主要内容完成渲染的时间。INP 观察用户交互从输入到下一次绘制的整体延迟，而且它关注的是较差的交互。CLS 衡量页面生命周期中的意外布局位移。优化的时候，LCP 要拆成服务端响应、资源发现、资源下载和元素渲染延迟；INP 要减少输入延迟、事件处理时间和呈现延迟；CLS 要为媒体和异步内容预留稳定空间。

### 对方很可能继续问

- LCP 图片已经下载完，为什么 LCP 仍很晚？
- INP 高但接口很快，应该查什么？
- SPA 路由切换如何采集性能？

### 一句话记住

LCP 看内容渲染，INP 看交互延迟，CLS 看布局位移，优化时各拆各的环节。

## Q3：如何优化 LCP？

### 这题在考什么

是否先确定 LCP 元素到底是什么，再按 TTFB、资源发现、资源下载、渲染延迟四段定位瓶颈，而不是笼统说一句"压缩图片"。

### 面试时可以这样说

> 第一步，先判断这个页面的 LCP 元素到底是什么，再把耗时拆成四段看。第一段是 TTFB，对应缓存、CDN、服务端渲染和后端耗时。第二段是资源发现，注意不要把首屏图片藏在异步脚本或 CSS 背景里，必要时才用 preload。第三段是资源下载，看尺寸是否合适、格式是否现代、有没有压缩、优先级是否合理。第四段是渲染延迟，减少阻塞 CSS/JS、长任务和客户端等待链。四段看完，瓶颈在哪一段就比较清楚了。

### 这里容易说错

不能默认给所有资源都加 preload。它会让资源之间互相抢优先级，滥用反而拖慢 LCP。

### 一句话记住

先确定 LCP 元素，再按 TTFB、资源发现、资源下载、渲染延迟四段找瓶颈。

## Q4：如何优化 INP 和长任务？

### 这题在考什么

是否会把一次慢交互拆成输入等待、事件回调、浏览器呈现来定位，并掌握长任务的处理手段和拆分边界。

### 面试时可以这样说

> 先用 Performance 录制较慢交互，把一次交互拆成输入等待、事件回调和浏览器呈现。JavaScript 长任务可以通过减少工作量、拆分任务并让出主线程、避免同步布局和把重计算移入 Worker 来处理。对框架应用还要检查无效更新、过大的响应式范围和一次渲染过多节点。拆分任务不能破坏操作原子性，关键用户反馈应优先呈现。

### 对方很可能继续问

- `setTimeout(0)`、`MessageChannel`、调度 API 如何选择？
- 为什么微任务不适合用来给渲染让路？
- React/Vue 中如何定位无效渲染？

### 一句话记住

把交互拆成输入等待、事件回调、呈现，让出主线程，但别破坏操作原子性。

## Q5：虚拟列表的原理和边界是什么？

### 这题在考什么

是否理解"只渲染视口附近节点、用占位高度维持滚动条"的原理，并能说清动态高度、滚动锚定这些额外成本，判断值不值得用。

### 面试时可以这样说

> 虚拟列表只渲染视口附近的少量节点，通过滚动位置计算可见区间，并用占位高度维持完整滚动条。定高列表可以直接用索引计算；动态高度需要缓存测量结果并修正偏移。它能减少 DOM 和渲染开销，但会增加定位、滚动锚定、无障碍和动态高度处理复杂度，小数据量不值得使用。

### 对方很可能继续问

- 动态高度如何避免滚动跳动？
- 快速滚动出现白屏怎么办？
- 如何支持滚动到指定索引？

### 一句话记住

少渲染 DOM、用占位高度撑滚动条，换来的是实现复杂度，小数据量不值得。

## Q6：如何优化内存？

### 这题在考什么

是否分得清峰值内存高和持续泄漏，并掌握多轮操作、快照对比、Retainers 引用链以及修复后验证回落这套完整流程。

### 面试时可以这样说

> 先区分峰值内存高和持续泄漏。对可复现操作进行多轮执行并触发回收，若基线持续上升，再通过 Heap Snapshot 比较对象数量和 retained size，沿 Retainers 找到引用源。常见问题是未清理订阅、脱离 DOM、无限缓存和大对象闭包。修复后要用相同操作验证对象能够回落，而不是只看代码已经加了清理函数。

### 一句话记住

判断泄漏看多轮操作后基线是否持续上涨，定位靠快照对比和 Retainers 引用链。

## Q7：性能优化如何证明有业务价值？

### 这题在考什么

是否能把技术指标连接到用户行为和业务结果，并用版本、流量、分位数这些口径让收益可验证，而不是只报一句"指标变好了"。

### 想体现资深度，可以再补一句

> 技术指标需要连接到用户行为，例如 LCP 改善是否降低跳出率，INP 改善是否减少重复点击和操作失败。验证时控制版本、流量和用户结构，观察 P75/P95 而不是只看平均值，同时检查错误率、转化和资源成本有没有恶化。没有足够流量时，可以先用实验室指标和任务完成时间作为替代证据，但要明确它不是最终业务结论。

### 一句话记住

技术指标要连到用户行为和业务结果，验证看 P75/P95，不是只看平均值。

## 用一个真实场景把答案讲完整

假设商品详情页的 LCP P75 是 4.2 秒。这时候不要直接说"做了图片压缩"，可以这样讲：

> 我先按页面和网络类型拆数据，发现慢请求主要集中在首次访问的移动网络。LCP 元素是首图，但它要等客户端脚本执行后才被发现，资源发现本身就晚了。我们先把首图放回 HTML 可发现路径，并设置正确优先级；然后按展示尺寸输出图片，减少下载量。改完后再看 LCP 四段耗时，确认资源发现和下载都下降。这里没有给所有图片加 preload，因为那会让非关键图片一起争抢带宽。

这段话里有问题、有证据、有动作、有取舍，比"压缩、懒加载、CDN"更像真实优化。

## 常见追问的参考答法

### 实验室很快，线上为什么仍然慢？

实验室的设备、网络和缓存状态都比较固定，真实用户那边还有低端机、弱网、不同地域和第三方脚本。所以先检查 RUM 的设备与网络分布，再按版本和页面拆分。注意一点：两套数据用途不同，实验室适合定位和回归，RUM 用来判断真实影响。

### 为什么只看平均值不够？

平均值会掩盖尾部用户。大量快速样本会把少数极慢样本稀释掉，而那些用户恰恰最容易流失。Web Vitals 通常看 P75；稳定性和关键接口还可能看 P95、P99，具体要根据业务风险来选。

### 优化后指标没变怎么办？

先确认三件事：优化有没有命中主要瓶颈、采集版本是否一致、样本量是否足够。如果资源下载只占 LCP 很小一段，继续压图片自然看不到明显改善。所以性能优化要看耗时分解，不能只看动作列表。

## 自测

1. 不列优化清单，先说完整性能治理过程。
2. 把一个 LCP 问题拆成四段。
3. 解释为什么微任务不能帮助浏览器尽快渲染。
4. 给出一次性能收益的数据口径。
