# 前端性能优化

## Q1：你会如何系统优化一个页面？

### 这题在考什么

这题不看你背了多少优化清单，而是看你会不会**先定义用户场景与指标**，再按耗时拆解定位瓶颈，最后用**同口径的数据验证收益**并防止回退。

### 面试时可以这样说

> 我不会先列懒加载、压缩和 CDN，而是先定义用户场景与指标。先用真实用户监控看 LCP、INP、CLS、错误率和关键业务耗时，再按网络瀑布、主线程、渲染和内存定位瓶颈。确定主要矛盾后做单变量优化，通过灰度和前后对比验证收益，同时设置性能预算避免回退。不同页面目标不同，例如内容页优先 LCP，复杂后台更关注 INP 和长任务。

先别急着报手段。把「指标 → 瓶颈 → 单变量 → 验证」这条线说完整，具体清单等面试官追问时再展开。

### 如果对方让你继续讲

完整过程：

1. 定义：设备、网络、地域、页面和用户分位数；
2. 测量：实验室工具定位，RUM 验证真实分布；
3. 归因：把指标拆到资源、主线程、渲染和后端链路；
4. 优化：优先解决影响用户最多且投入产出高的问题；
5. 验证：同口径、同分位数、足够样本，观察业务副作用；
6. 防回退：CI 预算、线上告警、版本对比。

资深回答一定要说清数据口径。如果只说"首屏从 3 秒降到 1 秒"，却说不出设备、网络和统计分位数，这个数据就不可信。

### 对方很可能继续问

**实验室数据很好，线上为什么还是慢？**

实验室的设备、网络和缓存状态都比较固定，真实用户那边还有低端机、弱网、不同地域和第三方脚本。所以先检查 RUM 的设备与网络分布，再按版本和页面拆分。另外两套数据用途不同：实验室适合定位和回归，RUM 用来判断真实影响，不能拿实验室数字直接当线上结论。

**优化做完，指标为什么没变化？**

先确认三件事：优化有没有命中主要瓶颈、采集版本是否一致、样本量是否足够。如果资源下载只占 LCP 很小一段，继续压图片自然看不到明显改善。所以性能优化要看耗时分解，不能只看动作列表——动手前先估算这一段理论上限能省多少。

**性能预算具体怎么落地？**

把性能变成工程约束：CI 里对 bundle 体积、首屏资源数、关键指标设阈值，超了卡流水线；线上用 RUM 按版本对比，超预算就告警。每次优化留下同口径的基线，后续版本和它比，而不是和自己比。

### 这里容易说错

- 把优化清单当答案。没有指标和瓶颈定位的清单，在面试官听来等于没做过优化。
- 只报"首屏从 3 秒降到 1 秒"，却说不出设备、网络和统计分位数，数据不可信。

### 一句话记住

先定指标和口径，再拆瓶颈定位，单变量验证、预算防回退。

## Q2：LCP、INP、CLS 分别是什么？

### 这题在考什么

是否清楚三个指标**各自衡量什么**，以及优化时能把每个指标**拆成哪些环节**，而不是只把缩写背出来。

### 面试时可以这样说

> 先说这三个指标分别衡量什么。LCP 衡量视口中主要内容完成渲染的时间。INP 观察用户交互从输入到下一次绘制的整体延迟，而且它关注的是较差的交互。CLS 衡量页面生命周期中的意外布局位移。优化的时候，LCP 要拆成服务端响应、资源发现、资源下载和元素渲染延迟；INP 要减少输入延迟、事件处理时间和呈现延迟；CLS 要为媒体和异步内容预留稳定空间。

### 对方很可能继续问

**LCP 图片已经下载完，为什么 LCP 仍很晚？**

图片下载完不代表开始渲染。常见原因是 LCP 元素要等客户端脚本执行后才发现，或者请求优先级被压低。先用 Performance 看图片的发现时机和优先级，再决定是加 `fetchpriority` 还是把它放回 HTML 的可发现路径。

**INP 高但接口很快，应该查什么？**

说明慢不在网络请求。把交互拆开看：输入等待是不是被长任务占着、事件回调里有没有同步布局或大量计算、呈现延迟是不是一次更新了太多 DOM。接口快只排除了数据这一段，主线程那段还得用 Performance 面板逐段看。

**SPA 路由切换如何采集性能？**

路由切换不触发页面加载事件，LCP、CLS 这些加载型指标不会按路由重新计算，INP 也只按整个页面生命周期上报。所以 SPA 内部导航要单独埋点：以路由变化为起点打 mark，内容渲染完成后补一个 measure 得到"路由切换耗时"；交互和长任务继续用 PerformanceObserver 监听，并给数据补上路由维度，避免不同页面混在一起。

### 这里容易说错

- INP 看的是**较差交互**的延迟，不是平均值，也不是只盯着最差那一次。
- CLS 只算"意外"位移。用 transform 做的动画不改变布局，不计入 CLS。

### 一句话记住

LCP 看内容渲染，INP 看交互延迟，CLS 看布局位移，优化时各拆各的环节。

## Q3：如何优化 LCP？

### 这题在考什么

是否**先确定 LCP 元素到底是什么**，再按 **TTFB、资源发现、资源下载、渲染延迟**四段定位瓶颈，而不是笼统说一句"压缩图片"。

### 面试时可以这样说

> 第一步，先判断这个页面的 LCP 元素到底是什么，再把耗时拆成四段看。第一段是 TTFB，对应缓存、CDN、服务端渲染和后端耗时。第二段是资源发现，注意不要把首屏图片藏在异步脚本或 CSS 背景里，必要时才用 preload。第三段是资源下载，看尺寸是否合适、格式是否现代、有没有压缩、优先级是否合理。第四段是渲染延迟，减少阻塞 CSS/JS、长任务和客户端等待链。四段看完，瓶颈在哪一段就比较清楚了。

### 如果对方让你继续讲

preload 只对"藏起来的关键资源"有价值：图片直接写在 HTML 里，浏览器自己就能发现，不需要加；由 CSS 背景图、JS 字符串拼出来的首图才需要 preload，或者干脆改成 `<img>`。比 preload 更细的工具是 `fetchpriority`，它能精确抬高单个资源的优先级，比无差别 preload 安全。

### 对方很可能继续问

**WebP、AVIF 这些新格式怎么选？**

按支持面给兜底：AVIF 压缩率最高，但编码慢、兼容性一般；WebP 覆盖面已经比较全。实践上用 `<picture>` 提供 AVIF/WebP 并回退到原格式，同时按展示尺寸出图、控制质量参数。小图的格式收益有限，别为了换格式把构建链搞得太复杂。

**SSR 是 LCP 的银弹吗？**

不是。SSR 的作用主要在资源发现：HTML 里直接带着内容和首图引用，浏览器不用等脚本执行就能发现 LCP 元素。但数据接口慢的页面，SSR 只是把等待搬到了服务端，TTFB 该慢还慢；水合太重还会推高交互延迟。所以上 SSR 之前先把后端耗时解决掉。

**怎么确定页面的 LCP 元素是什么？**

实验室工具（Lighthouse、DevTools Performance）会直接标出 LCP 元素和四段耗时；线上用 `PerformanceObserver` 监听 `largest-contentful-paint` 条目，拿到元素和时间戳。注意 LCP 元素可能随加载过程变化，要取最终确定的那一条，别拿中间状态做分析。

### 这里容易说错

- 不能默认给所有资源都加 preload。它会让资源之间互相抢优先级，滥用反而拖慢 LCP。
- 别把 LCP 等同于图片问题。TTFB 慢、阻塞渲染的 CSS/JS，都可能才是大头。

### 一句话记住

先确定 LCP 元素，再按 TTFB、资源发现、资源下载、渲染延迟四段找瓶颈。

## Q4：如何优化 INP 和长任务？

### 这题在考什么

是否会把一次慢交互拆成**输入等待、事件回调、浏览器呈现**来定位，并掌握长任务的处理手段和**拆分边界**。

### 面试时可以这样说

> 先用 Performance 录制较慢交互，把一次交互拆成输入等待、事件回调和浏览器呈现。JavaScript 长任务可以通过减少工作量、拆分任务并让出主线程、避免同步布局和把重计算移入 Worker 来处理。对框架应用还要检查无效更新、过大的响应式范围和一次渲染过多节点。拆分任务不能破坏操作原子性，关键用户反馈应优先呈现。

### 对方很可能继续问

**`setTimeout(0)`、`MessageChannel`、调度 API 如何选择？**

`setTimeout(0)` 在嵌套超过五层后最小间隔会被钳到 4ms，还可能被浏览器推迟；`MessageChannel` 的消息任务没有节流，让出主线程后能更快回来，适合高频拆分；`scheduler.yield()` 语义最明确，还保证让出之后自己的剩余工作优先于其他排队任务继续。一般场景用 MessageChannel 或 scheduler API 就够，微任务不行。

**为什么微任务不适合用来给渲染让路？**

渲染发生在当前宏任务结束、微任务队列清空之后。微任务在当前任务里就全部执行完，浏览器根本没机会绘制，所以用 `Promise.then` 拆任务等于没拆，反而把主线程占得更久。要让浏览器渲染，必须结束当前任务，把剩余工作排进新的宏任务。

**React/Vue 中如何定位无效渲染？**

React 用 Profiler 记录每次提交的渲染次数和耗时，定位到无效更新后，再用 memo、状态下沉、依赖收敛处理；Vue 用 `onRenderTriggered` 或 devtools 的渲染高亮，找出是哪个响应式依赖触发的。共同思路：先证明它真的在无效渲染，再动手加缓存——memo 本身也有比较成本。

### 这里容易说错

- 一上来就拆任务。先分清延迟来自输入等待、回调还是呈现，拆错地方白费功夫。
- `requestIdleCallback` 不适合交互路径上的工作，它可能几百毫秒都不执行，用户反馈等不起。

### 一句话记住

把交互拆成输入等待、事件回调、呈现，让出主线程，但别破坏操作原子性。

## Q5：虚拟列表的原理和边界是什么？

### 这题在考什么

是否理解**"只渲染视口附近节点、用占位高度维持滚动条"**的原理，并能说清动态高度、滚动锚定这些**额外成本**，判断值不值得用。

### 面试时可以这样说

> 虚拟列表只渲染视口附近的少量节点，通过滚动位置计算可见区间，并用占位高度维持完整滚动条。定高列表可以直接用索引计算；动态高度需要缓存测量结果并修正偏移。它能减少 DOM 和渲染开销，但会增加定位、滚动锚定、无障碍和动态高度处理复杂度，小数据量不值得使用。

### 如果对方让你继续讲

定高列表的核心计算只有一行：起始索引 = `Math.floor(scrollTop / 行高)`，再向下多渲染几行 overscan 做缓冲。动态高度的麻烦在于总高度是估出来的：未测量的行用预估高度占位，真实渲染后用测量值替换，并把差值修正到 `scrollTop` 和后续行的偏移上，否则滚动条会跳。

### 对方很可能继续问

**动态高度如何避免滚动跳动？**

维护"索引 → 高度、偏移"的缓存：没测过的行用预估高度占位，渲染后测出实际值，把差值补进总高度和后续所有行的偏移。关键是修正要发生在浏览器绘制之前，比如 React 里在 `useLayoutEffect` 中测量，这样用户看到的位置就不会跳。

**快速滚动出现白屏怎么办？**

本质是渲染速度跟不上滚动。缓解手段：加大 overscan 上下缓冲；快速滚动时先渲染占位骨架，滚动停下再精确渲染；超高列表可以按目标区间直接跳渲染，不逐帧跟 scrollTop。也可以配合 `content-visibility`，让浏览器跳过视口外内容的渲染开销。

**如何支持滚动到指定索引？**

定高列表直接算 `index * 行高` 设置 scrollTop；动态高度查偏移缓存，没测量过的行用预估值，滚过去后再触发测量修正。注意"平滑滚动到指定位置"要边滚边修正目标，实现成本比一次跳转高不少，产品上没有硬需求就别做。

### 这里容易说错

- 小数据量也上虚拟列表，白白增加定位、锚点和无障碍的复杂度。
- 把虚拟列表当"长列表万能药"：页内搜索、键盘导航、无障碍语义都要额外实现，不是白送的。

### 一句话记住

少渲染 DOM、用占位高度撑滚动条，换来的是实现复杂度，小数据量不值得。

## Q6：如何优化内存？

### 这题在考什么

是否**分得清峰值内存高和持续泄漏**，并掌握多轮操作、快照对比、Retainers 引用链以及修复后验证回落这套**完整流程**。

### 面试时可以这样说

> 先区分峰值内存高和持续泄漏。对可复现操作进行多轮执行并触发回收，若基线持续上升，再通过 Heap Snapshot 比较对象数量和 retained size，沿 Retainers 找到引用源。常见问题是未清理订阅、脱离 DOM、无限缓存和大对象闭包。修复后要用相同操作验证对象能够回落，而不是只看代码已经加了清理函数。

### 对方很可能继续问

**怎么证明是泄漏，而不是正常缓存？**

先定一组可重复操作，连续跑多轮，在垃圾回收之后看基线是否还在涨。缓存有上限、数量会稳定下来，多半只是正常占用；对象数量随操作次数线性增长才更像泄漏。再对比快照确认具体是哪个构造函数在涨，别把业务正常增长当成泄漏。

**detached DOM 是什么，怎么查？**

节点从文档里移除了，但 JS 变量、监听器或缓存还引用着它，整棵子树就都回收不掉。快照里按 Detached 过滤 DOM 节点能找到，再沿 Retainers 看是谁持有。常见来源：定时器回调里抓着旧节点、全局数组存 DOM 引用、自定义缓存没清。

**全局缓存怎么设上限？**

"上限 + 淘汰 + 监控"三件套：简单场景用 Map 手写 LRU，或者限制条数、按时间过期；需要 key 跟着对象自动回收，用 WeakMap。再配一个命中率或条数上报。只加缓存不设上限，等于把性能问题换成内存问题。

### 这里容易说错

- 内存曲线上涨一次不等于泄漏，要在多轮操作、GC 之后看基线走势。
- 只看"代码里加了清理函数"不算修复完成，要用快照验证对象真的能回落。

### 一句话记住

判断泄漏看多轮操作后基线是否持续上涨，定位靠快照对比和 Retainers 引用链。

## Q7：性能优化如何证明有业务价值？

### 这题在考什么

是否能**把技术指标连接到用户行为和业务结果**，并用**版本、流量、分位数**这些口径让收益可验证，而不是只报一句"指标变好了"。

### 面试时可以这样说

> 技术指标要连接到用户行为，例如 LCP 改善是否降低跳出率，INP 改善是否减少重复点击和操作失败。立项时我会先把要保护的指标、验证口径和预期收益写下来，做完按同一口径验收，避免"做了什么"和"业务得到什么"对不上号。

### 如果对方让你继续讲

验证时控制版本、流量和用户结构，观察 P75/P95 而不是只看平均值，同时检查错误率、转化和资源成本有没有恶化。没有足够流量时，可以先用实验室指标和任务完成时间作为替代证据，但要明确它不是最终业务结论，下结论要留余地。

### 对方很可能继续问

**为什么只看平均值不够？**

平均值会掩盖尾部用户。大量快速样本会把少数极慢样本稀释掉，而那些用户恰恰最容易流失。Web Vitals 通常看 P75；稳定性和关键接口还可能看 P95、P99，具体根据业务风险来选。

**流量不够做不了 A/B，怎么证明收益？**

退一步用前后对比加交叉验证：同一页面按版本拆分对比，用实验室数据、任务完成率这类替代证据补强，并排除改版、投放等混杂因素。结论表述要克制："与性能改善方向一致"，而不是断言因果。

**性能和业务需求冲突时怎么权衡？**

把预期收益放到同一个尺度上比：这个优化影响多少用户、多少转化，和要做的功能各自值多少。大多数性能手段和功能不冲突；真正要拒绝的是伤害用户体验换指标的极端做法。指标只是代理，长期留不住用户的改动都是负收益。

### 这里容易说错

- 把相关性说成因果。跳出率下降可能来自改版或投放，要控制版本和流量再下结论。
- 只报指标不报口径。没有设备和分位数的数据，业务方没法判断可信度。

### 一句话记住

技术指标要连到用户行为和业务结果，验证看 P75/P95，不是只看平均值。

## 用一个真实场景把答案讲完整

假设商品详情页的 LCP P75 是 4.2 秒。这时候不要直接说"做了图片压缩"，可以这样讲：

> 我先按页面和网络类型拆数据，发现慢请求主要集中在首次访问的移动网络。LCP 元素是首图，但它要等客户端脚本执行后才被发现，资源发现本身就晚了。我们先把首图放回 HTML 可发现路径，并设置正确优先级；然后按展示尺寸输出图片，减少下载量。改完后再看 LCP 四段耗时，确认资源发现和下载都下降。这里没有给所有图片加 preload，因为那会让非关键图片一起争抢带宽。

这段话里有问题、有证据、有动作、有取舍，比"压缩、懒加载、CDN"更像真实优化。

## 自测

1. 不列优化清单，先说完整性能治理过程。
2. 把一个 LCP 问题拆成四段。
3. 解释为什么微任务不能帮助浏览器尽快渲染。
4. 给出一次性能收益的数据口径。
