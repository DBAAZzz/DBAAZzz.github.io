# 微前端与 Monorepo

## Q1：什么时候需要微前端？

### 这题在考什么

能不能先分清微前端解决的真实问题——**多团队、多业务域需要独立开发和发布**，而不是把普通 SPA 拆得更"高级"；再看你能不能摆出团队边界、发布冲突、技术栈差异、故障隔离这些判断维度，同时**把引入成本说清楚**。

### 面试时可以这样说

> 先说结论：微前端主要解决的是多个团队、多个业务域要独立开发和发布的问题，它不是为了把一个普通 SPA 拆得更"高级"。所以我判断要不要上，先看四件事：团队边界、发布冲突、技术栈差异、故障隔离，这几项是不是已经成了真实瓶颈。如果只是代码量大，那模块化、Monorepo、明确领域边界，成本通常更低。真要上微前端，就要接受它带来的成本：运行时集成、重复依赖、路由、通信、样式、治理，一样都少不了。

判断题答完最好落回自己的例子：当初哪条瓶颈是真的，哪条只是想象中的。有量化证据的"该拆"，比背概念有说服力得多。

### 对方很可能继续问

**哪些指标能说明真的该拆了？**

看协作瓶颈有没有量化证据：发布互相排队等窗口的次数、跨团队改同一仓库的冲突频率、一个团队的故障拖垮其他业务的次数、整仓构建耗时。这些指标持续恶化，拆分的收益才可能覆盖成本；拿不出数字，就先做模块化和领域边界治理，别急着上运行时集成。

**为什么 Monorepo 不等于微前端？**

Monorepo 是代码组织方式：多个包放同一个仓库，换原子提交、统一工具链和影响分析；微前端是运行时集成方式：多个应用在同一页面独立加载、独立发布。Monorepo 里可以只放一个 SPA，也可以放微前端的全部子应用。判断标准是"是否运行时独立集成与发布"，不是"代码放在哪个仓库"。

**拆分粒度怎么确定？**

优先沿稳定业务域和团队所有权拆，而不是按 UI 组件切碎。适合作为子应用的，是一个团队能独立负责开发、测试和发布的完整业务区域。粒度太细时，路由、通信和依赖协调的成本会超过独立发布的收益。

**能结合你的项目讲讲为什么上微前端吗？**

当时我们有多个业务应用共享登录和导航，但发布窗口互相影响。我们先试了模块化拆包，发现主要冲突来自团队发布节奏，不只是代码组织，这才引入微前端。第一阶段只拆边界最清楚的应用，没有把所有页面一次迁走——先验证路由、监控和回滚链路，也给旧页面保留稳定入口，再逐步扩大。

### 一句话记住

微前端解决的是多团队独立开发和发布；先看瓶颈是否真实，而不是代码量大不大。

## Q2：qiankun、micro-app、iframe 和 Module Federation 如何选？

### 这题在考什么

是否按**独立部署、隔离强度、技术栈、路由、SSR、共享依赖和故障降级**这些维度去验证选型，而不是拿 API 数量的多少来比较框架。

### 面试时可以这样说

> 这四个方案，我分开看。iframe 隔离最强，但体验和集成成本高。qiankun 基于 single-spa 的生命周期来组织，生态成熟，一般通过代理沙箱和样式策略去集成子应用。micro-app 用自定义元素封装应用，接入体验直接。Module Federation 更偏向运行时共享模块，它不自动提供完整的应用治理。所以选型时，我会拿独立部署、隔离强度、技术栈、路由、SSR、共享依赖、故障降级这些维度做验证，而不是只比较 API 数量。

可以补一句自己的结论边界：主栈统一、要完整生命周期治理，多半在 qiankun 和 micro-app 里选；只为运行时共享模块、治理自己能兜住，才考虑 Module Federation。

### 对方很可能继续问

**iframe 真的过时了吗？**

没有。它是隔离强度最高的方案：样式、JS、路由天然隔离，接入旧系统和低信任的第三方页面时，反而是最省心、最安全的选择。代价在体验：路由不同步、弹窗出不了边界、通信只能走 `postMessage`、内存开销更高。选型不是新替旧，而是拿集成体验换隔离强度，要看你要哪一头。

**Module Federation 有哪些坑？**

它解决的是跨构建的运行时模块共享，不解决应用治理。共享依赖的版本协商发生在运行时，某个远端没就绪或版本不满足，影响的是整页；它也没有内置沙箱和生命周期管理，错误隔离、样式冲突都要自己补。所以用 MF 通常要配三件事：共享依赖的版本策略（不能全量 singleton 了事）、远程模块加载失败的超时降级、以及自己的监控归因。

**选型定了之后，第一步做什么？**

做一条最小 POC，验证的全是"集成之外"的事：主子路由协同、登录态传递、样式互相影响、独立发布一条完整链路、子应用错误在监控里能不能按应用归因。框架 demo 十分钟能跑起来，真正决定成败的是这些边界场景。

### 一句话记住

选型按独立部署、隔离强度、技术栈、路由、SSR、共享依赖和故障降级这些维度验证，不只比 API 数量。

## Q3：微前端如何做 JS 和样式隔离？

### 这题在考什么

是否把 JS 隔离说成 **Proxy 代理全局对象加副作用清理**，把样式隔离的几种方案说全；同时分得清**代理沙箱只是隔离手段，不是安全边界**。

### 面试时可以这样说

> JS 隔离这边，常用做法是用 Proxy 提供代理全局对象，把子应用对全局属性的修改记录下来，卸载时恢复；同时还要额外清理定时器、事件、订阅这些副作用。需要更强隔离的场景，就用 iframe。样式隔离呢，可选的手段有约定前缀、构建时作用域、Shadow DOM，或者严格限制容器范围。最后提醒一句：代理沙箱不是安全边界，同一页面里执行的代码仍然能访问共享能力，低信任内容应该用更强的隔离。

"沙箱不是安全边界"这句是区分度所在——能主动说出它，说明你理解隔离的能力边界而不是只会用框架。

### 对方很可能继续问

**代理沙箱如何处理副作用？**

只代理 `window.xxx` 不够。子应用可能注册 window/document 事件、启动定时器、创建 MutationObserver，或者修改 history。框架需要在挂载期间记录这些副作用，卸载时清理；业务代码自己也要遵守生命周期，不能完全依赖框架兜底。

**动态创建的脚本怎么拦截？**

静态 import 在打包期就能处理，麻烦的是运行时动态插入的 script。要在注入点做拦截：重写 `document.createElement`、`appendChild` 这类入口，给动态脚本包一层执行环境，记录它的副作用，卸载时清理。拦截不全，沙箱就会被这些脚本绕过，所以集成测试里要专门覆盖动态加载场景。

**子应用卸载后，怎么确认没有泄漏？**

做挂载-卸载循环验证：连续挂载卸载几十轮，对比 Heap Snapshot、window 上新增的属性、监听器和定时器数量，卸载后应该回到基线。框架负责记录和清理已知副作用，业务里的全局订阅也要在生命周期内释放，两边都不能指望对方兜底。

**Shadow DOM 对弹窗和全局主题有什么影响？**

两个典型问题。弹窗组件默认把节点挂到 body，就逃出了 Shadow DOM 的样式隔离范围，要么让弹窗挂回子应用容器，要么单独处理它的样式；主题方面，CSS 自定义属性能穿透 Shadow DOM 边界继承进去，类选择器进不去，所以主题要走 CSS variables 而不是覆盖类名。另外事件在 Shadow DOM 里会 retarget，全局监听拿到的 target 是宿主元素，排查问题时容易误导人。

### 一句话记住

代理沙箱隔离的是副作用，不是安全边界；低信任内容要上更强的隔离。

## Q4：主子应用如何通信？

### 这题在考什么

是否坚持用**版本化的最小契约**，而不是图方便共享整个 Store；同时看你能不能把通信配套的**所有权、初始化时序、错误处理和兼容策略**说全。

### 面试时可以这样说

> 通信上我的原则是：优先用版本化、最小化的契约，不要共享整个 Store。具体怎么分：导航、身份、主题，由主应用提供稳定接口；业务事件，用带明确 payload 的事件总线，或者 props；跨窗口就用 `postMessage`。除了这些，通信还要定义清楚几件事：所有权、初始化时序、错误处理、兼容策略。记住一句话：共享状态越多，独立发布能力越弱。

"谁拥有数据"比"用什么传"更重要：数据真源不明确，契约再漂亮也会在联调时崩掉。

### 对方很可能继续问

**为什么不共享整个 Pinia/Redux Store？**

共享整个 Store，会让子应用依赖其他应用的内部状态结构，任何一个字段调整都可能变成跨应用发布。更稳的做法是：主应用只提供少量稳定能力，比如用户身份、导航、主题；业务数据通过版本化事件或接口传递，同时明确谁是数据真源。

**主子应用的初始化时序怎么处理？**

契约里写清楚先后：主应用先挂载容器、注入全局能力，子应用等"就绪"信号再初始化，不能假设对方已经就绪。就绪信号用事件或 Promise 都行，关键是要定义失败路径：主应用没就绪时子应用等待并设超时降级，子应用初始化失败时主应用要有兜底 UI。

**跨应用的事件监听怎么防失控？**

事件名集中定义、带命名空间和 payload 类型；订阅时拿到取消函数，卸载时成对释放；总线要能列出当前所有订阅者，排查"谁在听这个事件"时不用翻代码。共享的订阅关系越多，越要这样管理。

### 一句话记住

不共享整个 Store，用版本化的最小契约；共享状态越多，独立发布能力越弱。

## Q5：Monorepo 解决什么问题？

### 这题在考什么

能不能说清 Monorepo 换来的是**原子提交、统一工具链、代码共享和影响分析**；同时不被"所有包一起发布""自动解决依赖混乱"这两个**误区**带走，并把配套治理和 CI 策略说全。

### 面试时可以这样说

> Monorepo 做的是把多个应用和包放进同一个版本库，好处有四个：原子提交、统一工具链、代码共享、影响分析。但有两个误会要先排掉：它不代表所有包一起发布，也不自动解决依赖混乱。真正要落地，还得配上 workspace 依赖、任务图、缓存、所有权、发布策略、边界检查。规模变大以后，CI 只执行受影响任务，再用远程缓存，这一步非常关键。

"不自动解决什么"和"带来什么"要说得一样多，这是这道题不被追问打穿的底气。

### 对方很可能继续问

**Monorepo 会不会让仓库越来越慢？**

会有这个风险。但解决点不在"换 pnpm"这一个动作，而是影响分析、任务缓存、按变更执行测试、目录所有权和依赖边界。缓存键如果漏掉环境变量或配置文件，还会得到错误产物，所以缓存命中率和正确性都要监控。

**什么时候不该用 Monorepo？**

团队需要完全独立的发布节奏和权限边界、跨组织协作拿不到统一的工具链维护投入、或者 CI 影响分析做不起来时，polyrepo 加私有包往往是更务实的选择。Monorepo 的收益前提是"同仓协作的收益大于同仓的摩擦"，这个前提不成立就别硬上。

**所有包一起发布不行吗？**

不行，这正是常见误区。发布应该按包独立进行：版本独立、变更记录独立，谁改了发谁。全量发布会让"一次改动、所有包升级"成为常态，下游被迫吞无关变更，独立发布的意义就没了。

### 一句话记住

Monorepo 换的是原子提交和影响分析，不自动解决发布和依赖问题；规模大了，CI 只跑受影响任务、上远程缓存是关键。

## Q6：pnpm 为什么适合 Monorepo？

### 这题在考什么

是否把 pnpm 的三个优势说清——**内容寻址存储、链接结构、更严格的依赖可见性**，再配上 workspace 协议；同时**不回避**链接结构兼容性、peer dependency 治理和版本收敛这些代价。

### 面试时可以这样说

> pnpm 适合 Monorepo，我讲三点。第一，它用内容寻址存储减少重复文件，再通过链接构建依赖结构。第二，它默认的依赖可见性更严格，能把幽灵依赖暴露出来。第三，Workspace 协议可以明确引用仓库内的包。当然它也有代价：部分旧工具对链接结构不兼容，peer dependency 要治理，版本要收敛。这些都得靠规则和 CI 检查来处理。

能主动讲代价是加分项：说明你真迁移过，而不是只看过 pnpm 的宣传页。

### 对方很可能继续问

**`dependencies`、`devDependencies`、`peerDependencies` 三者怎么划分？**

`dependencies` 是运行时需要的包，安装和构建都会带上；`devDependencies` 只在开发、构建、测试阶段需要，比如打包器和类型包；`peerDependencies` 表达"我需要它，但由宿主环境提供"，包管理器只校验宿主版本是否满足声明范围，而不是替宿主决定版本。分错的典型表现是把构建工具写进 dependencies，或者把运行时依赖写成 peer，导致装完就报错。

**`overrides` 解决什么问题，有什么风险？**

它强制整个仓库某个依赖统一使用指定版本，常用来修安全漏洞、收敛同一个包的多份版本。风险在于这是全局强改：被覆盖的包如果依赖新版本的 API，会到运行时才炸。所以 override 必须注释原因、尽量限定范围，并定期复查能不能移除。

**为什么组件库常把框架放在 peerDependencies？**

保证组件库和宿主应用用的是同一个框架实例。如果组件库自己带一份 Vue/React，页面里就存在两份框架，hooks、context、事件系统各自为政，运行时直接出问题。所以框架声明在 peer 里写出兼容范围，同时在 devDependencies 放一份供自己开发测试用。

### 这里容易说错

不要说"peerDependencies 不会被安装"——npm 7+ 会自动安装 peer，但语义仍然是"宿主应提供、版本需匹配"，组件库不能依赖这个自动行为。也别把幽灵依赖说成 pnpm 的 bug：恰恰是 pnpm 的严格可见性把 npm 扁平化掩盖的问题暴露出来了。

### 一句话记住

内容寻址加链接结构省空间，严格可见性暴露幽灵依赖；兼容和治理问题靠规则和 CI 兜底。

## Q7：Turborepo 的缓存为什么有效？

### 这题在考什么

是否把**缓存键的组成**说全——任务定义、输入文件、依赖任务、环境和配置；是否讲清**任务图**既保证依赖顺序、又允许无依赖任务并行；知不知道**漏声明真实输入输出**的后果。

### 面试时可以这样说

> Turborepo 的缓存，原理是这样：它根据任务定义、输入文件、依赖任务、环境、配置这几项算出缓存键，键命中了，就直接复用先前的输出。执行层面，它靠任务图保证依赖顺序，同时允许没有依赖的任务并行跑。要让缓存不出错，有个前提：真实输入、输出、环境变量都必须声明。漏掉隐式输入，你会拿到过期产物；把不可复现的任务缓存起来，也会制造问题。

缓存这道题的本质是"正确性优先于速度"——键不全的命中比不命中更危险，这个判断要主动说出来。

### 对方很可能继续问

**缓存命中了，结果一定可信吗？**

取决于缓存键是否覆盖全部真实输入：任务定义、输入文件、依赖任务、环境变量、相关配置任何一项漏声明，命中的都可能是过期产物。所以新增环境变量或配置文件时要同步进任务输入声明；依赖外部时间、外部网络状态这种不可复现的任务，要么修复，要么排除出缓存。

**远程缓存安全吗？**

远程缓存本质是共享的构建产物，要管两条：访问控制和完整性。缓存服务要鉴权，避免未授权读写；产物做哈希或签名校验，防止缓存被污染后直接投毒到所有开发机和 CI。敏感产物要么不进远程缓存，要么加密存储。

**命中率低怎么排查？**

先查哈希输入里的不稳定因素：时间戳、绝对路径、每次构建都会变的文件被声明成了输入；再查输入声明是否过宽，比如把整个目录算进去，任何无关改动都击穿缓存。用 dry-run 对比两次构建的哈希差异，能定位到具体是哪一项输入在变。

### 这里容易说错

不要把"缓存命中"当成构建正确性的证明——键声明不全时，命中恰恰说明拿到的是旧产物。命中率上升不全是好事，要先确认命中的产物是对的。

### 一句话记住

缓存键由任务定义、输入、依赖、环境和配置共同决定；漏掉真实输入输出，就会拿到过期产物。

## Q8：子应用独立发布如何保证安全？

### 这题在考什么

是否把发布安全串成一条**完整链路**：产物版本不可变、主应用只切版本引用、先灰度、入口失败有超时和降级、协议有兼容范围、指标可关联、能快速回滚——少一环都算答漏。

### 面试时可以这样说

> 我分七条讲。第一，子应用产物版本不可变。第二，主应用配置只切换版本引用，不改内容。第三，先灰度，再扩大流量。第四，入口加载失败要有超时和降级。第五，主子协议要定出兼容范围。第六，错误、性能和版本这三样要能关联起来。第七，支持快速回滚到上一稳定版本。

七条不用背顺序，但"版本不可变"和"只切引用"是整条链的地基，要先说这两条再展开其余。

### 对方很可能继续问

**主应用怎么知道该加载子应用的哪个版本？**

用一个独立的配置源：清单文件或配置中心维护"应用名 → 版本/入口 URL"，主应用启动或路由时读取并加载对应入口。配置本身要走发布流程，改配置等于一次发布，要可审计、可灰度、可回滚，不能谁都能随手改。

**灰度能细到什么程度？**

常见三档：按流量比例、按用户标签或白名单、按版本整体切换。关键是子应用版本和灰度规则要一起记录，出问题时能说清"这个用户当时跑的哪个版本"，监控才能按版本归因，否则灰度期间等于排障盲区。

**回滚怎么做才快？**

前提就是产物版本不可变：回滚只是把配置切回上一个稳定版本的引用，不需要重新构建。再配两条：监控的错误率按版本关联，达到阈值能自动或一键触发切换；回滚流程平时演练过，而不是第一次跑就在故障夜。

### 一句话记住

版本不可变、入口只切引用，配灰度、超时降级、指标关联和快速回滚。
