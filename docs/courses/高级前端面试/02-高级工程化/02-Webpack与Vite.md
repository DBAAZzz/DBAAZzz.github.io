# Webpack、Vite 与构建工具

## Q1：Webpack 的构建流程是什么？

### 这题在考什么

是否理解构建的**整体阶段**，以及 **Module、Chunk、Asset 三个概念的区别**，而不是把构建流程背成一条流水线。

### 面试时可以这样说

> Webpack 从配置和入口开始，先解析模块请求。Loader 在这里把不同类型资源，转成 Webpack 能继续处理的模块。接着递归解析，把模块依赖图建出来。有了依赖图，再根据入口和动态导入切出 Chunk。最后是优化、代码生成、输出资源，得到最终产物。Plugin 走的是 Tapable 暴露的生命周期钩子，整个过程都能参与。我讲流程的时候，会特意把 Module、Chunk、Asset 三个概念分开，不把“文件”混成一个东西。

### 对方很可能继续问

**Webpack 从入口开始，遇到 `import` 后具体做什么？**

先解析模块请求，结合 alias、extensions、package exports 等规则找到真实文件，再按 module rules 选择 Loader 转换，把结果解析为模块并收集新的依赖，递归建立依赖图。遇到动态 `import()` 也生成模块依赖，只是它会成为新 Chunk 的起点，而不是并入当前 Chunk。所以最后的 Chunk 不等于源文件，是按入口、动态导入和优化策略组织出来的代码单元。

**Loader 为什么从右向左执行？**

这是函数复合的设计：`['style-loader', 'css-loader']` 相当于 `style(css(source))`，右边的先处理、输出交给左边，和 Unix 管道的方向感一致。记住“离文件最近的先执行”就够；要调整优先级用 `enforce: 'pre' / 'post'`，而不是靠调换数组赌运气。

**Plugin 如何修改 compilation？**

插件在 `apply(compiler)` 里通过 `compiler.hooks.compilation.tap` 拿到 compilation，再 tap 它身上的钩子，比如在 `optimizeChunkAssets` 里修改 chunk 产物；写盘前的 `compiler.hooks.emit` 是最后修改 assets 的时机。核心是 Tapable 的发布订阅：插件不直接控制流程，而是在钩子里注册回调，拿到 compilation 对象增删改。

**Tapable 的同步、异步钩子有什么区别？**

同步钩子的回调只能同步执行，出错直接抛；异步钩子支持 `tapAsync`（callback 风格）和 `tapPromise`，能等异步逻辑完成再继续。编译主流程大多是异步系列钩子，所以插件里常见 `tapAsync` 或 `tapPromise`。用同步钩子注册异步逻辑，流程不会等你，产物就会不一致。

### 这里容易说错

- 把 Chunk 说成“就是最终文件”。Chunk 是代码组织单元，一个 Chunk 可能产出多个 Asset（JS、CSS、Source Map），也可能被拆分合并。

### 一句话记住

入口解析 → 依赖图 → Chunk → 产物；Loader 转模块，Plugin 管流程。

## Q2：Loader 和 Plugin 的区别？

### 这题在考什么

是否理解 Loader 和 Plugin **各自作用的对象与介入的阶段**，而不是只背“Loader 转文件、Plugin 做增强”这句结论。

### 面试时可以这样说

> Loader 只负责单个模块的内容转换。比如把 TypeScript、Vue SFC 或者 CSS，转成 Webpack 能继续处理的模块。Plugin 不一样，它监听整个编译生命周期，可以访问和修改编译、Chunk、Asset 这些全局对象，适合做产物生成、注入和构建分析。一句话总结：Loader 是模块转换管线，Plugin 是构建流程扩展。实际用哪个，还是看你操作的对象和介入的阶段。

被追问时补一句判断标准：只动一个模块的内容找 Loader；要碰构建流程和全局对象，找 Plugin。

### 对方很可能继续问

**写一个 Loader 要注意什么？**

Loader 本质是“输入内容 → 输出内容”的转换函数：拿到源文件或上一个 Loader 的结果，返回处理后的内容；有异步工作就用 `this.async()` 回调。实用要点：`this.getOptions()` 取参数、声明 `this.cacheable()` 让缓存生效、`test` 加 `include/exclude` 限定范围，别把 node_modules 一把捞进来全量转换。

**什么需求必须写 Plugin 而不是 Loader？**

看操作对象。只转换单个模块内容，用 Loader；要碰构建流程本身——产物分析、生成额外文件、emit 前修改 assets、注入版本信息——就得用 Plugin 监听 compiler/compilation 钩子。比如“统计每个模块的体积输出报告”，Loader 看不到全貌，Plugin 才拿得到所有 chunk。

**Loader 的 pitch 是干什么的？**

pitch 从左向右执行，和正常阶段方向相反；pitch 返回非空值会跳过剩余 Loader 和源文件处理，直接掉头执行已经过手的部分。典型用法是 style-loader：在 pitch 阶段拦截，把 CSS 模块改成运行时注入 DOM 的代码。业务里很少写 pitch，但它能解释一些 Loader 的行为。

### 这里容易说错

- 只会背“Loader 转文件、Plugin 做增强”。追问“你写过吗、操作对象是谁”就露馅，最好各准备一个自己写过的例子。

### 一句话记住

Loader 管单个模块的内容，Plugin 管整个构建流程。

## Q3：Webpack HMR 原理是什么？

### 这题在考什么

是否理解 HMR 的**完整链路**，以及**“可接受更新的边界”**这个概念，而不是把 HMR 说成“WebSocket 通知刷新”。

### 面试时可以这样说

> 文件一变，开发服务器做增量编译，然后通知浏览器有新更新。客户端拿到更新清单和新模块代码，在运行时沿着模块关系，找能够接受更新的边界。找到边界，就替换模块，执行 dispose、accept 逻辑。找不到，一般就退化成整页刷新。框架插件会帮我们维护组件状态和更新边界。所以 HMR 不只是 WebSocket 通知一下那么简单。

### 如果对方让你继续讲

找不到接受边界时有一套“冒泡”逻辑：模块自己不接受，就沿着父模块向上找，直到某个模块声明 accept，或到顶退化为整页刷新。框架插件（react-refresh、vue-loader）在组件模块上注册边界，并在替换时保留组件树状态，这就是“改样式不丢状态、改组件只局部更新”的由来。

### 对方很可能继续问

**为什么修改某个模块会整页刷新？**

说明运行时沿依赖图向上找，也没有找到接受这次更新的边界。常见原因：模块有顶层副作用、被 accept 边界之外的代码引用、或者框架插件没覆盖到这类文件。处理方式是给合适的模块（通常是组件入口）声明 accept，或者让这类文件走框架插件维护的边界。

**CSS HMR 和 JS HMR 有何区别？**

CSS 没有业务状态，style-loader 生成的模块直接 accept 自己，替换 `<style>` 标签内容就完事，几乎无感。JS 的状态散在模块和组件里，替换需要框架配合保留状态，所以 JS HMR 依赖框架插件维护更新逻辑，边界找不对就退化成刷新。

**Vite HMR 为什么通常更快？**

两个原因：一是 Vite 开发时不打包，失效的模块图小，要重新转换的只有变更的模块；二是模块用带查询参数的 URL 表达版本，更新时浏览器重新 import 改动的模块即可，配合 `import.meta.hot` 的 accept 语义。Webpack 要对依赖图做增量编译再走更新流程，链路更长。

### 这里容易说错

- 把 HMR 说成“WebSocket 通知就刷新”。整页刷新是找不到接受边界时的退化路径，不是 HMR 本身。

### 一句话记住

HMR 在运行时找可接受更新的边界，找不到就整页刷新。

## Q4：如何优化构建速度？

### 这题在考什么

是否理解**“先定位瓶颈、再选手段”**的优化思路，而不是把多进程、缓存这些工具当成**无条件正确**的答案。

### 面试时可以这样说

> 第一步是构建分析，先确定时间花在哪：解析、Loader、压缩还是 I/O。然后针对瓶颈去处理。常见手段有：缩小处理范围、开持久化缓存、减少重复转译和重型插件、利用增量构建。确实是 CPU 瓶颈，再上并行处理。升级工具链也可能带来收益。注意，多进程不是默认答案。小项目里，进程启动和通信的成本可能比收益还高。

### 如果对方让你继续讲

常见的落点：Webpack 5 开 `cache: { type: 'filesystem' }` 做持久化缓存，二次构建直接复用；`resolve` 收紧 extensions 和别名，Loader 用 `include/exclude` 缩小范围；压缩和图片处理确认并行开启；CI 上持久化缓存目录或接远端缓存。每一步都用构建分析的前后耗时验证，不凭感觉。

### 对方很可能继续问

**多进程什么时候真的有用？**

瓶颈在 CPU（大量 Loader 转译、JS 压缩）且文件量足够大时才有收益。小项目里进程启动和结果序列化的成本，可能比省下的时间还高。先看构建分析确认时间花在解析和压缩上，再开 thread-loader 或并行压缩，用数据对比前后。

**持久化缓存为什么会失效？**

缓存和构建输入关联：配置变化、依赖升级、Loader 版本、相关环境变量都可能触发失效。命中率低先查配置里是否引用了不稳定值（时间戳、随机 id），以及是否有模块在构建时改写文件。命中率可以用 stats 信息确认，别装上缓存就算完。

**升级 Webpack 5 主要图什么？**

持久化缓存开箱即用、Tree Shaking 增强（嵌套导出、部分 CommonJS 支持）、Node polyfill 不再自动注入、生态长期维护。迁移成本主要在插件兼容和 polyfill 显式化。遗留项目没有明显构建痛点时，可以先在 CI 缓存上下功夫，不必为大版本而大版本。

### 这里容易说错

不要把已经淘汰或维护停滞的方案当 Webpack 5 首选。优先使用内置 filesystem cache，而不是继续推荐 HardSourceWebpackPlugin。

### 一句话记住

先看时间花在哪再动手；缓存是首选，多进程不是默认答案。

## Q5：Tree Shaking 的原理是什么？

### 这题在考什么

是否理解 Tree Shaking 依赖 **ESM 静态结构**和 **`sideEffects` 配置**，而不是把它当成打包器自带的免费优化。

### 面试时可以这样说

> Tree Shaking 靠的是 ESM 的静态结构。先分析导入导出关系，标记哪些导出真的被用了，优化和压缩阶段再把不可达代码删掉。它能生效有三个条件：代码能被静态分析，模块没有会阻止删除的副作用，`sideEffects` 配置正确。`sideEffects: false` 是作者对包内容的承诺。标错了，CSS 导入或者注册代码可能被一起删掉。

### 如果对方让你继续讲

构建链上有个经典坑：`@babel/preset-env` 若把 ESM 转成 CommonJS，静态结构就没了，Tree Shaking 整体失效。所以 Webpack 项目里 preset-env 的 `modules` 保持默认（交给打包器决定），别手动设成 `'commonjs'`，也别在中间插件里做这个转换。

### 对方很可能继续问

**为什么 CommonJS 通常更难 Tree Shaking？**

CommonJS 的导入导出是运行时的对象读写：条件 `require`、动态拼接模块路径、在 `exports` 上随意挂载都可能发生，编译期无法确定哪些导出没人用。Webpack 5 对简单模式的 CommonJS 有部分支持，但动态用法天然超出静态分析能力，所以同时发 CJS 的库，摇树效果通常打折。

**`usedExports` 和最终删除代码是什么关系？**

两步走：`usedExports` 在优化阶段分析并标记哪些导出真的被使用；真正的删除发生在压缩阶段，Terser 依据标记把不可达代码去掉。所以只开 usedExports、不开压缩时，产物里代码还在，只是带了“未使用”的标注。

**库作者如何配置 `sideEffects`？**

在 package.json 用 glob 列出**有**副作用的文件，比如 `"sideEffects": ["*.css", "./es/register.js"]`——样式和顶层注册逻辑要排除在“无副作用”承诺之外，否则会被误删。直接写 `false` 是“全部无副作用”的强承诺，发版前要用真实业务项目验证摇树结果，别只跑本地 demo。

**Tree Shaking 没生效怎么查？**

先确认使用的是静态 ESM 导入；再看包是否被标记为有副作用，或者代码里确实存在顶层副作用；检查是否通过一个聚合入口把大量模块一起执行；最后用 bundle analyzer 或 stats 看模块为何被保留。不要看到包很大就直接加 `sideEffects: false`，这可能误删样式和注册代码。

### 这里容易说错

- 以为 `import` 了的代码一定会被打包、没 `import` 的一定不会——真正决定去留的是静态可达性和副作用标记。
- 构建链里任何一环把 ESM 转成了 CommonJS（常见于 preset-env 的 `modules` 配置），Tree Shaking 就整体失效。

### 一句话记住

Tree Shaking 靠 ESM 静态分析加 `sideEffects` 承诺，标错会误删代码。

## Q6：生产环境 Source Map 怎么选？

### 这题在考什么

是否理解生产环境 Source Map 要在**错误还原和源码安全之间做权衡**，而不是只会背 `hidden-source-map` 的选项名。

### 面试时可以这样说

> 生产环境选 Source Map，要同时掂量四件事：错误还原、构建时间、产物体积、源码暴露。我的做法是：生成完整 Map，但产物里不公开引用它。CI 按应用和版本把 Map 上传到监控系统，确认上传成功后，不部署到公共静态目录。错误事件带着版本号，解析服务按版本去匹配。具体选项要对着当前构建工具的文档确认，不要只背 `hidden-source-map` 一个名字。

### 如果对方让你继续讲

完整生命周期是四步：构建时生成 Map → CI 上传到监控平台（按应用和 release）→ 线上错误事件带 release 上报 → 解析服务按版本匹配 Map 还原堆栈。验收标准是“线上报错能在监控里还原到源码行列”，而不是“配了某个 devtool 选项”。

### 对方很可能继续问

**生产 Source Map 为什么按版本管理？**

同一个压缩文件名和行列号在不同版本对应的源码可能完全不同。错误事件必须带 release，CI 上传 Map 时也使用同一个 release。否则解析服务即使返回了文件名和源码行，也可能是错误版本，反而会误导排障。

**`hidden-source-map` 和 `nosources-source-map` 怎么选？**

`hidden-source-map` 生成完整 Map 但产物里不引用，配合上传监控系统，还原信息最全，适合排障流程完善的团队；`nosources-source-map` 不含 sourcesContent，只有行列映射，可以直接随产物部署，能定位到行列但基本不暴露源码。安全要求更高，就把源码和 Map 都留在监控平台侧。

**Map 部署到 CDN 就安全吗？**

不安全。Map 文件里带着压缩前源码、注释和内部路径，只要公网可访问就是泄露。原则是生成的 Map 不进公共静态目录、不随 CDN 发布；发版后抽查产物里没有 sourceMappingURL 注释指向可公开访问的 Map。

### 这里容易说错

- 只背选项名说不清链路。面试官要听的是“Map 从构建到还原的完整生命周期”，选项只是其中一环。

### 一句话记住

Map 上传 CI 不进公共目录，错误带 release 按版本匹配源码。

## Q7：Webpack、Vite、Rollup 如何选择？

### 这题在考什么

是否理解三个工具的**定位差异**和背后的**选型维度**，而不是只会说“Vite 快、Webpack 生态好”。

### 面试时可以这样说

> 三个工具定位不一样。Webpack 是成熟的应用打包平台，生态强，处理复杂兼容的能力也强。Vite 开发时基于原生 ESM，按需提供模块，转换工具很快，生产构建通常基于 Rollup。Rollup 更聚焦 ESM 打包和库产物。我的选择逻辑是：做应用，优先评估 Vite；复杂遗留项目，不要只为了“启动快”就盲目迁移；发布组件库，重点看多格式产物、类型声明、external 和 Tree Shaking，这时候 Rollup 或者基于它的工具更合适。

### 如果对方让你继续讲

选型维度：

- 项目是应用还是库；
- 浏览器兼容范围和遗留模块格式；
- 插件、SSR、微前端等生态需求；
- 冷启动、热更新、生产构建和 CI 时间；
- 迁移成本、团队熟悉度和长期维护。

现场没有真实数据时，套这个结构讲一次评估过程也不会空：

> 我们没有因为 Vite 新就迁。先统计了四组数据：开发冷启动、常用页面首次访问、HMR、CI 构建时间。再验证项目里的 CommonJS 包、旧浏览器目标和自定义 Webpack 插件。结论是开发体验收益明显，但有两个自定义插件需要重写。所以选择按应用逐步迁移，而不是一次切换整个仓库。

把真实约束和迁移成本补进去，选型答案就不会只剩“Vite 快、Webpack 生态好”。

### 对方很可能继续问

**Vite 为什么开发启动快？项目变大后呢？**

开发环境不打包：服务先起来，浏览器请求哪个源码模块，再按需转换哪个，省掉“先处理用不到的模块”的时间。第三方依赖预构建并强缓存，减少大量 CommonJS 转换和过细的模块请求。项目变大后这个模型依然成立，但不是没有成本：首次访问一条很深的路由，仍要现场请求和转换一串模块，可以用入口预热缓解。

**依赖预构建解决什么问题？**

两件事：把 CommonJS/UMD 依赖（如 React）转成 ESM，否则浏览器没法直接 import；把内部成百上千个小文件的包合并成单个文件，避免按需加载时的请求风暴。产物缓存在 node_modules/.vite，依赖不变就直接复用，这也是“启动快”的一部分。

**Vite 生产环境为什么仍需要打包？**

原生 ESM 直接上线有硬伤：嵌套 import 造成请求级联、没有 Tree Shaking 和压缩、做不了分块优化。所以生产还是交给打包器（Vite 默认基于 Rollup）做压缩、摇树和分块，开发快和生产质量两条策略分开。社区也在推进 Rolldown 这类 Rust 打包器替换 Rollup，方向是抹平两端差异。

### 这里容易说错

- 只会说“Vite 快、Webpack 生态好”。快在哪个环节、生态差异具体是什么，说不出细节就等于没选过型。

### 一句话记住

应用优先 Vite，库优先 Rollup，遗留项目别为启动快盲目迁移。

## Q8：Module Federation 解决什么问题？

### 这题在考什么

是否理解 Module Federation 解决的是**跨构建模块复用**，以及它**不负责解决哪些问题**，而不是把它当成微前端的一站式方案。

### 面试时可以这样说

> Module Federation 让独立构建出来的应用，在运行时互相暴露模块、消费模块，再协商共享依赖。适合那种既要独立发布、又想共享组件或业务能力的多应用系统。它解决的是跨构建模块复用。注意，它不自动解决路由、样式隔离、权限、版本兼容、故障治理这些事。远程模块不可用怎么办？要有超时、降级和版本策略。共享依赖也不能简单全部设成 singleton。

### 如果对方让你继续讲

共享依赖的核心配置是 `shared`：声明依赖名和可接受的版本范围，运行时协商用谁的版本。React 这类多实例会互相冲突的库要 `singleton: true`；工具库允许各带一份时就不必强制共享。远程模块的加载记得包一层超时和降级，别让一个远程应用的故障拖垮宿主。

### 对方很可能继续问

**共享依赖的版本协商是怎么做的？**

`shared` 里声明依赖和版本范围，运行时比较各应用带来的版本，能共享就复用已加载的满足版本。`singleton: true` 强制全局只有一份，React 必须开，否则双实例会导致 hooks 出错；`strictVersion` 控制版本不符时直接报错还是仅告警。原则：UI 框架强制共享，工具库按体积和一致性要求权衡。

**远程模块加载失败怎么办？**

动态 import 包一层超时和重试，失败走降级：渲染本地兜底组件或提示稍后重试，监控按远程应用维度上报。跨团队场景还要约定发版兼容策略，比如远程入口保留上一个版本，让宿主升级和远程发版不互相卡。

**MF 和 qiankun 这类微前端框架怎么比？**

粒度不同。qiankun 管的是“多个完整应用”的容器加载和沙箱隔离；MF 共享的是模块和依赖，粒度更细，适合独立开发、运行时组合。隔离上 MF 几乎不管样式和 JS 沙箱，要自己补。选型看隔离要求：强隔离选容器方案，重共享选 MF。

### 这里容易说错

- 把 MF 当微前端一站式方案。路由、样式隔离、权限、故障治理它都不管，这些要另外补齐。

### 一句话记住

MF 管跨构建模块复用，不管路由、隔离和故障治理。
