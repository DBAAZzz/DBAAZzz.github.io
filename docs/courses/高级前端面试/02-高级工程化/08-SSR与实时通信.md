# SSR 与实时通信

## Q1：SSR 有什么价值和成本？

### 这题在考什么

是否能把 SSR 的价值和成本同时讲清楚，而不是只报“更快、对 SEO 好”；同时看你能不能判断哪些页面并不值得上 SSR。

### 面试时可以这样说

> SSR 的价值，先说一句：服务端先把 HTML 生成好，用户和搜索引擎都能更早拿到内容。所以内容型页面、看重 SEO、首屏要求高的场景，它特别合适。但还有后半句：HTML 到了浏览器，客户端还得下载 JavaScript、完成 hydration，页面才能完整交互。成本这边：服务端要承担渲染计算，缓存和数据注入都变复杂，代码要兼容服务端环境，还要处理水合不一致。最后补一个判断：后台系统或者强交互应用，上 SSR 不一定有收益。

### 一句话记住

SSR 换来更早的内容和 SEO，代价是服务端成本、数据注入与 hydration 复杂度。

## Q2：SSR 的基本流程是什么？

### 这题在考什么

能否把“请求到服务端 → 渲染出 HTML → 客户端 hydration”这条链路按顺序讲完整，而不是只记得“服务端渲染 HTML”这一句；流式 SSR 的作用也要能补上。

### 面试时可以这样说

> 流程我按顺序拆成三步。第一步，请求到服务端，先匹配路由、加载数据。第二步，把组件渲染成 HTML，同时输出两样东西：客户端需要的序列化状态，还有资源链接。第三步，浏览器先展示 HTML，再加载 JavaScript，框架用 hydration 复用现有 DOM、把事件绑上。流式 SSR 可以再补一句：先发送已经准备好的壳和内容，后续边界完成再继续输出，用户不用等整页全部渲染完。

### 对方很可能继续问

- hydration mismatch 常见原因是什么？
- 如何防止序列化状态造成 XSS？
- SSR 缓存按什么维度设置？
- SSR 是否一定改善 LCP？

### 一句话记住

先渲染 HTML、输出状态，再 hydration 绑定事件；流式 SSR 提前发送壳和内容。

## Q3：CSR、SSR、SSG 如何选择？

### 这题在考什么

是否按“更新频率、个性化、首屏与 SEO、运行成本”这些维度给出选择理由，而不是背三种方案的优缺点清单。

### 面试时可以这样说

> 三种方案，我不背定义，直接说各自适合什么。CSR：运行时灵活，服务端简单，适合登录后的高交互应用。SSR：每次请求或者按缓存动态生成内容，适合个性化、又需要首屏和 SEO 的页面。SSG：构建时就把静态页面生成好，运行成本低，适合变化不频繁的公开内容。最后落到选择上：实际框架里可以按路由混合使用，关键看四个维度——内容更新频率、个性化程度、构建规模、缓存策略。

### 一句话记住

选择看四个维度：更新频率、个性化程度、构建规模和缓存策略；框架里可以按路由混合。

## Q4：WebSocket、SSE、轮询怎么选？

### 这题在考什么

能否按“通信方向、更新频率、基础设施”给出选择理由，并意识到选型不只是协议本身，还牵连代理、认证、补偿、规模和降级。

### 面试时可以这样说

> 三个方案，先按方向分。WebSocket：客户端和服务端之间的双向长连接，聊天、协作、高频双向消息用它。SSE：基于 HTTP，服务端往客户端单向推文本事件，浏览器原生支持重连，日志、通知、进度这些场景合适。轮询：最简单，低频更新或者基础设施受限的时候用。但选型不能只看协议本身，代理、认证、消息补偿、连接规模、降级，这些要一起考虑。

### 一句话记住

WebSocket 双向长连接、SSE 单向推送、轮询最简单；代理、认证、补偿、连接规模和降级要一起算。

## Q5：WebSocket 项目常见坑有哪些？

### 这题在考什么

是否真的在生产环境维护过长连接，能把重连、心跳、消息可靠性、状态恢复、多实例、权限和发送上限这些具体坑一条条讲出来。

### 面试时可以这样说

> 我按七个点说，都是实际会踩的。第一，断线重连要用指数退避，不然服务一恢复，容易出现连接风暴。第二，用心跳检测半开连接，但间隔不能过于频繁。第三，消息要有序号、确认或者幂等 ID，把“已发送”和“已处理”区分开。第四，页面切后台、网络切换之后，要能恢复状态。第五，服务端多实例时，用共享消息层或者一致路由。第六，Token 刷新、权限变更、连接关闭，要有明确的协议。第七，发送队列设上限，避免慢消费者耗尽内存。

### 一句话记住

重连退避、心跳、消息确认、状态恢复、多实例、权限协议、发送上限，都要提前设计。

## Q6：SSE 自动重连是否等于消息不丢？

### 这题在考什么

是否分清“连接恢复”和“消息不丢”是两件事，能不能说出补发断线期间消息需要的条件。

### 面试时可以这样说

> 不等于，这两件事要分开看。EventSource 自动重连，只是把连接重新建立起来；服务端还能用 retry 提示客户端重连间隔。断线期间的消息要补回来，得满足几个条件：服务端给事件设置 ID，保存可重放窗口，客户端重连时带上 Last-Event-ID，服务端按它补发。如果没有持久化和补发逻辑，重连后只能保证继续接收新消息，漏掉的消息不会自动补上。

### 这里容易说错

把自动重连当成消息不丢。自动重连解决的是连接层面；补发要靠事件 ID、可重放窗口和 Last-Event-ID，缺了这些，重连后只能保证继续接收新消息。

### 一句话记住

自动重连只保证连接恢复，不保证消息不丢；补发靠事件 ID 和 Last-Event-ID。

## 常见追问的参考答法

### SSR 为什么可能让服务器变慢？

组件渲染和数据拼装，原本在用户设备上执行，现在有一部分转移到了服务端。请求量上来后，CPU、下游接口和缓存命中率都会直接影响 TTFB。缓存、流式输出和降级要按页面来定，不能把所有路由都无差别 SSR。

### hydration mismatch 怎么排查？

先确认服务端 HTML 和客户端首次渲染是否使用了不同数据。常见原因包括：直接读取 `window`、使用当前时间或随机数、服务端和客户端时区不同、客户端首次渲染就读本地存储。修复原则是让首次输出确定且一致，只属于客户端的逻辑放到挂载之后。

### SSE 为什么不一定比 WebSocket 简单？

浏览器接收端确实简单，但认证、连接数、多实例路由、消息保留、断线补偿这些仍然要设计。EventSource 不方便设置任意请求头；使用 Cookie 时要处理跨域和会话，使用 URL Token 又有日志泄漏风险。

### WebSocket 重连后如何恢复？

客户端重连时带上上次确认的序号，或者当前文档版本，服务端据此补发缺失消息；如果差距太大，就下发完整快照，再继续增量。注意，重新建立 socket，不代表业务状态已经恢复。
