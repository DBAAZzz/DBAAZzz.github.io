# SSR 与渲染方案

## Q1：SSR 有什么价值和成本？

### 这题在考什么

是否能把 SSR 的**价值和成本同时讲清楚**，而不是只报“更快、对 SEO 好”；同时看你能不能判断哪些页面并不值得上 SSR。

### 面试时可以这样说

> SSR 的价值，先说一句：服务端先把 HTML 生成好，用户和搜索引擎都能更早拿到内容。所以内容型页面、看重 SEO、首屏要求高的场景，它特别合适。但还有后半句：HTML 到了浏览器，客户端还得下载 JavaScript、完成 hydration，页面才能完整交互。成本这边：服务端要承担渲染计算，缓存和数据注入都变复杂，代码要兼容服务端环境，还要处理水合不一致。最后补一个判断：后台系统或者强交互应用，上 SSR 不一定有收益。

### 对方很可能继续问

**SSR 为什么可能让服务器变慢？**

组件渲染和数据拼装，原本在用户设备上执行，现在有一部分转移到了服务端。请求量上来后，CPU、下游接口和缓存命中率都会直接影响 TTFB。缓存、流式输出和降级要按页面来定，不能把所有路由都无差别 SSR。

**SSR 一定能改善 LCP 吗？**

不一定。HTML 提前了，但如果服务端本身要等慢接口、TTFB 被拉长，或者 LCP 元素依赖字体、懒加载图片这些后到的资源，LCP 可能不升反降。结论要靠同口径的前后对比数据说话，不能“上了 SSR 所以更快”一笔带过。

**什么页面不值得上 SSR？**

登录后的后台、编辑器、仪表盘这类强交互应用：没有 SEO 需求，用户对首屏内容速度不敏感，反而要承担服务端成本和水合复杂度。它们更适合 CSR，配合代码分割和骨架屏。

**SSR 想稳定上线，最关键的配套是什么？**

页面级缓存和降级。渲染结果按 URL 和关键维度缓存，下游接口故障时能降级输出壳或兜底内容；否则 SSR 等于把全部流量集中到服务端这条最脆的链路上。

### 这里容易说错

只说“SSR 快”，不提 TTFB 和服务端负载；以为 HTML 到达页面就能交互，忽略 hydration 阶段。

### 一句话记住

SSR 换来更早的内容和 SEO，代价是服务端成本、数据注入与 hydration 复杂度。

## Q2：SSR 的基本流程是什么？

### 这题在考什么

能否把“请求到服务端 → 渲染出 HTML → 客户端 hydration”这条链路**按顺序讲完整**，而不是只记得“服务端渲染 HTML”这一句；流式 SSR 的作用也要能补上。

### 面试时可以这样说

> 流程我按顺序拆成三步。第一步，请求到服务端，先匹配路由、加载数据。第二步，把组件渲染成 HTML，同时输出两样东西：客户端需要的序列化状态，还有资源链接。第三步，浏览器先展示 HTML，再加载 JavaScript，框架用 hydration 复用现有 DOM、把事件绑上。流式 SSR 可以再补一句：先发送已经准备好的壳和内容，后续边界完成再继续输出，用户不用等整页全部渲染完。

### 如果对方让你继续讲

落到框架上：Next 的 loader、Nuxt 的 `useAsyncData` 负责数据预取；React 用 `renderToPipeableStream` 配合 Suspense 边界做流式输出——先发壳，边界内的组件就绪后，用内联 script 把内容补进对应位置；Vue 对应 `renderToNodeStream`。序列化状态一般内联在页面里，客户端 hydration 时直接读取，避免二次请求。

### 对方很可能继续问

**流式 SSR 带来什么新问题？**

响应头和前半截 HTML 发出去之后，就没法再整页 302 或切换错误页了——出错只能在流里内联处理，靠错误边界和客户端接管兜底。SEO 上也要确认目标爬虫对分块到达、逐步补齐的页面处理正常。

**如何防止序列化状态造成 XSS？**

状态内联进 script 标签前要转义：`</script>`、U+2028/U+2029 这类会破坏标签或被 JS 当成行终止符的序列必须处理，或者用框架提供的安全内联 API；同时做字段白名单，敏感字段和超大对象不下发。

**SSR 缓存按什么维度设置？**

URL 加真正影响输出的关键查询参数、语言、设备类型；个性化内容要么拆成客户端填充，要么用很短的微缓存。失效策略也要设计，防止改了内容缓存不更新。

### 一句话记住

先渲染 HTML、输出状态，再 hydration 绑定事件；流式 SSR 提前发送壳和内容。

## Q3：hydration 是什么？为什么需要它？

### 这题在考什么

是否理解**首屏内容和页面可交互之间还隔着一个阶段**；hydration 的本质是复用已有 DOM 而不是重新渲染，顺带考察水合不一致的处理经验。

### 面试时可以这样说

> 服务端渲染出来的 HTML 只是“死”的：用户看得见内容，但没事件、没状态，点按钮没反应。hydration 做的事情是，客户端 JS 加载后，框架在已有 DOM 上把组件重新执行一遍——但不重建 DOM，而是把事件监听、组件状态和后续更新能力接上去。所以从 HTML 可见，到页面真正可交互，中间隔着下载 JS、执行、hydration 这几步，这段时间用户点了没反应，这是 SSR 体验上最容易被忽略的一段。

### 如果对方让你继续讲

最常被追问的是 hydration mismatch：服务端 HTML 和客户端首次渲染对不上，浏览器报警告，严重时框架放弃服务端 DOM、整棵树在客户端重渲染，SSR 就白做了。常见原因：直接读 `window`、用当前时间或随机数、服务端和客户端时区不同、首次渲染就读本地存储。修复原则是让首次输出确定且一致，只属于客户端的逻辑放到挂载之后。

缓解这个阶段的方案也可以提：React 18 的选择性 hydration、Astro 的 islands（整页默认静态，只有交互组件各自水合）、Qwik 的 resumability（不重跑渲染，直接恢复状态）。

### 对方很可能继续问

**hydration mismatch 怎么排查？**

先确认服务端 HTML 和客户端首次渲染是否用了不同数据。常见原因包括：直接读取 `window`、使用当前时间或随机数、服务端和客户端时区不同、客户端首次渲染就读本地存储。修复原则是让首次输出确定且一致，只属于客户端的逻辑放到挂载之后。

**选择性 hydration 或 islands 架构是什么？**

思路都是把“整页一次性水合”拆小。React 18 配合 Suspense 可以哪块先到先水合哪块，用户点了哪里优先水合哪里；islands 架构默认整页是静态 HTML，只有标记为岛的交互组件各自加载并水合 JS，页面需要执行的脚本量大幅下降。

**HTML 已到和可交互之间，用户和爬虫各自体验到什么？**

爬虫直接拿完整 HTML，内容可索引，这是 SSR 的 SEO 收益；用户能立刻看到内容，但点击、输入要等 hydration 完成。所以 SSR 改善的是 FCP、LCP 这类内容指标，不必然改善 INP 这类交互指标。

### 这里容易说错

“HTML 出来页面就做好了”——hydration 完成前点不动；把 mismatch 警告当噪音忽略——它可能意味着整棵树在客户端重渲染。

### 一句话记住

hydration 是在已有 DOM 上接回事件和状态，完成之前页面看得见但点不动。

## Q4：SSR 的数据预取和状态注入怎么处理？

### 这题在考什么

是否理解**服务端取到的数据必须随 HTML 下发**、客户端 hydration 直接复用而不是再请求一次；以及序列化里的安全和环境差异问题。

### 面试时可以这样说

> 核心原则是“服务端取一次，客户端复用”。服务端渲染前先做数据预取——Next 的 loader、Nuxt 的 useAsyncData 这类钩子——拿到数据一边渲染 HTML，一边把它序列化内联进页面。客户端 hydration 直接读这份状态来初始化，不会再发重复请求。要处理的点有三个：一是序列化安全，防 XSS；二是环境差异，服务端没有 window、Cookie 要手动透传、相对路径要改成服务端可解析的地址；三是别把不该下发的字段序列化出去，比如其他用户的敏感数据或超大对象。

### 如果对方让你继续讲

性能上还有两个细节：预取要并行，别让接口之间形成请求瀑布，TTFB 是相加的；实时性、个性化强的小块数据可以刻意留给客户端取，配骨架屏，避免整页缓存被个人数据污染。

### 对方很可能继续问

**为什么不干脆让客户端 mounted 之后再请求一次？**

一是白等：SSR 的首屏优势被一段客户端 loading 抵消；二是两次请求结果可能不一致，hydration 后 UI 跳变；三是服务端和下游接口通常在同一内网，服务端取反而更快。只有不适合内联的个人化内容才留给客户端取。

**序列化状态怎么防 XSS？**

内联进 script 前转义 `</script>`、U+2028/U+2029，或改用 Base64，优先用框架提供的安全内联 API；再加一层字段白名单——转义只是防标签被破坏，不该下发的敏感数据要靠白名单直接拦在前面。

**服务端和客户端的请求环境差异怎么处理？**

鉴权靠转发请求的 Cookie 和 Header，不能指望浏览器自动带；接口地址用服务端可解析的配置而不是相对路径；超时和重试在服务端要更激进，因为用户正在等 TTFB，慢接口应该快速失败或降级。

### 这里容易说错

双份请求：服务端取一次、客户端 mounted 又取一次；把整个 store 无脑序列化下发，敏感字段和垃圾字段一起带出去。

### 一句话记住

服务端取一次数据、随 HTML 注入状态，客户端 hydration 直接复用，不重复请求。

## Q5：CSR、SSR、SSG 如何选择？

### 这题在考什么

是否按“更新频率、个性化、首屏与 SEO、运行成本”这些维度**给出选择理由**，而不是背三种方案的优缺点清单。

### 面试时可以这样说

> 三种方案，我不背定义，直接说各自适合什么。CSR：运行时灵活，服务端简单，适合登录后的高交互应用。SSR：每次请求或者按缓存动态生成内容，适合个性化、又需要首屏和 SEO 的页面。SSG：构建时就把静态页面生成好，运行成本低，适合变化不频繁的公开内容。最后落到选择上：实际框架里可以按路由混合使用，关键看四个维度——内容更新频率、个性化程度、构建规模、缓存策略。

### 如果对方让你继续讲

现代方案基本是混合态：营销页、文档走 SSG，个性化首页走 SSR 加 CDN 缓存，登录后的应用走 CSR。页面量大时用 ISR（增量静态再生）或按需生成替代全量构建；SSR 的压力用边缘或 CDN 缓存挡一层，只让缓存未命中的请求打到渲染服务。

### 对方很可能继续问

**ISR 是什么，解决什么问题？**

增量静态再生：构建时不生成全部页面，运行时首次访问触发生成并缓存，按时间周期或按需失效重建。它解决 SSG 在页面量大、内容偶发更新时的矛盾——全量构建太慢，内容又没必要每次请求都现算。

**页面量大到 SSG 构建跑不完怎么办？**

先分层：流量头部页面预渲染，长尾页面按需生成，用 ISR 或 SSR 加缓存；再压缩维度，检查是不是把不需要静态化的参数页也纳入了构建。本质是把“全部提前算”改成“按访问分布算”。

**同一个站点能混用多种渲染方案吗？**

能，而且是常态。Next、Nuxt 都支持按路由选择策略：文档和落地页静态化，搜索结果页 SSR，控制台 CSR。回答时按路由给出划分方案，比单选一种更像做过真实项目。

### 一句话记住

选择看四个维度：更新频率、个性化程度、构建规模和缓存策略；框架里可以按路由混合。
