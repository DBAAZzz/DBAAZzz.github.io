# Agent 架构、工作流与工程落地

本篇只讲「Agent 系统架构」：Agent 的组成部分、ReAct 与固定工作流选型、状态图与 checkpoint、短期与长期记忆、RAG 链路、多智能体、长任务失败恢复、可观测性、延迟与成本、Human-in-the-loop、Agent 前端、框架选型、Prompt 与上下文工程、多模态链路。

这篇不是让你背一串框架名。面试官真正想确认的是：你是否知道模型哪里不可靠，怎么把一次开放式推理变成可控制、可恢复、可观测的工程流程。

边界说明：AI 功能工程化（核心链路、MCP、流式结构化输出、评估、安全、Skill）见 [AI应用工程](07-AI应用工程.md)；AI 项目在面试里怎么讲出亮点，见 [AI应用与Agent项目](../03-项目防守/06-AI应用与Agent.md)。

## Q1：一个完整的 Agent 系统由哪些部分组成？

### 这题在考什么

考的不是罗列组件，而是你脑子里有没有一套**完整系统骨架**；关键判断点是**「Agent 可用性来自模型出错后系统不失控」**——副作用的最终决定权不在模型。

### 面试时可以这样说

> 我会把 Agent 拆成六部分。第一，目标和上下文，搞清楚用户要什么、现在有哪些约束。第二，状态，记下任务走到哪一步。第三，决策，由模型判断下一步是直接回答、调用工具，还是先请求补充信息。第四，工具层，用明确的 schema 对接搜索、数据库和业务接口。第五，执行控制，管超时、重试、幂等、停止条件和权限。第六，观测与评估，记下每一步的输入、输出、耗时和成本。
>
> 不过要补一句：真正让 Agent 可用的，不是模型多聪明，而是模型做错决定以后，系统不会跟着失控。像付款、删除、发消息这类副作用，最终决定权应该在业务代码和用户确认，而不是模型。

六部分不用死背顺序，可以按「决策—执行—护栏—观测」往外说，关键是每一层都说出它防的是什么。

### 如果对方让你继续讲

拿一个真实动作串一遍这六部分，说明决策层出错时护栏怎么接住它：

模型在决策层判断「应该调退款工具」，但参数生成时把金额单位算错，请求了 50000 元。工具层的 schema 只能校验「是数字」，拦不住「数值不合业务」；真正接住它的是执行控制层——退款前再过一遍业务规则（金额上限、订单状态、用户身份），超限就打回，转成等待人工确认。整个过程被观测层记录下来，事后才可能复盘出「决策层对单位敏感」这个规律。

反过来说，如果系统只有决策和工具两层，这个错误就会直接变成一笔 50000 元的退款。这套骨架的价值不在支持多复杂的功能，而在错误发生时系统有几层能接住它。

### 对方很可能继续问

**状态和聊天记录是一回事吗？**

不是。聊天记录只是上下文的一部分，状态还包括当前步骤、已经调用过的工具、结构化中间结果、错误次数、预算和待确认动作。只保存消息，任务中断后通常无法准确恢复。

**Planner 和 Executor 为什么要分开？**

分开后更容易限制权限和定位问题。Planner 可以提出下一步计划，Executor 只执行允许的动作，并重新校验参数。简单任务没必要物理拆成两个服务，但职责边界仍应该存在。

**这些部分一定要拆成独立服务吗？**

不需要。第一版一个函数、一个进程就能跑，重要的是职责边界在代码里清晰存在——决策的代码不直接执行副作用，执行的代码不信任模型参数。拆服务是流量和团队规模的问题，不是架构正确性的前提。

### 这里容易说错

把组件清单背成某个框架的模块名，一报框架名就把「系统设计」降级成了「工具使用」；或者把「六部分」说成六个微服务——考的是职责边界，不是部署形态。

### 一句话记住

Agent 可用性不在模型多聪明，而在模型出错后系统不失控。

## Q2：ReAct 和固定工作流怎么选？

### 这题在考什么

是否理解 ReAct 与固定工作流各自的**适用边界**——什么时候让模型自主、什么时候由代码控流程；以及能否用**基线数据**证明 Agent 真的更好，而不是凭感觉上 Agent。

### 面试时可以这样说

> ReAct 的核心，是让模型在「判断下一步、执行工具、观察结果」之间循环，适合路径事先定不下来、需要根据新信息调整的任务。固定工作流不一样，步骤由代码定死，适合审批、发布、数据写入这类规则明确的业务。
>
> 实际项目里我更倾向混合方案：主流程由代码或状态图控制，只在分类、信息抽取、工具选择这些局部节点用模型。这样既保留自然语言的灵活性，也能控制步骤、成本和副作用。我的判断标准是：能写成普通条件判断的流程，就没必要全部交给 Agent 自主规划。

一个可操作的检验：把业务流程画成流程图，画得出来就用工作流，画不出来才考虑开放循环。

### 如果对方让你继续讲

可以展开 ReAct 循环本身的失控模式和对应的控制手段：

- **循环不终止**：模型反复调用同一工具，或两个步骤互相等待，要靠最大步数、重复调用检测和总预算兜底；
- **幻觉工具或幻觉参数**：模型调用不存在的工具、编造参数值，要靠工具白名单加 schema 严格校验；
- **无效反思**：每轮「反思」没有新信息增量，只是在烧 token，要限制反思次数、要求反思必须引用新的观察结果。

所以即便是 ReAct，外圈也要有一层确定性控制——停止条件、权限、预算都写在代码里。完全放开的自主循环，在生产环境是不负责任的。

### 对方很可能继续问

**怎么判断用了 Agent 以后真的更好？**

先做固定规则或单次模型调用的基线，再比较任务完成率、人工介入次数、耗时和成本。如果 Agent 只是把三步确定流程变成十轮模型调用，效果没有明显提高，那就是过度设计。

**什么信号说明该从 ReAct 退回工作流？**

看执行数据：同类任务的步骤序列高度一致、失败集中在模型选错工具、单任务成本或步骤数持续超预算——说明「自主」没带来收益，流程其实可以固化。固化之后模型只在原节点内部做局部判断，可控性和成本都会立刻改善。这类回退不是架构失败，而是拿到数据之后的正常收敛。

**ReAct 每一步都要模型「想一想」，成本是不是很高？**

是。每轮循环都是一次模型调用，上下文还要带着全部历史，成本和延迟都随步数近似线性上涨。所以生产上要做三件事：简单步骤用小模型、压缩历史上下文、砍掉无信息增量的反思轮次——具体手段见后面延迟与成本那题。

### 这里容易说错

把 ReAct 等同于 Agent 的全部——它只是一种循环模式；或者说「我们全用 Agent 自主规划」，却拿不出和固定流程对比的基线数据。

### 一句话记住

固定流程交给代码，路径不确定才让模型自主规划，好坏用基线数据说话。

## Q3：为什么 Agent 需要状态图？LangGraph 一类框架解决了什么？

### 这题在考什么

是否理解状态图解决的是复杂流程的**可维护、可恢复**问题——显式表达跳转和结束条件、保存 checkpoint；以及能否说清**框架的价值边界**和选型条件，而不是报框架名。

### 面试时可以这样说

> 任务一旦出现分支、循环、人工确认、失败恢复，只靠一段 while 循环会越来越难维护。状态图的好处是：把每个节点的输入输出、允许的跳转和结束条件显式表达出来，还能在节点结束时保存检查点。这样任务中断后，可以从已经完成的节点继续，而不是把所有工具重新调用一遍。
>
> 那 LangGraph 这类框架的价值在哪？主要在状态、节点编排、条件边和 checkpoint，不是让模型回答得更聪明。选不选它要看流程复杂度。两三个固定步骤，用普通函数更直观；需要长任务恢复、多分支或人机协同时，状态图才有明显收益。

一句话分工：状态图管「流程怎么走、断了从哪续」，模型管「某个节点里怎么判断」。

### 如果对方让你继续讲

状态图就三个要素：

- **状态 schema**：整个任务共享的一份数据结构，节点读写它，而不是互相传自由文本；
- **节点**：输入状态、输出状态的最小工作单元，节点内部不再藏分支，这样它才可独立重试；
- **边**：无条件边按顺序走，条件边由谓词决定分支，图必须有明确的终止节点。

checkpoint 在节点边界落盘。恢复时加载检查点，校验权限和外部条件没有变化，再从中断的节点继续。人工确认也做成图里的一个等待节点，批准后从那里继续——「中断恢复」和「Human-in-the-loop」能统一在一套机制里，原因就在这。

### 对方很可能继续问

**Dify、Coze、n8n 和代码框架怎么选？**

低代码平台适合快速验证、连接常见数据源，产品或运营也能参与配置；缺点是复杂状态、版本管理、测试和深度定制容易受平台限制。代码框架开发成本更高，但可测试性、可观测性和业务集成更强。回答选型时不要只报工具名，要说团队、交付速度、流程复杂度和长期维护成本。

**不用框架，自己实现一个状态图难吗？**

核心不难：一个状态对象、一张节点函数表、边的谓词判断，再加一个持久化钩子，几百行就能跑通最小版本。真正难的是边角——checkpoint 的版本兼容（状态结构升级后旧任务还能恢复）、并发恢复的互斥、节点重试的幂等。框架买的主要是这些边角的成熟度；团队有能力自己兜住的话，自研完全可行。

**图的粒度怎么划分？**

节点对应「可独立重试、输入输出明确」的最小工作单元。粒度过细，图会膨胀、checkpoint 写入频繁；过粗，一个节点失败就要整段重跑。经验做法是让一个外部副作用对应一个节点，纯计算和模型判断可以合并。

### 这里容易说错

把状态图说成流程图工具里画的那张图——它是可执行的运行时结构；节点粒度不设边界，要么图爆炸，要么失败重跑的代价巨大。

### 一句话记住

状态图解决流程的显式表达和中断恢复，选不选框架看流程复杂度。

## Q4：短期记忆和长期记忆有什么区别？

### 这题在考什么

是否分清两类记忆的**生命周期和用途**；关键判断点是理解长期记忆的难点在**「什么值得写、什么时候取、旧信息怎么失效」**，而不是「怎么存」。

### 面试时可以这样说

> 短期记忆服务于当前任务，比如最近几轮对话、已执行步骤和临时变量，任务完成后可以过期。长期记忆跨任务保存，比如用户偏好、历史决策和经过确认的事实，通常要持久化，并按需检索。
>
> 长期记忆最大的难点不是存，而是三件事：决定什么值得写、什么时候取、旧信息怎么失效。不能把每句话都永久保存，否则会带来噪声、隐私和错误累积。我的做法是给记忆附上来源、时间、用户范围和置信信息；重要事实由用户确认，读取时结合当前任务检索，冲突时优先用更新且可信的来源。

### 如果对方让你继续讲

长期记忆的工程实现可以按「写、存、取、废」四步说：

- **写**：设门槛——用户显式确认过的事实、任务结束时提炼的结论才写入，闲聊不写；
- **存**：条目带元数据（用户或组织范围、时间、来源、置信度、TTL），向量库、KV、关系表都可以，选型看检索方式；
- **取**：按当前任务构造查询做检索，命中后带着来源注入上下文，不相关的不硬塞；
- **废**：过期删除、新版本覆盖旧版本、被用户纠正的条目降权或标记失效。

短期记忆相对简单：消息列表加滑动窗口，配合结构化任务状态和摘要，超出窗口的历史按需检索。

### 对方很可能继续问

**对话太长，直接做摘要可以吗？**

可以，但摘要会丢细节，也可能把模型误解固化下来。更稳妥的做法是保留关键结构化状态，对较早对话做摘要，原始记录按需检索。权限、金额、任务 ID 等关键字段不能只存在自然语言摘要里。

**长期记忆和 RAG 有什么区别？**

检索设施上常常共用同一套向量库，但语义不同：RAG 面向相对静态的知识库，内容以文档为单位、不带用户归属；记忆面向「这个用户、这段历史」，条目更碎、写入门控更严、失效更频繁、隐私更敏感。落地时记忆的元数据管理和生命周期管理是 RAG 没有的工作量，这也是很多人把它们混为一谈后做砸的原因。

**多用户场景下，记忆怎么隔离？**

记忆条目从写入起就带用户或组织维度，检索层用过滤条件强制隔离——查询时就带上用户 ID 做前置过滤，而不是取回来再筛。绝不能靠提示词写一句「只参考当前用户的信息」来实现隔离，那不是防线，和 RAG 权限过滤必须前置是同一个道理。

### 一句话记住

短期记忆过期，长期记忆要管好“写什么、何时取、怎么失效”。

## Q5：请讲清楚一条完整的 RAG 链路

### 这题在考什么

能否把 RAG 讲成一条**分阶段的完整链路**：离线建库、在线检索生成、事后评估；关键判断点是**企业场景下权限过滤必须前置**，RAG 不等于接一个向量数据库。

### 面试时可以这样说

> 我分两个阶段讲。离线阶段：先采集和清洗文档，按语义与结构切块，生成向量，同时保存正文、来源、版本和权限元数据。在线阶段：把用户问题改写或拆解后做检索，可以结合向量召回与关键词召回，再进行过滤和重排，把最相关的证据放进上下文。生成答案时要求引用来源。最后还要评估召回是否命中、答案是否忠于证据，而不是只看语言是否流畅。
>
> 还有一点容易被忽略：RAG 不等于接一个向量数据库。企业场景尤其要在检索前做权限过滤，不能先把无权查看的内容取回来，再指望模型不要说。

### 如果对方让你继续讲

每一段可以再往下拆一层：

- **切块**：按文档结构切（标题层级、段落、表格边界），每个块带「标题路径 + 父级信息」，检索命中后能还原上下文；
- **召回**：向量召回覆盖语义，关键词召回（BM25 一类）覆盖型号、代码、专有名词这类精确匹配，两边各取 top-k 合并；
- **过滤与重排**：先按权限元数据过滤（查询时下推，不取无权内容），再用重排模型把真正相关的排到前面；
- **组装**：top-k 证据带来源编号放进上下文，要求答案标注引用；
- **评估**：检索侧看命中率、排序质量，生成侧看忠实度（答案是否忠于证据），两边分开测。

### 对方很可能继续问

**回答错了，怎么判断是检索问题还是生成问题？**

先固定正确证据直接交给模型。如果仍然答错，问题更可能在提示、上下文组织或模型能力；如果给正确证据能答对，就回头看切块、查询改写、召回、权限过滤和重排。把检索与生成分开评估，比反复改 Prompt 更有效。

**切块越小越好吗？**

不是。块太大容易混入无关内容并浪费上下文，块太小又会丢失标题、条件和上下文关系。应该结合文档结构切分，保留标题与父级信息，并用真实问题集测试召回，而不是固定相信某个字符数。

**权限过滤放在检索前还是检索后？**

主防线必须前置：用户权限作为过滤条件在查询时一并下推，无权内容从一开始就不参与召回。后置过滤（取回来再删）只配做二次校验，因为「取回」这个动作本身已经构成越权——日志、缓存、模型上下文里都留下了无权内容。

### 一句话记住

证据要准、权限要前置，检索和生成分开评估。

## Q6：什么时候需要多智能体？

### 这题在考什么

是否理解多智能体的适用条件是**角色边界、并行性或权限隔离真实存在**；以及落地时能否管好**状态所有权、消息协议、冲突仲裁和预算**，而不是盲目跟风。

### 面试时可以这样说

> 多智能体适合几种情况：角色边界确实不同、任务可以并行，或者不同角色需要不同工具和权限。比如一个负责检索证据，一个负责生成方案，一个负责校验合规。反过来，如果只是把同一个问题交给多个模型互相聊天，通常只会增加延迟、成本和不确定性。
>
> 落地时要明确四件事：谁拥有最终状态、Agent 之间传什么结构化消息、冲突由谁裁决，以及总步骤和总预算。共享一整段聊天记录看似简单，但很容易造成上下文膨胀和责任不清。

### 如果对方让你继续讲

可以举 supervisor（主从）模式说明常见拓扑：一个主 Agent 拥有任务状态，把子任务分给子 Agent；每个子 Agent 只拿到自己那一段的上下文和工具白名单，完成后返回结构化结果。好处有两个：子 Agent 的中间推理不会撑爆主会话上下文，权限也能按角色收敛——负责检索的子 Agent 拿不到写接口。除主从外还有流水线（固定顺序传递）和评审制（生成者与校验者分离），选型依据还是那三条：分工、并行、权限隔离是否真实存在。

### 对方很可能继续问

**多 Agent 常见故障有哪些？**

- 两个 Agent 互相转交任务，形成死循环；
- 多个 Agent 重复调用同一写工具；
- 并行结果相互冲突，却没有仲裁规则；
- 共享上下文越来越长，成本和延迟失控；
- 一个 Agent 的错误结论被其他 Agent 当成事实继续传播。

解决思路是限制拓扑和步数、给写操作加幂等、设置单一状态所有者，并让关键结论携带证据，而不是只传自然语言结论。

**主 Agent 和子 Agent 之间传什么？**

传两样东西：任务书和结果报告，都是结构化的。任务书包含目标、约束、可用工具、返回格式；结果报告包含结论、支撑证据、不确定点。不共享整段聊天记录，中间推理留在各自的上下文里。关键结论必须带证据，这是防止错误结论被下游当事实传播的关键。

**什么时候明确不该用多 Agent？**

单 Agent 上下文装得下任务、没有真实并行需求、也不需要权限隔离的时候。判断标准很直接：如果把「多个 Agent」换成一个 Agent 内部的多个步骤，任务照样能完成，那多 Agent 就只是架构表演。

### 这里容易说错

把「多个模型互相讨论」当成多智能体的优势——没有分工、并行或权限隔离的讨论只是放大成本；把共享全部上下文当成协作的默认做法。

### 一句话记住

多智能体要有真实的分工或并行收益，落地先定状态所有权和冲突仲裁。

## Q7：长任务如何做到失败恢复？

### 这题在考什么

是否理解失败恢复靠**「可重复节点、状态持久化、幂等写操作、副作用显式处理」**这套组合；以及取消和不可回滚的副作用是否被当成**正式状态**处理，而不是以为所有任务都能自动重来。

### 面试时可以这样说

> 我会把任务拆成可重复执行的节点，每个节点结束后保存状态和结果。工具调用设置超时，并区分可重试错误与业务错误；重试用退避策略和次数上限。写操作必须带幂等键，避免恢复时重复创建数据。已经产生外部副作用的步骤如果无法回滚，就记录清楚并进入人工处理，而不是假装整条任务能够自动重来。
>
> 用户取消也要当正式状态处理：停止后续模型和工具调用，保留已经完成的步骤，并告诉用户哪些动作已经发生、哪些还没有发生。

### 如果对方让你继续讲

错误要先分类，策略完全不同：

- **瞬时错误**：网络抖动、限流、超时——指数退避重试，设次数上限；
- **确定性错误**：参数非法、权限不足、资源不存在——重试没有意义，直接失败并把原因写进状态；
- **模型错误**：输出不合 schema、同一节点反复失败——限制重生成次数，超过就转人工或换策略。

恢复流程是：加载 checkpoint → 校验（用户权限还在、工具版本没变、外部数据没过期）→ 从最后完成的节点继续。校验不通过的，重新执行受影响节点或转人工，不能盲目续跑。状态结构里要带 schema 版本号，方便将来结构升级后旧任务还能恢复。

### 对方很可能继续问

**checkpoint 应该保存什么？**

至少包括任务 ID、当前节点、节点输入输出、已完成工具调用、待确认动作、错误和版本信息。不要简单序列化所有内存对象；恢复后还要检查用户权限、工具版本和外部数据是否已经变化。

**幂等键怎么设计？**

用业务语义的键，比如「任务 ID + 节点序号 + 操作对象」，而不是随机 UUID——同一个步骤在重试和恢复时必须生成同一个键。服务端保存「键 → 结果」的映射，重放请求直接返回上次的结果。天然不幂等的动作（比如发消息）要么服务端加去重表，要么改造成可幂等的接口形态。验收标准很简单：同一个键打过来两次，业务结果必须只发生一次。

**恢复时发现外部世界变了怎么办？**

checkpoint 里除了自己的状态，还要存外部依赖的版本指纹（知识库版本、订单状态、配置版本）。恢复时先比对这些指纹：没变就继续；变了就重新执行受影响节点，或者把差异摆给用户重新确认。最忌讳的是拿着旧上下文硬续跑——任务最后显示「完成」，做的却是过时的事。

### 这里容易说错

以为有 checkpoint 就能随便重跑——副作用步骤重跑前必须过幂等；把「自动重试」当成万能恢复手段，确定性错误重试只是在烧钱。

### 一句话记住

恢复靠可重复节点加幂等写，取消和副作用都当成正式状态处理。

## Q8：如何做 Agent 的可观测性？

### 这题在考什么

是否理解可观测性不止记日志，而是用 **trace ID 串起整条链路、按阶段定位失败**；同时知道**日志和离线评测各自解决什么问题**。

### 面试时可以这样说

> 一次 Agent 请求不能只记最终答案。我会给整条任务分配 trace ID，记录每个节点使用的模型和 Prompt 版本、上下文来源、工具名与参数摘要、结果状态、token、耗时、重试和错误。敏感信息需要脱敏，工具返回过大时保存摘要和可追踪引用。
>
> 排障时先定位失败发生在哪一环：检索、模型决策、参数生成、工具执行，还是结果合并。指标层面除了成功率，还会看平均步骤数、工具调用正确率、P95 延迟、单任务成本、人工接管率和循环终止原因。

trace ID 最好从前端用户会话一路传下来，和常规的前端监控体系打通，用户报障时能直接关联到那次任务的完整链路。

### 如果对方让你继续讲

可以补两个实践中特别有用的聚合信号：

- **循环检测**：给每次工具调用算一个「工具名 + 参数摘要」的指纹，同一指纹连续出现超过阈值就判定循环、强制终止，并记录终止原因；
- **步骤数分布监控**：单任务步骤数的 P95 突然上涨，通常意味着新版本的 Prompt 或新工具引入了循环倾向，这比用户投诉早得多。

这两个都属于「不逐条看日志、只看聚合特征」的监控，是日志之上的一层。

### 对方很可能继续问

**日志都记下来了，为什么还要离线评测？**

日志告诉你线上发生了什么，评测集用来稳定复现并比较不同版本——模型、Prompt、检索和工具任何一项变化，都可能让旧任务退化。线上失败样本脱敏后应该回收到回归集，但不能拿用户隐私原样做测试数据。评估集怎么建、怎么判分，展开在 [AI应用工程](07-AI应用工程.md) 的评估那篇。

**怎么发现 Agent 陷入了循环？**

两个层面。运行时判定：工具调用指纹（工具名加参数摘要）连续重复超过阈值就强制终止，终止原因记「循环」而不是等到超时；指标监控：单任务平均步骤数和成本突涨往往是循环的信号，顺着 trace 看最近一次 Prompt 或工具变更基本能定位。前者是止损，后者是预警，都要做。

**成本怎么归因到功能或客户？**

trace 上打业务标签（功能模块、租户、任务类型），token 数按模型单价换算后聚合，就能得到「单位任务成本」「各功能成本占比」这类口径。没有归因，降本只能拍脑袋换模型；有了归因，才知道优化哪个环节收益最大，降本前后也有数据可比。

### 这里容易说错

只记最终答案和报错堆栈，中间节点全黑盒；把日志脱敏当可选项——用户内容原样进日志体系本身就可能构成合规问题。

### 一句话记住

用 trace ID 串起链路、按阶段定位失败；日志看线上，评测集比版本。

## Q9：如何降低 Agent 的延迟和成本？

### 这题在考什么

是否理解降本先靠 **trace 定位、再分层优化**——小模型、并行、缓存、预算；关键判断点是**缓存 key 必须覆盖权限、版本等维度**，而不是一上来换小模型或只按问题文本缓存。

### 面试时可以这样说

> 先看 trace，确认成本花在哪，而不是一上来换小模型。常见办法包括：简单分类和抽取交给更小的模型；独立工具并行调用；压缩重复上下文；缓存稳定的检索和工具结果；减少没有信息增量的反思循环；流式返回用户可读结果；对步骤数、token 和总时间设置预算。
>
> 缓存有个坑：不能只按用户问题文本做 key，还要考虑用户权限、知识库版本、工具参数和模型配置。涉及实时数据或个性化权限时，错误缓存可能比不缓存更危险。

### 如果对方让你继续讲

优化手段是有优先级的，可以按收益排序：先砍「无信息增量的调用」——多余的反思轮次、重复检索，这是纯赚；再做并行，独立工具同时调；然后是缓存，检索结果、工具结果、中间结论；最后才考虑换更小的模型，因为它影响质量，必须拿评估集验证。另外系统提示、工具定义这类稳定前缀，可以利用模型服务商的 Prompt 缓存（前缀 KV 复用），重复前缀不再重复计算和计费，对多轮 Agent 收益明显。

### 对方很可能继续问

**模型路由怎么做？**

可以按任务风险和复杂度分层。确定性的分类、格式转换使用便宜模型；复杂规划或高价值任务再升级模型；高风险动作无论模型大小都必须走业务校验和人工确认。路由效果同样要用任务集验证，不能仅凭模型榜单决定。

**Prompt 缓存和结果缓存是一回事吗？**

不是。结果缓存存的是「答案」，key 必须带权限、版本、参数这些维度，命中的是相同请求；Prompt 缓存是模型服务侧对相同前缀复用计算（KV 缓存），省的是重复前缀的推理成本和首 token 延迟，不涉及「答案复用」，所以没有权限串味问题。两者可以叠加：系统提示和长文档放前缀吃 Prompt 缓存，稳定的检索结果再做结果缓存。

**流式输出能降低延迟吗？**

不能降低总耗时，它降的是首字时间和用户的感知等待。真正压缩总延迟靠的是并行、裁剪和减少轮次。所以流式要做——用户几秒内就看到反馈——但别把它当性能优化来汇报，数据要分开说：首字时间降了多少、总耗时降没降。

### 这里容易说错

上来就换小模型，钱省了、质量降了，还没有评估集验证；结果缓存只拿问题文本当 key，权限不同、知识库版本不同的用户命中同一条缓存。

### 一句话记住

先定位成本再分层优化；缓存 key 要带权限和版本，错误缓存比不缓存更危险。

## Q10：什么是 Human-in-the-loop？哪些环节必须让人介入？

### 这题在考什么

是否理解人工介入只发生在**不可逆、高风险或置信不足的节点**，确认界面要**展示具体动作和依据**；同时知道人工介入还包括**异常升级**，而不是每一步都弹窗。

### 面试时可以这样说

> Human-in-the-loop 不是每一步都弹窗，而是在不可逆、高风险或模型置信不足的节点，把控制权交给人。比如付款、删除、对外发送、权限变更和影响大量用户的操作。确认页面应该展示将要执行的具体动作、关键参数和依据，不能只问一句“是否继续”。
>
> 人工介入还包括异常升级：连续失败、证据冲突、超出预算或没有合适工具时，Agent 应该停止并说明缺少什么，而不是继续猜。

### 如果对方让你继续讲

工程实现上，确认就是状态图里的一个等待节点：任务停在「等待确认」状态并落库，同时给用户生成一条待办。用户有三个出口——批准、拒绝、修改参数后批准；批准后任务从该节点恢复执行，拒绝则进入拒绝终态。等待确认的动作要有 TTL，到期自动作废并通知发起人。

### 对方很可能继续问

**等待确认的任务，超时没人处理怎么办？**

待确认动作设置 TTL，到期自动取消，任务标记为「已过期未执行」，并通知发起人。绝对不能默认放行——超时放行等于把确认变成装饰，只要拖过确认窗口动作就能自动执行，整个机制就失效了。超时策略要作为设计的一部分写清楚，而不是事故之后再补。

**用户每次都无脑点确认，怎么办？**

确认疲劳要靠设计缓解，不是靠加弹窗解决。第一，只对不可逆且高风险的动作确认，高频低风险动作改成事后审计；第二，确认卡片给足决策信息——动作、参数、依据、影响范围，让人三秒内能做出正确判断；第三，盯确认通过率：某类确认长期 100% 通过，说明阈值定错了，要么降低确认等级、要么改成事后审计。让确认留在真正需要人的地方，它才有意义。

**确认被拒绝之后，任务怎么走？**

拒绝是合法出口：任务进入「被拒绝」终态，记录清楚拒的是什么动作、用户有没有留修改意见，然后给用户下一步建议——改参数重新发起，或者放弃。有一条红线：不允许「用户拒绝了，系统换个措辞或换个路径再执行一次」，那等于否决权失效，比没有确认更糟。

### 这里容易说错

把确认做成一句「是否继续」的弹窗，人看了也没法判断风险；把异常升级说成「再多试几次」——升级是停下来交给人，不是继续猜。

### 一句话记住

人只在不可逆、高风险或置信不足的节点介入，确认时要展示具体动作和依据。

## Q11：Agent 前端和普通聊天页面有什么不同？

### 这题在考什么

是否理解 Agent 前端要表达**持续变化的任务状态**——区分多种状态、可取消、可定位失败；以及**统一事件协议、序号、以服务端状态为准**这些工程细节。

### 面试时可以这样说

> 普通聊天 UI 主要展示消息，Agent 前端还要表达一个持续变化的任务。前端至少要区分等待模型、调用工具、等待确认、重试、完成、失败和已取消，不能只用一个 loading。用户应该看得到当前在做什么，能取消长任务，也能知道失败发生在哪一步。
>
> 流式文本、结构化结果和工具事件，最好走统一事件协议，并带 task ID、step ID 和序号。前端按任务状态合并事件，断线重连后从服务端快照恢复。工具执行结果属于服务端事实，不能因为前端少收到一个数据块就自行推断成功。

### 如果对方让你继续讲

事件协议可以举例：`task_started / step_started / tool_call / awaiting_confirmation / token / step_done / task_done / task_failed / task_cancelled`，每种事件带 task ID、step ID 和递增序号。前端维护一个和后端图状态对应的状态机，收到事件就迁移状态，序号断档就触发快照拉取。传输层选 SSE 还是 WebSocket 属于实现细节，见 [实时通信](09-实时通信.md)；关键是守住一条纪律——事件只是通知，状态以服务端为准。

### 对方很可能继续问

**为什么要有事件序号？**

流式连接可能重连、重复推送或乱序到达。序号能帮助前端去重和发现缺口，但最终仍以服务端保存的任务状态为准。对于已经产生副作用的动作，UI 必须明确区分「请求已发出」和「服务端确认成功」。

**用户中途关掉页面，回来怎么恢复现场？**

重连后先拉任务快照——当前节点、已完成步骤、待确认动作、最终结果（如果已结束），把前端状态机直接对齐到快照，再用序号续订增量事件。前端永远不靠本地缓存的事件去「推算」任务进行到哪了，因为推算出来的状态可能和服务端的真实执行已经不一致。

**工具执行的中间过程要展示给用户吗？**

展示「正在做什么」，不展示原始全量。比如显示「正在查询订单系统…」加一个参数摘要，原始入参和完整返回按需展开。原因有两个：大 JSON 刷屏没有信息量，还拖慢渲染；更重要的是避免用户把中间态误读成最终结果——中间结果必须有明显的过程态标记。

### 这里容易说错

把前端状态当事实源，用「有没有收到最后一个数据块」推断任务成败；所有阶段只给一个 loading，用户既不能取消，也不知道失败发生在哪一步。

### 一句话记住

Agent 前端展示的是任务状态而不是消息流；事件带序号，以服务端状态为准。

## Q12：怎么回答“你用过哪些 Agent 框架”？

### 这题在考什么

考的不是框架名清单，而是你有没有**真实使用经历**、能否说清**框架解决了什么、哪些能力框架不负责**，以及是否懂得**控制抽象成本**。

### 面试时可以这样说

> 我在 `[真实项目或练习]` 中使用过 `[真实框架]`，主要用到的是 `[状态图/工具调用/checkpoint/工作流编排]`。选择它是因为 `[真实原因]`。业务里的鉴权、幂等、评测和监控不是框架自动解决的，我们另外做了 `[真实实现]`。它目前的限制是 `[真实限制]`；如果只是简单的两三步调用，我会直接用普通代码，减少框架带来的抽象成本。

按这个顺序说：真实场景 → 用到的核心能力 → 选择理由 → 框架不管的部分 → 已知限制 → 什么时候不用它。「框架不管的部分」和「限制」这两段最有区分度，它们最像真用过的人说的话。

### 如果对方让你继续讲

如果确实没有生产经验，不要编。直接承认没有生产经验，然后说明你理解它解决的问题，并用自己做过的状态管理、工作流或工具调用作类比——这些和框架里的 checkpoint、编排、工具注册是同一类问题。编造的框架经验，很容易在 API 细节、调试过程和失败案例的追问上被穿。

还可以主动展示对框架边界的理解：框架通常解决编排、状态和 checkpoint，但鉴权、幂等、评测、监控这些生产化能力始终要自己建——这正好接回本篇前面的内容。

### 对方很可能继续问

**不用框架，一个最小的 Agent 循环要写哪些东西？**

六样：状态对象（当前步骤和中间结果）、工具注册表（schema 加执行函数）、决策调用（把状态和工具清单交给模型，拿回下一步或工具参数）、执行与校验（schema 校验、权限、幂等）、终止条件（最大步数、预算、完成判定）、事件日志。两三百行就能跑通。能不能不查资料把这六样说出来，就是「用过框架」和「懂 Agent」的分界线。

**怎么避免被框架绑架？**

把业务核心留在自己代码里：状态结构、校验规则、幂等、审计都不依赖框架的类型和数据结构，框架只承担编排。依赖收口在一层适配器上，换框架时业务规则不动。检验标准是：删掉框架，你的鉴权和幂等代码应该一行都不用改。

### 这里容易说错

报菜名式罗列框架名，却答不出任何一处真实限制；把「看过教程、跑过 demo」说成生产经验——这两点在追问里都会暴露。

### 一句话记住

讲真实使用和真实限制，别报框架清单；没经验就讲理解，别编。

## Q13：Prompt 工程和上下文工程有什么区别？

### 这题在考什么

是否理解 **Prompt 工程只是上下文工程的一部分**；关键判断点是能否说清上下文的**分层组织**——系统规则、用户状态、历史记忆、检索证据、工具结果——以及**外部内容默认不可信**的处理原则。

### 面试时可以这样说

> Prompt 工程主要关注怎样表达任务、约束输出和提供示例。上下文工程的范围更大，它决定模型这一次到底能看到哪些系统规则、用户状态、历史记忆、检索证据和工具结果，以及这些内容如何排序、裁剪和更新。Agent 做不好，很多时候不是提示词写得不够花，而是拿到了错误、过期或互相冲突的上下文。
>
> 我的做法是分层：系统规则、业务数据、外部文档和用户输入分开处理，动态数据带上来源与版本。外部内容默认是不可信数据，不能因为文档里写了“忽略之前指令”，就改变系统权限或直接触发工具。

### 如果对方让你继续讲

分层可以再具体一点，每一层有不同的组织和更新策略：

- **系统规则**：稳定、置顶，只放角色、硬约束、输出契约，频繁变化的数据不放这里；
- **用户状态**：结构化保存任务目标和已确认信息，不靠自然语言记忆；
- **历史记忆**：摘要加按需检索，机制见前面记忆那题；
- **检索证据**：带来源和版本注入，权限在检索侧前置过滤；
- **工具结果**：裁剪摘要后注入，超大结果存引用。

裁剪时按层定优先级：结构化状态 > 当前任务必需的证据 > 摘要历史，而不是各层均匀删。信息冲突时，更新、来源更可信的内容优先，用户显式纠错可以覆盖历史记忆。上下文配得好不好，最终靠任务集评估，单次回答说明不了问题。

### 对方很可能继续问

**上下文窗口越来越大，还需要裁剪吗？**

需要。更大的窗口不代表模型能同等准确地利用所有内容，而且会增加延迟和成本。应保留完成当前步骤需要的信息，关键状态结构化保存，历史内容做摘要或按需检索，并通过评测判断裁剪是否损害任务结果。

**System Prompt 里该放什么、不该放什么？**

放每次会话都不变的东西：角色定义、硬性约束、输出格式契约、工具使用边界。不放会变化的数据（走状态注入或检索），不放长文档（稀释关键规则还烧钱）。一个简单的检验：这条内容是不是对每一轮、每一个用户都成立？成立才配进系统层，否则就下放到对应的数据层。

**怎么发现并处理上下文里的冲突信息？**

冲突的典型来源是新旧版本文档并存、用户纠错和历史记忆打架。治理要靠组装时的机制而不是靠模型自觉：内容带时间和版本元数据，同主题按「更新、更可信」排序并淘汰旧的；关键事实以结构化状态为准，自然语言历史只做补充；用户显式纠错要能覆盖对应的记忆条目。评测集里也应该放几条故意带冲突的样本，验证系统按预期处理。

### 这里容易说错

把上下文工程说成「把提示词写得更好」；外部文档内容被当成可信指令直接执行——前者低估了工程量，后者高估了模型的判断力。

### 一句话记住

Prompt 工程管“怎么说”，上下文工程管“看到什么”，外部内容默认不可信。

## Q14：多模态 Agent 的链路怎么设计？

### 这题在考什么

是否理解多模态 Agent 是**「前置校验与识别、模型理解决策、证据留存」三段式链路**，而不只是「把图片传给模型」；以及大文件的工程问题和**识别错误不能直接触发副作用**的兜底设计。

### 面试时可以这样说

> 多模态 Agent 不只是把图片和文字一起传给模型。前面通常要做文件类型、大小和权限校验，再根据场景完成 OCR、版面分析、音视频转写或关键帧抽取。模型基于这些内容做理解和决策，必要时调用搜索、知识库或业务工具。最终结果需要保留原文件和证据位置，方便用户核对。
>
> 工程上要特别关注大文件带来的上传、切分、超时和成本，也要处理识别错误。比如 OCR 得到的金额不能直接触发付款，仍要让用户确认或用确定性规则复核。前端则要展示处理进度、失败文件和可定位到原文的引用。

### 如果对方让你继续讲

三段各自再拆开：

- **进站与识别**：类型、大小、权限校验在前；大文件走分片上传和异步任务，进度事件推给前端（对应前面 Agent 前端那题的事件协议）；识别按文件类型分流——文档走 OCR 加版面分析，音频走转写，视频抽关键帧；
- **理解决策**：识别产物作为证据进入模型上下文，决策和工具调用与文本 Agent 同构，只是证据多了一层「识别置信度」；
- **证据留存**：原文件、识别文本、坐标或时间戳一起存，答案里的引用能回跳到原图原句——这是多模态结果可信度的关键。

### 对方很可能继续问

**什么时候用专门模型，什么时候用通用多模态模型？**

高频且边界清楚的任务，例如 OCR、语音识别，可以先用专门模型获得稳定结构化结果，再交给通用模型理解；开放式图片问答可以直接使用多模态模型。最终还是看真实任务集中的准确率、延迟、成本和部署要求，不能只比较一次演示效果。

**多模态内容怎么进 RAG？**

文档类先解析成带结构的文本——保留标题层级、表格、页码这些定位信息再入库；图表这类纯视觉内容，通常先用多模态模型生成文字描述，让描述文本参与检索。要如实说局限：靠描述参与检索，纯视觉细节的召回精度有限；命中后的引用必须能定位回原图原页，让用户自己核对。

**识别结果不可靠时怎么兜底？**

三层：关键字段（金额、日期、账号）用确定性规则复核——格式、范围、校验位；置信度低的区域降级为人工确认，或把原文对照摆出来让用户修改；所有识别结果一律按「草稿」对待，不允许直接触发写操作。兜底原则和整篇一致：识别只是模型的判断，副作用要过业务代码和用户确认。

### 这里容易说错

把「前端支持传图」当成多模态架构——校验、识别、证据留存三层都没了；让识别结果（比如 OCR 出的金额）直接触发业务动作。

### 一句话记住

多模态链路等于前置校验与识别、模型理解决策、证据留存；识别结果不能直接触发副作用。
