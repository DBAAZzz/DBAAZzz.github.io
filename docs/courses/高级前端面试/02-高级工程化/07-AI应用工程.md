# AI 应用与 Agent 工程

## Q1：一个 AI 应用的核心链路是什么？

### 这题在考什么

是否把 AI 应用当成完整系统来设计，而不是只会调一次模型 API；有没有把模型当作不稳定依赖，提前在关键动作上做校验和兜底。

### 面试时可以这样说

> 我先说结论：一个能用的 AI 应用，不只是调一次模型 API 那么简单。你把它拆开看，完整链路是这么几段——先做输入和权限，再构建上下文，然后才是模型调用、工具执行、流式输出、结构化校验，最后是观测评估和安全兜底。设计的时候有一条心法：把模型当成不稳定的依赖。它的输出可能出错、可能超时、可能格式损坏，也可能一次调用就花掉很多钱。所以关键动作上，必须有 schema 校验、权限确认、幂等和可追踪日志。

### 一句话记住

把模型当不稳定依赖：关键动作必须有校验、确认、幂等和日志。

## Q2：MCP 解决什么问题？

### 这题在考什么

是否理解 MCP 只是统一接入协议、解决的是重复适配成本，而不是安全方案；生产环境还缺哪些环节，要能自己补出来。

### 面试时可以这样说

> MCP 我先给它一个定位：它是 AI 客户端和外部能力之间的一套统一协议。服务端通过它把工具、资源和提示这些能力暴露出来，客户端负责发现，然后去调用。它的价值在哪？以前每个模型应用都要单独适配一堆数据源和工具，现在一套协议就能接上，重复适配的成本降下来了。但我要强调一句：它不自动解决权限、安全和业务语义。到了生产环境，身份认证、参数校验、最小权限、审计，还有高风险动作的确认，这些一样都不能少。

### 对方很可能继续问

- Tool、Resource、Prompt 三者有什么区别？
- 本地传输和远程传输怎么选？
- 如何防止工具调用越权？

### 一句话记住

MCP 统一接入协议、降低适配成本，但不负责权限和安全。

## Q3：Agent 和普通聊天应用有什么区别？

### 这题在考什么

是否理解 Agent 的本质是多步决策循环，而不是一个新名词；难点在状态、工具契约、停止条件、成本预算这些工程环节，以及有没有确定性优先的判断。

### 面试时可以这样说

> 最直观的区别是：普通聊天是一轮输入、一轮输出，模型答完就结束了。Agent 不一样，它围绕一个目标做多步决策——调用工具、观察结果，再决定下一步，一直执行到完成、失败，或者撞到限制为止。这里我要提醒一句：工程上的难点从来不在这个循环本身，而在循环外面那一圈——状态怎么管理、工具契约怎么定、停止条件是什么、成本预算多少、中途断了怎么恢复、副作用怎么控制。最后再加一个判断：能用确定性工作流解决的问题，就别硬塞给开放式 Agent 去决策。

### 一句话记住

Agent 是多步决策循环，难点在循环之外的状态、契约、停止条件和成本控制。

## Q4：如何处理流式结构化输出？

### 这题在考什么

是否理解流式 JSON 在完成前天然不完整、不能边收边 parse；有没有一套增量解析、UI 安全和最终校验的完整处理思路。

### 面试时可以这样说

> 先说一个容易踩的坑：流式传输的时候，JSON 在完成之前天然就是不完整的。所以不能每收到一段就调一次 `JSON.parse`，那样肯定出问题。正确做法分两步：要么用一个支持增量状态的解析器，要么让 SDK 按 schema 生成部分对象；UI 这边只渲染已经安全解析出来的字段。等流真正结束了，再做一次完整的 schema 校验。另外还有一堆边角情况要兜住：字符串截断、转义没闭合、数组还没结束、模型中途改写前文，还有连接直接断掉。

### 对方很可能继续问

- 如何判断一个对象已经完整？
- Zod 是只做 TypeScript 类型吗？
- 连接中断后，已经收到的部分结果怎么处理？

### 一句话记住

流式 JSON 完成前不完整：增量解析、只渲染安全字段、结束时再做完整校验。

## Q5：如何让模型有效使用上下文？

### 这题在考什么

是否理解上下文管理的核心是相关性、来源和排序，而不是堆文本；以及上下文效果要用任务集评估，不能凭一次回答下结论。

### 面试时可以这样说

> 先破一个误区：让模型用好上下文，不是把更多文本塞进去。真正要做的是三件事——只给完成当前任务必需的信息，每条信息来源要明确，排序要合理。具体怎么操作？长内容先进检索、先分段，同时保留引用来源；系统规则、任务数据和用户输入要分层放，别搅在一起；过期信息要设置版本。最后强调一句：上下文配得怎么样，要用任务集来评估，不能拿一次回答的好坏下结论。

### 一句话记住

上下文只给任务必需、来源明确、排序合理的信息，效果靠任务集评估。

## Q6：如何评估 AI 应用质量？

### 这题在考什么

是否理解评估要先拆成可验证维度、再建回归集，然后按确定性断言和人工或模型评审两条路走；以及每次变更都要回归。

### 面试时可以这样说

> 评估的第一步，是把任务拆成可以验证的维度。比如事实正确率、工具选择对不对、参数正确率、完成率，再加上延迟、成本和安全违规。第二步，建一个小型回归集，样本要覆盖三种：正常样本、边界样本、对抗样本。第三步，分两条路去判：能靠程序判断的，用确定性断言；开放式的回答，用人工标注，或者用做过校准的模型评审。最后定一条规矩：模型、提示、工具、检索，哪一样变了，都要把回归跑一遍；线上失败的样本也要留下来。

### 一句话记住

评估先拆维度、再建回归集：能断言的用断言，开放的用评审，每次变更都回归。

## Q7：如何控制 AI 应用的安全风险？

### 这题在考什么

是否把模型输出当成不可信输入来设计，有没有覆盖执行、校验、鉴权、注入、确认、机密和成本这些环节的完整防线。

### 面试时可以这样说

> 这道题我给一个总原则：模型可能出错，所以安全控制要一层一层兜住。第一，模型输出永远不能直接当命令执行。第二，工具参数用 schema 严格校验。第三，用户身份和工具权限，在服务端重新判断一次，别信前端的说法。第四，外部文档一律当成不可信数据，防止提示注入。第五，高风险的写操作要用户确认，并且提供幂等和回滚。第六，机密信息进入模型上下文，做到最小化。第七，对调用次数、耗时和费用，设硬限制。

### 一句话记住

把模型输出当不可信输入：执行、校验、鉴权、注入、确认、机密、成本，逐层设防。

## Q8：什么是 Skill，如何与工具区分？

### 这题在考什么

是否理解 Skill 是任务说明和流程约束、Tool 是实际执行能力，以及 Skill 本身不直接等于外部权限。

### 面试时可以这样说

> 一句话先把两边分开：Skill 是说明，Tool 是能力。Skill 针对某一类任务，给出工作说明和流程约束，告诉 Agent 步骤怎么组织、用哪些资源、要达到什么质量标准；Tool 不一样，它是真正能读数据、能执行动作的那只手。注意一个点：Skill 本身通常不等于外部执行权限，真要动手，还是得通过工具。所以设计 Skill 的时候，触发条件、输入输出、失败处理和安全边界，都要提前定清楚。

### 一句话记住

Skill 是任务说明和流程约束，Tool 是执行能力；Skill 不直接等于外部权限。

## 常见追问的参考答法

### 模型已经支持 JSON 模式，为什么还要校验？

JSON 格式正确，只说明语法上能解析，不代表字段符合业务规则。模型可能返回一个不存在的用户 ID、一个越权的操作，或者一个超出范围的金额。所以结构化输出之后，仍要做 schema、权限和业务约束校验；高风险动作还要用户确认。

### RAG 检索到文档后，为什么回答仍然错？

原因可能出在链路的任何一段：分块把上下文切断了、召回没有命中、排序把关键段落排到了后面，也可能模型本身没有正确使用证据。排查时把链路拆开评估——先测检索召回，再测拿到正确上下文之后的回答质量。不能把所有问题都归到模型能力上。

### Agent 什么情况下应该停？

除了任务完成，还要设这些停止条件：最大步骤数、总时间、费用上限、重复调用检测和不可恢复错误。连续几次得到相同失败结果的时候，继续调用通常只是在烧成本。这时应该返回清楚的失败原因，或者请用户补充信息。

### 工具调用如何防止重复执行？

模型可能重试，也可能重复提出同一个动作，所以防重是关键。写操作要带幂等键，服务端保存执行结果；工具返回里明确标记已经完成。付款、发消息、删数据这类动作，还要用户确认和审计，不能只凭模型的自然语言说一句“应该执行”就动手。

## 一个更完整的 AI 项目回答

> 我们先把任务拆成两部分：确定性流程和模型判断。权限、数据读取和写入由代码控制；模型负责从有限的候选中做选择，并生成说明。输出先通过 schema 校验，才能进入下一步；写操作再由服务端鉴权一次。上线前用固定的任务集比较完成率、参数正确率、延迟和成本，线上失败样本脱敏之后回到评估集。

这段话能体现你在做系统，而不是只会调一个模型接口。
