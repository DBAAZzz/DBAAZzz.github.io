# 实时通信

## Q1：WebSocket、SSE、轮询怎么选？

### 这题在考什么

能否按“通信方向、更新频率、基础设施”**给出选择理由**，并意识到选型不只是协议本身，还牵连代理、认证、补偿、规模和降级。

### 面试时可以这样说

> 三个方案，先按方向分。WebSocket：客户端和服务端之间的双向长连接，聊天、协作、高频双向消息用它。SSE：基于 HTTP，服务端往客户端单向推文本事件，浏览器原生支持重连，日志、通知、进度这些场景合适。轮询：最简单，低频更新或者基础设施受限的时候用。但选型不能只看协议本身，代理、认证、消息补偿、连接规模、降级，这些要一起考虑。

### 如果对方让你继续讲

协议本质各一句话：WebSocket 是独立协议，先发一个带 Upgrade 头的 HTTP 请求，拿到 101 之后切换协议；SSE 就是普通 HTTP 响应，`Content-Type: text/event-stream`，服务端一直不写完响应体；轮询是反复发短请求。降级链路也可以提：优先长连接，连不上退 SSE，再退轮询，很多推送系统就是这么分层的。

### 对方很可能继续问

**SSE 为什么不一定比 WebSocket 简单？**

浏览器接收端确实简单，但认证、连接数、多实例路由、消息保留、断线补偿这些仍然要设计。EventSource 不方便设置任意请求头；使用 Cookie 时要处理跨域和会话，使用 URL Token 又有日志泄漏风险。

**WebSocket 和长轮询的本质区别是什么？**

长轮询还是一个个 HTTP 请求：服务端有消息才返回，客户端收到后立刻再发起新请求挂住，实时性靠挂起连接实现，每次都有完整 HTTP 头开销，服务端要维护大量挂起请求。WebSocket 一次握手升级后双向复用一条 TCP，帧开销小，双向都能主动发。定性区别是“协议升级”和“反复短请求”。

**网关和 Nginx 对这些方案有什么影响？**

长连接要调代理读超时、关掉响应缓冲（比如 `proxy_buffering off`）；HTTP/1.1 下浏览器同域名连接数上限会挤占 SSE；WebSocket 需要 Upgrade/Connection 头透传，部分老代理不支持。这些没配好，典型表现就是“本地一切正常，线上频繁掉线”。

**什么信号说明该从轮询升级到 SSE 或 WebSocket？**

轮询频率和延迟要求开始冲突——要秒级实时，但轮询间隔压不下来；或者服务端 QPS 被大量空轮询吃掉。升级前同时评估团队对长连接运维的储备：重连、监控、扩容、多实例广播，这些成本比换协议本身高。

### 一句话记住

WebSocket 双向长连接、SSE 单向推送、轮询最简单；代理、认证、补偿、连接规模和降级要一起算。

## Q2：WebSocket 项目常见坑有哪些？

### 这题在考什么

是否**真的在生产环境维护过长连接**，能把重连、心跳、消息可靠性、状态恢复、多实例、权限和发送上限这些具体坑一条条讲出来。

### 面试时可以这样说

> 我按七个点说，都是实际会踩的。第一，断线重连要用指数退避，不然服务一恢复，容易出现连接风暴。第二，用心跳检测半开连接，但间隔不能过于频繁。第三，消息要有序号、确认或者幂等 ID，把“已发送”和“已处理”区分开。第四，页面切后台、网络切换之后，要能恢复状态。第五，服务端多实例时，用共享消息层或者一致路由。第六，Token 刷新、权限变更、连接关闭，要有明确的协议。第七，发送队列设上限，避免慢消费者耗尽内存。

### 如果对方让你继续讲

七条里最能体现深度的是第三条和第七条：可靠性不靠“连接没断”，靠序号加确认；背压不靠 TCP 自愈，靠发送队列上限——socket 的 `bufferedAmount` 持续增长说明消费端跟不上了，要么断开重置，要么降级成让客户端拉快照。

### 对方很可能继续问

**WebSocket 鉴权怎么做？连接期间 Token 过期怎么办？**

建连时浏览器 WS API 不能自定义请求头，常见做法是走 Cookie，或者把 Token 放查询参数、再在首帧消息里二次校验；查询参数要注意访问日志泄漏。连接期间的过期要有协议：服务端下发“要求重新认证”事件，客户端刷新凭证后重连；权限变更、账号踢出也要能通过这条通道即时生效，不能等自然断线。

**服务端多实例怎么广播消息？**

用户的连接只落在其中一个实例上：实例内直接推，跨实例靠共享消息层——Redis pub/sub 或消息队列扇出到所有实例，各自推给本地连接；或者按用户 ID 做一致性路由。实例发布或崩溃会造成批量重连，客户端必须带抖动，否则就是连接风暴。

**慢消费者怎么处理？**

每个连接维护发送队列并设上限：消费跟不上先丢弃可合并的通知，还不行就断开，让客户端重连后拉快照。判断依据是 `bufferedAmount` 或队列长度，不能无限堆积把服务端内存打爆。

**半开连接是什么？**

对端或中间网络已经断了，但本端没收到 FIN，连接看起来还活着，写操作可能长时间不报错。TCP 层发现不了，只能靠应用层心跳超时主动判死。

### 一句话记住

重连退避、心跳、消息确认、状态恢复、多实例、权限协议、发送上限，都要提前设计。

## Q3：心跳和断线重连怎么设计？

### 这题在考什么

是否分清**检测半开连接**和**恢复连接**是两件事；有没有指数退避、抖动、重试上限这些真实生产细节，而不是“onclose 里 reconnect 一下”。

### 面试时可以这样说

> 我分两半说。心跳解决“发现断了”：客户端定时发心跳消息，服务端回执，比如 30 秒一轮，连续两轮没有回执就判定连接已死，主动关闭进入重连。间隔要权衡——太密浪费流量和电量，太疏半开连接挂太久。重连解决“接回去”：指数退避加随机抖动，1 秒起步、翻倍增长、封顶比如 30 秒，避免服务端恢复的瞬间所有客户端一起涌入，造成二次连接风暴。同时设重试上限，超限后把 UI 明确置成“连接已断开，点击重试”，而不是无限静默重试。还有两个细节：页面切后台可以放宽心跳频率，回前台立刻补一次检测；发消息前先检查 socket 状态，别往死连接里写。

### 如果对方让你继续讲

为什么应用层心跳不能省：NAT 表项过期、代理静默丢弃这类半开状态，TCP 层发现不了。另一个细节是浏览器端的 WebSocket 协议级 ping/pong 帧由浏览器自动应答，JS 拿不到事件，所以浏览器里通常用自定义心跳消息（比如 `{"type":"ping"}`）实现，服务端顺带用它测 RTT 和判活。

### 对方很可能继续问

**心跳间隔怎么定？**

常见落点是 25 到 60 秒：要小于链路上最激进的 NAT 或代理空闲超时，否则连接会被中间设备静默回收；又不能密到流量和电量不可接受。服务端按两倍间隔没收到心跳就判死。移动端可以在后台动态放宽、回前台恢复正常。

**为什么重连要指数退避还要加抖动？**

固定间隔会让所有失败的客户端按同一节奏重试，服务端一恢复就被洪峰再次打挂。指数退避把无效尝试的间隔越拉越长，抖动把同时重连的客户端在时间上打散，两者配合才能避免“重连风暴”这个经典事故。

**TCP keepalive 不就行了吗？**

不够。keepalive 默认间隔是小时级，等它发现问题早就过了几分钟；而且它只能证明传输层通，不能证明应用进程正常、代理还在转发、认证还有效。应用层心跳还能顺带携带时间戳，用于算 RTT 和校准。

**重连成功之后要做什么？**

重建 socket 只是第一步：还要恢复订阅、用上次确认的序号补发缺失消息，必要时拉快照重建状态；UI 上把“已断开”的状态清掉，让用户知道重新在线了。

### 这里容易说错

把 `onclose` 当唯一断线信号——半开连接不触发它；把“重连成功”当成“状态恢复”——漏掉的消息不会自己回来。

### 一句话记住

心跳发现半开连接，退避加抖动重连，超限之后把选择权交还用户。

## Q4：SSE 自动重连是否等于消息不丢？

### 这题在考什么

是否分清**“连接恢复”和“消息不丢”是两件事**，能不能说出补发断线期间消息需要的条件。

### 面试时可以这样说

> 不等于，这两件事要分开看。EventSource 自动重连，只是把连接重新建立起来；服务端还能用 retry 提示客户端重连间隔。断线期间的消息要补回来，得满足几个条件：服务端给事件设置 ID，保存可重放窗口，客户端重连时带上 Last-Event-ID，服务端按它补发。如果没有持久化和补发逻辑，重连后只能保证继续接收新消息，漏掉的消息不会自动补上。

### 如果对方让你继续讲

机制再补一句：服务端每个事件写一行 `id:`，浏览器记下最后收到的事件 ID；断线自动重连时，请求头会自动带上 `Last-Event-ID`；`retry:` 字段则告诉浏览器下次重连等多久。协议给了“从哪续传”的钩子，但“存不存、补不补”完全是服务端自己的事。

### 对方很可能继续问

**Last-Event-ID 具体怎么工作？**

服务端给每个事件标 ID，客户端断线重连时浏览器自动在请求头带上最后收到的 ID，服务端找出 ID 更大的事件补发。注意它的语义是“最后收到”不是“确认处理”，服务端并不知道客户端是否真的处理过，应用层的可靠性协议要自己再加。

**可重放窗口指什么？**

服务端把近期事件按 ID 存进内存、Redis 或磁盘，保留一段时间或固定条数；重连时窗口内的能补，超出窗口的补不了，只能退化为发快照或提示刷新。窗口大小是丢失风险和服务端成本的折中。

**客户端怎么知道自己漏了消息？**

事件 ID 有序的话，新到的 ID 出现跳号就说明有缺口，可以立刻按最后 ID 请求补发，或触发全量刷新；纯通知类、无序的消息做不到缺口检测，只能接受个别丢失，再用未读数这类聚合字段兜底校准。

### 这里容易说错

把自动重连当成消息不丢。自动重连解决的是连接层面；补发要靠事件 ID、可重放窗口和 Last-Event-ID，缺了这些，重连后只能保证继续接收新消息。

### 一句话记住

自动重连只保证连接恢复，不保证消息不丢；补发靠事件 ID 和 Last-Event-ID。

## Q5：消息可靠性和去重怎么做？

### 这题在考什么

是否区分**已发送、已送达、已处理**三个状态；有没有序号、ACK、幂等去重、快照兜底这套组合，而不是把可靠性寄托在“连接没断”上。

### 面试时可以这样说

> 我的原则是：长连接只负责快，可靠性靠协议补。第一，消息带会话内递增序号，客户端记录已确认位置，收到消息回 ACK，服务端没收到 ACK 的，重连后补发。第二，去重靠幂等：重连后客户端可能收到重复消息，用消息 ID 或序号去重，已处理过的直接丢弃；写操作用幂等键，服务端保证同一个键只执行一次。第三，差距太大就别逐条补了，直接下发快照，再从快照版本继续增量。总结一句：已发送不等于已送达，已送达不等于已处理，三者在协议里要分开表达。

### 如果对方让你继续讲

可以类比 TCP：序号加确认加重传，本来就是传输层验证过的可靠性模型，应用层把它照搬进消息协议。业务侧再加一条保险：关键状态（未读数、余额、库存）以服务端为准，定期拉快照校准，即使长连接漏了消息也不会越错越远。

### 对方很可能继续问

**WebSocket 重连后如何恢复？**

客户端重连时带上上次确认的序号，或者当前文档版本，服务端据此补发缺失消息；如果差距太大，就下发完整快照，再继续增量。注意，重新建立 socket，不代表业务状态已经恢复。

**客户端收到重复消息怎么去重？**

客户端维护一个已处理的序号游标，或最近 N 条消息 ID 的集合，重复的直接丢弃。更稳的是让处理逻辑本身幂等——就算去重集合失效（换设备、清缓存），同一条消息执行两遍也不产生额外副作用。

**ACK 协议怎么设计才不会拖垮连接？**

逐条 ACK 流量大，改成累计确认：用“已处理到序号 N”代替逐条回复，ACK 还可以搭在心跳消息上顺带携带。服务端只对写操作这类关键消息等 ACK，普通通知靠序号缺口检测触发补发。

**消息顺序怎么保证？**

单条连接内 TCP 本身有序，乱序出在多连接、多实例、多生产者：按会话或实体 ID 分区路由到同一条处理链路，或统一由服务端定序后再投递，客户端按服务端序号排序展示，不能拿各自的本地时间排。

### 一句话记住

长连接只负责快，可靠性靠序号、ACK、幂等和快照兜底。

2. 设计 WebSocket 重连后的状态恢复流程。
