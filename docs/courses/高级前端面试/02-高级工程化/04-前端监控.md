# 前端监控系统

## Q1：如何设计一个前端监控系统？

### 这题在考什么

是否能把监控系统拆成一条从采集到告警的完整闭环，并把上报、聚合、还原、告警这些环节串起来，而不是只罗列采集点；同时要意识到监控 SDK 自身不能影响业务。

### 面试时可以这样说

> 我会把整条链路拆开讲：采集、加工、上报、接收、存储分析，再到告警，是一个闭环。先说采集：SDK 采错误、性能、请求和用户行为，并且统一补充应用、版本、页面、会话和环境信息。接着是上报层，负责批量、采样、重试和限流。数据到服务端之后，做清洗、聚合、Source Map 还原和去重。最后按影响用户数、版本和业务等级告警，还要能关联发布、支持快速回滚。别忘了监控 SDK 自身必须轻量、可降级，不能影响业务。

### 如果对方让你继续讲

再往下讲，要覆盖这些失败路径：

- SDK 初始化失败不能阻塞应用；
- 上报接口失败不能无限重试；
- 监控服务异常不能反过来拖垮业务；
- Source Map 必须和版本严格对应；
- 告警要聚合降噪，避免同一错误风暴；
- 敏感信息在端侧和服务端都要脱敏。

### 一句话记住

一条闭环：采集、上报、聚合还原、告警；SDK 自身轻量、可降级、不影响业务。

## Q2：不同错误如何采集？

### 这题在考什么

是否分得清不同错误各自的采集入口——同步错误、Promise 拒绝、资源错误、框架错误、请求错误各有监听方式，边界不能混。

### 面试时可以这样说

> 我按错误类型分开说。同步运行错误，通过全局 `error` 事件或者 `window.onerror` 获取；未处理的 Promise 拒绝，用 `unhandledrejection`；静态资源错误，需要在捕获阶段监听 `error`，并通过事件目标来区分；框架错误，接入 React Error Boundary 或 Vue errorHandler；请求错误，通过统一请求层或者网络 API 包装来采集。另外跨域脚本、异步边界，以及被业务 catch 后吞掉的错误，都需要单独处理。

### 这里容易说错

`try/catch` 不能跨异步回调捕获未来抛出的错误，但可以捕获 `await` 到的 Promise 拒绝。资源错误不冒泡，监听时要使用捕获阶段。

### 一句话记住

五类错误各有入口：`error`/`window.onerror`、`unhandledrejection`、捕获阶段 `error`、Error Boundary/errorHandler、统一请求层；异步和 catch 吞掉的单独处理。

## Q3：Source Map 如何安全管理？

### 这题在考什么

是否理解 Source Map 的管理不止是“不上传公网”，还要版本严格对应、控制访问权限和保留周期，两头都不能丢。

### 面试时可以这样说

> 先说原则：构建时生成完整的 Source Map，但不在公开产物中引用它。上传走 CI，用应用名、版本和文件路径作为索引，传到受控存储里，确认成功之后再发布对应代码。错误事件携带同一版本标识，解析服务根据压缩文件的位置和行列号找到 Source Map。还要设置访问权限、保留周期和发布删除策略。这样既能避免源码暴露，也能避免版本对不上，导致错误定位错。

### 一句话记住

Source Map 按应用名、版本、路径索引上传受控存储，发布前确认、限制访问，保证源码不暴露、版本对得上。

## Q4：弱网下如何提高上报成功率？

### 这题在考什么

是否理解弱网上报要串成一条链：内存队列、卸载发送、离线补发、幂等去重，同时有资源上限意识。

### 面试时可以这样说

> 我分三层说。第一层，页面还在的时候，先用内存队列，再批量发送；离开页面时，优先用 `sendBeacon`，必要时用 `fetch` 的 keepalive。第二层，失败的事件可以有限重试，使用指数退避；重要事件暂存 IndexedDB，网络恢复后再补发。第三层，所有事件要有唯一 ID，服务端做幂等去重，并且设置队列上限和过期时间。底线是不能为了保证上报，反而耗尽用户的存储和网络。

### 对方很可能继续问

- `sendBeacon` 是否一定成功？
- 离线队列如何避免重复上报？
- 错误风暴时如何保护服务端？

### 一句话记住

内存队列批量发，卸载走 `sendBeacon` 或 `fetch` keepalive，重要事件落 IndexedDB 补发，唯一 ID 加服务端幂等。

## Q5：白屏如何检测？

### 这题在考什么

是否理解白屏判断要组合多个信号并治理误报，而不是靠单一 API 或单一条件下结论。

### 面试时可以这样说

> 先说结论：白屏不是一个单一信号，我会把路由就绪、根节点内容、关键元素和视口采样组合起来判断。常见做法是设置一个合理超时，然后用 `elementFromPoint` 对视口里的多个点采样，看命中的元素是不是仍然只有 `html`、`body` 或空挂载容器，再结合页面错误和资源失败来降低误报。注意 `MutationObserver` 更适合观察变化，不适合作为唯一的白屏结论。另外，不同页面要允许配置各自的关键元素和等待时间。

### 对方很可能继续问

- 骨架屏会不会造成误判？
- 长列表空状态是不是白屏？
- 如何衡量检测准确率？

### 一句话记住

白屏靠组合信号：路由就绪、根节点、关键元素加视口采样，再结合页面错误和资源失败降误报。

## Q6：采样率应该按用户还是按事件？

### 这题在考什么

是否理解按用户和按事件采样分别服务什么分析目标，以及采样必须记录权重才能还原估计。

### 面试时可以这样说

> 这取决于分析目标。性能分布，通常按会话或者用户稳定采样，保证同一个会话的链路完整；高频成功请求，可以按事件随机采样，把量级降下来；错误和关键业务失败，一般全量采，或者用更高采样率。有一点必须做：采样要在事件中记录权重或者采样率，分析时才能还原估计。服务端还要支持动态采样，用来应对错误风暴。

### 这里容易说错

不能把 `rate = 10` 说成“采样率 10%”却又用 `Math.random() < 1/rate` 而不解释口径。配置名称应明确使用 `sampleRate = 0.1` 或 `sampleEvery = 10`。

### 一句话记住

按会话或用户采样保链路，按事件采样降量级，错误全量或高采样，事件必须带权重。

## Q7：如何采集性能数据？

### 这题在考什么

是否知道性能条目从哪里采、SPA 场景要补什么，并且理解聚合要看分位数而不是平均值。

### 面试时可以这样说

> 采集走 Performance Timeline 和 `PerformanceObserver`，采 navigation、resource、paint、longtask，还有 Web Vitals 相关的条目。光采这些不够，还要补充路由、设备、网络、版本和页面状态这些上下文。如果是 SPA，还要定义软导航的起点和业务可用点。端侧只做必要的计算，服务端按页面和版本聚合 P75/P95，避免只看平均值。

### 一句话记住

`PerformanceObserver` 采 navigation、resource、paint、longtask 和 Web Vitals，SPA 补软导航起点，聚合看 P75/P95。

## Q8：监控 SDK 如何做到低侵入？

### 这题在考什么

是否理解低侵入要落在结构拆分、异常隔离、资源预算和兼容原生 API 这些具体动作上，而不是只喊“不打扰业务”。

### 面试时可以这样说

> 我从几个层面来做。先拆结构：核心包和可选插件分开。初始化走异步，异常全部隔离。资源上，包体积、CPU、内存和请求量都设预算。包装原生 API 时，`this`、参数、返回值和属性都要保持。功能上支持关闭、降级和远程配置，数据脱敏默认开启。最后用 SDK 自监控观察丢弃量和上报失败，但要注意防止递归上报。

### 一句话记住

低侵入靠：插件拆分、异步初始化、异常隔离、资源预算、包装保 `this` 和参数、脱敏默认开启。

## 常见追问的参考答法

### `window.onerror` 和 `error` 事件为什么都有人用？

`window.onerror` 能拿到运行时错误的 message、文件、行列和 Error 对象。捕获阶段的 `error` 事件，还能处理图片、脚本和样式等资源加载失败。接入时要通过 `event.target` 区分资源元素和 window，不要把同一个运行时错误重复上报两次。

### 业务已经 catch 了错误，监控还能收到吗？

如果业务 catch 之后既不重新抛出、也不主动上报，全局监控通常看不到。SDK 可以提供显式的 capture API，关键边界在完成用户提示或降级之后主动上报。不能为了监控，强行把所有已处理错误重新抛出，那可能改变业务行为。

### `sendBeacon` 会保证送达吗？

不会。它只是让浏览器更适合在页面卸载阶段安排小量数据发送，并不提供业务级的送达确认。关键事件仍然需要本地队列、事件 ID、服务端幂等和有限补发；同时设置存储上限，避免坏网络下无限积压。

### 错误指纹怎么做？

可以用错误类型、归一化消息、还原后的顶层堆栈和业务标签组成指纹。URL、数字 ID 这类动态内容要做归一化，否则同一个错误会被拆成无数条；但也不能只按 message 合并，否则不同代码位置的错误会混在一起。

## 一个更完整的系统回答

> 我们先解决一条最短闭环：发布后出了什么问题、影响多少用户、能不能定位到源码。第一版只采运行错误、资源错误和关键请求，事件带应用、版本、页面和会话。SDK 批量发送，服务端按指纹聚合，并关联 Source Map。白屏和行为回放放到后续，因为误报治理、隐私和成本更高。这样做的取舍是能力不全，但能更快验证整条链路。

这比一次性宣称要采集所有数据，更符合真实系统的建设路径。
