# 前端监控系统

## Q1：如何设计一个前端监控系统？

### 这题在考什么

是否能把监控系统拆成一条**从采集到告警的完整闭环**，把上报、聚合、还原、告警这些环节串起来，而不是只罗列采集点；同时有没有意识到**监控 SDK 自身不能影响业务**。

### 面试时可以这样说

> 我会把整条链路拆开讲：采集、加工、上报、接收、存储分析，再到告警，是一个闭环。先说采集：SDK 采错误、性能、请求和用户行为，并且统一补充应用、版本、页面、会话和环境信息。接着是上报层，负责批量、采样、重试和限流。数据到服务端之后，做清洗、聚合、Source Map 还原和去重。最后按影响用户数、版本和业务等级告警，还要能关联发布、支持快速回滚。别忘了监控 SDK 自身必须轻量、可降级，不能影响业务。

建议先画闭环再顺着链路讲，比一次性罗列二十个采集点更清楚；"SDK 不能影响业务"这句要主动说，是高级岗的加分判断。

### 如果对方让你继续讲

再往下讲，要覆盖这些失败路径：

- SDK 初始化失败不能阻塞应用；
- 上报接口失败不能无限重试；
- 监控服务异常不能反过来拖垮业务；
- Source Map 必须和版本严格对应；
- 告警要聚合降噪，避免同一错误风暴；
- 敏感信息在端侧和服务端都要脱敏。

如果对方问"这个系统你会怎么一步步建"，给出版本规划：第一版只打通一条最短闭环，白屏和行为回放这类误报治理、隐私、成本都更高的能力放后续。

### 对方很可能继续问

**监控系统第一版应该先做什么？**

先解决一条最短闭环：发布后出了什么问题、影响多少用户、能不能定位到源码。第一版只采运行错误、资源错误和关键请求，事件统一带应用、版本、页面和会话；SDK 批量发送，服务端按指纹聚合，并关联 Source Map。白屏和行为回放放到二期，因为误报治理、隐私和成本更高。这个取舍让链路更快跑通、更快被业务信任，比一次性宣称采集所有数据更符合真实系统的建设路径。

**SDK 自身挂了，怎么保证不影响业务？**

初始化走异步，SDK 内部异常全部隔离，绝不把错误抛到业务层；再配自监控观察丢弃量和上报失败，但自监控数据要打来源标记、走独立通道，防止递归上报。最后留远程开关，SDK 出问题可以一键关闭采集或某个插件，不用发版止血。

**告警怎么设计才不会被人忽略？**

按影响用户数、版本和业务等级分级，同一指纹聚合降噪，错误风暴只发一条升级通知；告警消息必须能关联发布和 Source Map，收到的人第一眼就知道"哪个版本、影响谁、去哪看"。没有分级和降噪的告警群，很快会被全员静音，监控系统也就失效了。

### 一句话记住

一条闭环：采集、上报、聚合还原、告警；SDK 自身轻量、可降级、不影响业务。

## Q2：不同错误如何采集？

### 这题在考什么

是否分得清不同错误**各自的采集入口**——同步错误、Promise 拒绝、资源错误、框架错误、请求错误各有监听方式，**边界不能混**。

### 面试时可以这样说

> 我按错误类型分开说。同步运行错误，通过全局 `error` 事件或者 `window.onerror` 获取；未处理的 Promise 拒绝，用 `unhandledrejection`；静态资源错误，需要在捕获阶段监听 `error`，并通过事件目标来区分；框架错误，接入 React Error Boundary 或 Vue errorHandler；请求错误，通过统一请求层或者网络 API 包装来采集。另外跨域脚本、异步边界，以及被业务 catch 后吞掉的错误，都需要单独处理。

说完入口，主动补一句这套入口"覆盖不到的地方"——被 catch 吞掉的错误、跨域脚本。主动说边界，比被追问出来更好看。

### 对方很可能继续问

**`window.onerror` 和 `error` 事件为什么都有人用？**

`window.onerror` 能拿到运行时错误的 message、文件、行列和 Error 对象。捕获阶段的 `error` 事件，还能处理图片、脚本和样式等资源加载失败。接入时要通过 `event.target` 区分资源元素和 window，不要把同一个运行时错误重复上报两次。

**业务已经 catch 了错误，监控还能收到吗？**

如果业务 catch 之后既不重新抛出、也不主动上报，全局监控通常看不到。SDK 可以提供显式的 capture API，关键边界在完成用户提示或降级之后主动上报。不能为了监控，强行把所有已处理错误重新抛出，那可能改变业务行为。

**跨域脚本报错只有 `Script error.` 怎么办？**

浏览器对跨域脚本做了脱敏，JS 拿不到具体错误。解法是给 script 标签加 `crossorigin="anonymous"`，同时静态资源服务返回对应的 CORS 响应头，浏览器才会放行完整错误信息。第三方脚本改不了的场合，退一步按脚本 URL 维度聚合上报，至少能定位到是哪个外部脚本在出错。

### 这里容易说错

`try/catch` 不能跨异步回调捕获未来抛出的错误，但可以捕获 `await` 到的 Promise 拒绝。资源错误不冒泡，监听时要使用捕获阶段。

### 一句话记住

五类错误各有入口：`error`/`window.onerror`、`unhandledrejection`、捕获阶段 `error`、Error Boundary/errorHandler、统一请求层；异步和 catch 吞掉的单独处理。

## Q3：Source Map 如何安全管理？

### 这题在考什么

是否理解 Source Map 的管理不止是"不上传公网"，还要**版本严格对应**、**控制访问权限和保留周期**，两头都不能丢。

### 面试时可以这样说

> 先说原则：构建时生成完整的 Source Map，但不在公开产物中引用它。上传走 CI，用应用名、版本和文件路径作为索引，传到受控存储里，确认成功之后再发布对应代码。错误事件携带同一版本标识，解析服务根据压缩文件的位置和行列号找到 Source Map。还要设置访问权限、保留周期和发布删除策略。这样既能避免源码暴露，也能避免版本对不上，导致错误定位错。

核心是两个"对得上"：产物和版本对得上、错误事件和 Map 对得上；源码不暴露只是其中一半。

### 对方很可能继续问

**Source Map 放在受控存储，还会有泄露风险吗？**

风险主要来自流程而不是存储本身：误把 map 随静态资源一起发布、对象存储权限配错、告警或日志里带出还原后的源码片段。所以发布流水线要校验公开产物里没有指向公网的 `sourceMappingURL`，存储加访问控制和审计，还原只在服务端做，浏览器永远拿不到 map。

**版本对不上、还原失败怎么办？**

流程上保证"先上传、确认成功、再发布"，让 Map 一定先于流量到位。还原服务找不到 Map 时不要静默失败：上报原始压缩堆栈并标记"未还原"，同时按版本统计还原率，还原率突然下跌本身就要告警——通常意味着发布流程断了。

**还原本身有性能问题吗？**

行列号到源码的映射解析是有成本的，所以还原不要放在上报的关键路径上：异步做、结果按版本缓存。错误指纹建议用还原后的顶层堆栈生成，这样同一个错误即使原始堆栈每次行列号都不同，也能聚成一条。

### 一句话记住

Source Map 按应用名、版本、路径索引上传受控存储，发布前确认、限制访问，保证源码不暴露、版本对得上。

## Q4：弱网下如何提高上报成功率？

### 这题在考什么

是否理解弱网上报要串成一条链：**内存队列、卸载发送、离线补发、幂等去重**，同时有**资源上限意识**——不能反过来耗尽用户存储。

### 面试时可以这样说

> 我分三层说。第一层，页面还在的时候，先用内存队列，再批量发送；离开页面时，优先用 `sendBeacon`，必要时用 `fetch` 的 keepalive。第二层，失败的事件可以有限重试，使用指数退避；重要事件暂存 IndexedDB，网络恢复后再补发。第三层，所有事件要有唯一 ID，服务端做幂等去重，并且设置队列上限和过期时间。底线是不能为了保证上报，反而耗尽用户的存储和网络。

### 对方很可能继续问

**`sendBeacon` 会保证送达吗？**

不会。它只是让浏览器更适合在页面卸载阶段安排小量数据发送，并不提供业务级的送达确认。关键事件仍然需要本地队列、事件 ID、服务端幂等和有限补发；同时设置存储上限，避免坏网络下无限积压。

**离线队列如何避免重复上报？**

事件带唯一 ID，本地在收到成功确认后才从 IndexedDB 删除，补发时可能多发，由服务端按 ID 幂等去重。取舍是宁可偶尔重复，也不能因为"怕重"丢掉关键错误——重复可以合并，丢了就是永久损失。

**错误风暴时如何保护服务端？**

端上对同一指纹的错误做本地聚合计数，只上报"指纹 + 次数"而不是每条都发；服务端支持动态降采样和限流，同一指纹合并入库。告警侧同样按指纹聚合，否则风暴时监控系统自己先被打爆，告警先于业务失效。

### 这里容易说错

`sendBeacon` 有体积上限（多数浏览器约 64KB）且拿不到响应，需要回执的关键事件要走普通请求或补发通道。重试要有最大次数和过期时间，指数退避不设上限会在坏网络下持续制造流量。

### 一句话记住

内存队列批量发，卸载走 `sendBeacon` 或 `fetch` keepalive，重要事件落 IndexedDB 补发，唯一 ID 加服务端幂等。

## Q5：白屏如何检测？

### 这题在考什么

是否理解白屏判断要**组合多个信号**并治理**误报**，而不是靠单一 API 或单一条件下结论。

### 面试时可以这样说

> 先说结论：白屏不是一个单一信号，我会把路由就绪、根节点内容、关键元素和视口采样组合起来判断。常见做法是设置一个合理超时，然后用 `elementFromPoint` 对视口里的多个点采样，看命中的元素是不是仍然只有 `html`、`body` 或空挂载容器，再结合页面错误和资源失败来降低误报。注意 `MutationObserver` 更适合观察变化，不适合作为唯一的白屏结论。另外，不同页面要允许配置各自的关键元素和等待时间。

白屏检测最大的工程难点不是"怎么判定"，而是误报治理——误报多的告警没人信。

### 对方很可能继续问

**骨架屏会不会造成误判？**

会。骨架屏阶段视口采到的不是空白而是骨架节点，只判断"根节点有内容"会漏报，只判断"命中的是容器"又可能误报。更稳的做法是把骨架屏纳入判定：关键元素一直没渲染、超时窗口又覆盖了骨架屏应当消失的时间，才算白屏；骨架屏的预期消失时间也做成配置项。

**长列表空状态是不是白屏？**

不是。空状态是业务正常渲染出的内容，说明应用活着。所以白屏判定要支持页面级配置：每个页面声明自己的关键元素或白名单，空态页声明"我有内容"，避免检测器把业务空态误报成白屏。

**如何衡量检测准确率？**

灰度期先只上报不告警，抽样把"判定为白屏"的会话用回放或截图做人工核对，统计误报率和漏报率；上线后持续看误报率，超过阈值就收紧条件或调整超时。没有这一步，白屏告警很快会变成"狼来了"。

### 一句话记住

白屏靠组合信号：路由就绪、根节点、关键元素加视口采样，再结合页面错误和资源失败降误报。

## Q6：采样率应该按用户还是按事件？

### 这题在考什么

是否理解按用户和按事件采样分别服务什么分析目标，以及**采样必须记录权重**才能还原估计。

### 面试时可以这样说

> 这取决于分析目标。性能分布，通常按会话或者用户稳定采样，保证同一个会话的链路完整；高频成功请求，可以按事件随机采样，把量级降下来；错误和关键业务失败，一般全量采，或者用更高采样率。有一点必须做：采样要在事件中记录权重或者采样率，分析时才能还原估计。服务端还要支持动态采样，用来应对错误风暴。

### 对方很可能继续问

**采了样，性能数据还准吗？**

只要事件里记录了采样率和权重，分析时做加权还原，分位数仍然是有统计意义的估计。真正的风险是样本量不足：低流量页面或冷门版本的 P75 会抖，所以聚合要保证"每个页面、每个版本"有最低样本数，不够就合并到更粗的维度再看。

**错误也采样吗？**

错误和关键业务失败一般全量或高采样，因为量小、价值高。只有错误形成风暴时才动态降采样，而且要配合指纹聚合计数，保证"总共错了多少次"这个信息不丢——降采样降的是明细量，不是结论。

### 这里容易说错

不能把 `rate = 10` 说成"采样率 10%"却又用 `Math.random() < 1/rate` 而不解释口径。配置名称应明确使用 `sampleRate = 0.1` 或 `sampleEvery = 10`。

### 一句话记住

按会话或用户采样保链路，按事件采样降量级，错误全量或高采样，事件必须带权重。

## Q7：如何采集性能数据？

### 这题在考什么

是否知道性能条目**从哪里采**、SPA 场景要**补什么上下文**，并且理解聚合要看**分位数而不是平均值**。

### 面试时可以这样说

> 采集走 Performance Timeline 和 `PerformanceObserver`，采 navigation、resource、paint、longtask，还有 Web Vitals 相关的条目。光采这些不够，还要补充路由、设备、网络、版本和页面状态这些上下文。如果是 SPA，还要定义软导航的起点和业务可用点。端侧只做必要的计算，服务端按页面和版本聚合 P75/P95，避免只看平均值。

### 对方很可能继续问

**为什么不能只看平均值？**

性能数据是重尾分布，少数极慢用户会被平均值掩盖，而他们往往正是流失的那批。所以按页面和版本聚合 P75/P95，这也是 Core Web Vitals 官方采用的口径。平均值可以看趋势，但不能当达标标准。

**SPA 软导航的性能指标怎么采？**

先把起点和终点定义清楚：路由变化作为软导航起点，关键接口返回加首帧渲染作为业务可用点。原生 paint、resource 条目是页面级的，要按路由归因；longtask 也记录发生时所在的路由。否则聚合出来的"页面性能"，其实是整个 SPA 混在一起的数据，没法定位是哪个页面退化。

**`PerformanceObserver` 注册晚了会丢数据吗？**

会。paint 这类条目在注册之前就可能已经发生。用 `buffered: true` 可以让观察者拿到注册前缓冲的历史条目；同时要处理 buffer 溢出和多观察者的边界，否则数据是静默丢的，聚合口径看起来还一切正常。

### 一句话记住

`PerformanceObserver` 采 navigation、resource、paint、longtask 和 Web Vitals，SPA 补软导航起点，聚合看 P75/P95。

## Q8：监控 SDK 如何做到低侵入？

### 这题在考什么

是否理解低侵入要落在**结构拆分、异常隔离、资源预算和兼容原生 API**这些具体动作上，而不是只喊"不打扰业务"。

### 面试时可以这样说

> 我从几个层面来做。先拆结构：核心包和可选插件分开。初始化走异步，异常全部隔离。资源上，包体积、CPU、内存和请求量都设预算。包装原生 API 时，`this`、参数、返回值和属性都要保持。功能上支持关闭、降级和远程配置，数据脱敏默认开启。最后用 SDK 自监控观察丢弃量和上报失败，但要注意防止递归上报。

"低侵入"要说出可验证的动作和预算数字；只说"我们很克制"，对方没法判断你是不是真的做过。

### 对方很可能继续问

**SDK 怎么防止递归上报？**

自监控捕获到 SDK 自身的错误后，数据要打上来源标记，并且只允许走一层：自监控上报本身不再进入捕获逻辑。更简单的兜底是给上报通道加深度计数，超过一层直接丢弃、本地计数，事后随其他数据带出。

**包装原生 API 要注意什么？**

保持 `this`、参数和返回值的原语义，函数对象上的自定义属性也尽量保留，否则业务或第三方库踩到差异非常难查。包装里只做记录和转发，不夹带业务逻辑——一旦夹带，SDK 升级就可能改变业务行为。

**SDK 出问题怎么快速止损？**

远程配置要支持三档动作：调采样率、关单个插件、整体关闭采集，配置拉取失败时落到安全的默认值。这样线上 SDK 出问题不需要发版，先降级止血，修复后再恢复采集，避免业务为监控系统承担风险。

### 一句话记住

低侵入靠：插件拆分、异步初始化、异常隔离、资源预算、包装保 `this` 和参数、脱敏默认开启。
