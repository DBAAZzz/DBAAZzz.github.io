# 资深开放题：技术选型

## Q1：你如何做技术选型？

### 这题在考什么

是否把选型当成**约束下的取舍流程**，而不是追求“最先进”的工具；能不能说清**评估维度、PoC 验证、假设记录和灰度验证**这条完整链路。

### 面试时可以这样说

> 我做选型，一般分三步走。第一步，先把业务目标和硬约束转成评估维度，再筛出少量候选方案，做针对性 PoC。第二步，除了功能，还会比较性能、稳定性、安全、团队熟悉度、迁移和退出成本、社区维护，还有长期所有权。第三步，结论要记录假设和适用边界，再用小流量灰度验证，出现约定信号就重新评估。

三步讲完就停，等对方追问再展开决策记录的格式，不要一口气把所有维度背完。

### 如果对方让你继续讲

可以把每次选型落到一份决策记录里：

```text
问题：为什么必须做决定？
约束：哪些条件不可改变？
候选：为什么只比较这几个？
证据：PoC 测了什么，数据是什么？
决定：选哪个，牺牲了什么？
退出：什么信号出现时重新评估？
```

### 对方很可能继续问

**团队熟悉 Vue，是不是就应该选 Vue 生态方案？**

熟悉度只是成本之一，不能盖过关键约束。安全、性能、部署或长期维护不满足时，再熟悉也不能成为决定性理由。反过来，如果两个方案能力接近，选团队能维护的方案，通常比追逐新技术更稳。

**选型做错了怎么办？**

先把决定做得可撤回：对外包一层稳定接口，小流量接入，保留旧路径，并定义什么指标出现时停止扩大。做错并不可怕，最危险的是等底层方案渗透到所有业务之后，才发现无法替换。

**怎么让业务方接受选型结论？**

把评估结果翻译成业务语言：对交付周期、故障恢复成本、招聘和维护人力的影响，配上 PoC 数据和退出方案。业务方不需要懂技术细节，但需要看到风险有边界、决定可回退，这样才批得下去。

### 一句话记住

技术选型是在当前约束下做可撤回的决定，不是找“最先进”的工具。

## Q2：如何避免 PoC 变成演示项目？

### 这题在考什么

是否把 PoC 当成**风险验证**，而不是能跑起来的演示：有没有用**真实数据和真实链路**去验证最可能失败的部分。

### 面试时可以这样说

> 核心就一句：PoC 必须验证最可能失败的部分，而不是只跑 Hello World。具体我会盯这几件事：用真实体量的数据；接入一个遗留模块，看它跟真实系统的摩擦；验证构建、监控、测试和部署；主动模拟依赖不可用和版本不兼容；把迁移工作量记下来；最后，让未来真正接手维护的人参与评价。

### 对方很可能继续问

**PoC 要投入多少、做到什么程度？**

先给时间盒，比如一到两周、一两个人，产出是结论和决策记录，不是可上线的代码。开跑前写下要验证的两三个风险点和通过标准，防止范围膨胀成一堆演示页面。

**PoC 通过了就能直接全量上吗？**

不能。PoC 只验证了技术风险，全量还要考虑迁移成本、监控告警、团队培训和灰度计划。正确路径是小流量接入真实业务，观察真实负载和长尾问题，再逐步扩大。

**没有时间做 PoC 怎么办？**

那就选约束最少、退出成本最低的方案：外包一层适配接口、保留旧路径，把验证后移到灰度阶段，并明确写下回退信号。风险越高的决定，越不允许在没有验证的情况下全量押注。

### 一句话记住

PoC 验证的是最可能失败的部分，而不是只跑 Hello World。

## Q3：团队意见不一致怎么办？

### 这题在考什么

是否会把分歧**还原成各自担心的风险**，用共同确认的标准、有期限的实验和透明流程把决定收敛下来。

### 面试时可以这样说

> 遇到分歧，我一般分三步。第一步，先把各自的观点还原成他真正担心的风险，比如交付速度、稳定性，或者维护成本，再一起把决策标准定下来。第二步，能通过实验验证的，就做一个有截止时间的 PoC；不能量化的，就明确负责人和可撤回的方案。第三步，决策之后，把反对意见和复查时间记录下来，避免会议结束之后还有人暗中争论。

### 对方很可能继续问

**决策标准本身定不下来怎么办？**

把标准升一级：回到业务目标做排序，比如线上稳定性优先于交付速度、交付速度优先于长期优雅，请业务方或架构委员会确认这个排序。排序定了，多数技术分歧会自动消失，剩下的才是真正的取舍。

**最终决定和多数人意见相反，怎么推进？**

决策记录公开，写清理由和牺牲了什么；邀请反对者负责定义停止和回退信号，把他的担心变成防线。执行到约定复查点，用数据重新审视，而不是靠时间冲淡分歧。

**分歧开始影响交付节奏怎么办？**

给讨论设截止时间，到期由事先约定的决策人拍板，分歧记录在案。先按决定推进，把“再次评估”排到复查点，不允许无限期讨论阻塞交付。

### 一句话记住

不是所有决定都需要所有人同意，但过程和责任必须透明。

## Q4：什么时候自研，什么时候使用开源方案？

### 这题在考什么

是否有清晰的判断标准：**非差异化基础能力优先用成熟方案**，只有核心需求长期不匹配且团队具备持续所有权时才考虑自研，并把**升级、安全响应等成本算进总成本**。

### 面试时可以这样说

> 我的判断线就一条：非差异化的基础能力，优先用成熟方案。什么时候才考虑自研？三个条件同时满足：核心需求与现有方案长期不匹配；改造成本高于维护核心子集；团队具备持续所有权。算总成本时，要把二次开发、升级、安全响应、文档，还有人员流动都算进去。真决定自研，第一版要缩小范围，同时准备好迁移或退出接口。

### 对方很可能继续问

**自研以后由谁维护？**

选型结论里必须写明所有者、值班或安全响应方式、版本计划和退出条件。没有持续维护人、只靠最初作者热情的自研方案，生命周期通常很短。

**基于开源二次开发算自研吗？**

算“带责任的绑定”，要单独评估三件事：许可证是否允许这种用法；和上游的同步策略——改动越深，升级越痛；上游断供时怎么办。工程上尽量用外层封装和插件形式改，把修改面控制住，不要直接 fork 改核心。

**怎么判断“核心需求长期不匹配”？**

看演进方向是否一致：连续多个版本都要靠 hack 绕过、提的 issue 长期不被接受、瓶颈出在它的架构根因上，这才叫长期不匹配。偶尔缺一两个功能，优先考虑贡献回去，而不是自己造一套。

### 一句话记住

非差异化基础能力用成熟方案；自研只在核心需求长期不匹配、团队具备持续所有权时考虑。

## Q5：如何评估一个开源项目？

### 这题在考什么

是否有系统的评估框架：**需求匹配、维护状态、安全与许可证、升级路径、成本与性能、失败退路**，而不是只看 Star 数。

### 面试时可以这样说

> 我不会只看 Star 数，而是按一套清单评估：先确认它是否满足关键需求和运行环境；再看发布频率、维护者结构和 issue 响应速度；接着查安全历史、依赖树和许可证；然后看 API 稳定性和升级路径；还要评估包体积、性能和可观测性；最后想清楚失败路径——能不能降级、替换或者直接 fork。评估结果落成两点：需求匹配度和长期维护成本，再决定是引入还是绕开。

### 这里容易说错

只说“Star 多、社区活跃”就下结论，等于没评估。真正容易漏掉的是安全历史、许可证和失败退路，这三项出了问题，换库成本最高。

### 对方很可能继续问

**开源项目半年不维护了怎么办？**

先看当前版本是否仍满足需求和安全要求——不维护不等于立刻迁移。评估未修复漏洞、运行环境变化和关键 issue，同时验证替代方案和迁移成本。若它位于核心链路，应提前通过适配层降低绑定，并明确是内部接管还是迁移。

**许可证具体看什么？**

先看是否允许商用和闭源集成；GPL 类传染性协议会让衍生代码被迫开源，做 SaaS 还要特别注意 AGPL。再看专利授权条款，最后检查依赖树里各包的许可证是否兼容——主协议没问题、传递依赖有问题的情况很常见。

**Star 数和下载量哪个更可信？**

都只是弱信号。更有信息量的是 npm 周下载量、issue 关闭速度、release 频率、核心维护者人数和是否有团队在生产环境长期使用。最终还是要回到自己环境里的 PoC，别人的热度代替不了你的场景。

### 一句话记住

Star 数只能作为很弱的参考，看需求匹配和失败退路。
