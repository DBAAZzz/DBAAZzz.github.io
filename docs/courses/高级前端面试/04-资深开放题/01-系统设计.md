# 资深开放题：系统设计

## 开放题的答题顺序

不要听到“设计一个系统”就开始画技术组件。先按以下顺序：

```text
目标与用户 → 规模与约束 → 核心链路 → 数据与接口
→ 失败路径 → 安全与观测 → 演进与取舍
```

## Q1：设计一个前端发布平台

### 这题在考什么

是否理解发布平台的核心是**构建调度、制品不可变和状态可追踪**，而不是一上来就画技术组件；还要看你会不会先确认规模，并**主动讲失败路径和第一版边界**。

### 面试时可以这样说

> 我先确认平台服务多少应用和团队，是否需要多环境、审批、灰度与回滚。核心链路是代码版本进入构建任务，产出不可变制品，经过检查和审批后部署，再按流量策略切换版本。系统必须保证三件事：同一个提交可重复构建，任务状态可追踪，制品可校验。指标一旦异常，还要能快速回切到上一个稳定版本。

如果面试官不给具体数字，就主动做假设，把范围收住：

> 我先按内部平台、数百个应用、每天几千次任务来设计。第一版优先保证构建可复现、状态可追踪和快速回滚，不先做跨云调度。

这两句话就把第一版边界定下来了。资深系统设计不是把所有组件都画上去，而是先决定第一版要解决什么。

### 如果对方让你继续讲

按层展开，每层说清职责：

- 接入层：仓库、分支、提交、环境和权限；
- 调度层：任务队列、并发控制、超时和取消；
- 构建层：隔离环境、依赖缓存、日志和制品；
- 发布层：部署、健康检查、灰度与回滚——流程编排、放量策略和回滚的操作细节这里不展开，见 [发布与灰度](06-发布与灰度.md)，这一层只需说明平台要提供哪些能力；
- 治理层：审批、审计、密钥、配额；
- 观测层：构建成功率、耗时、发布错误率和业务指标。

失败路径至少准备这几条：构建容器崩溃；日志连接断开；制品上传成功但状态写入失败；发布部分节点成功；新版本健康但业务指标异常。

### 对方很可能继续问

**构建任务执行到一半，Worker 挂了怎么办？**

调度器不能只靠一个 running 状态。Worker 领取任务时获得带过期时间的租约，并定期续租；租约过期后，调度器把任务标记为待恢复。能否自动重跑取决于步骤是否幂等，已经上传的制品用任务 ID 和内容哈希去重。原 Worker 恢复之后，也不能继续提交一个已被接管的任务结果。

**为什么制品要不可变？**

同一个版本 URL 如果内容可以覆盖，缓存、回滚和审计都会失去依据。不可变制品让“测试过的东西”和“上线的东西”保持一致，环境间只晋级同一份产物。配置差异通过运行时配置或受控注入解决，不重新 build 一遍。

**和自己搭一套 Jenkins 流水线有什么区别？**

Jenkins 解决的是“单个仓库怎么构建”，发布平台解决的是“几十上百个应用怎么有序发布”：统一的制品规范、环境晋级模型、权限审批、灰度回滚和跨应用的观测。平台完全可以拿 Jenkins 这类引擎当执行层，但状态机、制品管理和发布策略要自己建——这是自研平台真正的价值所在。

### 这里容易说错

失败路径只答“失败后重试”。资深答案必须说明幂等键、状态机和补偿：哪一步可以重试、重试以什么为键、卡在中间状态怎么办。

### 一句话记住

发布平台的核心：构建可复现、状态可追踪、制品可校验，回滚要快。

## Q2：设计一个组件库平台

### 这题在考什么

是否理解组件库的价值在**稳定契约和交付一致性**，而不是组件数量；还要看版本策略、质量防线和推广落地**有没有完整思路**。

### 面试时可以这样说

> 组件库的目标不是积累组件数量，而是用稳定契约提高交付一致性。我会先定义使用方、主题和无障碍要求，再设计组件分层、版本策略、文档示例和测试发布链。基础组件保持低业务耦合，复杂业务模板由领域团队维护；通过视觉回归、交互测试、类型检查和变更说明控制质量。

说完架构，主动补一句治理：组件库最常见的死法是没人响应使用方诉求，所以要给每个组件定负责人和反馈渠道。

### 对方很可能继续问

**如何处理破坏性升级？**

破坏性变更集中在 major 版本发布，不零散混进小版本。配套三件事：提前发废弃警告，给使用方留迁移窗口；提供迁移指南和 codemod，把手工改造变成机械操作；用类型检查和视觉回归兜底，确认迁移后行为不变。旧 major 在窗口期内只修关键问题。

**主题系统如何避免运行时性能问题？**

主题优先走编译期或 CSS 变量，而不是运行时 CSS-in-JS 重算。切换主题只替换根节点的变量或 class，不重新渲染整棵组件树；多套复杂皮肤在构建期生成，运行时只做切换。主题方案的性能开销要写进组件库的验收标准，而不是上线后被业务方发现。

**如何推动团队使用，而不是强制迁移？**

先把接入成本降下来：脚手架一键接入、文档示例可搜索、旧用法有 codemod。再分层推进：新页面默认用组件库，旧页面随业务改动顺手迁移，不做停机式大迁移。同时公示覆盖率、缺陷率这类数据，用收益说话，行政命令只配当最后手段。

### 一句话记住

组件库靠稳定契约换交付一致性，组件数量不是目标。

## Q3：设计一个大文件上传系统

### 这题在考什么

是否理解大文件上传的关键是**分片、续传和合并一致性**，而不是只答“切片后上传”；还要看**服务端校验和安全边界**有没有说清。

### 面试时可以这样说

> 客户端把文件切片，计算文件标识并向服务端申请上传会话；服务端返回已存在分片，客户端按并发上限上传缺失部分，失败可以重试，也可以断点续传；所有分片完成后请求合并并校验最终哈希。需要控制内存、并发、超时和取消，大文件哈希可在 Worker 中增量计算。安全方面，要限制文件类型、大小和用户配额，并且在服务端重新校验。

补充一句取舍：切片大小和并发数都是可调参数，先按弱网用户设计兜底，再给高速场景加速，顺序别反。

### 这里容易说错

在主线程算整个文件的哈希，页面直接卡死；或者不设内存上限，分片全部堆在内存里。哈希要增量计算，分片用完即释放。

### 对方很可能继续问

**秒传如何防止越权读取别人的文件？**

服务端不能因为客户端声称某个 hash 已存在，就直接把别人的文件关联给当前用户。仍要检查当前用户是否有权使用该文件，或者只复用底层内容块但创建新的权限记录。hash 也要在服务端最终校验，不能完全相信客户端。

**切片大小如何选择？**

本质是平衡请求数和单片失败的重传成本。切得太小，请求数多、协议开销大；切得太大，一片失败要重传很多数据，内存占用也高。常见取 2~10MB，弱网环境调小，配合并发上限控制总吞吐；同一个会话内切片大小要固定，续传时才能对齐。

**合并请求重复发送如何保证幂等？**

用文件会话 ID 或内容 hash 做幂等键。合并前服务端先查会话状态：分片不齐直接拒绝；正在合并就返回进行中；已经合并的重复请求直接返回原文件标识，不重复执行。合并动作本身要原子——要么生成完整文件，要么状态不变，不能留下半成品状态。

### 一句话记住

大文件上传：分片、断点续传，最后在服务端重新校验。

## Q4：设计一个实时协作页面

### 这题在考什么

是否理解实时协作要先分清**“状态通知”和“多人编辑”两种场景**，而不是把 WebSocket 当成完整答案；编辑类协作还要说清**并发冲突语义**。

### 面试时可以这样说

> 先确认是光标和状态通知，还是多人同时编辑同一文档。前者可以用 WebSocket 加服务端顺序号；后者需要处理并发操作合并，可选择 OT 或 CRDT。客户端维护本地乐观状态和未确认操作，断线后带版本恢复；服务端负责权限、持久化、顺序与广播。还要定义冲突语义，而不是只说“使用 WebSocket”。

通道层的协议选型、心跳重连和消息可靠性是另一道独立题目，见 [实时通信](../02-高级工程化/09-实时通信.md)；这道题的分野在于编辑语义，不在于通道。

### 对方很可能继续问

**实时协作为什么不能只说用 WebSocket？**

WebSocket 只解决消息通道，不解决多人同时修改的冲突语义。必须说明文档版本、操作顺序、断线恢复和冲突合并。如果题目只是光标位置通知，顺序号加最新状态可能够用；真正的富文本协作才需要继续讨论 OT 或 CRDT。

**OT 和 CRDT 怎么选？**

OT 把并发操作交给服务端做变换，中央服务器是权威，实现复杂但行为可控，Google Docs 这类中心化文档常用。CRDT 的收敛性由数据结构本身保证，天然支持离线和去中心化，代价是状态体积和内存开销更大。实际项目里优先考虑 Yjs、ShareDB 这类成熟实现，先讲清场景约束再选，不要自己造算法。

**断线重连后怎么恢复？**

客户端保存本地未确认操作队列和最新已知版本号；重连后带版本号向服务端请求增量更新，服务端补发缺失操作，或直接下发最新快照。本地未确认操作要先把服务端新状态合并进来再重放，避免用本地旧状态覆盖别人这段时间的修改。

**光标、在线状态这类高频消息怎么优化？**

客户端节流合并、只发增量，服务端按房间聚合后广播，过期位置直接丢弃、只保留最新。这类消息允许丢帧，文档操作不允许丢，两条链路的可靠性要求要分开设计。

### 一句话记住

实时协作先分清通知和编辑，编辑才谈 OT 或 CRDT。

## 自测

1. 每道题是否先确认规模和非功能要求？
2. 是否画出数据真源和状态转换？
3. 是否说出至少三个失败路径？
4. 是否说明第一版不做什么？
