# 资深开放题：发布、灰度与回滚

## Q1：完整前端发布流程是什么？

### 这题在考什么

是否把发布理解成一条从确定版本到可回滚的完整链路，而不是零散步骤的清单；会不会主动讲出构建与部署分离这个关键约束。

### 面试时可以这样说

> 我按顺序讲一遍。第一步，确定源码版本，也就是这次到底发布哪个提交。第二步，做依赖锁定、构建、测试和安全检查，这几件事跑完，产出一个不可变制品。第三步，把制品上传，先做环境验证，再按灰度策略逐步放量。发布期间，我会把错误率、性能和关键业务指标跟版本关联起来看，一旦异常，就切回上一个稳定制品。这里有个关键点：构建和部署要分离，同一个制品在环境之间晋级，不要让每个环境重新构建出不一样的结果。

### 一句话记住

构建一次、部署按策略放量；异常时切回上一稳定制品，而不是重新构建。

## Q2：如何设计灰度系统？

### 这题在考什么

是否理解灰度系统的核心是稳定分桶加受控放量；分桶键怎么选、放量由什么指标控制，都要能说清。

### 面试时可以这样说

> 设计灰度，第一步是选一个稳定的分桶键，比如用户、组织或者设备哈希，保证同一个用户每次都命中同一个版本。第二步，定义规则：优先级、流量比例、白名单，还有过期时间。第三步，网关或者配置层根据这些规则返回版本化的入口，客户端把自己实际命中的版本上报回来。最后，放量不是拍脑袋，由错误率、关键业务成功率和性能阈值来控制，支持自动暂停，也能一键回切。

### 对方很可能继续问

- 未登录用户怎么稳定分桶？
- 多个实验同时进行，怎么避免冲突？
- 为什么用户刷新后不能随机换版本？

### 一句话记住

稳定分桶保证同人同版本，放量由指标阈值控制，支持自动暂停和一键回切。

## Q3：前端静态资源如何回滚？

### 这题在考什么

是否理解静态资源回滚的本质是切入口指向，而不是覆盖资源；会不会主动提到接口兼容窗口和 Service Worker 这两个容易翻车的点。

### 面试时可以这样说

> 前端资源回滚，靠的不是覆盖文件。JS/CSS 用内容哈希和不可变 URL，旧版本的制品一直保留着，由 HTML 或者入口配置决定当前引用哪个版本。所以回滚的时候，把入口切回旧制品就行，而不是去覆盖同名的缓存资源。还有一个坑：接口变更必须保持向后兼容窗口，否则前端就算回滚成功，也可能无法工作。Service Worker 的场景更麻烦，缓存和激活策略要单独处理。

### 一句话记住

回滚只切入口指向，不覆盖同名缓存资源；接口兼容窗口是回滚能生效的前提。

## Q4：如何避免发布后资源 404？

### 这题在考什么

是否理解资源 404 主要来自发布顺序、缓存策略和 CDN 刷新顺序出了问题，并能把从部署顺序到健康检查的预防手段讲完整。

### 面试时可以这样说

> 我从六个环节讲。第一，顺序要对：先上传新的 hash 资源，再切换 HTML 或者入口。第二，旧资源要保留足够长的时间，不要一发布就删。第三，HTML 的缓存和重新验证策略要合适。第四，CDN 刷新和源站部署的顺序要可控。第五，启动前先做资源清单健康检查。第六，入口切换失败要支持幂等重试。

### 一句话记住

新资源先传、旧资源缓删、入口切换可幂等重试；部署顺序和缓存策略一起管。

## Q5：复杂构建任务如何调度？

### 这题在考什么

是否把构建任务当作有状态任务来设计，能不能说清状态转换、幂等键、租约和缓存复用条件这些可靠性手段。

### 面试时可以这样说

> 我分两层讲。第一层，把构建表示成有状态任务：状态就是 queued、running、succeeded、failed、cancelled 这几个，还要明确哪些转换是合法的。第二层是调度：调度器按项目的配额和优先级，分配隔离的执行环境，每一步的日志和产物都记录下来。任务要带幂等键，超时了可以取消；Worker 失联之后，靠租约机制重新判定。缓存这一块要克制，只复用那些输入完整匹配、而且可复现的步骤。

### 一句话记住

任务状态显式建模，调度带幂等和租约；缓存只复用输入完整匹配且可复现的步骤。

## Q6：发布成功后指标异常怎么办？

### 这题在考什么

是否理解异常时的决策顺序是先止损、再定位，而不是先找根因；灰度价值在于用小影响换决策时间。

### 面试时可以这样说

> 先别急着找根因。第一步，暂停继续放量，确认异常是不是集中在新版本和灰度人群上。如果它影响关键链路，或者还在持续扩大，那就直接回切，不要等完整的根因出来。回切之后，先验证指标有没有恢复，同时把现场数据保留下来，再去分析代码、配置、接口和用户分群。说到底，灰度系统的价值，就是用比较小的影响，换来做决策的时间。

### 一句话记住

异常先暂停放量，影响关键链路就回切，止损优先于找根因。

## 一次发布过程可以这样讲

> CI 根据提交生成唯一版本，依赖锁定后，在隔离环境里构建一次。测试、扫描和制品校验，都针对同一份产物。先把 hash 资源上传，验证可访问，再发布入口配置。灰度从内部账号开始，然后按用户稳定分桶逐步扩大。监控同时看前端错误、白屏、接口成功率和关键业务指标；异常时只切入口版本，不重新构建。

如果当前项目没有完整做到这些，回答时要明确「现状」和「理想设计」，不要混在一起。

## 几个追问的参考答法

### 为什么按用户稳定分桶，而不是每个请求随机？

同一个用户如果刷新一次，就在新旧版本之间跳，会出现缓存、前端状态和接口行为不一致，出了问题也不利于复现。稳定 hash 让用户在一次灰度期间保持同一版本，同时总体比例仍然可控。

### 灰度版本需要兼容哪些后端？

放量期间，新旧前端会同时存在，所以后端接口至少在一个窗口内要同时兼容两者。数据库迁移也一样：先做向后兼容的变更，再切流量，最后才清理旧字段。否则前端就算一键回滚，也救不了已经不兼容的接口。

### Service Worker 为什么让回滚更复杂？

它可能继续从自己的 Cache Storage 提供旧入口或旧资源，而且新的 Worker 需要经过安装、等待和激活。所以发布策略要设计缓存版本、更新提示和激活时机，必要时提供清理路径，不能只切 CDN 上的 HTML。

### 构建任务重试会不会重复发布？

构建和发布要分开建模。构建重试只会产生或者复用相同内容哈希的制品；发布动作用环境、应用和版本组成幂等键，并且先检查当前目标状态。不能让一个超时重试无条件地重复切流量。

## 自测

1. 解释为什么构建和部署要分离。
2. 设计未登录用户的稳定灰度分桶。
3. 说明前端回滚为什么依赖后端兼容。
4. 画出构建任务状态机。
