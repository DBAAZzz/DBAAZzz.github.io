# 资深开放题：发布、灰度与回滚

## Q1：完整前端发布流程是什么？

### 这题在考什么

是否把发布理解成**一条从确定版本到可回滚的完整链路**，而不是零散步骤的清单；会不会主动讲出**构建与部署分离**这个关键约束。

### 面试时可以这样说

> 我按顺序讲一遍。第一步，确定源码版本，也就是这次到底发布哪个提交。第二步，做依赖锁定、构建、测试和安全检查，这几件事跑完，产出一个不可变制品。第三步，把制品上传，先做环境验证，再按灰度策略逐步放量。发布期间，我会把错误率、性能和关键业务指标跟版本关联起来看，一旦异常，就切回上一个稳定制品。这里有个关键点：构建和部署要分离，同一个制品在环境之间晋级，不要让每个环境重新构建出不一样的结果。

### 如果对方让你继续讲

可以带一个完整发布过程：

> CI 根据提交生成唯一版本，依赖锁定后，在隔离环境里构建一次。测试、扫描和制品校验，都针对同一份产物。先把 hash 资源上传，验证可访问，再发布入口配置。灰度从内部账号开始，然后按用户稳定分桶逐步扩大。监控同时看前端错误、白屏、接口成功率和关键业务指标；异常时只切入口版本，不重新构建。

如果当前项目没有完整做到这些，回答时要明确「现状」和「理想设计」，不要混在一起。

### 对方很可能继续问

**为什么构建和部署要分离？**

同一份制品在环境之间晋级，才能保证“测过的就是上线的”；每个环境重新构建会带来依赖漂移，制品也不可追溯。分离还让回滚变成切制品指针，秒级完成，不用等一次新的构建。

**版本号怎么生成？**

以提交为源：commit SHA 或其派生加上构建号，保证唯一；制品带元数据（提交、构建时间、构建参数）以便校验。禁止在制品生成后再手工改动或重传——那等于绕过了整个可追溯体系。

**发布需要审批吗？**

按风险分级：核心应用和生产的首次发布、破坏性变更需要审批；常规小版本走自动化门禁直接过。所有审批记录在案，紧急修复走快速通道，但事后必须补审计——分级是为了快，不是为了绕。

### 一句话记住

构建一次、部署按策略放量；异常时切回上一稳定制品，而不是重新构建。

## Q2：如何设计灰度系统？

### 这题在考什么

是否理解灰度系统的核心是**稳定分桶加受控放量**；分桶键怎么选、放量由什么指标控制，都要能说清。

### 面试时可以这样说

> 设计灰度，第一步是选一个稳定的分桶键，比如用户、组织或者设备哈希，保证同一个用户每次都命中同一个版本。第二步，定义规则：优先级、流量比例、白名单，还有过期时间。第三步，网关或者配置层根据这些规则返回版本化的入口，客户端把自己实际命中的版本上报回来。最后，放量不是拍脑袋，由错误率、关键业务成功率和性能阈值来控制，支持自动暂停，也能一键回切。

### 对方很可能继续问

**为什么按用户稳定分桶，而不是每个请求随机？**

同一个用户如果刷新一次，就在新旧版本之间跳，会出现缓存、前端状态和接口行为不一致，出了问题也不利于复现。稳定 hash 让用户在一次灰度期间保持同一版本，同时总体比例仍然可控。

**未登录用户怎么稳定分桶？**

用设备指纹或本地生成的匿名 ID（localStorage、cookie），网关侧可以拿 IP 加 UA 哈希兜底；关键是同一设备多次访问的结果要稳定。用户登录后把匿名 ID 映射到用户 ID，避免灰度期间切换分桶。

**多个实验同时进行，怎么避免冲突？**

入口只有一个版本，所有规则必须在同一个决策点合并，输出唯一命中结果。做法是分层正交：不同层之间流量正交、互不干扰；同层内实验互斥，按优先级分配流量。没有统一决策点、各实验各自改入口，冲突只是时间问题。

### 一句话记住

稳定分桶保证同人同版本，放量由指标阈值控制，支持自动暂停和一键回切。

## Q3：前端静态资源如何回滚？

### 这题在考什么

是否理解静态资源回滚的本质是**切入口指向，而不是覆盖资源**；会不会主动提到**接口兼容窗口**和 **Service Worker** 这两个容易翻车的点。

### 面试时可以这样说

> 前端资源回滚，靠的不是覆盖文件。JS/CSS 用内容哈希和不可变 URL，旧版本的制品一直保留着，由 HTML 或者入口配置决定当前引用哪个版本。所以回滚的时候，把入口切回旧制品就行，而不是去覆盖同名的缓存资源。还有一个坑：接口变更必须保持向后兼容窗口，否则前端就算回滚成功，也可能无法工作。Service Worker 的场景更麻烦，缓存和激活策略要单独处理。

### 对方很可能继续问

**灰度版本需要兼容哪些后端？**

放量期间，新旧前端会同时存在，所以后端接口至少在一个窗口内要同时兼容两者。数据库迁移也一样：先做向后兼容的变更，再切流量，最后才清理旧字段。否则前端就算一键回滚，也救不了已经不兼容的接口。

**Service Worker 为什么让回滚更复杂？**

它可能继续从自己的 Cache Storage 提供旧入口或旧资源，而且新的 Worker 需要经过安装、等待和激活。所以发布策略要设计缓存版本、更新提示和激活时机，必要时提供清理路径，不能只切 CDN 上的 HTML。

**回滚多快算合格？**

入口切换本身应该分钟级完成，这依赖 HTML 短缓存加资源不可变 URL 的组合策略；CDN 刷新只是加速手段，不是正确性前提。检验方法是演练：真实切一次回滚，记录端到端时间。超过半小时才能完成的回滚，不能算可靠。

### 一句话记住

回滚只切入口指向，不覆盖同名缓存资源；接口兼容窗口是回滚能生效的前提。

## Q4：如何避免发布后资源 404？

### 这题在考什么

是否理解资源 404 主要来自**发布顺序、缓存策略和 CDN 刷新顺序**出了问题，并能把从部署顺序到健康检查的**预防手段**讲完整。

### 面试时可以这样说

> 我从六个环节讲。第一，顺序要对：先上传新的 hash 资源，再切换 HTML 或者入口。第二，旧资源要保留足够长的时间，不要一发布就删。第三，HTML 的缓存和重新验证策略要合适。第四，CDN 刷新和源站部署的顺序要可控。第五，启动前先做资源清单健康检查。第六，入口切换失败要支持幂等重试。

### 对方很可能继续问

**旧资源要保留多久？**

覆盖最长的用户会话、已发布的 HTML 缓存 TTL 和回滚窗口三者的最大值；经验上至少保留数个版本或一到两周，再结合访问日志确认旧资源几乎没有流量后才清理。删早了，404 一定出现在长会话用户身上。

**CDN 刷新失败怎么办？**

正确性不依赖刷新：入口 HTML 用短 TTL 加重新验证，资源用不可变 URL，这样即使刷新失败，过期后也能自愈。刷新失败要有重试和告警，必要时延长旧资源保留期兜底。

**怎么第一时间发现资源 404？**

三路监控：页面全局错误监听捕获资源加载失败；服务端 404 日志按 referer 和版本聚合；发布后自动跑一遍资源清单健康检查。新版本出现 404 要立即告警并阻断后续放量，不要等用户投诉。

### 一句话记住

新资源先传、旧资源缓删、入口切换可幂等重试；部署顺序和缓存策略一起管。

## Q5：复杂构建任务如何调度？

### 这题在考什么

是否把构建任务当作**有状态任务**来设计，能不能说清**状态转换、幂等键、租约和缓存复用条件**这些可靠性手段。

### 面试时可以这样说

> 我分两层讲。第一层，把构建表示成有状态任务：状态就是 queued、running、succeeded、failed、cancelled 这几个，还要明确哪些转换是合法的。第二层是调度：调度器按项目的配额和优先级，分配隔离的执行环境，每一步的日志和产物都记录下来。任务要带幂等键，超时了可以取消；Worker 失联之后，靠租约机制重新判定。缓存这一块要克制，只复用那些输入完整匹配、而且可复现的步骤。

### 对方很可能继续问

**构建任务重试会不会重复发布？**

构建和发布要分开建模。构建重试只会产生或者复用相同内容哈希的制品；发布动作用环境、应用和版本组成幂等键，并且先检查当前目标状态。不能让一个超时重试无条件地重复切流量。

**Worker 失联后任务怎么办？**

Worker 领任务时拿到带过期时间的租约并定期续租；租约过期，调度器把任务置为待恢复。自动重跑的前提是步骤幂等，制品用任务 ID 加内容哈希去重；原 Worker 恢复后提交会被状态机拒绝，避免已被接管的任务收到两份结果。

**怎么提升构建速度？**

先测耗时分布再动手：依赖安装和构建产物用缓存，但只复用输入完整匹配且可复现的步骤；大仓做受影响范围的增量构建；队列按优先级和配额调度，避免互相挤占。盲目加机器通常只优化了非瓶颈。

### 一句话记住

任务状态显式建模，调度带幂等和租约；缓存只复用输入完整匹配且可复现的步骤。

## Q6：发布成功后指标异常怎么办？

### 这题在考什么

是否理解异常时的决策顺序是**先止损、再定位**，而不是先找根因；**灰度价值在于用小影响换决策时间**。

### 面试时可以这样说

> 先别急着找根因。第一步，暂停继续放量，确认异常是不是集中在新版本和灰度人群上。如果它影响关键链路，或者还在持续扩大，那就直接回切，不要等完整的根因出来。回切之后，先验证指标有没有恢复，同时把现场数据保留下来，再去分析代码、配置、接口和用户分群。说到底，灰度系统的价值，就是用比较小的影响，换来做决策的时间。

### 对方很可能继续问

**怎么确认异常确实由新版本引起？**

三个对照：版本对照——新版本人群和旧版本人群同指标对比；时间对齐——异常起点要和放量节奏吻合；分群一致——异常集中在命中新版本的桶里。再排除采集变更和外部因素，才能归因到版本。

**小流量阶段要盯哪些指标？**

三类：技术指标（错误率、白屏率、性能分位数）、关键业务成功率、本次版本特有的新功能指标。每个指标配阈值和自动暂停，而不是靠人盯盘——人盯盘总会走神，阈值不会。

**回切之后要通知业务方吗？**

要。回切也是一次变更，通知要带影响范围、持续时间和下一步计划，事后补一份简短复盘。业务方的信任来自“出事有人兜底、信息透明”，而不是“永远不出事”。

### 一句话记住

异常先暂停放量，影响关键链路就回切，止损优先于找根因。

## 自测

1. 解释为什么构建和部署要分离。
2. 设计未登录用户的稳定灰度分桶。
3. 说明前端回滚为什么依赖后端兼容。
4. 画出构建任务状态机。
