# 资深开放题：重构与团队推进

## Q1：你如何推动一次大型前端重构？

### 这题在考什么

考的是你有没有把重构从“技术愿望”翻译成一套**能落地的推进计划**：目标可量化、阶段能回滚、业务不中断，而不是一句“技术栈旧了就要换”。

### 面试时可以这样说

> 我先不急着聊技术栈。第一步，讲清楚这次重构到底解决什么业务问题，而且要说成可量化的目标，比如发布失败率、构建时间、改动成本，而不是一句“因为技术栈旧了”。第二步，拉一份依赖和风险清单，哪些先动、哪些不能碰，心里有数。第三步，把目标拆成一个个阶段，每个阶段都能独立上线、都能回滚，中间靠适配层和双轨验证，避免一次性切换。每个阶段都要定好成功指标、负责人和停止条件，指标不达标就叫停。还有一件事要提前想好：重构期间业务交付不能停，所以迁移成本要直接算进计划里。

### 如果对方让你继续讲

可以按六步展开：

1. 基线：摸清现状指标、痛点和债务；
2. 边界：明确不改什么，第一阶段只解决什么；
3. 路线：选 Strangler、适配层，或模块逐步替换；
4. 验证：自动化测试、流量对比和数据一致性；
5. 推进：迁移手册、工具、负责人和业务窗口；
6. 收尾：删除旧路径、关闭双写、更新文档和所有权。

### 对方很可能继续问

**双写期间数据不一致怎么办？**

先明确唯一真源。影子写入只用于比对，不参与用户读取；每条记录带上关联 ID，离线比较差异并分类。达到约定的一致率后，再切读路径。如果两个系统同时可写，又没有冲突规则，双轨的风险会非常高。

**重构拖了半年还没结束怎么办？**

先检查三件事：是否缺少可交付的阶段、迁移是否还在靠手工、旧系统是否仍允许新增。然后把目标缩到一个能上线的业务切片，给常见迁移开发工具。如果收益假设已经不成立，也应该停止，而不是因为已经投入很多就继续投入。

**第一刀从哪里切？**

从边界清晰、风险低、有独立流量入口的模块开始，比如一个独立页面或组件域。目的不是这块本身多重要，而是先把“迁移、验证、回滚”的完整流程和工具跑通，建立团队信心，再去啃核心模块。

### 一句话记住

先定可量化目标，再拆成能独立上线、能回滚的阶段，业务交付不能停。

## Q2：业务一直插需求，重构怎么进行？

### 这题在考什么

考的是你能否**把重构嵌入业务节奏**，而不是做成一个与业务对立的长期项目；也看你愿不愿意**用旧系统的真实成本去争取资源**，以及会不会止损。

### 面试时可以这样说

> 我不会把重构包装成一个长期项目，然后让业务先别提需求，那样肯定推不动。我的做法是让重构搭业务的车：新需求只进新架构；谁要改旧模块，就顺手把相邻边界迁掉。迁移成本能省就省，重复的部分用自动化工具接住。同时我会跟业务方把账算清楚：旧系统让一个需求平均多交付几天、出一次事故要恢复多久。拿着这些数，给关键基础阶段争取一段固定容量。反过来，如果收益怎么都量化不出来，就不该要求团队长期投入，该停就停。

### 对方很可能继续问

**如何说服业务给时间？**

不要只说“代码难维护”。把旧系统对业务的影响摆出来：一个需求平均多交付几天、事故要恢复多久、有多少次发布被阻塞。再提出分阶段投入和每个阶段的可见收益，让业务方知道这不是一个长期黑盒项目。

**新需求进新架构，新旧要交互怎么办？**

在边界上定义清晰的接口或事件协议，旧系统通过适配层调用新能力，交互点补集成测试。要守住一条线：新模块不能反向依赖旧实现，否则迁移结束后旧系统永远删不掉。

**业务方不配合“顺手迁移”怎么办？**

不强求。把顺手迁移做成低成本的自动化选项——工具一键迁移加自动验证，让业务改动方几乎没有额外负担；同时持续量化旧系统的拖慢成本，等下一次大需求或事故复盘时再谈固定容量。

### 一句话记住

让重构搭业务的车，而不是让业务为重构停摆。

## Q3：如何处理团队成员反对？

### 这题在考什么

考的是你处理分歧的方式：能不能**先把对方反对的对象分清**（目标、方案还是成本），再把情绪化的反对转成**可验证的风险**，按既定标准决策，而不是靠职位或个人输赢压下去。

### 面试时可以这样说

> 有人反对，我先不急着说服。先搞清楚一件事：他反对的到底是目标本身、具体方案，还是迁移成本。然后请他帮个忙，把这条反对意见写成一条可验证的风险，同时邀请维护者一起参与 PoC 和迁移设计。写下来之后就好办了：风险确实合理，就调整方案；如果只是偏好不同，就按大家事先约定的标准决策。推进过程里，数据公开、问题也公开。最后还有一条我给自己定的底线：方案采不采纳，不是我的个人输赢。

### 对方很可能继续问

**团队成员能力不一致，如何推进？**

先把关键边界和示例做出来，提供迁移脚本、检查规则和结对支持；高风险模块让熟悉的人先迁，稳定后再扩散。培训不能只开一次分享会，还要在真实迁移和 Review 中持续给反馈。

**反对的人是技术负责人怎么办？**

更要把他的风险点写成验证项，并邀请他设计验证方案；可以给他对停止条件的确认权——数据不达标由他叫停。把他的权威变成质量保障而不是阻塞，方案通过后的执行阻力也会小很多。

**PoC 做完还有人不服怎么办？**

用事先约定的验收标准说话，数据公开给所有人。允许保留意见并设复查时间点；如果过程中出现新证据，诚实修正决定。愿意根据证据改主意，比坚持输赢更能积累信任。

### 一句话记住

把反对拆成“反对什么”，再写成可验证的风险，按约定标准决策。

## Q4：如何做 Code Review？

### 这题在考什么

考的是你有没有**明确的 Review 优先级和边界**：先保证正确性再谈风格，同时能说清评审时机、评论方式和目的，而不是把 Review 做成找茬或纯格式检查。

### 面试时可以这样说

> 我做 Review 有个固定顺序。先看需求实现得对不对、行为对不对；接着看边界、失败路径、安全、测试和可维护性；风格放最后。写评论时，我会说清楚这个改动会带来什么影响、建议怎么改，而不是只丢一句“这样不行”。时机也要挑：高风险的设计，要在作者写大量代码之前先评审，别等代码堆完再推翻。格式问题直接交给自动化工具。我理解的 Review 有两个目标：降低系统风险，把上下文传播出去，而不是证明 reviewer 比作者聪明。

### 对方很可能继续问

**Review 太慢拖累迭代怎么办？**

分级处理：高风险改动指定专家快审并约定响应时限，小改动走轻量流程；用自动化把 lint、类型、测试这些机械问题前置消化，让人只审逻辑和风险。评论区分“必须修改”和“建议参考”，别让作者在偏好问题上无限拉扯。

**作者不同意评审意见怎么办？**

先分清分歧类型：事实问题（有数据、有规范依据）就执行；偏好问题 Reviewer 只能建议、不阻塞。实在解决不了，拉第三个人或按团队规范裁定，把争论从代码评论区挪到决策规则上。

**怎么避免 Review 流于形式？**

控制单次 PR 体量，给出检查单（正确性、边界、失败路径、测试），对“秒过 LGTM”的 PR 抽查复盘。Review 质量是团队习惯，靠抽查和反馈养出来，不是靠制度罚出来。

### 一句话记住

Review 先看对不对，再看能不能维护；评论给影响和建议，格式交给工具。

## Q5：如何培养高级工程师？

### 这题在考什么

考的是你是否理解**资深度来自责任边界和可观察行为**，而不是年限或代码难度；以及你愿不愿意**用行为标准给反馈、逐步放权**。

### 面试时可以这样说

> 培养高级工程师，我的思路不是给他安排越来越难的代码，那只是难度，不是资深度。我会逐步扩大他的问题所有权：先给明确任务，再让他自己比较方案、做跨团队协作、盯上线指标，最后带复盘，每一步都及时给反馈。评价标准也要换掉：用可观察的行为来描述，比如能不能独立拆解一个模糊问题、能不能识别风险、能不能把一件事推动到闭环，而不是看他工作了多少年。

### 对方很可能继续问

**怎么判断一个人到高级了？**

看行为：拿到模糊问题能自己拆解并给出取舍方案；设计和 Review 中能识别关键风险；交付有闭环——上线、看指标、做复盘；遇到疑难问题别人愿意找他。满足这几条，比“会写难的代码”更接近高级的定义。

**放权之后出问题了怎么办？**

放权不等于放手：高风险决策设检查点，上线前一起确认预案；出了问题先一起复盘系统缺口，把这次出错变成团队的教学材料。因为怕出错就收回全部权限，人就不会再成长。

**没有晋升名额还怎么激励？**

用问题所有权和可见度激励：负责一个领域、对外做分享、参与选型决策；把成长记录写进反馈和晋升材料，让对方看到差距和预期时间线。画饼和兑现是两回事，关键是每一步都有可验证的进展。

### 一句话记住

高级不是写更难的代码，而是拥有更大的问题所有权，标准看行为不看年限。

## Q6：如何偿还技术债？

### 这题在考什么

考的是你能不能按**影响、概率和成本**给债务排优先级，并区分**止血、里程碑和随业务处理**三类动作；同时看你会不会给每项债务留下治理信息，避免清单变成没人懂的废纸。

### 面试时可以这样说

> 还技术债，我不会看到哪条修哪条。先排优先级，看三个数：业务影响、发生概率、修复成本。排完之后分三类处理。第一类，能用规则、测试或平台默认值拦住新增的，先做掉，这叫止血。第二类，高风险的债务，放进明确的里程碑排期。第三类，低影响的，不单独立项，等相关的业务改动路过时顺手修掉。还有一条：每项债务都要记下触发条件和所有者，不然时间一长，这份清单就没人看得懂了。

### 对方很可能继续问

**技术债要全部还清吗？**

不需要，也不经济。欠债是一种决策，不是罪恶；目标是把债务显性化、评估它的“利息”——拖慢交付和引发事故的概率，让“暂时欠着”成为有意决策。只还高利息的部分，低息债务放着完全合理。

**怎么防止新债失控？**

定义门禁拦住新增：类型检查、测试覆盖、重复率、依赖健康度，超线就挡在流水线里；架构评审聚焦接口边界而不是细节。再把“已知债务登记”做成习惯，让债务可见——看不见的债才会失控。

**业务方问“为什么之前欠了这么多债”，怎么回应？**

诚实说明当时的取舍：交付优先、当时信息不足，这本身就是工程决策的一部分。重点放在现在怎么避免重复同样的模式——展示债务登记、偿还计划和门禁机制，而不是追究过去谁的责任。

### 一句话记住

债务先按影响排序，再分三类：止血、进里程碑、随业务顺手修。

## 一个更完整的重构回答

> 旧系统最大的成本是：每次改公共模块都要全量发布，失败后也很难回滚。所以我没有把目标写成“升级到最新框架”，而是先定三个指标：构建时间、发布失败率和单应用可独立回滚。第一阶段先加适配层，让新旧模块可以同时运行；新需求只进新路径，旧模块在被修改时逐步迁移。每阶段只扩大一部分流量，指标异常就切回旧实现。最后一定要安排删除旧入口，否则双轨会变成永久负担。

这里的框架名字可以替换，回答结构不变：为什么改、怎么分阶段、如何验证、怎么退出旧系统。

## 自测

1. 给重构定义三个业务可理解的指标。
2. 说明一个可回滚的迁移阶段。
3. 把一次团队反对转换成可验证风险。
4. 区分高价值 Review 与风格评论。
